# Session 5: The Type System

---

## 5.0 The Central Tension

KorE sits at the intersection of two incompatible worlds.

Kotlin's type system assumes a closed world: sealed classes are exhaustive, generics are checked at compile time, nullability is tracked end-to-end. The JVM is a hostile environment full of `null`, but Kotlin fences it off.

The BEAM is a different kind of hostile: values are dynamically typed at the runtime level, message passing is untyped, processes can crash and restart mid-flight, hot code reloading replaces modules while the system runs, and foreign Erlang code has no type information at all.

Every design decision in this session is a negotiation between those two realities. There is no perfect answer. Every language that has tried has made tradeoffs, and those tradeoffs are visible in production code. This session maps them exhaustively so you can choose deliberately.

---

## 5.1 What Does "Typed" Mean on BEAM?

Before choosing a strategy, you need to agree on what the type system is *for*. There are three distinct goals, and they are in tension with each other.

**Goal A: Correctness guarantees.** The type system prevents you from passing a string where an integer is expected. Errors are caught at compile time, not at runtime. This is what Gleam optimizes for.

**Goal B: Documentation and tooling.** The type system records intent so that IDEs can autocomplete, Dialyzer can warn, and developers reading code can understand what flows where. This is what Erlang's `-spec` and Elixir's `@spec` provide today.

**Goal C: BEAM interoperability.** The type system must not prevent you from calling Erlang modules, using OTP, or receiving messages from untyped processes. This is the goal that forces every BEAM language to make concessions.

Gleam chose A at the cost of C. Erlang/Elixir chose B and C while treating A as aspirational. KorE's philosophy ("wrapping BEAM power in Kotlin syntax") points toward B and C as non-negotiable, with A as the target for code you control.

**My recommendation:** KorE should be a **gradually typed language** where code you write is fully typed, code you import from Erlang/Elixir is dynamically typed with optional type declarations, and the boundary between the two is explicit and visible. This is the TypeScript model applied to the BEAM.

---

## 5.2 The Type Enforcement Spectrum

Six positions exist. Every real language lands somewhere on this axis.

```
Pure dynamic          Gradual (sound)       Gradual (unsound)     Full static
     |                     |                      |                    |
  Erlang             Elixir 1.18+           TypeScript             Gleam
  (no checking)      (dynamic() + sound)    (any = escape)        (no escape)
```

| Position | Language | What it means |
|---|---|---|
| Pure dynamic | Erlang | No compile-time checking. Dialyzer is optional post-hoc analysis. |
| Optional analysis | Erlang + Dialyzer | Dialyzer infers success types, warns only on definite errors. |
| Gradual (unsound) | TypeScript | `any` opt-out is infectious, runtime errors possible through type assertions. |
| Gradual (sound) | Elixir 1.18+, academic | `dynamic()` propagates uncertainty, never silently loses information. |
| Typed with escape | Kotlin (platform types) | Mostly typed, but Java interop introduces `T!` platform types that are trusted without verification. |
| Fully static | Gleam, Haskell | No escape. Interop with Erlang is through declared external types that must be trusted by declaration. |

KorE's position should be **gradual (sound)** — the Elixir 1.18+ model. This means:

- Code written in KorE is fully typed
- Values from Erlang interop arrive as `Dynamic` (the top uncertainty type)
- `Dynamic` propagates: operations on `Dynamic` produce `Dynamic`
- You must explicitly narrow `Dynamic` to a concrete type before using it in typed code
- The narrowing is checked (at compile time if possible, at runtime if not)
- There is no `as` cast that silently discards checking — narrowing always produces a `Result` or requires a guard

## 5.3 Type Inference Strategy

### How the Reference Languages Do It

| Language | Strategy | Annotation burden |
|---|---|---|
| Erlang | None in language; Dialyzer infers success types post-hoc | None (but specs help Dialyzer) |
| Elixir | Currently none; 1.18+ adds forward inference | None required (specs become type annotations) |
| Gleam | Hindley-Milner bidirectional inference | None required; public APIs recommended |
| Kotlin | Local inference (not HM); annotations required at function boundaries | Required on function signatures |
| Scala 3 | Local + limited HM; annotations at function boundaries | Required on function signatures |
| TypeScript | Local structural inference | Optional everywhere; inferred from usage |
| Swift | Local bidirectional inference | Optional; inferred from context |

### Options for KorE

**Option A: Hindley-Milner full inference (Gleam model)**

The compiler infers all types throughout the program from usage. Annotations are optional and used for documentation only.

```kore
// No annotations needed
fun double(x) = x * 2          // inferred: (Int) -> Int
fun greet(name) = "Hello $name" // inferred: (String) -> String

// Annotations optional, validated when present
fun add(x: Int, y: Int): Int = x + y
```

Pros: minimal annotation burden, clean code, easy for beginners.
Cons: error messages can be confusing (inference failures surface far from root cause); does not scale well to complex OTP callback systems where types cross module boundaries; Hindley-Milner requires rank-1 polymorphism, which limits some useful patterns.

**Option B: Local inference + required boundary annotations (Kotlin model)**

Inference within function bodies. Function signatures require annotations. Class members require annotations.

```kore
// Annotations required at boundaries
fun add(x: Int, y: Int): Int = x + y

// Inferred locally
fun process(items: List<Int>): List<Int> {
    val doubled = items.map { it * 2 }   // List<Int> inferred
    val filtered = doubled.filter { it > 5 } // List<Int> inferred
    return filtered
}
```

Pros: errors surface at the right place (function boundary); documentation is always present; works well with IDE tooling; scales to large codebases.
Cons: more verbose than HM; still requires thought at every function signature.

**Option C: Bidirectional with opt-in inference (Swift/Scala model)**

Inference flows both forward and backward from context. Annotations are optional but the compiler will ask for them at ambiguous sites.

```kore
// Both work
val x = 42              // inferred Int
val x: Int = 42         // explicit

// Contextual inference
val result: Result<Int, Error> = runCatching { parseInt(input) }
// runCatching's return type is inferred from the declared type of result
```

Pros: most flexible; balances clarity and brevity.
Cons: more complex compiler; error messages can be cryptic at bidirectional boundaries.

**My recommendation: Option B** — local inference with required boundary annotations. This is the right choice for KorE for three reasons. First, OTP callbacks have complex types that should be visible at boundaries. Second, when Erlang interop is involved, you want explicit types at the point where `Dynamic` enters the typed world. Third, Kotlin developers already know this model and will not be surprised by it.

## 5.4 The Core Type Hierarchy

### Primitive Types

```kore
// Numeric
Int        // Erlang integer() — arbitrary precision
Float      // Erlang float() — IEEE 754 double
Number     // Int | Float

// Text
String     // Erlang binary() encoded as UTF-8
Char       // Single Unicode codepoint (Int internally)
Atom       // Erlang atom() — see Session 3.5

// Logic
Boolean    // true | false (Erlang atoms)

// Nothing
Unit       // Erlang ok atom — function with no meaningful return
Nothing    // Bottom type — a function that never returns (crashes, loops forever)

// Gradual escape
Dynamic    // Erlang term() — untyped value, must be narrowed before use
```

### Collection Types

```kore
List<T>        // Erlang list()
Tuple<A, B>    // Erlang {A, B} — see section 5.8
Map<K, V>      // Erlang map()
Set<T>         // Erlang sets set()
Binary         // Erlang binary() — raw bytes
BitString      // Erlang bitstring() — sub-byte aligned
```

### Concurrency Types

```kore
Pid<T>         // Erlang pid() — phantom type T = accepted message type
Ref            // Erlang reference()
Port           // Erlang port()
Subject<T>     // Typed channel (Gleam-inspired) — a Pid + phantom message type
```

### Optional and Error Types

```kore
T?             // Nullable — sugar for T | Null — maps to Erlang undefined atom
Result<T, E>   // Ok(T) | Err(E) — maps to {:ok, T} | {:error, E}
Option<T>      // Some(T) | None — maps to {:ok, T} | :none
```

## 5.5 Null Safety

Erlang has no `null`. It has `undefined` (an atom), `nil` (an atom), and `:none`. The BEAM is fundamentally null-safe in the sense that `null` cannot cause a segfault — you just get a badmatch error when a pattern fails.

But Kotlin's null safety is one of its most important DX features. The question is how to bring it to KorE.

### Options

**Option A: Kotlin-style nullable types (`T?`)**

```kore
val name: String? = getNameOrNull()

// Must handle null explicitly
val length = name?.length          // Int?
val upper = name?.uppercase() ?: "UNKNOWN"  // String

// Smart cast after null check
if (name != null) {
    val len = name.length  // name is String here, not String?
}
```

`String?` desugars to `String | Null` internally. `Null` is a sealed type with one value: `null`. Maps to Erlang `undefined` atom at the runtime level.

Pros: Kotlin developers know this exactly. IDE integration is mature. Eliminates null-related crashes for KorE code.
Cons: Erlang libraries return atoms like `undefined`, `none`, `nil` — these are not `null`, so the mapping is imprecise. You would need explicit unwrapping when crossing the BEAM boundary.

**Option B: No nullable types — use `Option<T>` everywhere**

```kore
val name: Option<String> = getNameOrNone()

// Must unwrap
val length = name.map { it.length }              // Option<Int>
val upper  = name.getOrElse { "UNKNOWN" }        // String
val upper  = name.map { it.uppercase() }.orNull() // String?
```

Pros: maps directly to Erlang's `{:ok, Value} | :none` convention. Consistent with functional style. No implicit null anywhere.
Cons: more verbose. Kotlin developers coming from Spring/JVM code will miss `?.`.

**Option C: Both — `T?` is sugar for `Option<T>` with unwrapping syntax**

```kore
val name: String? = getNameOrNull()
// identical to
val name: Option<String> = getNameOrNull()

// Both styles work
val upper = name?.uppercase()               // using ? syntax
val upper = name.map { it.uppercase() }    // using Option style
```

The compiler treats `T?` as `Option<T>` internally. `?.` desugars to `.map { }`. `?:` desugars to `.getOrElse { }`.

Pros: gives Kotlin developers familiar syntax; the functional Option style is also available; maps to BEAM naturally since `Option<T>` is `{:ok, T} | :none`.
Cons: two ways to do the same thing is a maintenance burden. Beginners may not know which to use.

**My recommendation: Option C** — `T?` as sugar for `Option<T>`. The Kotlin syntax is too familiar and too important for the enterprise audience to drop. But it must be grounded in `Option<T>` to map correctly to BEAM semantics. The compiler rewrites it during lowering so the BEAM output is always correct Erlang idiom.

## 5.6 The Gradual Type: `Dynamic`

`Dynamic` is the type of every value coming from Erlang code that has no KorE type declaration. It is also what you use when you intentionally opt out of type checking.

### The Rules

```kore
// Dynamic comes from untyped Erlang calls
val result: Dynamic = ErlangModule.some_function(args)

// Operations on Dynamic produce Dynamic
val x = result + 1        // Dynamic (not Int — you don't know it's a number)
val y = result.someField  // Dynamic

// You CANNOT use Dynamic where a typed value is expected without narrowing
fun greet(name: String): String = "Hello $name"
greet(result)  // COMPILE ERROR — Dynamic is not String
```

### Narrowing Dynamic

**Pattern-based narrowing:**

```kore
when (result) {
    is String -> greet(result)          // result is String in this branch
    is Int    -> result * 2             // result is Int in this branch
    is Tuple<*, *> -> handleTuple(result)
    else -> error("unexpected: $result")
}
```

**Guard-based narrowing:**

```kore
val name = result.narrow<String>()
// returns Result<String, NarrowingError>
// forces you to handle the failure case

val name = result.narrowOrThrow<String>()
// throws at runtime if wrong type — use only when you are certain
```

**Erlang guard BIF narrowing:**

```kore
if (result.isAtom()) {
    val atom: Atom = result.asAtom()  // safe after guard
}

if (result.isList()) {
    val list: List<Dynamic> = result.asList()
}
```

### `Dynamic` vs `Any`

A common confusion:

| Type | Meaning | Operations |
|---|---|---|
| `Dynamic` | "I don't know the type — came from untyped code" | All operations allowed, return `Dynamic`. Must narrow before typed context. |
| `Any` | "I know this is a typed KorE value but I don't know which type" | Only operations defined on `Any`: `toString()`, `equals()`, `hashCode()`. Must smart-cast or pattern match to use further. |
| `Nothing` | "This code never produces a value" | No operations — bottom type. Used as return type of `error()`, `throw`, infinite loops. |

```kore
val x: Any = 42          // Int stored as Any — fully typed, just widened
val y: Dynamic = erlang  // could be anything — genuinely untyped

when (x) {
    is Int -> x * 2     // smart cast — safe
    is String -> x.length
}

when (y) {
    is Int -> y * 2     // narrowing — still safe, but runtime check
    else   -> error("expected Int")
}
```

## 5.7 Algebraic Data Types

ADTs are the primary tool for modeling domain data in KorE. They map directly to Erlang tagged tuples and atoms.

### Sum Types (Sealed Classes)

```kore
sealed class Shape {
    data class Circle(val radius: Float) : Shape()
    data class Rectangle(val width: Float, val height: Float) : Shape()
    data class Triangle(val base: Float, val height: Float) : Shape()
}

fun area(shape: Shape): Float = when (shape) {
    is Shape.Circle    -> Math.PI.toFloat() * shape.radius * shape.radius
    is Shape.Rectangle -> shape.width * shape.height
    is Shape.Triangle  -> 0.5f * shape.base * shape.height
    // exhaustive — no else needed. Adding a subclass is a compile error here.
}
```

**BEAM representation:** `Shape.Circle(5.0)` compiles to `{circle, 5.0}`. `Shape.Rectangle(3.0, 4.0)` compiles to `{rectangle, 3.0, 4.0}`. The tag is the lowercased class name by default, configurable with `@BeamTag("my_tag")`.

### Product Types (Data Classes)

```kore
data class User(
    val id: Int,
    val name: String,
    val email: String,
    val role: Role = Role.User
)

// Compiler generates: equals, hashCode, toString, copy, destructuring
val alice = User(1, "Alice", "alice@example.com")
val admin = alice.copy(role = Role.Admin)
val (id, name) = alice   // destructuring
```

**BEAM representation:** `User` compiles to an Erlang record `#user{id=1, name= <<"Alice">>, ...}` by default, or a map `#{id => 1, name => <<"Alice">>}` with `@BeamMap`. The Session 1 decision on map vs record applies here.

### Enum Types

```kore
enum class Role {
    User, Admin, Moderator
}

enum class HttpStatus(val code: Int) {
    Ok(200), NotFound(404), ServerError(500);

    fun isSuccess(): Boolean = code in 200..299
}
```

**BEAM representation:** Simple enums (no payload) compile to atoms: `Role.User` → `:user`, `Role.Admin` → `:admin`. Enums with payload compile to tagged tuples: `HttpStatus.Ok` → `:ok`, `HttpStatus.NotFound` → `:not_found`.

### Option A: Keep Kotlin sealed class syntax exactly

Same syntax as Kotlin. Most familiar to the target audience. The compiler handles BEAM lowering transparently.

```kore
sealed class Result<out T> {
    data class Ok<T>(val value: T) : Result<T>()
    data class Err(val reason: Dynamic) : Result<Nothing>()
}
```

Pro: zero learning curve for Kotlin developers.
Con: verbose for simple cases. Erlang's `{ok, Value}` is shorter than `Result.Ok(value)`.

### Option B: Gleam-style custom types

```kore
type Result(t, e) {
    Ok(value: t)
    Err(reason: e)
}
```

Pro: concise, maps cleanly to BEAM, less ceremony.
Con: different from Kotlin, breaks the "Kotlin syntax" promise.

### Option C: Kotlin sealed class with shorthand construction (Elixir-inspired)

```kore
sealed class Result<out T, out E> {
    data class Ok<T>(val value: T) : Result<T, Nothing>()
    data class Err<E>(val reason: E) : Result<Nothing, E>()
}

// But construction uses lowercased shorthand
val r1 = .ok(42)         // Result.Ok(42) — atom-style shorthand
val r2 = .err("oops")   // Result.Err("oops")

// Pattern matching uses the same shorthand
when (result) {
    is .ok  -> result.value
    is .err -> handleError(result.reason)
}
```

Pro: bridges Kotlin sealed classes with BEAM atom aesthetics. Consistent with the `.atom` syntax decided in Session 3.5.
Con: two ways to construct the same thing (`.ok(42)` and `Result.Ok(42)`).

**My recommendation: Option C.** The sealed class is the type-system representation (used for declarations, type annotations, documentation). The dot-shorthand is the expression syntax (used at call sites, in pattern matching). They are the same thing — one is the declaration form, one is the usage form. This mirrors how Swift's `case .success(let value)` works: the enum exists as a declared type, but usage always uses the dot prefix.

## 5.8 Tuple Types

Erlang tuples are fundamental. Kotlin has `Pair<A, B>` and `Triple<A, B, C>` but no general n-ary tuple. This is a real gap.

### Options

**Option A: Fixed arity tuple types like Kotlin**

```kore
val pair: Pair<Int, String> = Pair(1, "hello")
val triple: Triple<Int, String, Boolean> = Triple(1, "hello", true)
val (a, b) = pair
```

Pro: familiar to Kotlin developers.
Con: stops at 3. Erlang uses tuples of 4, 5, 6+ elements regularly. OTP message formats are often 4-tuples.

**Option B: Structural n-ary tuples (Scala/Haskell style)**

```kore
val t2: (Int, String) = (1, "hello")
val t4: (Int, String, Boolean, Float) = (1, "hello", true, 3.14)
val (a, b, c, d) = t4
```

Pro: matches Erlang tuples directly. Clean syntax. Can represent any arity.
Con: unfamiliar to Kotlin developers. Scala developers know it but it was controversial.

**Option C: Tuple as a special syntax sugar over data classes**

```kore
// Anonymous tuple
val t = tuple(1, "hello", true)   // Tuple<Int, String, Boolean>

// Named inline record (closer to Erlang record feel)
val point = record(x = 1.0, y = 2.0)  // anonymous record type
```

**Option D: Erlang-style bare tuple syntax with type-level arity**

```kore
// Erlang native tuple feel
val t = {1, "hello", true}        // inferred as Tuple3<Int, String, Boolean>
val {a, b, c} = t                 // destructuring

// In type annotations
fun process(t: {Int, String, Boolean}): Int = t.first
```

Pro: maps directly to BEAM. Reads like Erlang/Elixir. Tuple syntax is a first-class part of the language.
Con: curly braces are already used for blocks. Ambiguity for the parser.

**My recommendation: Option B** — structural n-ary tuple types with `(A, B, C)` syntax for the type and `(a, b, c)` for construction. This is consistent with Kotlin's destructuring syntax, maps directly to BEAM tuples, and avoids the parser ambiguity of curly braces. For OTP-specific tagged tuples, the sealed class approach in section 5.7 is used instead.

## 5.9 Typing Message Passing

This is the hardest problem in the space. No BEAM language has solved it fully. Here is the full option map.

### Why It Is Hard

In Erlang:
```erlang
Pid ! {request, self(), payload}
% Pid could be any process
% {request, self(), payload} is dynamically typed
% The receiving process could accept or reject it with no compile-time check
```

The type of a PID is its process identity, not its message protocol. Any process can be given any PID. Message sends are fire-and-forget. `receive` matches whatever is in the mailbox.

### Option A: Untyped message passing (Erlang model)

```kore
// PIDs are untyped — just process addresses
val pid: Pid = spawn { receive { msg -> handleMsg(msg) } }
pid ! MyMessage(payload)   // no type check — Dynamic send

// receive is untyped
receive {
    is MyMessage -> handleMyMessage(it)
    else         -> unhandled(it)
}
```

Pro: full BEAM interoperability. No restrictions. OTP works as-is.
Con: all the type safety you built in the rest of the language disappears at process boundaries. Errors surface at runtime.

**Cross-reference — Elixir:** This is exactly what Elixir does today. The new type system does not (yet) type message passing.

**Cross-reference — Erlang:** Same. `-spec` does not reach into `receive` blocks.

**Cross-reference — Akka Classic:** Same. `ActorRef` had no message type parameter. Akka admitted this was a mistake and built Akka Typed.

**Option B: Phantom-typed PIDs — `Pid<T>` (Akka Typed / Gleam model)**

```kore
// A PID is typed to the messages it accepts
val pid: Pid<CounterMessage> = spawn<CounterMessage> {
    receive {
        is CounterMessage.Increment -> ...
        is CounterMessage.Get       -> ...
    }
}

// Send is type-checked
pid ! CounterMessage.Increment(1)   // OK
pid ! SomeOtherMessage()            // COMPILE ERROR

// Receiving narrows the type
val subject: Subject<CounterMessage> = pid.asSubject()
```

`Pid<T>` is a phantom type — `T` is erased at runtime. The underlying BEAM PID has no type. The type exists only in the KorE compiler.

Pro: send operations are type-safe for KorE-to-KorE communication. IDE shows you what messages a process accepts. Huge improvement in large codebases.
Con: phantom types are lies the programmer tells the compiler — the runtime does not enforce them. An untyped Erlang process can send any message to a `Pid<T>` and it will arrive in the mailbox. The type guarantee is one-directional (your sends are checked, incoming from Erlang is not).

**Cross-reference — Akka Typed:** `ActorRef[T]` is exactly this. Send is checked. But incoming interop with classic (untyped) Akka requires unsafe adapters.

**Cross-reference — Gleam:** `Subject(msg)` is exactly this. Works well for pure-Gleam systems. Falls apart at the Erlang OTP boundary.

**Option C: Session types (full bidirectional protocol typing)**

```kore
// Define a protocol as a type-level state machine
protocol CounterProtocol {
    state Idle {
        on Increment(amount: Int) -> Idle
        on GetValue(replyTo: Subject<Int>) -> Idle
        on Stop -> Terminal
    }
}

// Process is typed to a protocol
val counter: Session<CounterProtocol.Idle> = spawn { ... }
```

Session types guarantee that both sides of a communication follow the protocol. They can detect:
- Sending a message that the protocol does not expect in the current state
- Failing to reply when a reply is expected
- Communication deadlocks (in theory)

Pro: the most complete type-safety possible for concurrent programs.
Con: enormous complexity. Academic research is still active. No production language on BEAM has implemented this. Even in the academic world, session types are rarely used in full form. The type annotations become as complex as the code.

**Cross-reference:** The closest practical approach is Rust's ownership-based session types. Even Rust does not use them in practice — the community prefers channels with simpler types.

**Option D: Two-tier — typed subjects for KorE code, `Pid` for BEAM interop**

```kore
// KorE-to-KorE: use Subject<T> (typed, phantom)
val counter: Subject<CounterMessage> = Actor.spawn(CounterActor())
counter.send(CounterMessage.Increment(1))  // type-checked

// KorE-to-Erlang: use raw Pid (untyped)
val erlangPid: Pid = ErlangRegistry.whereis(.my_service)
erlangPid.sendRaw(Dynamic.tuple(.request, self(), payload))  // explicitly untyped

// Receiving: typed receive for known protocol, wild receive for BEAM messages
receive<CounterMessage> {
    is CounterMessage.Response -> it.value
}

receiveAny {
    is Dynamic -> handleRaw(it)  // catch-all for BEAM messages
}
```

The explicit distinction (`send` vs `sendRaw`, `receive` vs `receiveAny`) makes the typed/untyped boundary visible at every call site.

**My recommendation: Option D** — two-tier typed/untyped with explicit boundary markers. Full session types are not practical. Fully untyped message passing throws away everything KorE type-checks. Phantom-typed `Subject<T>` for KorE-to-KorE is the right model (Akka Typed proved this in production), and `Pid` for Erlang interop accepts reality. The explicit boundary markers (`sendRaw`, `receiveAny`) make the safety degradation visible — you know exactly where you left the type system.

## 5.10 Generics

### Variance

KorE inherits Kotlin's declaration-site variance model.

```kore
// Covariant — T only produced (returned)
interface Source<out T> {
    fun next(): T
}

// Contravariant — T only consumed (accepted)
interface Sink<in T> {
    fun accept(value: T)
}

// Invariant — T both produced and consumed
interface Buffer<T> {
    fun put(value: T)
    fun get(): T
}

// Star projection — unknown type parameter
fun printSize(source: Source<*>) {
    // can receive from source but result is Any?
}
```

**BEAM implications:** Variance is a compile-time construct only. All generic type parameters are erased on the BEAM. `List<Int>` and `List<String>` are identical at runtime — both are Erlang lists. This is identical to JVM erasure.

### Type Bounds

```kore
fun <T : Comparable<T>> max(a: T, b: T): T = if (a >= b) a else b

fun <T> sort(list: List<T>) where T : Comparable<T>, T : Serializable: List<T>
```

### Reified Generics

On the JVM, Kotlin uses `inline` + `reified` to work around erasure. On the BEAM, there is no equivalent mechanism — you cannot ask the runtime "what is the type of this value's type parameter."

```kore
// On BEAM: this cannot work as cleanly as Kotlin/JVM
inline fun <reified T> List<Dynamic>.filterType(): List<T> {
    // On JVM: T is available via reification
    // On BEAM: T is erased — this requires a different approach
}
```

### Options for BEAM Reification

**Option A: No reified generics — require explicit type tags**

```kore
fun <T> List<Dynamic>.filterType(tag: KClass<T>): List<T> {
    return this.filter { tag.isInstance(it) }.map { tag.cast(it) }
}

list.filterType(String::class)  // explicit tag required
```

Pro: honest about what the BEAM can and cannot do.
Con: more verbose than Kotlin's `reified`.

**Option B: Synthetic reified via match specs**

```kore
inline fun <reified T> List<Dynamic>.filterType(): List<T> {
    // Compiler generates a type-test closure based on T's compile-time shape
    // e.g., for T = String, generates: filter { it is String }
    // for T = User, generates: filter { it.isRecord("user") }
    return this.filter { it.isKoreType<T>() }.map { it.narrow<T>() }
}

list.filterType<String>()  // looks like Kotlin reified
```

The compiler generates the correct BEAM type-test for `T` at the call site. This works for concrete types known at compile time. It fails for type variables.

**My recommendation: Option B** for concrete types, Option A for type variables. The `inline reified` syntax is too important for the Kotlin DX to drop entirely, and for concrete types the compiler can generate correct BEAM type checks.

## 5.11 Opaque Types

Opaque types enforce abstraction boundaries. The internal representation is hidden from callers.

```kore
// Declare opaque type in a module
opaque class UserId(private val value: Int) {
    companion object {
        fun create(n: Int): Result<UserId, String> =
            if (n > 0) .ok(UserId(n)) else .err("UserId must be positive")
    }

    fun toInt(): Int = value  // controlled exposure
}

// External code:
val id = UserId.create(42)    // OK — goes through factory
val raw = id.value             // COMPILE ERROR — value is private
val n = id.toInt()            // OK — explicitly exposed
```

**BEAM representation:** The compiler does not wrap the value in a container. `UserId(42)` compiles to the integer `42` on the BEAM — zero overhead. The type distinction exists only in the KorE compiler, exactly like Scala 3 opaque types.

**Cross-reference — Erlang:** `-opaque` is the equivalent. Enforced by Dialyzer, not the runtime. KorE's opaque types would be enforced by the compiler — stronger guarantee.

**Cross-reference — Scala 3:** `opaque type UserId = Int` is identical semantics. Zero runtime cost, module-scoped visibility.

**Cross-reference — Gleam:** External types function similarly — the internal representation is hidden and the type is only manipulable through declared functions.

## 5.12 Type Aliases

Two distinct kinds: transparent aliases and opaque aliases.

```kore
// Transparent alias — UserId =:= Int everywhere
typealias UserId = Int
typealias Handler<T> = (T) -> Result<Unit, Error>

// Opaque alias (see 5.11 for full semantics)
opaque class UserId(val raw: Int)
```

Transparent aliases are purely for readability. They do not create distinct types. Use them for complex generic signatures and domain vocabulary.

## 5.13 The Type System and OTP Callbacks

This is where all the theory meets practice. OTP callbacks have specific return types. How those return types are expressed in KorE is a Session 3.5 decision that the type system must make concrete.

### GenServer Callback Signatures

Using the sealed-class DSL decision from Session 3.5:

```kore
abstract class GenServer<State, Call, Cast> {

    abstract fun init(args: List<Dynamic>): InitResult<State>

    abstract fun handleCall(
        request: Call,
        from: From,
        state: State
    ): CallResult<State>

    abstract fun handleCast(
        message: Cast,
        state: State
    ): CastResult<State>

    fun handleInfo(
        message: Dynamic,
        state: State
    ): CastResult<State> = noReply(state)  // default implementation

    fun terminate(reason: Dynamic, state: State): Unit = Unit
}

// Return types are sealed classes
sealed class InitResult<out S> {
    data class Ok<S>(val state: S) : InitResult<S>()
    data class OkTimeout<S>(val state: S, val timeout: Long) : InitResult<S>()
    data class Stop(val reason: Dynamic) : InitResult<Nothing>()
}

sealed class CallResult<out S> {
    data class Reply<S>(val reply: Dynamic, val state: S) : CallResult<S>()
    data class NoReply<S>(val state: S) : CallResult<S>()
    data class Stop<S>(val reason: Dynamic, val state: S) : CallResult<S>()
}

sealed class CastResult<out S> {
    data class NoReply<S>(val state: S) : CastResult<S>()
    data class Stop<S>(val reason: Dynamic, val state: S) : CastResult<S>()
}
```

**With DSL shorthand (Session 3.5 two-tier model):**

```kore
class CounterServer : GenServer<Int, CounterCall, CounterCast>() {

    override fun init(args: List<Dynamic>) = ok(0)

    override fun handleCall(request: CounterCall, from: From, state: Int) =
        when (request) {
            is CounterCall.Get       -> reply(state, state)
            is CounterCall.Increment -> noReply(state + 1)
        }

    override fun handleCast(message: CounterCast, state: Int) =
        when (message) {
            is CounterCast.Reset -> noReply(0)
        }
}
```

The type system enforces that `handleCall` returns a `CallResult<Int>` and that the `when` expression is exhaustive over `CounterCall`. Adding a new variant of `CounterCall` without handling it in `handleCall` is a **compile error**. This is a genuine improvement over raw Erlang gen_server where missing a clause is a silent runtime failure.

abstract class GenStatem<State : Enum<State>, Data, Event> {

    data class KeepState<S, D>(val data: D) : StatemResult<S, D>()
    data class KeepStateAndData<S, D> : StatemResult<S, D>()

    // Actions: timeout, reply, nextEvent etc. as a list

## 5.14 The `-spec` Compatibility Layer

KorE should emit `-spec` and `-type` annotations in the compiled `.beam` files. This means:

1. KorE types are visible to Dialyzer when Erlang code calls KorE modules
2. Dialyzer can type-check Erlang code that uses KorE-compiled modules
3. KorE types are visible in `observer` and crash reports

The mapping:

| KorE type | Erlang `-type` |
|---|---|
| `Int` | `integer()` |
| `Float` | `float()` |
| `String` | `binary()` |
| `Boolean` | `boolean()` |
| `Atom` | `atom()` |
| `List<T>` | `[T]` |
| `Map<K, V>` | `#{K => V}` |
| `Tuple<A, B>` | `{A, B}` |
| `Option<T>` | `{ok, T} \| none` |
| `Result<T, E>` | `{ok, T} \| {error, E}` |
| `Dynamic` | `term()` |
| `Nothing` | `no_return()` |
| `Pid<T>` | `pid()` (T erased) |
| `Subject<T>` | `pid()` (T erased) |
| `sealed class Foo` | `-type foo() :: ...` |
| `data class Bar(val x: Int)` | `-record(bar, {x :: integer()})` or `-type bar() :: #{x := integer()}` |

## 5.15 Cross-Language Type Design Summary

| Feature | Erlang | Elixir 1.18+ | Gleam | Kotlin/JVM | KorE recommendation |
|---|---|---|---|---|---|
| Inference | None | Forward + bidirectional | Full HM | Local | Local + required boundaries |
| Null safety | No null | No null (use ok/error) | No null (Option) | `T?` | `T?` sugar over `Option<T>` |
| Sum types | Tagged tuples (untyped) | `@type` + tagged tuples | Sealed ADTs | Sealed classes | Sealed classes → BEAM tuples |
| Exhaustiveness | None | None (soon) | Full | Full (sealed) | Full (sealed) |
| Generics | None | None | Full (HM) | Full (erased) | Full (erased on BEAM) |
| Opaque types | `-opaque` (Dialyzer) | `@opaque` (Dialyzer) | External types | Wrapper classes | `opaque class` (compiler) |
| Message typing | Untyped | Untyped | Typed subjects | N/A | Two-tier: Subject<T> + Pid |
| Gradual escape | `term()` | `dynamic()` | None | Platform types (`T!`) | `Dynamic` (sound) |
| Runtime enforcement | None | None | None | Partial (null) | Guards at Dynamic boundary |
| Spec emission | `-spec` | `@spec` → Dialyzer | N/A | N/A | Auto-emitted from types |

## 5.16 Open Decisions to Make

Before implementing the type system, these three questions must be answered:

1. **Where does `Dynamic` come from explicitly?** Is it opt-in (`val x: Dynamic = ...`) or is it inferred when an Erlang function has no KorE type declaration? I recommend the latter — Erlang imports are `Dynamic` unless you provide a KorE type declaration for them (see Session 6).

2. **Are `sealed class` subclasses required to be in the same file or same module?** Kotlin went from "same file" to "same package" to "same module" across versions. Each choice has different exhaustiveness guarantees. "Same module" is the most flexible; "same file" is the most rigid and gives the strongest compile-time exhaustiveness. For KorE, "same file" for closed hierarchies and `open sealed` (an extension) for cross-file hierarchies is the most predictable model.

3. **Does the type checker run before or after macro expansion?** This matters if you implement the `@GenServer` annotation or any other compile-time code generation. If macros run first, the type checker sees the expanded code. If the type checker runs first, macros must produce type-correct output or the system is unsound. Kotlin's compiler plugins run after type checking. This is the correct model — macros produce typed code, not untyped code.
