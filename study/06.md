# Session 6: Interoperability — Calling Erlang and Elixir from KorE

---

## 6.0 The Interop Contract

Interop is not a feature you add later. It is a foundational design constraint. KorE lives inside the BEAM ecosystem. Every Erlang and Elixir library ever written is a potential dependency. If calling `:gen_server.call/2` from KorE is awkward, developers will not use KorE for real systems.

The contract KorE must fulfill, stated plainly:

1. KorE modules are `.beam` files. Erlang and Elixir can call them without knowing KorE exists.
2. KorE can call any Erlang or Elixir module with no runtime overhead beyond a normal function call.
3. The type boundary is managed by KorE's compiler, not by runtime reflection.
4. When types don't match at the boundary, the error is a compile warning or a clean runtime error — never silent data corruption.
5. Atoms, PIDs, references, ports, and binaries cross the boundary as-is. No wrapping, no boxing.

---

## 6.1 The Fundamental Model: What BEAM Actually Sees

Every KorE source file compiles to exactly one `.beam` file. At the BEAM level, a KorE module is indistinguishable from an Erlang module. The BEAM scheduler, OTP supervisor, distributed Erlang, and every Erlang tool (Observer, Dialyzer, `sys:get_state/1`) see native BEAM module format.

This is not aspirational — it is the same model Elixir and Gleam use. The consequence is:

```
KorE file      → Erlang atom module name
KorE fun       → Exported BEAM function
KorE val       → BEAM term (atom, binary, integer, tuple, map, list, pid, ref)
KorE data class → Tagged tuple or map at runtime
KorE sealed class → Tagged tuple (same as Gleam custom types)
```

No JVM. No bridge process. No reflection layer. Direct BEAM-to-BEAM calls.

---

## 6.2 Module Naming Strategy

This is the first thing to decide because it affects every other interop story.

Every language on BEAM has chosen a different strategy:

| Language | Module `Foo.Bar` | Erlang atom |
|---|---|---|
| Erlang | `foo_bar` | `foo_bar` |
| Elixir | `Foo.Bar` | `'Elixir.Foo.Bar'` |
| Gleam | `foo/bar` | `'foo@bar'` |
| LFE | `foo-bar` | `'foo-bar'` |
| Hamler | `Foo.Bar` | `'Foo.Bar'` |

### Option A: `'KorE.com.example.Foo'` (Elixir-style prefix)

```kotlin
// package com.example, class Foo
// → BEAM module atom: 'KorE.com.example.Foo'

// Erlang calling KorE:
'KorE.com.example.Foo':greet(<<"Alice">>).

// Elixir calling KorE:
:"KorE.com.example.Foo".greet("Alice")
```

Pros: unambiguous, no collision with Elixir (`Elixir.`) or Gleam (`@`), readable hierarchy.
Cons: verbose, Java package names make atoms long.

### Option B: `'kore@com.example.Foo'` (Gleam-style prefix with `@`)

```kotlin
// → 'kore@com.example.Foo'

// Erlang calling KorE:
'kore@com.example.Foo':greet(<<"Alice">>).
```

Pros: compact prefix, `@` is conventional for non-Erlang BEAM languages.
Cons: `@` in atoms requires quoting in Erlang, same as Gleam modules.

### Option C: Flat snake_case with `kore_` prefix

```kotlin
// package com.example, class Foo → kore_foo
// Only short, unpackaged modules benefit

// Erlang calling KorE:
kore_foo:greet(<<"Alice">>).
```

Pros: most ergonomic for Erlang callers.
Cons: name collisions, no hierarchy, doesn't scale to real packages.

### Option D: User-controlled with `@BEAMModule` annotation (override)

```kotlin
@BEAMModule("my_greeter")
class Foo {
    fun greet(name: String): String = "Hello $name"
}
// → Erlang module: my_greeter
// Erlang: my_greeter:greet(<<"Alice">>).
```

This can coexist with any default strategy. The annotation overrides the generated name.

**My recommendation: Option A (`'KorE.'` prefix) as default, with Option D as override.**

The `'KorE.'` prefix is unambiguous, mirrors established convention from Elixir, and makes module origins instantly readable in Observer/crash logs. The `@BEAMModule` annotation covers the cases where Erlang ergonomics matter — public APIs, wrapper modules, OTP application entry points.

## 6.3 Calling Erlang from KorE

The primary interop mechanism. Every Erlang OTP library, every community library written in Erlang, every BIF.

### Option A: Direct call with `:erlang` module prefix syntax (Elixir-style)

```kotlin
// KorE adopts Elixir's :module.function() syntax
val sorted = :lists.sort(listOf(3, 1, 2))
val hash   = :crypto.hash(:sha256, data)
val ref    = :erlang.make_ref()
val time   = :erlang.system_time(:millisecond)
```

Pros: instantly familiar to anyone coming from Elixir, minimal syntax overhead.
Cons: `:lists` in KorE looks odd in an otherwise Kotlin-like file.

### Option B: `erlang { }` import block

```kotlin
import erlang {
    lists.sort as sort
    lists.map as listMap
    crypto.hash
    erlang.make_ref as makeRef
}

val sorted = sort(listOf(3, 1, 2))
val ref    = makeRef()
```

Pros: explicit, clean at the call site, aliasable.
Cons: verbose import block, shadows potential KorE names.

### Option C: `@External` function declaration (Gleam-style)

```kotlin
@External("lists", "sort")
fun <T : Comparable<T>> erlangSort(list: List<T>): List<T>

@External("crypto", "hash")
fun cryptoHash(algorithm: Atom, data: ByteArray): ByteArray

@External("erlang", "make_ref")
fun makeRef(): Reference

// Usage: normal function calls
val sorted = erlangSort(listOf(3, 1, 2))
val ref    = makeRef()
```

Pros: typed, discoverable, IDE-friendly, compiler can verify arity, cleanest at call sites.
Cons: requires a declaration for every function used, more boilerplate for one-off calls.

### Option D: Hybrid — `@External` for typed wrappers, direct escape for raw calls

```kotlin
// Typed wrapper (preferred for frequently used functions):
@External("lists", "sort")
fun <T> erlangSort(list: List<T>, comparator: (T, T) -> Boolean): List<T>

// Raw escape hatch for one-offs:
val result = erlang.call("crypto", "strong_rand_bytes", listOf(32))
    .expect<ByteArray>()
```

Pros: typed path for common usage, raw escape for uncommon cases.
Cons: two different syntaxes for the same concept.

**My recommendation: Option C (`@External`) as primary, with a raw escape for edge cases.**

The reason is the type system. Option A and B give you no compile-time information about what the Erlang function returns. Option C forces you to write down what you expect the boundary to look like, which is where the type work happens. This is exactly how Gleam and Kotlin/JVM handle it and it is the right model. The raw escape hatch covers NIFs, dynamically named modules, and other edge cases without polluting the primary API.

## 6.4 The `@External` Declaration in Detail

```kotlin
// Full syntax:
@External(module = "crypto", function = "hash")
fun cryptoHash(algorithm: Atom, data: ByteArray): ByteArray

// Shorthand (positional args):
@External("crypto", "hash")
fun cryptoHash(algorithm: Atom, data: ByteArray): ByteArray

// With a KorE fallback body (used when KorE doesn't target BEAM — future):
@External("erlang", "phash2")
fun termHash(term: Any): Int {
    // fallback for non-BEAM targets if KorE ever supports them
    term.hashCode()
}

// Calling a BIF (module = "erlang"):
@External("erlang", "make_ref")
fun makeRef(): Reference

@External("erlang", "system_time")
fun systemTime(unit: Atom): Long

// Variadic-like (use Dynamic when arity is variable or unknown):
@External("erlang", "apply")
fun erlangApply(module: Atom, function: Atom, args: List<Dynamic>): Dynamic
```

### What the compiler does with `@External`

1. Verifies arity matches: if `crypto:hash/2` exists in the Erlang stdlib's PLT, it checks that the KorE declaration has 2 parameters.
2. Generates a direct BEAM call instruction — no wrapper function, zero overhead.
3. If the Erlang module is unavailable at compile time (external dep), emits a warning and defers to runtime.
4. Erases generic type parameters — `List<T>` becomes a plain BEAM list at the call site.
5. Injects a runtime type check when the return type is not `Dynamic` (configurable — can be disabled per-function with `@Trusted`).

## 6.5 Calling Elixir from KorE

Elixir modules compile to `.beam` files named `'Elixir.ModuleName'`. Calling them from KorE is identical to calling any Erlang module, with the atom name difference.

```kotlin
// Calling Elixir's String module:
@External("Elixir.String", "upcase")
fun elixirUpcase(s: String): String

// Calling a custom Elixir module:
@External("Elixir.MyApp.Router", "dispatch")
fun dispatch(conn: Dynamic): Dynamic

// Using Elixir's Enum:
@External("Elixir.Enum", "map")
fun <A, B> elixirMap(list: List<A>, f: (A) -> B): List<B>
```

The atom `'Elixir.String'` is just a string. The KorE compiler treats it as any other Erlang module name atom.

### Elixir Structs at the Boundary

Elixir structs are maps with a `__struct__` key. When KorE receives an Elixir struct, it arrives as a `Map<Atom, Dynamic>` with `__struct__` as one of the keys.

```kotlin
// Option A: work with it as Dynamic
val conn: Dynamic = dispatch(request)
val method = conn["method"].expect<String>()

// Option B: define a KorE data class that mirrors the struct shape
data class ElixirConn(
    val method: String,
    val path: String,
    val params: Map<String, Dynamic>
)

@ElixirStruct("Elixir.Plug.Conn")  // tells KorE how to decode this
val conn: ElixirConn = dispatch(request).decode<ElixirConn>()

// Option C: write a KorE shim module that decodes at the boundary
fun decodeConn(raw: Dynamic): Conn {
    val map = raw.expect<Map<Atom, Dynamic>>()
    return Conn(
        method = map[atom("method")].expect<String>(),
        path   = map[atom("path")].expect<String>()
    )
}
```

**My recommendation: Option B with `@ElixirStruct` annotation.** It documents the contract explicitly, allows the compiler to generate the decoder, and keeps KorE code clean of map-access boilerplate.

## 6.6 Publishing KorE Modules for Erlang and Elixir Callers

When you want Erlang or Elixir code to call your KorE module, you control the surface with annotations.

### What Erlang sees by default

Every KorE `fun` in a top-level `object` or `companion object` that is marked `public` becomes an exported BEAM function:

```kotlin
// com.example.Greeter.kt
object Greeter {
    fun greet(name: String): String = "Hello, $name"
    private fun helper() = "internal"
}

// Erlang module: 'KorE.com.example.Greeter'
// Exports: greet/1
// NOT exported: helper/0 (private)
```

```erlang
% Erlang calling KorE:
'KorE.com.example.Greeter':greet(<<"Alice">>).
```

### Controlling the published API

```kotlin
// Override module name for Erlang ergonomics:
@BEAMModule("greeter")
object Greeter {

    // Override function name:
    @BEAMName("greet")
    fun greet(name: String): String = "Hello, $name"

    // Suppress export entirely (even if public):
    @BEAMPrivate
    fun internalHelper(): String = "not exported"

    // Declare what Erlang exception class this may raise:
    @ThrowsErlang(ErlangExceptionClass.ERROR)
    fun riskyOp(): String = TODO()
}

// Erlang: greeter:greet(<<"Alice">>).
```

### Generating multiple arities (Erlang convention)

Erlang functions with optional arguments are expressed as multiple arities. KorE default parameters should emit multiple arities:

```kotlin
// KorE source:
fun connect(host: String, port: Int = 5432, timeout: Int = 5000): Connection

// KorE compiler emits three BEAM functions:
//   connect/1  → connect(host) → connect(host, 5432, 5000)
//   connect/2  → connect(host, port) → connect(host, port, 5000)
//   connect/3  → connect(host, port, timeout) → actual implementation
```

This is the `@JvmOverloads` pattern applied to BEAM. Unlike Java, Erlang programs frequently pass explicit arity, so having the multiple arities emitted is critical for ergonomic interop.

## 6.7 String Representation Across Languages

This is the most common day-to-day interop pain point in the BEAM ecosystem.

| Language | String literal | Runtime representation |
|---|---|---|
| Erlang | `"hello"` | Charlist: `[104,101,108,108,111]` |
| Erlang | `<<"hello">>` | Binary: `<<104,101,108,108,111>>` |
| Elixir | `"hello"` | UTF-8 binary |
| Gleam | `"hello"` | UTF-8 binary |
| KorE | `"hello"` | UTF-8 binary |

**KorE's rule:** Kotlin `String` = Erlang binary (UTF-8). Always. No exceptions.

The consequence: any Erlang function that expects a charlist must be wrapped. KorE should provide a stdlib module that wraps the common offenders:

```kotlin
// The old Erlang string module expects charlists.
// KorE wraps it so KorE devs never touch charlists:
object ErlangString {
    fun toUpper(s: String): String {
        val charlist = s.toCharlist()          // KorE stdlib: String → List<Int>
        val result = `:string.to_upper`(charlist) // returns charlist
        return result.fromCharlist()           // List<Int> → String
    }
}

// Or more directly, KorE wraps with @External + automatic conversion:
@External("string", "to_upper", convertArgs = [StringConversion.TO_CHARLIST], convertReturn = StringConversion.FROM_CHARLIST)
fun erlangToUpper(s: String): String
```

The `convertArgs`/`convertReturn` hint tells the compiler to inject conversion at the call site. No runtime overhead beyond the conversion itself.

### Charlist access for when you need it

Some Erlang APIs require charlists and there's no avoiding it. KorE provides an explicit escape:

```kotlin
val charlist: List<Int> = "hello".toCharlist()
val str: String = listOf(104, 101, 108, 108, 111).fromCharlist()

// Or use the Charlist type alias explicitly:
typealias Charlist = List<Int>

@External("inet", "getaddr")
fun inetGetAddr(host: Charlist, family: Atom): Pair<Atom, Dynamic>

// Call site is explicit about the conversion:
inetGetAddr("example.com".toCharlist(), atom("inet"))
```

## 6.8 Atom Handling at the Boundary

From Session 3.5 and 5, KorE has a two-tier atom system: compile-time atoms (`.ok`, `.error`, etc.) and dynamic strings that stay as binaries. At the interop boundary, a third case arises: Erlang functions returning atoms that KorE needs to handle.

### Receiving atoms from Erlang

```kotlin
// Erlang returns: ok | {error, Reason}
@External("file", "read_file")
fun readFile(path: String): Dynamic
// Returns Dynamic because the return is a union: ok-atom or {error, reason}-tuple

// Better: map the return explicitly
fun readFile(path: String): Result<ByteArray, Atom> {
    return when (val raw = erlangReadFile(path)) {
        is Tuple -> when (raw[0].atom) {
            .ok    -> Ok(raw[1].expect<ByteArray>())
            .error -> Err(raw[1].expect<Atom>())
            else   -> Err(.unknown)
        }
        else -> Err(.badreturn)
    }
}
```

### Atom comparison and pattern matching

When an Erlang function returns an atom, KorE receives it as an `Atom` type. Comparison against KorE compile-time atoms works via structural equality:

```kotlin
val result: Atom = erlangCall()

when (result) {
    .ok      -> handleOk()
    .error   -> handleError()
    .timeout -> handleTimeout()
    else     -> handleUnknown(result)
}
```

The `else` branch is mandatory because atoms from Erlang are an open set — we cannot prove exhaustiveness at compile time for dynamically received atoms. This is one of the hard limits of gradual typing on BEAM.

### Creating atoms safely

```kotlin
// Safe: only creates atom if it already exists
val a: Atom? = Atom.get("ok")           // returns null if not interned

// Compile-time atoms (defined in atoms {} block or built-in) — safe, no table growth:
val a: Atom = .ok
val b: Atom = .error

// Unsafe (use only when you know the atom is bounded):
val a: Atom = Atom.create("my_atom")   // inserts into atom table
```

## 6.9 Erlang Records at the Boundary

Erlang records are compile-time macros expanded to tuple indices. At runtime, `#person{name="Alice", age=30}` is the tuple `{person, "Alice", 30}`. There is no runtime record type.

This creates a sharp problem: KorE cannot introspect an Erlang record's field names at runtime without extra information.

### Strategy 1: Shim module (safest)

Write a thin Erlang shim that includes the `.hrl` and exposes field accessors:

```erlang
% file: kore_inet_shim.erl
-include_lib("kernel/include/inet.hrl").
-export([hostent_addr_list/1, hostent_name/1]).

hostent_addr_list(#hostent{h_addr_list = Addrs}) -> Addrs.
hostent_name(#hostent{h_name = Name}) -> Name.
```

```kotlin
// KorE side:
@External("kore_inet_shim", "hostent_addr_list")
fun hostentAddrList(hostent: Dynamic): List<Dynamic>

@External("kore_inet_shim", "hostent_name")
fun hostentName(hostent: Dynamic): String
```

This is the most robust approach. The Erlang shim owns the knowledge of the record structure. If the record changes, the shim fails to compile — you catch it early.

### Strategy 2: `@ErlangRecord` annotation

```kotlin
// KorE annotation that generates the shim automatically at compile time:
@ErlangRecord(
    header   = "kernel/include/inet.hrl",
    record   = "hostent",
    fields   = ["h_name", "h_aliases", "h_addrtype", "h_length", "h_addr_list"]
)
data class Hostent(
    val hName: String,
    val hAliases: List<String>,
    val hAddrtype: Atom,
    val hLength: Int,
    val hAddrList: List<Dynamic>
)
```

The compiler generates the Erlang shim from the annotation. Cleaner DX, same safety.

### Strategy 3: Raw tuple access (fragile, explicit)

```kotlin
// Last resort: access by known tuple index
// Records are {tag, field1, field2, ...} — tag at index 0, fields at 1..N
val hostent: Dynamic = getHostent()
val name: String = hostent.asTuple()[1].expect<String>()  // h_name is field 1
```

Explicitly fragile. Reserve for throwaway scripts and hotfixes.

**My recommendation: Strategy 2 (`@ErlangRecord`) as the DX-first path, Strategy 1 (manual shim) for complex cases.**

## 6.10 Exception Class Mapping

Erlang has three exception classes with distinct semantics. Kotlin has checked and unchecked exceptions. The mapping must be explicit.

### The three Erlang classes

```erlang
throw(some_value)   % controlled non-local return — "this is a valid outcome"
error(badarg)       % programming error — stack trace generated
exit(reason)        % process lifecycle — propagates through links
```

### Mapping to KorE

**Option A: Three distinct KorE exception types**

```kotlin
// Three exception base classes:
class ErlangThrow(val value: Any) : Exception()       // maps to throw
class ErlangError(val reason: Any) : RuntimeException() // maps to error
class ErlangExit(val reason: Any) : Exception()        // maps to exit

// KorE catch:
try {
    riskyErlangCall()
} catch (e: ErlangThrow) {
    // controlled throw from Erlang code
    handleValue(e.value)
} catch (e: ErlangError) {
    // programming error
    log(e.reason)
} catch (e: ErlangExit) {
    // process exit — unusual to catch this
    handleExit(e.reason)
}
```

**Option B: Unified `ErlangException` with class field**

```kotlin
class ErlangException(
    val exClass: ExClass,
    val reason: Any,
    val stacktrace: List<StackFrame>? = null
) : Exception()

enum class ExClass { THROW, ERROR, EXIT }

try {
    riskyErlangCall()
} catch (e: ErlangException) {
    when (e.exClass) {
        ExClass.THROW -> handleThrow(e.reason)
        ExClass.ERROR -> handleError(e.reason)
        ExClass.EXIT  -> handleExit(e.reason)
    }
}
```

**Option C: `Result` wrapping at the boundary — no exceptions**

```kotlin
// @Safe annotation wraps the call in try/catch and returns Result:
@External("risky", "operation")
@Safe
fun riskyOp(): Result<String, ErlangException>

val result = riskyOp()
    .onSuccess { handle(it) }
    .onFailure { log(it.reason) }
```

**My recommendation: Option A (three distinct types) for the type system, Option C (`@Safe`) as DX sugar for common cases.**

Three distinct types is correct because the semantics are genuinely different — `throw` is a flow control mechanism, `error` is a bug, `exit` is a process signal. Collapsing them loses information. Option C makes the common case (`result = call().or(default)`) clean without requiring catch blocks.

When KorE code raises an uncaught exception, it should become an `error` class exception with the exception object as the reason. OTP supervisors will restart the process. This is correct BEAM behavior.

## 6.11 Hot Code Reload Across the Boundary

BEAM hot code reload is per-node, per-module. Two versions of a module can co-exist briefly. The `code_change/3` callback handles state migration.

### What KorE must do for safe hot reload

**Problem 1: State serialization.** KorE GenServer state is a KorE object. When the class definition changes, the BEAM term representing the state is now a stale layout. `code_change/3` must transform it.

```kotlin
// KorE generates a code_change/3 implementation:
@GenServer
class Counter {
    data class State(val count: Int)

    // KorE requires explicit migration when State changes:
    @CodeChange
    fun migrateState(oldVsn: Any, oldState: Dynamic): State {
        // oldState is the raw BEAM term from the old version
        return when (oldVsn) {
            "1" -> State(count = oldState.asTuple()[1].expect<Int>())
            else -> throw ErlangError(.unknown_version)
        }
    }
}
```

If no `@CodeChange` is provided, KorE emits a default `code_change/3` that accepts the state unchanged — safe only if the state layout did not change.

**Problem 2: Erlang record layout changes.** If an Erlang library you call via `@External` changes a record layout between hot reloads, any hardcoded tuple indices break silently. The shim approach from Section 6.9 mitigates this: the shim is also hot-reloaded when the record changes.

**Problem 3: Distributed hot reload.** If a KorE node and an Erlang node are communicating, they can run different versions simultaneously during a rolling upgrade. The only safe approach is backward-compatible message schemas — messages must be interpretable by both old and new code during the transition window.

## 6.12 The Type Boundary: `Dynamic` in Depth

When KorE receives a value from Erlang and the type is not declared, the value is `Dynamic`. This is not a failure — it is an honest representation of the BEAM's runtime nature.

### Decoding Dynamic

```kotlin
// Pattern matching on Dynamic:
fun process(raw: Dynamic): String = when (raw) {
    is Atom    -> raw.value                       // .ok, .error, etc.
    is Int     -> raw.toString()
    is String  -> raw                             // already a binary string
    is Tuple   -> raw[0].expect<Atom>().value + "-tuple"
    is KoreList<*> -> "list of ${raw.size}"
    else       -> "unknown: ${raw.erlangType()}"
}

// Structured decode with a decoder:
data class User(val id: Int, val name: String)

val decoder: Decoder<User> = decode {
    val id   = field<Int>("id")
    val name = field<String>("name")
    User(id, name)
}

val user: Result<User, DecodeError> = raw.decode(decoder)
```

### The `Dynamic` narrowing rules

After a type check, `Dynamic` is narrowed within that branch:

```kotlin
val raw: Dynamic = erlangCall()

if (raw is String) {
    raw.uppercase()   // smart cast: raw is String here
}

// With when — exhaustive on known types, else required for open types:
when (raw) {
    is Int    -> raw * 2          // raw: Int
    is String -> raw.length       // raw: String
    is Atom   -> raw.value        // raw: Atom
    else      -> handleUnknown()  // could be a tuple, list, map, pid...
}
```

## 6.13 Distribution: Sending KorE Terms to Erlang Nodes

When a KorE process sends a message to an Erlang process on another node, the path is:

```
KorE term  →  ETF serialization  →  TCP/TLS  →  ETF deserialization  →  Erlang term
```

The Erlang node receives native BEAM terms. It does not know the terms originated in KorE. This is the strength of BEAM distribution.

### What KorE terms become in ETF

| KorE type | ETF encoding | Erlang receives |
|---|---|---|
| `Int` | `SMALL_INTEGER_EXT` or `INTEGER_EXT` | `integer()` |
| `Long` | `SMALL_BIG_EXT` or `INTEGER_EXT` | `integer()` |
| `Double` | `NEW_FLOAT_EXT` | `float()` |
| `String` | `BINARY_EXT` | `binary()` |
| `Boolean` | `SMALL_ATOM_UTF8_EXT` (`true`/`false`) | `boolean()` |
| `Atom` | `SMALL_ATOM_UTF8_EXT` | `atom()` |
| `List<T>` | `LIST_EXT` or `NIL_EXT` | `list()` |
| `Tuple` | `SMALL_TUPLE_EXT` or `LARGE_TUPLE_EXT` | `tuple()` |
| `Map<K,V>` | `MAP_EXT` | `map()` |
| `ByteArray` | `BINARY_EXT` | `binary()` |
| `Pid` | `NEW_PID_EXT` | `pid()` |
| `Reference` | `NEWER_REFERENCE_EXT` | `reference()` |
| `data class` | `SMALL_TUPLE_EXT` (tagged) | `{tag, field1, field2}` |
| `sealed class` | `SMALL_TUPLE_EXT` | `{tag, ...}` or bare `atom()` |

**Atom table growth:** Every KorE atom that an Erlang node receives for the first time is inserted into that node's atom table. If KorE is sending dynamic strings as atoms (you should never do this — use binaries), the Erlang node's atom table grows unboundedly.

### Distribution safety checklist for KorE

- Never send `Charlist` — send `String` (binary)
- Never send user-input strings as atoms — send as binary
- `data class` instances serialize as tagged tuples — the receiving Erlang code must know the tag and field order
- For schema stability, define an explicit serialization layer rather than relying on generated tuple format

## 6.14 KorE Interop Annotation Reference

A complete reference of all KorE interop annotations:

| Annotation | Where | What it does |
|---|---|---|
| `@External("mod", "fun")` | fun declaration | Replaces body with Erlang call |
| `@BEAMModule("name")` | class/object | Override generated Erlang module name |
| `@BEAMName("name")` | fun | Override generated Erlang function name |
| `@BEAMPrivate` | fun | Suppress BEAM export even if KorE-public |
| `@ErlangArity(n)` | fun | Emit `n` arities for default param functions |
| `@ErlangRecord(...)` | data class | Generate record shim and decoder |
| `@ElixirStruct("Mod")` | data class | Decode from Elixir struct map |

## 6.15 Interop Strategy Summary

**For calling Erlang from KorE:**
Use `@External` declarations. Write a thin typed wrapper per Erlang library you depend on. Group these wrappers into a module named `*Interop` or `*Erlang`. The rest of KorE code calls the typed wrappers, never raw Erlang directly. This mirrors how Elixir wraps Erlang — `:erlang.monitor/2` exists, but you use `Process.monitor/1`.

**For Erlang calling KorE:**
Use `@BEAMModule` and `@BEAMName` to control the published API. Emit multiple arities for functions with default parameters. Provide `-spec` type annotations in the generated `.beam` for Dialyzer users on the Erlang side.

**For Elixir calling KorE:**
KorE modules are callable as `:'KorE.com.example.Foo'` from Elixir. With `@BEAMModule`, Elixir callers get an ergonomic name. Elixir supervision trees can supervise KorE GenServers transparently.

**For data crossing the boundary:**
- `String` ↔ binary. No charlists.
- `data class` ↔ tagged tuple. Document the tag name.
- `sealed class` ↔ tagged tuple or atom.
- `Atom` ↔ atom. Only compile-time atoms at the boundary.
- `Dynamic` is the honest type for values from Erlang whose shape is not statically known.

**For exceptions crossing the boundary:**
- Erlang `throw` → `ErlangThrow` in KorE
- Erlang `error` → `ErlangError` in KorE
- Erlang `exit` → `ErlangExit` in KorE (usually handled at actor level)
- KorE uncaught exception → Erlang `error` class exception (OTP supervisor sees it as crash, may restart)
