# Session 11: aKt — The BEAM-Native Component UI Framework

---

## 11.1 — Philosophy & Design Principles

aKt exists because of a gap. LiveView solved the right problem — stateful server-rendered UI without a JavaScript framework — but it solved it for Elixir developers. React developers look at `.heex` templates and see something unfamiliar: a template-first file where the logic lives elsewhere, where the HTML is the primary artifact and the backing module is an afterthought. That's not how React developers think. They think in components: a single file, logic and markup together, props flowing down, events bubbling up.

aKt's thesis is that you can have both. You can give React developers the single-file component model they already know, the JSX-style colocation of logic and markup, the file-based routing of Next.js, the `useState`-shaped mental model — and underneath, run it all as BEAM processes communicating over WebSocket. No Node. No hydration bundle. No Virtual DOM reconciliation on the client. One GenServer per component instance, living on the server, sending minimal HTML diffs to the browser.

---

### Principle 1: React DX, BEAM Execution

The surface area of aKt is designed to be recognizable to anyone who has written a React application in the last five years. `useState` becomes an assignment on a server process. `useEffect` becomes `mount` and `handle_info`. `useContext` becomes PubSub. The mapping is not perfect — the execution model is fundamentally different — but it is close enough that a React developer can be productive in aKt within an afternoon.

The execution model is LiveView's: a persistent WebSocket connection, server-side process per component instance, diffs sent over the wire. This is not a compromise. It is a strict upgrade for real-time UIs, collaborative tools, dashboards, and forms with server-side validation. For these applications, shipping zero JavaScript for your component logic is not a limitation; it is the correct architecture.

---

### Principle 2: The Single-File Component Is the Right Unit

LiveView's separation of `MyComponent.ex` and `my_component.html.heex` is reasonable for MVC developers. But React developers spent years arguing that separation of concerns does not mean separation of files. A button component's markup, behavior, and style are all concerns of the button. They belong together.

The `.akt` file is KorE's answer. One file, logic and markup. The template is not the whole file — it is a section of the file, just as the `return` statement is a section of a React function component. This is the `.tsx` model, not the `.heex` model.

---

### Principle 3: What Translates from Next.js

| Next.js concept | aKt equivalent |
|---|---|
| File-based routing | `pages/users/[id].akt` → `/users/:id` |
| Server Components | The default. Every component is server-side. |
| Client Components | `use client` at top of file — JS island |
| Layouts | `_layout.akt` in any directory |
| Loading states | `_loading.akt` |
| Error boundaries | `_error.akt` |
| `getServerSideProps` | `suspend fun loadData(props, session)` |
| SSR | Everything, always |

---

### Principle 4: What Does Not Translate

- **No Node.js.** aKt runs on the BEAM.
- **No hydration bundle.** Server components produce zero client JavaScript. There is no rehydration step.
- **No Virtual DOM.** The server maintains component state and a compiled render function. Diffs are computed from the template structure, not from comparing two in-memory trees.
- **No `useEffect` for data fetching.** Data fetching happens in `mount` or `loadData`, which are server-side functions.
- **No Redux/Zustand.** PubSub and process registries are the global state mechanism.

---

### Principle 5: The Diff Protocol as the Core Abstraction

A template like:

```
<div class="user-card">
  <h2>{ user.name }</h2>
  <p>{ user.email }</p>
</div>
```

has static parts (`<div class="user-card"><h2>`, `</h2><p>`, `</p></div>`) and dynamic parts (`user.name`, `user.email`). The compiler identifies this split at compile time. Static parts are sent to the client once, assigned numeric identifiers. Subsequently, only dynamic values are transmitted. A state change that updates `user.name` sends `{0: "Jane Doe"}` over the WebSocket — not the entire HTML.

This is what "no Virtual DOM" means in practice: the diff is derived from the structure of the compiled template, which the compiler has already analyzed.

## 11.2 — The `.akt` File Format

### The Structure

A `.akt` file contains two logical sections:

1. **Logic section**: Imports, type declarations, props, state, lifecycle functions, event handlers. Valid KorE code.
2. **Template section**: Markup with embedded KorE expressions.

The central design question is: how does the file indicate where the logic ends and the template begins?

---

### Option A: `template { }` Block

```kotlin
// UserCard.akt
import kore.akt.*

@Component
props UserCardProps {
    val user: User
    val showEmail: Boolean = true
}

fun formatName(user: User): String = "${user.firstName} ${user.lastName}"

template {
    <div class="user-card">
        <h2>{ formatName(props.user) }</h2>
        { if (props.showEmail) {
            <p class="email">{ props.user.email }</p>
        } }
    </div>
}
```

**Tradeoffs:** Unambiguous, familiar to Vue developers. Cost: verbosity, the `{ }` wrapping a template is confusing when `{ }` also means "KorE expression" inside the template, and the block semantics differ from a function body.

---

### Option B: `---` Separator (Astro/Svelte Style)

```kotlin
// UserCard.akt
import kore.akt.*

@Component
props UserCardProps {
    val user: User
    val showEmail: Boolean = true
}

fun formatName(user: User): String = "${user.firstName} ${user.lastName}"

---

<div class="user-card">
    <h2>{ formatName(props.user) }</h2>
    { if (props.showEmail) {
        <p class="email">{ props.user.email }</p>
    } }
</div>
```

**Tradeoffs:** Visually clean. Reads "here is the code, here is the output." Fragile if `---` appears in a multiline string in the logic section (the compiler handles this by requiring the `---` line to have no surrounding context), and the template runs to EOF which is slightly asymmetric. Split point is a context-free token any parser can find quickly.

---

### Option C: `render()` Function (JSX Style)

```kotlin
fun render(props: UserCardProps): AktNode {
    return (
        <div class="user-card">
            <h2>{ formatName(props.user) }</h2>
        </div>
    )
}
```

**Tradeoffs:** Most consistent with KorE syntax — the template is just code. No special file format. Cost: blurs the boundary between markup and logic. For stateful components, `render()` needs access to state somehow (implicit receiver or parameter). The parser must recognize `(` followed by `<` as the start of markup — a context-sensitive rule.

---

### Recommendation: Option B (`---` Separator), with `template { }` retained for multi-template files

The `---` separator is the right default. Clean, unambiguous for the common case, familiar to Astro/Svelte developers. `template { }` blocks are retained for components that need to declare multiple named templates (e.g., a `template(name = "loading")` variant).

The `render()` approach is rejected: it makes the logic/markup boundary a matter of convention rather than syntax.

**The canonical `.akt` file:**

```kotlin
// Counter.akt

import kore.akt.*
import kore.akt.live.*

props CounterProps {
    val initialCount: Int = 0
    val step: Int = 1
    val label: String = "Count"
}

data class CounterState(
    val count: Int,
    val lastUpdated: Instant?
)

fun mount(props: CounterProps): CounterState =
    CounterState(count = props.initialCount, lastUpdated = null)

fun handleIncrement(state: CounterState, props: CounterProps): CounterState =
    state.copy(count = state.count + props.step, lastUpdated = Instant.now())

fun handleDecrement(state: CounterState, props: CounterProps): CounterState =
    state.copy(count = state.count - props.step, lastUpdated = Instant.now())

fun handleReset(state: CounterState): CounterState =
    state.copy(count = 0, lastUpdated = null)

---

<div class="counter" role="region" aria-label={props.label}>
    <h3>{ props.label }: { state.count }</h3>
    <div class="controls">
        <button onClick={handleDecrement} aria-label="Decrease count">−</button>
        <button onClick={handleReset} aria-label="Reset count">Reset</button>
        <button onClick={handleIncrement} aria-label="Increase count">+</button>
    </div>
    { if (state.lastUpdated != null) {
        <p class="timestamp">Last updated: { state.lastUpdated.format("HH:mm:ss") }</p>
    } }
</div>
```

---

### The Markup Language

**HTML elements:** Standard HTML, self-closing with `/>`. `class` attributes accept static strings or expressions. No special class-binding syntax needed.

**KorE expressions:** Embedded with `{ }` (single braces, like JSX). Any KorE expression evaluating to a renderable value:

```kotlin
---
<div>
    <p>Hello, { user.name }!</p>
    <p>{ formatDate(order.createdAt) }</p>
    <span class={ when { state.isActive -> "active"; else -> "inactive" } }>Status</span>
    <Avatar user={user} size={.lg} />
</div>
```

**Component invocations:** PascalCase tags. The compiler distinguishes `<div>` (HTML, lowercase) from `<UserCard>` (component, uppercase).

**Conditional rendering — three forms:**

```kotlin
---
// Form 1: directive (recommended for multi-line blocks)
<div>
    {if state.isLoggedIn}
        <UserMenu user={state.user} />
    {else if state.isLoading}
        <LoadingSpinner />
    {else}
        <LoginButton />
    {/if}
</div>

// Form 2: inline expression
<div>
    { if (state.isLoggedIn) <UserMenu user={state.user} /> else null }
</div>

// Form 3: when expression (recommended for multi-branch value switching)
<div>
    { when (state.status) {
        .loading -> <LoadingSpinner />
        .error   -> <ErrorMessage message={state.error} />
        .ready   -> <UserMenu user={state.user} />
    } }
</div>
```

**List rendering — two forms:**

```kotlin
---
// Form 1: directive (recommended for block-level)
<ul>
    {for user in state.users}
        <li key={user.id}><UserCard user={user} /></li>
    {/for}
</ul>

// Form 2: pipeline (recommended when transforming)
<ul>
    { state.users
        |> filter { it.isActive }
        |> sortBy { it.name }
        |> map { user -> <li key={user.id}>{ user.name }</li> }
    }
</ul>
```

`key` is required on list children. Missing `key` → compiler warning. `key` must be a `String` expression.

**Attribute binding:**

```kotlin
---
<input
    type="text"
    value={state.inputValue}
    class={"form-input " + if (state.hasError) "error" else ""}
    disabled={state.isSubmitting}
    aria-invalid={state.hasError}
    aria-describedby={ if (state.hasError) "error-msg" else null }
/>
```

A `null` expression in an attribute position omits the attribute entirely. Boolean attributes: `disabled={true}` renders as `disabled`; `disabled={false}` omits it.

**Event binding:**

```kotlin
fun handleClick(event: ClickEvent, state: CounterState): CounterState =
    state.copy(count = state.count + 1)

fun handleInput(event: InputEvent, state: FormState): FormState =
    state.copy(value = event.value)

---
<div>
    <button onClick={handleClick}>Click me</button>
    <button onClick={ { _ -> state.copy(count = 0) } }>Reset</button>
    <input type="text" value={state.value} onChange={handleInput} onBlur={handleBlur} />
    <form onSubmit={handleSubmit}>...</form>
</div>
```

Handler signatures (compiler-verified):
```kotlin
fun handler(event: EventType, state: S): S
fun handler(state: S): S
fun handler(event: EventType, state: S): Pair<S, List<Command>>
fun handler(event: EventType, state: S, props: P): S
```

**Slots and children:**

```kotlin
// Card.akt — default children
props CardProps { val title: String }

---
<div class="card">
    <div class="card-header"><h3>{ props.title }</h3></div>
    <div class="card-body">{ children }</div>
</div>
```

Usage:
```kotlin
---
<Card title="User Profile">
    <UserAvatar user={user} />
    <UserDetails user={user} />
</Card>
```

Named slots:
```kotlin
// AppLayout.akt
---
<div class="app-layout">
    <nav>{ slot("nav") ?: <DefaultNav /> }</nav>
    <main>{ children }</main>
    <footer>{ slot("footer") ?: <DefaultFooter /> }</footer>
</div>
```

Usage:
```kotlin
---
<AppLayout>
    <slot name="nav"><CustomNav /></slot>
    <slot name="footer"><ArticleFooter /></slot>
    <ArticlePage article={state.article} />
</AppLayout>
```

Scoped slots — data from component back to caller:
```kotlin
// DataTable.akt
props DataTableProps<T> { val rows: List<T>; val rowKey: (T) -> String }

---
<table>
    <tbody>
        {for row in props.rows}
            <tr key={props.rowKey(row)}>{ slot("row", row) }</tr>
        {/for}
    </tbody>
</table>
```

Usage:
```kotlin
---
<DataTable rows={state.users} rowKey={ u -> u.id }>
    <slot name="row" let:row>
        <td>{ row.name }</td>
        <td>{ row.email }</td>
    </slot>
</DataTable>
```

**Fragments:** `<>...</>` for multiple root elements with no wrapper.

**Comments:** `{/* ... */}` = compile-time only, not rendered. `<!-- -->` = rendered to client HTML.

---

### `.akt` Compilation Phases

**Phase 1:** Find `---` line. Split. Error if missing.

**Phase 2:** Parse logic section as normal KorE. Collect props type, state type, function declarations.

**Phase 3:** Parse template section with the aKt template parser. Produces `TemplateAST`.

**Phase 4:** Type-check template. Scope = `{ props, state, all top-level functions }`. Verify every `{ expr }` is renderable, every component invocation matches its props type, every event handler matches its expected signature.

**Phase 5:** Static/dynamic split. Classify every node. Extract static subtrees as binary constants.

**Phase 6:** Code generation. Emit Erlang Abstract Format. For `@LiveComponent`: GenServer module + render function + handle_event dispatch + handle_info dispatch.

**Generated BEAM modules for `pages/users/[id]/Profile.akt`:**

```
'KorE.Pages.Users.Id.Profile'         — the GenServer
'KorE.Pages.Users.Id.Profile.Render'  — render functions (separated for testability)
'KorE.Pages.Users.Id.Profile.Props'   — props type module
```

## 11.3 — The Component Model

### Stateless Function Components (`@Component`)

No state, no lifecycle, no process. The compiler generates a single BEAM module with a `render/1` function. Zero process overhead.

```kotlin
// UserCard.akt
import kore.akt.*
import myapp.domain.User

@Component
props UserCardProps {
    val user: User
    val size: AvatarSize = .medium
    val showRole: Boolean = false
    val onClick: ((User) -> Unit)? = null
}

---

<div
    class={"user-card user-card--${props.size.name}"}
    role={ if (props.onClick != null) "button" else null }
    tabIndex={ if (props.onClick != null) 0 else null }
    onClick={ if (props.onClick != null) { _ -> props.onClick!!(props.user) } else null }
>
    <Avatar src={props.user.avatarUrl} alt={props.user.name} size={props.size} />
    <div class="user-card__info">
        <span class="user-card__name">{ props.user.name }</span>
        { if (props.showRole) {
            <span class="user-card__role">{ props.user.role.displayName }</span>
        } }
    </div>
</div>
```

**Inline component declarations** (multiple small components in one file):

```kotlin
// badges.akt
@Component
props BadgeProps { val label: String; val variant: BadgeVariant = .default }

component Badge {
    <span class={"badge badge--${props.variant.name}"}>{ props.label }</span>
}

@Component
props StatusDotProps { val online: Boolean }

component StatusDot {
    <span
        class={"status-dot " + if (props.online) "status-dot--online" else "status-dot--offline"}
        aria-label={ if (props.online) "Online" else "Offline" }
    />
}
```

Inline `component` declarations use a block body instead of `---`.

### Stateful Server Components (`@LiveComponent`)

Each mounted instance = one GenServer process. The process holds component state. When state changes, the process re-runs the render function and sends the diff to the client.

```kotlin
// LiveSearch.akt
import kore.akt.*
import kore.akt.live.*
import myapp.services.SearchService

@LiveComponent
props LiveSearchProps {
    val placeholder: String = "Search..."
    val minLength: Int = 2
    val onSelect: ((SearchResult) -> Unit)? = null
}

data class LiveSearchState(
    val query: String = "",
    val results: List<SearchResult> = emptyList(),
    val loading: Boolean = false,
    val selected: SearchResult? = null
)

fun mount(props: LiveSearchProps): LiveSearchState = LiveSearchState()

fun handleQueryChange(event: InputEvent, state: LiveSearchState, props: LiveSearchProps): Pair<LiveSearchState, List<Command>> {
    val newQuery = event.value
    return if (newQuery.length >= props.minLength) {
        Pair(
            state.copy(query = newQuery, loading = true, results = emptyList()),
            listOf(Command.async("search") { SearchService.search(newQuery) })
        )
    } else {
        Pair(state.copy(query = newQuery, results = emptyList(), loading = false), emptyList())
    }
}

fun handleSearchResult(results: List<SearchResult>, state: LiveSearchState): LiveSearchState =
    state.copy(results = results, loading = false)

fun handleSelect(result: SearchResult, state: LiveSearchState, props: LiveSearchProps): Pair<LiveSearchState, List<Command>> {
    val commands = if (props.onSelect != null) {
        listOf(Command.callParent(props.onSelect!!, result))
    } else emptyList()
    return Pair(state.copy(selected = result, query = result.title, results = emptyList()), commands)
}

---

<div class="live-search" role="combobox" aria-expanded={state.results.isNotEmpty()}>
    <input
        type="text"
        value={state.query}
        placeholder={props.placeholder}
        onChange={handleQueryChange}
        aria-autocomplete="list"
        aria-controls="search-results"
    />
    { if (state.loading) {
        <div class="live-search__spinner" role="status" aria-label="Searching..." />
    } }
    { if (state.results.isNotEmpty()) {
        <ul id="search-results" class="live-search__results" role="listbox">
            {for result in state.results}
                <li
                    key={result.id}
                    class={"live-search__result" + if (result == state.selected) " live-search__result--selected" else ""}
                    role="option"
                    aria-selected={result == state.selected}
                    onClick={ { _ -> handleSelect(result, state, props) } }
                >
                    { result.title }
                    { if (result.subtitle != null) {
                        <span class="live-search__subtitle">{ result.subtitle }</span>
                    } }
                </li>
            {/for}
        </ul>
    } }
</div>
```

### Props System


### Component Composition

Stateless components compose by nesting: outer render evaluates inner render function, splices result.

Stateful components compose as **process composition**: each `@LiveComponent` in the tree is an independent GenServer. The parent sends props to the child process; the child runs its own render cycle and sends its own diffs. Diffs are merged by the client runtime.

```kotlin
// Parent to child: via props (normal)
<ChildComponent value={state.someValue} />

// Child to parent: via callback prop
fun handleChildEvent(result: ChildResult, state: ParentState): ParentState =
    state.copy(childResult = result)

// In template:
<ChildComponent onResult={handleChildEvent} />
```

## 11.4 — State and Lifecycle

### `useState` → Component State

React: multiple independent `useState` calls.

aKt: one typed `data class` state record, initialized in `mount`, updated by returning new value from handlers.

```kotlin
data class MyState(val count: Int = 0, val user: User? = null)

fun mount(props: MyProps): MyState = MyState(count = props.initialCount)

fun handleIncrement(state: MyState): MyState = state.copy(count = state.count + 1)
fun handleSetUser(user: User, state: MyState): MyState = state.copy(user = user)
```

If managing multiple independent pieces of state feels cumbersome, that is a signal to split the component.

---

### `useEffect(() => {}, [])` → `mount`

```kotlin
fun mount(props: DashboardProps): Pair<DashboardState, List<Command>> {
    return Pair(
        DashboardState(),
        listOf(
            Command.run { Analytics.track(.pageView, mapOf("page" to "dashboard")) },
            Command.subscribe("updates:${props.userId}")
        )
    )
}
```

When `mount` needs side effects, return `Pair<State, List<Command>>`. When it needs no side effects, return `State` directly.

---

### `useEffect(() => {}, [dep])` → `update`

```kotlin
fun update(newProps: PostListProps, oldProps: PostListProps, state: PostListState): Pair<PostListState, List<Command>> {
    return if (newProps.userId != oldProps.userId) {
        Pair(
            state.copy(posts = emptyList(), loading = true),
            listOf(Command.async("fetch_posts") { PostService.getUserPosts(newProps.userId) })
        )
    } else {
        Pair(state, emptyList())
    }
}
```

There is no reactive dependency tracking. If the "dependency" is an internal state value rather than a prop, trigger the effect directly from the state transition that changes the value.

---

### `useEffect(() => { return cleanup }, [])` → `terminate`

```kotlin
fun mount(props: FeedProps): Pair<FeedState, List<Command>> =
    Pair(FeedState(), listOf(Command.subscribe("feed:${props.userId}")))

fun terminate(state: FeedState, props: FeedProps): Unit {
    ConnectionPool.release(state.connection)  // Explicit cleanup for non-Command resources
}
```

`Command.subscribe` automatically unsubscribes on terminate. Explicit `terminate` is needed only for resources outside of `Command` lifecycle management.

---

### `useReducer` → Explicit State Machine

`useReducer` is not needed as a distinct construct. Event handler functions collectively ARE the reducer. For complex state machines:

```kotlin
sealed class CounterEvent {
    object Increment : CounterEvent()
    object Decrement : CounterEvent()
    data class Reset(val to: Int = 0) : CounterEvent()
}

data class CounterState(val count: Int, val step: Int = 1)

fun reduce(event: CounterEvent, state: CounterState): CounterState = when (event) {
    is CounterEvent.Increment -> state.copy(count = state.count + state.step)
    is CounterEvent.Decrement -> state.copy(count = state.count - state.step)
    is CounterEvent.Reset     -> state.copy(count = event.to)
}

fun handleIncrement(state: CounterState) = reduce(CounterEvent.Increment, state)
fun handleDecrement(state: CounterState) = reduce(CounterEvent.Decrement, state)
```

---

### `useContext` → PubSub and Process Registry

For application-wide global state:

```kotlin
fun mount(props: ThemedComponentProps): Pair<ThemedState, List<Command>> =
    Pair(
        ThemedState(theme = ThemeRegistry.current()),
        listOf(Command.subscribe("theme:changes"))
    )

fun handle_info(msg: ThemeChanged, state: ThemedState): ThemedState =
    state.copy(theme = msg.newTheme)
```

For per-session data (current user, locale): passed through the router as session context, accessible in `mount`:

```kotlin
fun mount(props: MyProps, session: Session): Pair<MyState, List<Command>> {
    val currentUser = session.get<User>("current_user")
    return Pair(MyState(currentUser = currentUser), emptyList())
}
```

---

### `useRef` → JS Hook Handle

For DOM imperatives (focus, scroll), use the `use:` directive:

```kotlin
---
<input
    type="text"
    use:focus={state.shouldFocus}  // JS hook triggers focus when true
    value={state.value}
    onChange={handleChange}
/>
```

For storing server-side mutable references across renders, store in state — unlike React, state fields not referenced in the template do not trigger diff work.

---

### `useMemo` / `useCallback` → Not Needed

`useMemo` is unnecessary on the BEAM. There is no Virtual DOM reconciliation to prevent. The diff protocol only sends changed dynamic values. Functions in the template are pure KorE functions called on every render; this is correct and cheap.

```kotlin
// No useMemo needed
fun sortedUsers(state: UserListState): List<User> = state.users.sortedBy { it.name }

---
<ul>
    {for user in sortedUsers(state)}
        <li key={user.id}>{ user.name }</li>
    {/for}
</ul>
```

If a computation is genuinely expensive, store the result in state and update it only when the source changes:

```kotlin
fun handleUsersLoaded(users: List<User>, state: UserListState): UserListState =
    state.copy(
        users = users,
        sortedUsers = users.sortedBy { it.name }
    )
```

---

### `useTransition` → `Command.async`

```kotlin
fun handleTabChange(tab: Tab, state: PageState): Pair<PageState, List<Command>> =
    Pair(
        state.copy(activeTab = tab, loading = true),
        listOf(Command.async("load_tab_data") { TabService.loadData(tab) })
    )

fun handleTabDataLoaded(result: Ok<TabData>, state: PageState): PageState =
    state.copy(tabData = result.value, loading = false)
```

### Complete Lifecycle Diagram

```
Client connects
      │
      ▼
  loadData(params, session)    ← Page-level data loading (like getServerSideProps)
      │
      ▼
  mount(props)                 ← GenServer starts, initial state set, Commands dispatched
      │
      ▼
  render(state)                ← Template evaluated, Rendered diff tree produced
      │                        ← Initial HTML sent to client
      ▼
  ┌─────────────────────────────────────────────────────────────┐
  │                    Component Running                        │
  │                                                             │
  │  User event   → handle_event → new state → render → diff   │
  │  Async result → handle_info  → new state → render → diff   │
  │  PubSub msg   → handle_info  → new state → render → diff   │
  │  Props change → update       → new state → render → diff   │
  │                                                             │
  └─────────────────────────────────────────────────────────────┘
      │
      ▼
  terminate(state)             ← Client disconnects or navigates, cleanup runs
```

**Complete lifecycle example:**

## 11.5 — Event Handling

### The Round-Trip Model

User clicks → aKt JS runtime captures event → WebSocket message sent → component GenServer receives → handler called → new state → render + diff → diff sent → DOM updated.

The round trip typically completes in under 50ms on a co-located server.

---

### Standard Events

| aKt attribute | DOM event | Payload type |
|---|---|---|
| `onClick` | `click` | `ClickEvent` |
| `onChange` | `change` | `ChangeEvent` |
| `onInput` | `input` | `InputEvent` |
| `onSubmit` | `submit` | `SubmitEvent` |
| `onKeyDown` | `keydown` | `KeyboardEvent` |
| `onKeyUp` | `keyup` | `KeyboardEvent` |
| `onFocus` | `focus` | `FocusEvent` |
| `onBlur` | `blur` | `FocusEvent` |
| `onMouseEnter` | `mouseenter` | `MouseEvent` |
| `onMouseLeave` | `mouseleave` | `MouseEvent` |
| `onDragStart` | `dragstart` | `DragEvent` |
| `onDrop` | `drop` | `DragEvent` |
| `onScroll` | `scroll` | `ScrollEvent` |

**Full round-trip for `onClick`:**

1. aKt JS runtime detects `click` event
2. Reads `phx-click="handleAddItem"` attribute from element
3. Sends `{"type": "event", "name": "handleAddItem", "payload": {}}` over WebSocket
4. GenServer dispatches to `handleAddItem`
5. Handler returns `(newState, [Command.run(...)])`
6. GenServer updates state, executes commands, runs `render(newState)`, diffs against previous render
7. Diff sent to client
8. aKt JS runtime applies patch to DOM

---

### Event Payload Types

### Preventing Default


## 11.6 — Server vs Client Components

### The Default: Everything Is a Server Component

Every `.akt` component runs on the server by default. No JavaScript is shipped for its logic. Full access to database, process registry, PubSub. Server-side secrets never exposed. Search engines see fully-rendered HTML. Zero JavaScript bundle growth as you add components.

This is stronger than Next.js server components, which require explicit opt-in. In aKt, you opt out.

---

### `use client` — Client-Side Islands

```kotlin
// SortableList.akt
use client  // Must be the first non-comment line

import akt.client.*

props SortableListProps {
    val items: List<SortableItem>
    val onReorder: (List<String>) -> Unit
}

data class SortableListState(val items: List<SortableItem>)

fun mount(props: SortableListProps): SortableListState =
    SortableListState(items = props.items)

---

    {for item in state.items}
        <li key={item.id} class="sortable-list__item" data-id={item.id}>{ item.label }</li>
    {/for}
</ul>
```

A `use client` component:
- Compiled to JavaScript (TypeScript via aKt-to-TS backend), included in the browser bundle
- Runs in the browser, not the server
- No corresponding GenServer process
- Communicates with parent server component via props and callbacks

---

### The Boundary Rules

**Rule 1: Server components can use client components.** A server template may include `<SortableList>`. The server renders the island's initial HTML, marks it with island metadata, and the client runtime hydrates it.

```kotlin
// Dashboard.akt (server component)
---
<div class="dashboard">
    <DashboardStats stats={state.stats} />       // Server component
    <RecentActivity feed={state.feed} />          // Server component
    <SortableList                                  // Client component (island)
        items={state.widgets}
        onReorder={handleWidgetReorder}
    />
</div>
```

**Rule 2: Client components cannot use server components.** Compile error if attempted.

**Rule 3: Props crossing the boundary must be serializable.** Primitives, strings, lists, maps of serializable types, `data class` types where all fields are serializable. Not serializable: function references (except callbacks), PIDs, opaque Erlang terms. The compiler verifies this at the call site.

**Rule 4: Callbacks** are serialized as `"__cb:binding_name"` strings. When the client invokes a callback, it sends an event to the parent server component, which dispatches it.

## 11.8 — Async Data Loading

### `Command.async` — The Core Pattern

```kotlin
// Elixir LiveView's assign_async:
assign_async(socket, [:user], fn -> {:ok, %{user: fetch_user(id)}} end)

// aKt equivalent:
Command.async("load_user") { UserService.getById(userId) }
```

`Command.async(name, block)` runs the block in a separate BEAM process. When it completes, sends `AsyncResult<name, T>` to the component process, handled by the matching `handle_info`.

**Naming is compile-time checked.** Every `Command.async("name")` must have a corresponding `handle_info(msg: AsyncResult<"name", T>)`. Missing handler → compile warning `W0030`.

**Cancellation:** If a new `Command.async("name")` is issued before the previous one completes, the previous result is discarded. This prevents stale data races.

**Parallel loading:**

```kotlin
fun mount(props: PageProps): Pair<PageState, List<Command>> =
    Pair(

        listOf(
            Command.async("users")    { UserService.getAll() },
            Command.async("tags")     { TagService.getAll() },
            Command.async("settings") { SettingsService.get() }

// These three run concurrently, resolve independently, trigger separate handle_info calls
```

### `AsyncValue<T>` — Loading State Pattern

```kotlin
sealed class AsyncValue<out T> {
    object Loading : AsyncValue<Nothing>()
    data class Error(val message: String) : AsyncValue<Nothing>()
    data class Ready<T>(val value: T) : AsyncValue<T>()
    data class Refreshing<T>(val staleValue: T) : AsyncValue<T>()

    val isLoading: Boolean get() = this is Loading || this is Refreshing
    val valueOrNull: T? get() = when (this) {
        is Ready -> value; is Refreshing -> staleValue; else -> null
    }
}
```

```kotlin
    is AsyncValue.Refreshing -> (
        <>
            <div class="feed__refreshing-banner" aria-live="polite">Refreshing...</div>
            <PostList posts={state.posts.staleValue} />
        </>
    )
    is AsyncValue.Ready  -> <PostList posts={state.posts.value} />
    is AsyncValue.Error  -> <FeedError message={state.posts.message} onRetry={handleRefresh} />
} }
```

---

### Streaming Is the Default

The aKt diff protocol inherently streams. As each `Command.async` completes and `handle_info` runs, the client receives an incremental update. There is no "flush" step. Streaming is not a special feature — it is the default behavior when multiple async commands are in flight.

## 11.10 — The aKt Compiler Pipeline

### The Parsing Phase

**File splitting:** The compiler scans for a line equal to exactly `"---"`. If not found: `E0001: .akt file missing --- separator`. Logic section = everything above. Template section = everything below.

**Template AST node types:**

```kotlin
sealed class TemplateNode {
    data class TextNode(val content: String, val span: Span) : TemplateNode()
    data class CommentNode(val content: String, val span: Span) : TemplateNode()
    data class ElementNode(val tag: String, val attributes: List<Attribute>,
        val children: List<TemplateNode>, val selfClosing: Boolean, val span: Span) : TemplateNode()
    data class ComponentNode(val name: String, val attributes: List<Attribute>,
        val slotChildren: Map<String, List<TemplateNode>>,
        val defaultSlotChildren: List<TemplateNode>, val span: Span) : TemplateNode()
    data class ExpressionNode(val expr: kore.ast.ExpressionNode, val span: Span) : TemplateNode()
    data class ConditionalNode(val branches: List<CondBranch>, val span: Span) : TemplateNode() {
        data class CondBranch(val condition: kore.ast.ExpressionNode?, val body: List<TemplateNode>)
    }
    data class LoopNode(val binding: String, val indexBinding: String?,
        val collection: kore.ast.ExpressionNode, val keyExpr: kore.ast.ExpressionNode?,
        val body: List<TemplateNode>, val span: Span) : TemplateNode()
    data class SlotNode(val name: String, val fallback: List<TemplateNode>, val span: Span) : TemplateNode()
    data class FragmentNode(val children: List<TemplateNode>, val span: Span) : TemplateNode()
}
```

**Attribute types:**

```kotlin
sealed class Attribute {
    data class StaticAttribute(val name: String, val value: String, val span: Span) : Attribute()
    data class DynamicAttribute(val name: String, val expr: kore.ast.ExpressionNode, val span: Span) : Attribute()
    data class EventAttribute(val eventName: String, val handler: kore.ast.ExpressionNode, val span: Span) : Attribute()
    data class HookAttribute(val hookName: String, val span: Span) : Attribute()
    data class KeyAttribute(val expr: kore.ast.ExpressionNode, val span: Span) : Attribute()
    data class BooleanAttribute(val name: String, val span: Span) : Attribute()
}
```

**Recursive expression parsing:** When the template parser encounters `{`, it hands control to the KorE expression parser, tracking brace depth to find the closing `}`. Any valid KorE expression is legal inside `{ }`. Declarations (`val x = ...`) are not permitted inside `{ }`.

**Disambiguating components from elements:** First character of tag name. Lowercase → `ElementNode`. Uppercase → `ComponentNode`. Unambiguous because HTML is always lowercase and KorE types are always PascalCase.

---

### The Type Checking Phase

**Template scope:** `props` (props record type), `state` (state data class, `@LiveComponent` only — referencing `state` in a `@Component` is a hard error), all top-level functions from the logic section, all imported names. Loop bindings extend scope within their body. Local variable declarations are not permitted in templates.

**Prop type checking:** For every `<ComponentNode>`: resolve to target `.akt` file → read `props` block → check each attribute (type match, unknown attribute → error, missing required → error, duplicate → error).

**Event handler verification:** Every `EventAttribute` must resolve to a function matching the expected signature for its event type. Hard error `E0060` on mismatch with found/expected types.

**`key` attribute:** Must be `String` expression. Non-String → compile error. Missing on list children → compile warning.

**Renderable types:** `String`, `Int`/`Long`/`Float`/`Double`, `TemplateNode`, `List<TemplateNode>`. Any other type in `{ }` position → compile error.

---

### Static/Dynamic Analysis

Bottom-up walk. Each node classified as `Static`, `Props`, `State`, or `Both`.

- `TextNode`, `CommentNode` → always `Static`
- `ExpressionNode` → free-variable analysis on the KorE expression AST
- `ElementNode`, `ComponentNode` → maximum dependency of attributes and children
- `ConditionalNode`, `LoopNode` → always at least `Props` or `State`

Static subtrees → serialized to HTML strings at compile time → stored as binary constants.

**The `Rendered` data structure:**

```erlang
%{
  :s => ["static0", "static1", "static2"],   %% static string parts in order
  0  => DynamicPart0,                         %% dynamic slot 0
  1  => DynamicPart1,                         %% dynamic slot 1
}
```

Static strings and dynamic slots are interleaved: `s[0]` + slot0 + `s[1]` + slot1 + `s[2]` = full HTML.

**Concrete example** — Counter template:
```
<div class="counter"><h1>{ props.title }</h1><p>Count: { state.count }</p>...</div>
```

```erlang
%{
  :s => [
    <<"<div class=\"counter\"><h1>">>,
    <<"</h1><p>Count: ">>,
    <<"</p><button phx-click=\"decrement\">-</button><button phx-click=\"increment\">+</button></div>">>
  ],
  0 => <<"My Counter">>,   %% props.title
  1 => <<"42">>            %% state.count
}
```

Diff after one increment (count: 42 → 43): `%{1 => <<"43">>}` — two bytes over the wire.

### Compile-Time Optimizations

- **Static part hoisting:** Binary constants as module-level `-define` macros — allocated once on module load, shared across all render calls without copying.
- **Dead prop detection:** Prop declared but never referenced → `W0020`.
- **Unhandled `Command.async` result:** `Command.async("name")` with no matching `handle_info(AsyncResult<"name", T>)` → `W0030`.
- **Event handler signature mismatch:** Hard error `E0060` with found/expected types.

## 11.11 — JavaScript Interop

### The aKt JS Runtime

The browser-side `akt-runtime` npm package. Responsibilities:

**WebSocket management:** Auto-reconnect with exponential backoff (base 500ms, max 30s, ±25% jitter). Heartbeat pings every 30 seconds. Graceful reconnection by requesting a full render from the server.

**Diff application:** Receives `Rendered` diffs → merges into current in-memory `Rendered` map → renders full HTML by interleaving static and dynamic parts → applies targeted DOM updates (not full page replacement).

**Event dispatch:** Single delegated event listener at `document.body` per event type. On event: walk DOM from target to find `phx-click` (or equivalent) attribute → extract handler name + component ID → serialize relevant event fields → send over WebSocket.

**Hook lifecycle management:** Registry of hook instances keyed by DOM element. Calls `mounted`, `beforeUpdate`, `updated`, `beforeDestroy`, `destroyed`, `disconnected`, `reconnected` at the appropriate times.

**Client component hydration:** Finds `[data-akt-island]` elements → deserializes props from `data-akt-props` → imports bundle at `data-akt-bundle` → calls `hydrate(element, props)`. Reuses server-rendered HTML (progressive hydration).

**Navigation:** `Command.navigate` → `window.history.pushState` + page remount. `Command.patch` → `pushState` without remount.

## 11.12 — Language Feature Requirements Inventory

### 1. `.akt` File Format Recognition

**What:** The KorE compiler must distinguish `.akt` from `.kore` and route through the aKt pipeline.

**What it does:** Extension check in file loader. `.akt` → aKt pre-processor → `---` split → separate parsers. Missing `---` → `E0001`, halt. Empty logic section (nothing above `---`) → allowed. Empty template section → hard error.

**Phase:** File loading / pre-processing, before parse phase.

**Open questions:** Should `.akt` files be able to import from `.kore` and vice versa? Currently yes. Should a `.akt` file without `---` be valid as a pure logic module? No.

---

### 2. Template AST Definition

**What:** Complete set of `TemplateNode` node types.

**What it does:** `TemplateNode` sealed class defined in compiler's IR module. Separate from KorE declaration/expression ASTs but `ExpressionNode` embeds `kore.ast.ExpressionNode`. All nodes carry `Span` references for diagnostics.

**Phase:** Compiler IR definition; populated by template parser.

**Open questions:** Preserve `CommentNode` in output? Current decision: strip from `Rendered` output, preserve in AST for tooling. Include `RawHtmlNode` for `{@html expr}`? Not planned initially — security-sensitive addition.

---

### 3. Template Parser

**What:** Recursive descent parser for the template section.

**What it does:** Implements grammar for `element`, `component`, `expression`, `conditional`, `loop`, `fragment`, `text`, `comment`. Delegates `{ expr }` to KorE expression parser. Disambiguates elements from components by first character case.

**Phase:** Parse phase, after `---` split.

**Open questions:** `@for` with destructuring bindings `@for ((a, b) in pairs)`? Currently supported. `@when` as a template directive? Planned.

---

### 4. Template Scope Resolution

**What:** Mechanism for resolving identifiers in template expressions.

**What it does:** Template scope = `{ props, state (LiveComponent only), all top-level functions, all imports }`. Passed to KorE type checker for `ExpressionNode` checking. Loop bindings extend scope within body. `val` declarations inside `{ }` → hard error. No `this`.

**Phase:** Type checking phase.

**Open questions:** Computed properties (zero-arg functions) accessible as `props.derivedValue`? Current position: function call syntax only `derivedValue()`.

---

### 5. Component Prop Type Checking

**What:** Verification of `<MyComponent prop={expr}>` against declared `props` block.

**What it does:** Resolve component name via import graph → read `props` block → check each attribute: type match, unknown attribute → error, missing required → error, duplicate → error.

**Phase:** Type checking phase, after import resolution.

**Open questions:** Allow `data-*` on component nodes? Currently not permitted. Allow `class` merging across usage site and component template? Not yet designed.

---

### 6. Event Handler Type Verification

**What:** Verification of `onClick={handler}` signatures.

**What it does:** Compiler maintains event-name → expected-signature table. For each `EventAttribute`: resolve handler type, verify assignable to either `State`-returning or `Pair<State, List<Command>>`-returning variant. Error `E0060` on mismatch. For `@Component` (stateless): any event attribute → immediate error.

**Phase:** Type checking phase.

**Open questions:** Custom event names? Supported: `onCustomEvent={handler}`, type checking rules not yet fully specified. Handler as a `val` of function type? Yes — any expression of correct function type is permitted.

---

### 7. Static/Dynamic Split Implementation

**What:** Algorithm classifying every template node as static or dynamic.

**What it does:** Bottom-up walk. Compute `Dependency` enum `{Static, Props, State, Both}` per node. Free-variable analysis on KorE expression ASTs. Static subtrees → serialized to HTML strings at compile time, stored as binary constants. Result stored in `ClassifiedNode` IR wrapper.

**Phase:** Static analysis phase, after type checking.

**Open questions:** Transitive purity analysis through function calls? Deferred — current rule: any expression containing `props.*` or `state.*` as subexpression is dynamic.

---

### 8. `Rendered` Data Structure Generation

**What:** The exact Erlang term produced by `render_template/2` and the code generation algorithm.

**What it does:** Number dynamic slots depth-first, left-to-right. Generate: (1) list of static string segments as module-level `-define` constants, (2) `render_template(State, Props)` function building `:s` list and evaluating each dynamic slot, (3) nested `ComponentNode` renders as nested `Rendered` maps. Events compile to `phx-click="handler_name"` static attributes.

**Phase:** Code generation phase.

**Open questions:** `ConditionalNode` and `LoopNode` variable-size slots? Answer: conditionals as nested `Rendered` maps with `:d` branch-index key. Loops as lists of `Rendered` maps. Full diff semantics for conditionals and loops deferred to later specification.

---

### 9. GenServer Generation for `@LiveComponent`

**What:** Full Erlang GenServer module for every `@LiveComponent`.

**What it does:** Generates: `-record(component_state, {state, props, prev_rendered, socket})`, `init/1` calling `mount/1`, one `handle_call` clause per event handler, `handle_cast` for prop updates, `handle_info` dispatch for async results / PubSub / hook events, `terminate/2`, `do_render/1` for render+diff+send cycle, `process_command/2` dispatch.

**Phase:** Code generation phase.

**Open questions:** Supervised? Yes — `DynamicSupervisor` managed by aKt runtime. Hot code upgrade (`code_change/3`)? Deferred — requires state migration function design.

### 10. Event Binding Compilation

**What:** How `onClick={handler}` compiles to a wire-protocol attribute.

**What it does:**

| aKt attribute | Compiled HTML attribute |
|---|---|
| `onClick={f}` | `phx-click="f"` |
| `onInput={f}` | `phx-change="f"` |
| `onChange={f}` | `phx-change="f"` |
| `onSubmit={f}` | `phx-submit="f"` |
| `onKeyDown={f}` | `phx-keydown="f"` |
| `onFocus={f}` | `phx-focus="f"` |
| `onBlur={f}` | `phx-blur="f"` |

Event attributes compile to static HTML strings — they appear in the static segment of `Rendered` and are never diffed. Swapping event handlers at runtime is not supported; conditional dispatch belongs in the handler function.

**Phase:** Code generation phase.

**Open questions:** Full DOM event object vs selected fields? Selected fields only (typed subset by event type). Declarative debounce/throttle on bindings? `onClick(debounce=300)={handler}` planned but not yet specified.

### 11. `Command.async` Result Routing

**What:** Compile-time tracking and runtime routing of async task results.

**What it does:** Compile-time: collect all `Command.async("name")` names and all `handle_info(AsyncResult<"name", T>)` names. Names in async set not in handled set → `W0030`. Code generation: pattern-matched `handle_info` dispatch on `{async_result, Name, Result}`. `AsyncResult<"name", T>` is a compile-time marker; `T` is type-checked but erased at Erlang level. Catch-all clause emits `Logger.warn` for unrecognized names.

**Phase:** Static analysis (warning), code generation (dispatch).

**Open questions:** Timeout support? `Command.async("name", timeout = 5000) { ... }` with automatic error on expiry — planned.

### 12. File-Based Routing Code Generation

**What:** Scanning `pages/` and generating a Ping router module.

**What it does:** Scan `pages/` recursively. Compute URL path from file position. Detect `_layout.akt`, `_loading.akt`, `_error.akt`. Verify all page-level `.akt` files are `@LiveComponent`. Generate Ping router module:

```kotlin
router {
    scope("/", pipeline = "live") {
        live("/",          'KorE.Pages.Index')
        live("/users/:id", 'KorE.Pages.Users.Show', params = ["id"])
    }
}
```

**Phase:** Post-processing step after all page `.akt` files individually compiled.

**Open questions:** POST/PUT/DELETE routes for API from pages? No — API routes declared manually in Ping router. Parallel routes (Next.js-style)? Not planned for initial release.

### 13. Client Component (`use client`) Bundling

**What:** Separate compilation path for `use client` files.

**What it does:**
1. Detect `use client` as literal first line
2. Route to TS/JS backend
3. Same parse + type checking phases, generates TypeScript
4. Emits: TypeScript class file in `priv/static/akt/src/`, compiled hashed JS bundle in `priv/static/akt/`, server-side Erlang module with `render_initial/1` for SSR (only `mount` compiled twice — once to TS, once to Erlang)
5. Props serialized as JSON; callbacks as `"__cb:name"` strings
6. Island metadata embedded in HTML via `data-akt-island`, `data-akt-bundle`, `data-akt-props`

`use client` components cannot use KorE stdlib functions with no TS equivalent — compiler flags these at TS code generation phase.

**Phase:** Pre-processing (detection), TS/JS backend during parse/type-check/codegen.

**Open questions:** `Command`-like system for client components? Not planned initially. Bundler configurable? Fixed at esbuild for initial release.

### 14. The aKt Runtime JS Library

**What:** The browser-side `akt-runtime` npm package.

**Public API:**

```typescript
new AktRuntime(config: AktConfig): AktRuntime

interface AktConfig {
    endpoint: string
    hooks?: Record<string, Hook>
    params?: Record<string, string>
    logger?: Logger
}

runtime.connect(): void
runtime.disconnect(): void
runtime.pushEvent(target: string | Element, name: string, payload: object): void
runtime.handleEvent(name: string, callback: (payload: object) => void): () => void

interface Hook {
    mounted?(): void
    beforeUpdate?(): void
    updated?(): void
    beforeDestroy?(): void
    destroyed?(): void
    disconnected?(): void
    reconnected?(): void
    handleEvent?(name: string, payload: object): void
}
```

**What it does NOT provide (by design):**
- No Virtual DOM — all diffing is server-side, client only applies pre-computed patches
- No component tree — components are server concepts
- No React-style hooks — state lives on the server or in `use client` islands
- No routing logic beyond applying History API commands from server
- No templating engine — templates compiled server-side

**Size target:** ~15–20 kB gzipped (comparable to Alpine.js, not React). WebSocket management + diff application + event delegation + hook lifecycle is implementable in a small footprint.

**Package distribution:** Published as `akt-runtime` on npm. Versioned alongside the aKt compiler. Included automatically in `priv/static/` by the aKt build plugin — manual npm installation not required for standard projects.
