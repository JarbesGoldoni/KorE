## 1. How the Erlang Compiler Works

### 1.1 Full Pipeline

```
source.erl
  │
  ▼
epp (preprocessor)
  │  - macro expansion (-define, -ifdef, -include, -include_lib)
  │  - produces token stream with source annotations
  ▼
erl_scan (lexer)
  │  - tokenizes: atoms, integers, floats, strings, operators, punctuation
  │  - each token carries anno (line+column since OTP 24)
  ▼
erl_parse (parser)
  │  - recursive descent + operator precedence
  │  - produces Erlang Abstract Format (EAF) — a list of erl_parse:abstract_form()
  ▼
parse_transforms (optional, zero or more)
  │  - Module:parse_transform(Forms, Options) -> Forms'
  │  - operates on EAF terms before lint
  ▼
erl_lint (semantic checks)
  │  - undefined functions, unused vars, behaviour callbacks, type checks
  │  - uses erl_expand_records to desugar record syntax
  ▼
erl_expand_records
  │  - records desugared to tuple operations
  │  - produces expanded EAF (.exp file with 'E' option)
  ▼
v3_core (EAF → Core Erlang)
  │  - produces cerl:c_module()
  │  - normalizes: pattern matching, let-bindings, tail position
  ▼
core_lint (validate Core Erlang)
  │
  ▼
core_transforms (optional, analogous to parse_transforms)
  │
  ▼
sys_core_fold (Core Erlang optimizer)
  │  - constant folding, dead clause elimination, inlining
  ▼
sys_core_alias (share sub-expressions)
  ▼
sys_core_bsm (binary match optimization)
  ▼
v3_kernel (Core Erlang → Kernel Erlang)
  │  - pattern matching compilation: cerl case → flat switch/select
  │  - explodes nested patterns into decision trees
  │  - introduces explicit block structure
  ▼
v3_codegen / beam_ssa_codegen
  │  - Kernel Erlang → BEAM SSA (Static Single Assignment)
  │  - SSA form: each variable assigned exactly once
  ▼
beam_ssa_* passes (many optimization passes)
  │  beam_ssa_opt      - general SSA optimizations
  │  beam_ssa_type     - type-based optimization (OTP 22+)
  │  beam_ssa_bool     - boolean expression optimization
  │  beam_ssa_recv     - selective receive optimization
  │  beam_ssa_throw    - exception optimization
  │  beam_ssa_share    - code sharing
  │  beam_ssa_bsm      - binary match codegen
  ▼
beam_ssa_pre_codegen
  │  - register allocation prep (BEAM has no real registers, this is
  │    about slot allocation in the process stack frame)
  ▼
beam_block / beam_codegen
  │  - SSA → BEAM assembly (.S format, the beam_asm input)
  ▼
beam_peep / beam_clean / beam_jump / beam_trim
  │  - peephole optimizations on raw instruction stream
  ▼
beam_asm (assembler)
  │  - instruction encoding
  │  - atom table construction
  │  - literal table construction
  │  - export/import table construction
  ▼
beam_validator
  │  - safety check: verifies stack discipline, no uninitialized reads
  │  - this is the "type safety" check the runtime relies on
  ▼
.beam file (IFF container with named chunks)
```

The `compile:options()` call at the Erlang REPL prints every intermediate listing option in pass order, which is the definitive pass sequence for a given OTP version.

### 1.2 Key compile options affecting the pipeline

```erlang
% Stop at various points:
'P'          % after parse + parse_transforms → .P file (EAF pretty-printed)
'E'          % after erl_expand_records → .E file
to_abstr     % dump EAF terms → .abstr
to_exp       % dump expanded EAF → .exp
to_core      % dump Core Erlang → .core
'S'          % dump BEAM assembly → .S

% Enter at various points:
from_abstr   % input is .abstr EAF terms
from_core    % input is .core Core Erlang
from_asm     % input is .S BEAM assembly (STRONGLY DISCOURAGED)

% Debug/info:
debug_info         % stores debug_info chunk (EAF or Core, pluggable backend)
{debug_info, {Backend, Data}}   % custom debug info backend
verbose            % print passes as they run
{parse_transform, Mod}  % add a parse transform
{core_transform, Mod}   % add a core transform (less commonly used)
binary             % return beam binary, don't write file
{outdir, Dir}
deterministic      % omit non-deterministic compile_info entries
```

### 1.3 parse_transform system

A parse transform is an Erlang module that exports:

```erlang
-module(my_transform).
-export([parse_transform/2]).

parse_transform(Forms, Options) ->
    % Forms :: [erl_parse:abstract_form()]
    % Options :: [compile:option()]
    % Returns :: [erl_parse:abstract_form()]
    %
    % Walk and transform the EAF term list.
    % erl_syntax and erl_syntax_lib provide helpers.
    Forms.
```

Key properties:
- Runs **after** preprocessing and parsing, **before** `erl_lint`
- Gets called once per module, not per function
- The transform sees the full module including attributes, type specs, etc.
- Compile errors from the transform crash it as `{parse_transform, Mod, {Class, Reason, Stacktrace}}`
- Can call `compile:file/2` recursively but should use `noenv_file/2` to avoid re-reading `ERL_COMPILER_OPTIONS`
- The `parse_transform_info/0` callback (optional) can declare `{error_location, column | line}`

Classic examples:
- `ms_transform` — rewrites `ets:fun2ms(fun(Pat) -> Body end)` into match specs at compile time
- `lager_transform` — rewrites log calls to check log level before evaluating arguments
- `ct_expand` — evaluates constant expressions at compile time

**For KorE**: parse transforms are not the right insertion point since KorE generates its own AST. The right insertion point is either the Abstract Format or Core Erlang.

## 2. Erlang Abstract Format (EAF) in Depth

EAF is the Erlang term representation of parsed source. It is what `erl_parse:parse_form/1` produces and what `compile:forms/2` accepts as input. This is the **recommended entry point for KorE** per the official documentation.

### 2.1 Module-level structure

```erlang
% A module is a list of forms:
[
  {attribute, Anno, module, my_module},
  {attribute, Anno, export, [{foo, 1}, {bar, 2}]},
  {attribute, Anno, import, {lists, [{map, 2}]}},
  {attribute, Anno, vsn, "1.0.0"},
  {attribute, Anno, record, {my_rec, [
    {record_field, Anno, {atom, Anno, field1}},
    {record_field, Anno, {atom, Anno, field2}, {integer, Anno, 0}}
  ]}},
  {attribute, Anno, type, {my_type, {type, Anno, list, [{type, Anno, integer, []}]}, []}},
  {function, Anno, foo, 1, [
    {clause, Anno, [{var, Anno, 'X'}], [], [
      {call, Anno, {atom, Anno, bar}, [{var, Anno, 'X'}, {integer, Anno, 42}]}
    ]}
  ]},
  {function, Anno, bar, 2, [...]},
  {eof, Anno}
]
```

`Anno` is an opaque annotation term from `erl_anno`. You construct it with `erl_anno:new(Line)` or `erl_anno:new({Line, Column})`. When generating from KorE source, you carry the KorE source location through and embed it here.

### 2.2 Key expression forms

```erlang
% Variables
{var, Anno, 'X'}                          % uppercase atom
{var, Anno, '_'}                          % wildcard

% Literals
{atom,    Anno, foo}
{integer, Anno, 42}
{float,   Anno, 3.14}
{char,    Anno, $A}                       % integer value 65
{string,  Anno, "hello"}                  % list of integers

% Compound data
{nil, Anno}                               % []
{cons, Anno, Head, Tail}                  % [H | T]
{tuple, Anno, [E1, E2, E3]}               % {E1, E2, E3}

% Operators
{op, Anno, '+', Left, Right}              % binary
{op, Anno, '-', Operand}                  % unary

% Function calls (local)
{call, Anno, {atom, Anno, Name}, Args}

% Function calls (remote / inter-module)
{call, Anno, {remote, Anno, {atom, Anno, Mod}, {atom, Anno, Fun}}, Args}

% Pattern match / assignment
{match, Anno, Pattern, Expr}

% Case
{'case', Anno, Expr, [Clause1, Clause2, ...]}

% Clause
{clause, Anno, Patterns, Guards, Body}
% Guards is [[GuardTest, ...], ...] (list of guard conjunctions, OR-ed)

% If
{'if', Anno, [Clause1, ...]}

% Anonymous function
{'fun', Anno, {clauses, [Clause1, ...]}}
{'fun', Anno, {function, Name, Arity}}
{'fun', Anno, {function, {atom,Anno,Mod}, {atom,Anno,Fun}, {integer,Anno,Arity}}}

% Try
{'try', Anno, Body, OfClauses, CatchClauses, AfterBody}
% OfClauses: [] if no 'of'
% CatchClauses: [] if no 'catch'
% AfterBody: [] if no 'after'

% Receive
{'receive', Anno, [Clause, ...]}
{'receive', Anno, [Clause, ...], TimeoutExpr, TimeoutBody}

% Catch (old style)
{'catch', Anno, Expr}

% Block
{block, Anno, [Expr1, Expr2, ...]}

% Comprehensions
{lc, Anno, Template, Qualifiers}
{bc, Anno, Template, Qualifiers}
{mc, Anno, Template, Qualifiers}          % map comprehension (OTP 26+)
% Qualifiers:
{generate, Anno, Pattern, ListExpr}       % P <- E
{b_generate, Anno, Pattern, BinExpr}     % P <= E

% Binaries
{bin, Anno, [{bin_element, Anno, Expr, Size, TypeSpecList}, ...]}
% Size: 'default' | Expr
% TypeSpecList: 'default' | [integer | float | binary | bytes | bitstring | bits | utf8 | utf16 | utf32 | signed | unsigned | big | little | native | {unit, N}]

% Map creation
{map, Anno, [{map_field_assoc, Anno, Key, Val}, ...]}
% Map update
{map, Anno, Expr, [{map_field_assoc|map_field_exact, Anno, Key, Val}, ...]}

% Records (syntactic sugar, desugared by erl_expand_records)
{record, Anno, Name, Fields}
{record, Anno, Expr, Name, Fields}        % update
{record_index, Anno, Name, Field}
{record_field, Anno, Expr, Name, Field}   % access
```

### 2.3 Generating EAF from KorE

KorE's compiler should:
1. Parse KorE source → KorE AST (typed)
2. Resolve names, infer/check types
3. Lower KorE AST → EAF terms, carrying source location in `Anno`
4. Call `compile:forms(EafForms, [debug_info, return_errors, {outdir, Dir}])`

Source location mapping: use `erl_anno:new({Line, Column})` with KorE source positions. This makes error messages from the Erlang backend refer back correctly.

## 3. Core Erlang in Depth

Core Erlang is a strict, explicitly-typed (at the level of structure, not Hindley-Milner types), functional IR derived from the Erlang lambda calculus. It was specified by Carlsson et al. It normalizes Erlang's syntactic surface while preserving all semantics.

### 3.1 What Core Erlang normalizes away

| Erlang source construct | Core Erlang equivalent |
|------------------------|----------------------|
| Multi-clause functions | Single function body with `case` |
| `if` expressions | `case` with guard-only clauses |
| Record syntax | Tuple operations |
| List comprehensions | Recursive `letrec`/`apply` |
| `begin...end` blocks | `let` sequences |
| Guard sequences | Guard trees in `case` clauses |
| String literals | Lists of integers or literal terms |
| Operator sugar (`1 + 2`) | `call 'erlang':'+'(1, 2)` |

### 3.2 Core Erlang syntax (textual .core format)

The `.core` file format is what you get with `compile:file(F, [to_core])`. It is also what `from_core` reads.

```
module 'my_module' ['foo'/1, 'bar'/2]
    attributes []
  'foo'/1 =
    fun (_0) ->
      case _0 of
        <X> when 'true' ->
          let <_1> = call 'erlang':'+'(X, 42)
          in  apply 'bar'/2(X, _1)
      end
  'bar'/2 =
    fun (_0, _1) ->
      let <Result> =
        case _0 of
          <'ok'> when 'true' ->
            _1
          <'error'> when 'true' ->
            primop 'raise'('error', 'badarg', [])
        end
      in  Result
end
```

### 3.3 Core Erlang node types (from cerl.erl)

The `cerl` module (OTP's `compiler` app, `lib/compiler/src/cerl.erl`) is the canonical API.

**Module:**
```erlang

% Name       :: c_literal()  (atom)
% Exports    :: [c_var()]    (function-name variables like {foo, 1})
% Attributes :: [{c_literal(), c_literal()}]
% Definitions:: [{c_var(), c_fun()}]  % each def is (fname_var, fun_body)

% Example construction:
ModName = cerl:c_atom(my_module),
Exports = [cerl:c_fname(foo, 1)],
Attrs   = [],
Defs    = [{cerl:c_fname(foo, 1), FunBody}],
Mod     = cerl:c_module(ModName, Exports, Attrs, Defs).
```

**Variables:**
```erlang
cerl:c_var(Name)
% Name :: atom() | integer() | {atom(), integer()}
% - atom(): regular variable e.g. c_var('X')
% - {atom(), integer()}: function name variable e.g. c_var({foo, 1})
%   (same as c_fname(foo, 1))
% - integer(): compiler-generated variable

cerl:c_fname(foo, 1)   % equivalent to c_var({foo, 1})
```

**Literals:**
```erlang
cerl:c_atom(foo)          % atom literal
cerl:c_int(42)            % integer literal
cerl:c_float(3.14)        % float literal
cerl:c_nil()              % empty list []
cerl:c_char($A)           % character (= integer 65)
cerl:c_string("hello")    % string (= list of integers, or compact literal)
cerl:abstract(Term)       % any literal Erlang term → c_literal()
% Note: c_literal wraps ANY Erlang term as a literal node:
cerl:c_literal([1,2,3])   % list literal
cerl:c_literal({a, b})    % tuple literal
```

**Compound data:**
```erlang
cerl:c_cons(Head, Tail)           % list cell
cerl:c_tuple([E1, E2, E3])        % tuple constructor
cerl:c_binary([Seg1, Seg2])       % binary constructor
cerl:c_bitstr(Val, Size, Unit, Type, Flags)
% Type: c_atom(integer|float|binary|utf8|utf16|utf32)
% Flags: c_literal([signed|unsigned, big|little|native])
cerl:c_map([Pair1, Pair2])                    % #{} map creation
cerl:c_map(ArgExpr, [Pair1, Pair2])           % map update
cerl:c_map_pair(Key, Val)                     % K => V  (assoc)
cerl:c_map_pair_exact(Key, Val)               % K := V  (exact/update)
```

**Let binding (sequential, non-recursive):**
```erlang
cerl:c_let(Vars, ArgExpr, BodyExpr)
% Vars    :: [c_var()]  — list of variables being bound
% ArgExpr :: cerl()     — expression producing the values
% BodyExpr:: cerl()     — expression in scope of vars
%
% Example: let <X> = foo(42) in bar(X)
Let = cerl:c_let(
    [cerl:c_var('X')],
    cerl:c_apply(cerl:c_fname(foo, 1), [cerl:c_int(42)]),
    cerl:c_apply(cerl:c_fname(bar, 1), [cerl:c_var('X')])
).
%
% Multi-value let (used for multi-return):
% let <X, Y> = some_call() in ...
cerl:c_let([cerl:c_var('X'), cerl:c_var('Y')], Expr, Body)
```

**LetRec (mutually recursive, for local functions and closures):**
```erlang
cerl:c_letrec(Defs, BodyExpr)
% Defs :: [{c_var(), c_fun()}]   — fname vars paired with fun bodies
%
% Used for:
% - Named recursive lambdas
% - Local function groups that are mutually recursive
% - Closures in the compiler output
%
% Example: letrec loop/1 = fun(N) -> ... apply loop/1(N-1) ... in apply loop/1(0)
LoopVar  = cerl:c_fname(loop, 1),
LoopBody = cerl:c_fun([cerl:c_var('N')],
               cerl:c_apply(LoopVar, [
                   cerl:c_call(cerl:c_atom(erlang), cerl:c_atom('-'),
                               [cerl:c_var('N'), cerl:c_int(1)])])),
LetRec   = cerl:c_letrec([{LoopVar, LoopBody}],
               cerl:c_apply(LoopVar, [cerl:c_int(0)])).
```

**Fun (anonymous function / closure):**
```erlang

% Vars :: [c_var()]
% Body :: cerl()
%
```

```erlang

% Name   :: cerl()  — usually c_atom(function_name)
```

### 3.4 Pattern matching compilation in Core Erlang

Erlang's multi-clause functions are compiled by `v3_core` into a single `c_case`. The algorithm is a variant of the matrix-based pattern matching compilation (Wadler's algorithm from "The Implementation of Functional Programming Languages").

```erlang
% Erlang source:
foo({ok, X}) -> X;
foo({error, _}) -> default.

% Core Erlang equivalent (simplified):
'foo'/1 =
  fun (_0) ->
    case _0 of
      <{ok, X}> when true -> X
      <{error, _}> when true -> 'default'
    end
```

For KorE's pattern matching, you generate these `c_case` nodes directly. The BEAM backend (`v3_kernel`) then further compiles the case into a decision tree (select/switch).

Nested patterns are kept nested in Core Erlang — the flattening happens in `v3_kernel`.

### 3.5 Tail calls in Core Erlang

Core Erlang does not have an explicit tail call annotation. The BEAM backend identifies tail calls by position: if a `c_apply` or `c_call` is the last expression in a function body (or in the body of a let/case/try), it becomes a tail call in BEAM.

**Critical rules:**
- `c_apply` of a local function in tail position → `call_last` or `apply_last` BEAM opcode (true tail call, no stack growth)
- `c_call` of a remote function in tail position → `call_ext_last` BEAM opcode
- Any call NOT in tail position → stack frame is allocated

There is no `tailcall` marker to add. Just ensure the call is the final expression.

### 3.6 Module structure with annotations

Every Core Erlang node carries an annotation list (the `anno` field in the record structs). You attach source locations as:

```erlang
Ann = [{file, "foo.kore"}, {location, {10, 5}}],
Node = cerl:set_ann(cerl:c_var('X'), Ann),
% or:
cerl:ann_c_var(Ann, 'X')
% Most constructors have an ann_* variant.
```

### 3.7 Core Erlang tools

- `cerl` — AST construction/decomposition (the API)
- `core_lint` — validates Core Erlang (call `core_lint:module/2`)
- `core_pp` — pretty-prints Core Erlang (call `core_pp:format/1`)
- `cerl_trees` — tree traversal utilities (`cerl_trees:fold/3`, `cerl_trees:map/2`)
- `cerl_clauses` — clause analysis utilities
- `sys_core_fold` — the Core Erlang optimizer (you can call individual passes)


## 4. The .beam File Format

### 4.1 Container format

`.beam` files use the **EA IFF 1985** interchange format (same structure as AIFF/IFF files). The outermost container has a 4-byte magic `FOR1`, 4-byte big-endian content length, 4-byte form type `BEAM`, followed by chunks. Each chunk has:

```
ChunkId   :: 4 bytes ASCII, e.g. "AtU8", "Code", "ExpT"
ChunkSize :: 4 bytes big-endian (byte count of Data, NOT including padding)
Data      :: ChunkSize bytes
Padding   :: 0-3 bytes of zero to align to 4-byte boundary
```

```
+-------+-------+-------+
| FOR1  | Size  | BEAM  |
+-------+-------+-------+
| AtU8  | Size  | Data  |  ← atom table (UTF-8, OTP 20+)
| Code  | Size  | Data  |  ← instruction stream
| ExpT  | Size  | Data  |  ← export table
| ImpT  | Size  | Data  |  ← import table
| LocT  | Size  | Data  |  ← local function table
| Attr  | Size  | Data  |  ← module attributes (binary_to_term)
| CInf  | Size  | Data  |  ← compile info (binary_to_term)
| Dbgi  | Size  | Data  |  ← debug info (pluggable, optional)
| LitT  | Size  | Data  |  ← literal pool (zlib-compressed terms)
| Docs  | Size  | Data  |  ← EEP-48 documentation (OTP 23+)
| ...   | ...   | ...   |  ← any extra chunks
+-------+-------+-------+
```

### 4.2 Chunk details

**AtU8 / Atom** — Atom table

`AtU8` (UTF-8 atoms, OTP 20+) supersedes old `Atom`. Format:
```
Count  :: uint32 (number of atoms)
For each atom:
  Len  :: uint8 (byte length of atom name)
  Data :: Len bytes, UTF-8 encoded
```
Atom index 0 is always the module name. All other chunks refer to atoms by 0-based index.

**Code** — Instruction stream

```
SubWordSize   :: uint32 (always 4 for 32-bit legacy; irrelevant now)
MaxOpcode     :: uint32 (highest opcode number used)
LabelCount    :: uint32 (number of labels)
FunctionCount :: uint32 (number of function entries)
Instructions  :: packed BEAM opcodes
```

Each instruction is a tag-encoded sequence. The tag encoding for operands:
```
tag bits [2:0]:
  000 = u  (unsigned literal)
  001 = i  (integer/signed)
  010 = a  (atom index)
  011 = x  (x register)
  100 = y  (y register, stack slot)
  101 = f  (label/failure)
  110 = h  (character)
  111 = z  (extended tag follows)
extended tag z:
  00_111 = list  (followed by length, then elements)
  01_111 = float literal (8 bytes)
  10_111 = allocation list
  11_111 = literal (index into literal pool)
```

Values use a variable-length encoding: if the low 3 bits are the tag and bit 3 is 0, the upper 4 bits are a 4-bit unsigned value. If bit 3 is 1, more bytes follow.

**ExpT** — Export table
```
Count :: uint32
For each export:
  Function  :: uint32 (atom index)
  Arity     :: uint32
  Label     :: uint32 (instruction label within Code chunk)
```

**ImpT** — Import table
```
Count :: uint32
For each import:
  Module    :: uint32 (atom index)
  Function  :: uint32 (atom index)
  Arity     :: uint32
```
Import table entries are referenced by index from call instructions.

**LocT** — Local function table (same format as ExpT, but not exported)

**LitT** — Literal pool
```
UncompressedSize :: uint32
Data :: zlib-compressed, containing:
  Count :: uint32
  For each literal:
    Size  :: uint32 (byte length of external term format)
    Term  :: Size bytes (erlang:term_to_binary format)
```
Literals are referenced by index from `{z, literal, Index}` operands.

**Attr** — Module attributes
```
Data :: term_to_binary([{vsn, ...}, {other_attr, ...}])
```

**CInf** — Compile info
```
Data :: term_to_binary([{version, "X.Y.Z"}, {options, [...]}, {source, "path"}, ...])
```

**Dbgi** — Debug info (OTP 20+, pluggable)
```
Data :: term_to_binary({debug_info_v1, Backend, BackendData})
% Standard backends:
%   erl_abstract_code — stores EAF (Erlang Abstract Format)
%   core — stores Core Erlang
```

**Docs** — EEP-48 documentation (OTP 23+)
```
Data :: term_to_binary(#docs_v1{...})
```

**Meta** — (OTP 27+) General metadata, format TBD per OTP version.

### 4.3 Reading .beam files with beam_lib

```erlang
% Read specific chunks:
{ok, {Module, Chunks}} = beam_lib:chunks("foo.beam",
    [atoms, exports, imports, compile_info, debug_info, literals]),

% Read all chunks as raw binaries:
{ok, Module, AllChunks} = beam_lib:all_chunks("foo.beam"),

% Build a beam binary from chunks (for writing):
{ok, BeamBinary} = beam_lib:build_module(Chunks),

% Strip debug info:
{ok, {Module, Stripped}} = beam_lib:strip("foo.beam"),

% Get module info:
Info = beam_lib:info("foo.beam"),
% Returns: [{file,F},{module,M},{chunks,[{Id,Pos,Size},...]}]
```

### 4.4 BEAM instruction set (key opcodes)

## 5. Kernel Erlang (v3_kernel)

Kernel Erlang is an internal IR that exists between Core Erlang and BEAM assembly. It is **not exposed as a public API** and is not documented externally. Understanding it is useful for knowing what the Core-to-BEAM translation does.

Key differences from Core Erlang:

| Core Erlang | Kernel Erlang |
|------------|---------------|
| Nested patterns in `case` | Flat, non-nested match operations |
| `let`/`letrec` bindings | Explicit block structure with named function closures |
| Unified `c_apply`/`c_call` | Split: `#k_call{}`, `#k_enter{}` (tail), `#k_bif{}` |
| `c_try` with 3-var handler | `#k_try{}`, `#k_catch{}`, `#k_try_enter{}` |
| `c_receive` | `#k_receive{}` with `#k_receive_accept{}`, `#k_receive_next{}` |
| Multi-value `c_values` | `#k_values{}` |
| Guards as expressions | Guards compiled to boolean-returning code sequences |

Kernel Erlang performs the critical **pattern matching compilation** step: it takes nested `c_case` patterns and converts them to a decision tree of type-tests and equality checks, eliminating the need for backtracking.

**For KorE**: you never need to generate Kernel Erlang directly. Generate Core Erlang and let `v3_kernel` do the compilation.

## 6. How Elixir Compiles

### 6.1 Elixir's pipeline

```
source.ex
  │
  ▼
:elixir_tokenizer (Elixir's own lexer)
  │  - handles UTF-8, sigils, heredocs, interpolation markers
  ▼
:elixir_parser (Elixir's own parser — yecc grammar)
  │  - produces Elixir quoted form (AST)
  ▼
Elixir Macro Expansion
  │  - expands all macros, including:
  │    - special forms (quote, unquote, require, import, alias, use)
  │    - user macros via Module.__before_compile__ / __using__
  │    - built-in macros (if, unless, cond, case, for, with)
  │  - iteratively expands until no more macros remain
  ▼
:elixir_expand (normalize expanded AST)
  │
  ▼
:elixir_erl (Elixir AST → Erlang Abstract Format)
  │  - converts the fully-expanded Elixir AST to EAF terms
  │  - handles Elixir-specific constructs: protocols, structs, etc.
  ▼
:compile (Erlang compiler, from_abstr or forms/2)
  │  - runs the full Erlang compiler pipeline from EAF
  ▼
.beam file
```

### 6.2 Elixir's quoted form (AST)

Elixir's AST uses three-element tuples for calls and operators:

```elixir
{function_name_or_op, metadata, arguments_or_context}
```

Where:
- `function_name_or_op`: atom for calls/ops, or another tuple for qualified calls
- `metadata`: keyword list, e.g. `[line: 10, column: 5]`
- `arguments_or_context`: list of args for calls, atom (module context) for variables

```elixir
# Inspect any expression's AST:
quote do: 1 + 2
#=> {:+, [], [1, 2]}

quote do: foo(x, y)
#=> {:foo, [], [{:x, [], Elixir}, {:y, [], Elixir}]}

quote do: Foo.bar(1)
#=> {{:., [], [{:__aliases__, [], [:Foo]}, :bar]}, [], [1]}

quote do: %{a: 1}
#=> {:%{}, [], [a: 1]}

quote do: {:ok, x}
#=> {:{}, [], [:ok, {:x, [], Elixir}]}

# Two-element tuples are literal (not wrapped in {:{}, ...}):
quote do: {1, 2}
#=> {1, 2}
```

### 6.3 Macro expansion

A macro is a function that runs at compile time and returns a quoted form:

```elixir
defmacro my_if(condition, do: then_branch, else: else_branch) do
  quote do
    case unquote(condition) do
      x when x in [false, nil] -> unquote(else_branch)
      _ -> unquote(then_branch)
    end
  end
end
```

`quote` captures code as AST. `unquote` splices values into a quoted form. The macro receives AST and returns AST — the expansion is substituted at the call site.

Macro expansion is recursive and iterative: the expander keeps expanding until no more macro calls remain.

`use Module` calls `Module.__using__/1` which is a macro, injecting code into the caller's module.

`__before_compile__/1` is invoked as a macro just before the module is compiled.

`__after_compile__/2` is invoked as a callback (not macro) after compilation, receiving the module's bytecode.

### 6.4 Elixir → Erlang Abstract Format

`:elixir_erl` converts the expanded Elixir AST to EAF. Key mappings:

- Elixir atoms (`:foo`) → `{atom, Anno, foo}`
- Elixir strings (binary) → remain as binary literals or `{bin, ...}` in EAF
- Elixir `def`/`defp` → `{function, Anno, Name, Arity, Clauses}`
- Elixir pattern matching → EAF clauses
- Elixir `case/cond/if` → `{'case', Anno, Expr, Clauses}`
- `Module.function(args)` → `{call, Anno, {remote, Anno, Mod, Fun}, Args}`

Elixir does NOT go through Core Erlang directly — it produces EAF and feeds it to `compile:forms/2`. The Erlang compiler then handles the EAF → Core Erlang → BEAM path.

### 6.5 Mix incremental compilation

Mix tracks compilation state in `_build/env/lib/app_name/.mix/`:
- `.compile.elixir` — manifest file tracking each source file's last-compile hash, dependencies, and exported modules
- Each `.ex` file is compiled to its own `.beam` files in `ebin/`

Dependency tracking is based on:
1. **Compile-time dependencies**: files that were `require`d, `import`ed, or whose macros were called
2. **Exports dependencies**: files that use a module's public API (tracked at type level with `@external_resource`)
3. **Runtime dependencies**: not tracked for recompilation purposes

When a file changes, Mix recompiles it and any files that have compile-time deps on it (transitively). This is why changing a module with heavily-used macros triggers a large recompile.

## 7. How Gleam Compiles

### 7.1 Gleam's pipeline

```
source.gleam
  │
  ▼
gleam_compiler::parse (Rust, nom-based lexer+parser)
  │  - produces Gleam AST (UntypedModule)
  ▼
gleam_compiler::type_ (type inference and checking)
  │  - Hindley-Milner with let-polymorphism + row-typed records
  │  - produces TypedModule (AST annotated with types)
  │  - resolves imports, checks exhaustiveness of patterns
  ▼
gleam_compiler::codegen (backend selection)
  │
  ├──▶ erlang target:
  │      gleam_compiler::erlang::Erlang::render()
  │      - TypedModule → Erlang source code string (.erl)
  │      - Written to _gleam_artefacts/ as .erl files
  │      - Then compiled by erlc / compile:file/2 to .beam
  │
  └──▶ javascript target:
         gleam_compiler::javascript::JavaScript::render()
         - TypedModule → JavaScript source code string (.mjs)
```

Gleam compiles to **Erlang source code**, not directly to EAF or Core Erlang. The generated `.erl` files are then compiled by the normal Erlang compiler.

### 7.2 Key Gleam → Erlang mappings

```gleam
// Gleam:
pub fn add(x: Int, y: Int) -> Int { x + y }
```
```erlang
% Generated Erlang:
-module(module_name).
-export([add/2]).
add(X, Y) -> erlang:'+'(X, Y).
```

```gleam
// Gleam pattern matching:
case value {
  Ok(x) -> x
  Error(_) -> 0
}
```
```erlang
case Value of
  {ok, X} -> X;
  {error, _} -> 0
end
```

Gleam's `Result(a, b)` maps to `{ok, a} | {error, b}` tuples. Gleam's `Option(a)` maps to `{some, a} | none`.

### 7.3 Gleam's module system and compilation units

Each Gleam module is one `.gleam` file → one `.erl` file → one `.beam` file. The Gleam compiler tracks transitive dependencies between modules and recompiles in topological order.

Gleam uses a content-addressed cache (`~/.cache/gleam/`). Build artifacts are keyed by the hash of the module and its dependencies.

### 7.4 Dual target (Erlang + JavaScript)

The typed AST is the single shared IR. After type checking, the codegen forks based on target. Both backends receive the same `TypedModule`. The Erlang backend generates idiomatic Erlang; the JS backend generates ES modules. Type erasure happens in codegen.

## 8. GHC's Pipeline (for architectural reference)

### 8.1 GHC pipeline stages

```
source.hs
  │
  ▼
GHC Parser → Haskell AST (HsSyn/GhcPs)
  │
  ▼
Renamer → HsSyn/GhcRn (names resolved, scopes bound)
  │
  ▼
Type checker → HsSyn/GhcTc (types inferred/checked)
  │
  ▼
Desugaring → Core (System F-omega with coercions)
  │  - pattern matching compiled
  - syntactic sugar eliminated
  - class methods desugared to dictionary passing
  ▼
Core simplifier (many passes):
  │  - inlining, case-of-case, worker/wrapper, strictness analysis,
  │    demand analysis, join points, let-floating, common sub-expression
  ▼
Core → STG (Spineless Tagless G-machine)
  │  - explicit closures, thunks, update frames
  - evaluation order made explicit (lazy)
  ▼
STG → Cmm (C--) or LLVM IR
  │
  ▼
Native code gen / LLVM → object code
```

### 8.2 GHC Core (System F-omega)

GHC Core is a typed IR. Every binder and expression carries a type. Key constructs:

```haskell
-- Var: variable with type
x :: Int

-- Lit: literal
42# :: Int#  -- unboxed

-- App: function application
f x :: b    -- (where f :: a -> b, x :: a)

-- Lam: lambda abstraction
\(x :: Int) -> x + 1 :: Int -> Int

-- Let: non-recursive let
let x :: Int = 42 in f x

-- Let (recursive):
letrec f :: Int -> Int = \n -> if n == 0 then 1 else n * f (n-1)
in f 10

-- Case: pattern matching + forcing
case e :: T of { DEFAULT -> e1; C1 a b -> e2; ... }
-- Note: case also forces evaluation (unlike Haskell surface which is lazy)

-- Type application and abstraction:
/\a -> \(x :: a) -> x    -- identity :: forall a. a -> a
id @Int 42

-- Coercions (type equality evidence for newtype, GADT, etc.)
```

### 8.3 Simplifier passes

The Core simplifier runs multiple times. Each "simplification phase" involves:
1. **Inlining**: small functions inlined at call sites; `INLINE` pragmas force inlining
2. **Beta reduction**: `(\x -> e) v` → `e[v/x]`
3. **Case-of-case**: `case (case e of ...) of ...` → merged case
4. **Case-of-known-constructor**: `case {x, y} of (a, b) -> ...` → direct substitution
5. **Eta expansion/reduction**
6. **Common sub-expression elimination**
7. **Dead code elimination**

### 8.4 Relevance for KorE

KorE will need analogous normalization passes at the Core Erlang level:
- **Constant folding**: `c_call(erlang, '+', [c_int(1), c_int(2)])` → `c_int(3)`
- **Case-of-known-constructor**: `case {a, b} of {X, Y} -> ...` → direct let-bindings
- **Dead clause elimination**: clauses whose patterns can never match the discriminant's type
- **Inlining**: small functions that are called once (or annotated inline)
- **Let-floating**: moving bindings to widen or narrow their scope for optimization
- **Join points**: identify recursive calls that could become loops (OTP's `sys_core_fold` does some of this)

## 9. Kotlin Compiler Architecture (for KorE frontend reference)

### 9.1 K2 compiler pipeline (Kotlin 2.0+)

```
source.kt
  │
  ▼
Kotlin Lexer (tokenizer)
  │
  ▼
Kotlin Parser → PSI (Program Structure Interface) tree
  │  - PSI is an IntelliJ-specific mutable AST used for IDE tooling
  │  - One PSI tree per file
  ▼
FIR (Frontend Intermediate Representation)
  │  - New in K2 (replaced the old FE10/descriptor-based frontend)
  │  - Designed for parallel, incremental analysis
  │  - Phases:
  │    1. Raw FIR generation from PSI
  │    2. FIR resolution (types, names, overload resolution)
  │    3. Checkers run on resolved FIR
  │  - FIR is a tree where every node has a resolved type
  ▼
IR (Backend Intermediate Representation)
  │  - FIR → IR lowering
  │  - IR is shared across all backends (JVM, JS, Native, WASM)
  │  - Typed, SSA-like, contains explicit null checks, type casts
  │  - Tree structure: IrFile → IrClass → IrFunction → IrBody → IrExpression
  ▼
Backend-specific lowering:
  ├──▶ JVM backend: IR → JVM bytecode (ASM library)
  ├──▶ JS backend: IR → JavaScript AST → JS source
  ├──▶ Native backend: IR → LLVM IR → native object code
  └──▶ WASM backend: IR → WASM binary
```

### 9.2 FIR (Frontend IR) key properties

- **Persistent** (immutable-like, designed for incremental reuse)
- **Phase-separated**: each phase can be run and cached independently
- **Lazy resolution**: declarations are resolved on demand, enabling fast project-wide analysis
- Replaces the old "binding context + descriptor" model which was inherently sequential
- Enables the K2 speed improvements (~2-4x faster than K1 for large projects)

FIR node types mirror Kotlin semantics closely: `FirFunction`, `FirProperty`, `FirClass`, `FirExpression`, `FirWhenExpression` (Kotlin's `when`), etc.

### 9.3 IR (Backend IR) key properties

IR is the "universal backend language". All optimizations and transformations targeting multiple backends happen here.

```
IrElement
├── IrDeclaration
│   ├── IrClass (class/object/interface)
│   ├── IrFunction (fun/constructor)
│   ├── IrProperty (val/var)
│   └── IrVariable (local val/var)
├── IrExpression
│   ├── IrCall (function call)
│   ├── IrWhen (when expression)
│   ├── IrReturn
│   ├── IrGetValue / IrSetValue
│   ├── IrConst (literal)
│   ├── IrBlock (sequence)
│   ├── IrTry
│   └── ...
└── IrBody
    ├── IrBlockBody (list of statements)
    └── IrExpressionBody (single expression)
```

IR lowering passes (run before backend codegen):
- `InlineClassLowering` — value classes inlining
- `TailrecLowering` — `tailrec` modifier → loop
- `SuspendLambdaLowering` — coroutines/suspend functions
- `PropertyReferenceLowering` — property references to KProperty objects
- `EnumClassLowering` — enum desugaring
- `DefaultArgumentStubGenerator` — default parameter implementations

### 9.4 Lessons for KorE design

KorE has Kotlin syntax but targets BEAM. The natural architecture is:

```
KorE source
  │
  ▼
KorE Frontend (KorE-specific)
  │  - Lexer/Parser (based on Kotlin grammar, adapted)
  │  - KorE AST (untyped)
  │  - Type inference (Hindley-Milner or Kotlin-style bidirectional)
  │  - Typed KorE AST
  ▼
KorE IR (KorE-specific, analogous to Kotlin IR)
  │  - Language-level IR: closures, pattern matching, data classes, etc.
  │  - Lowering passes:
  │    - data class desugaring → tuple representations
  │    - when expressions → Core Erlang case
  │    - tailrec functions → explicit tail calls
  │    - inline functions
  ▼
Core Erlang generation (target: BEAM)
  │  - KorE IR → cerl:c_module()
  │  - Source location preservation
  ▼
Erlang compiler backend
  │  - compile:forms(CoreModule, [from_core, ...])
  │    or directly: v3_kernel + beam_ssa_codegen
  ▼
.beam file
```

## 10. Parse Transforms vs. Compiler Plugins

### 10.1 Erlang parse transforms

```erlang
% Required exports:
-export([parse_transform/2]).
% Optional:
-export([parse_transform_info/0]).

parse_transform_info() ->
    #{error_location => column}.   % or 'line'

parse_transform(Forms, Options) ->
    % Walk + transform Forms (EAF list)
    % Use erl_syntax / erl_syntax_lib for easier tree manipulation
    lists:map(fun transform_form/1, Forms).

transform_form({function, Anno, foo, 1, Clauses}) ->
    % Transform specific function
    {function, Anno, foo, 1, transform_clauses(Clauses)};
transform_form(Other) ->
    Other.
```

**erl_syntax** provides a higher-level API over raw EAF tuples:
```erlang
% erl_syntax works with both raw tuples and erl_syntax nodes
Tree = erl_syntax:function(
    erl_syntax:atom(foo),
    [erl_syntax:clause(
        [erl_syntax:variable('X')],
        none,
        [erl_syntax:application(erl_syntax:atom(bar), [erl_syntax:variable('X')])]
    )]
),
Form = erl_syntax:revert(Tree),  % convert back to raw EAF tuple
```

**erl_syntax_lib** provides tree walkers:
```erlang
% Walk entire tree, transform matching nodes:
NewTree = erl_syntax_lib:map(
    fun(Node) ->
        case erl_syntax:type(Node) of
            atom ->
                case erl_syntax:atom_value(Node) of
                    old_name -> erl_syntax:atom(new_name);
                    _ -> Node
                end;
            _ -> Node
        end
    end,
    Tree
).
```

### 10.2 Core transforms

Less common than parse transforms. Operate on Core Erlang:
```erlang
% Specified as: {core_transform, Module} compile option
% Module must export:
core_transform(CoreModule, Options) ->
    % CoreModule :: cerl:c_module()
    % transform and return cerl:c_module()
    CoreModule.
```

### 10.3 What a KorE plugin system should look like

KorE has different needs than Erlang's parse_transform:

1. **KorE AST plugins** — run on typed KorE AST, before lowering to Core Erlang. Most useful for deriving instances, code generation macros.

2. **Core Erlang plugins** — run on the `cerl:c_module()` after KorE lowering, before the BEAM backend. Useful for instrumentation, custom optimizations.

3. **Annotation-driven** (like Kotlin compiler plugins) — plugins declare which annotations they handle and are invoked when those annotations appear on declarations.

Recommended interface:
```kotlin
// KorE plugin interface (sketch):
interface KoreCompilerPlugin {
    // Called on typed AST, returns transformed AST
    fun transformTypedAst(module: KoreModule, ctx: CompilationContext): KoreModule
    
    // Called on Core Erlang, returns transformed Core Erlang
    fun transformCoreErlang(module: CerlModule, ctx: CompilationContext): CerlModule
    
    // Annotations this plugin handles
    val handledAnnotations: List<FqName>
}
```

## 11. Incremental Compilation Requirements

### 11.1 Erlang's model

`erlc` has no built-in dependency tracking. It compiles one file at a time. Build tools (rebar3, mix, erlang.mk) layer dependency tracking on top.

rebar3's incremental compilation:
- Stores compile hashes in `_build/default/lib/app/.rebar3/`
- Tracks `{module, [{mtime, T}, {hash, H}]}` for each file
- Recompiles if mtime changed, then verifies hash
- Does NOT track semantic dependencies (changing a header rerequires knowing which files include it)

### 11.2 Elixir/Mix dependency tracking

Mix tracks three types of dependencies stored in `.mix/compile.elixir`:

```
each_file -> %{
  source_path => %{
    compile_references: [modules called at compile time via macros/require],
    struct_references:  [modules whose structs are used],
    runtime_references: [modules called at runtime],
    exports: [module_name],
    timestamp: integer
  }
}
```

**Recompilation triggers:**
1. File modified (mtime/hash change)
2. A module in `compile_references` was recompiled
3. A module providing macros changed

**For KorE**, Mix-style tracking is the right model:
- Separate compile-time deps (macros/inlining) from runtime deps
- Only force recompile when compile-time deps change
- Store a content hash, not just mtime

### 11.3 Gleam's model

Gleam uses a content-addressed build cache. Module identity is the hash of:
- Source content
- All transitive imported module interfaces (type signatures only, not implementations)

If only an implementation changes but the public interface doesn't, dependents don't recompile. This is the key insight: **track interface hashes separately from implementation hashes**.

### 11.4 KorE's incremental build design

```
For each KorE module M:
  - Store: source_hash, interface_hash, compile_deps_hash
  - interface_hash = hash of all exported function signatures and types
  - compile_deps_hash = hash of all interfaces of modules M depends on at compile time

Recompile M if:
  - source_hash changed (M itself modified)
  - compile_deps_hash changed (a compile-time dep's interface changed)

Recompile dependents of M if:
  - M's interface_hash changed

Skip recompile of dependents if:
  - M's source changed but interface_hash is unchanged
    (implementation-only change: safe to skip dependents)
```

This is the Gleam model extended with compile-time dep tracking from Mix.

For correctness, KorE needs to track:
1. **Import declarations**: which modules are imported
2. **Inline annotations**: functions marked `inline` create compile-time deps
3. **Macro-equivalent constructs**: anything evaluated at compile time
4. **Type-level deps**: if using a type from another module in a function signature, that module's interface is a compile-time dep

## 12. KorE Compiler Recommendations Summary

### Entry point into the BEAM toolchain

**Use Erlang Abstract Format** (`compile:forms/2`). Per the OTP documentation:
> Our recommendation is to use either the abstract format or Erlang source code.

Core Erlang is also viable but primops can change between OTP major versions. EAF is more stable and maps cleanly from typed AST.

### Core Erlang if needed

If you generate Core Erlang directly (for more control over optimization), use `compile:forms(CoreModule, [from_core, binary, debug_info, {outdir, Dir}])`. The `cerl` module is your construction API. Always run `core_lint` before passing to the backend.

### Source location

Carry KorE source positions through the entire lowering pipeline. Use `erl_anno:new({Line, Column})` in EAF, or `cerl:set_ann(Node, [{file, "..."}, {location, {L, C}}])` in Core Erlang. This is what makes BEAM stack traces and error messages point to KorE source, not generated Erlang.

### Pattern matching

Generate nested patterns in Core Erlang `c_case` nodes. Don't flatten them manually — `v3_kernel` handles that. For EAF, generate Erlang-style multi-clause patterns and let the compiler handle it.

### Tail calls

No special annotation needed. Ensure the call is the final expression in the function body (or case branch, let body). The BEAM backend detects and generates `call_last`/`call_ext_last` automatically.

### Multi-value returns

Erlang/Core Erlang doesn't have native multi-value returns like some languages. Use tuples `{ok, Value}` / `{error, Reason}` for the BEAM idiom. Core Erlang's `c_values` is for internal multi-binding in `let`, not for returning from functions.

### Closures

Generate `c_fun` nodes. The `letrec` form is used for named recursive closures. Free variables in `c_fun` bodies are captured automatically by the BEAM codegen (`make_fun3` instruction).

### Module initialization

KorE module-level `val` declarations (top-level constants) should be compiled to a function (convention: `'-'(init, 0)` or stored as literals in the LitT chunk). Large immutable data structures should use `cerl:abstract(Term)` to emit them as literals.

### Atoms vs strings

BEAM atoms are limited to 255 UTF-8 bytes and are global (interned in the atom table). Use atoms for: module names, function names, known symbolic constants, `true/false/nil/ok/error`. Use binaries for: user strings, dynamic values, data that shouldn't pollute the atom table.

### The `no_lint` option

When generating EAF, pass `no_lint` to skip `erl_lint`. Only do this if you've already done semantic checking in the KorE frontend. Without `no_lint`, the Erlang linter will run and will produce confusing error messages about "your" generated code.

```erlang
compile:forms(Forms, [
    no_lint,
    binary,
    debug_info,
    {outdir, OutputDir},
    {compile_info, [{kore_version, "0.1.0"}, {kore_source, SourceFile}]}
])
```
