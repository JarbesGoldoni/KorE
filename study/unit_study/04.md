# Type Systems: Exhaustive Technical Reference

## 1. Erlang

### Dialyzer: Success Typing

Dialyzer uses **success typing**, not Hindley-Milner inference and not traditional type checking. The core principle:

> A type error is only reported when Dialyzer can *prove* that a call **cannot** succeed under any valid input. If a call *might* succeed, no error is reported.

This is a deliberate conservative choice: **no false positives, but potentially many false negatives**.

The algorithm (PLT-based, Persistent Lookup Table):
1. Build a call graph of the entire codebase
2. Infer the **success type** of each function — the most permissive type for which the function can return without crashing
3. Propagate constraints bottom-up through the call graph
4. Report only when a call site's argument types are *disjoint* from the callee's success type

Example: if `f(0) -> ok; f(1) -> ok`, the success type is `f(0 | 1) -> ok`, not `f(integer()) -> ok`. Dialyzer infers the minimal domain.

**What `-spec` does and doesn't do:**
```erlang
-spec add(integer(), integer()) -> integer().
add(X, Y) -> X + Y.
```
- `-spec` provides a **user-declared contract**
- Dialyzer checks: is the declared spec *consistent* with the inferred success type?
- If you call `add(atom, 1)`, Dialyzer will warn — but only if it can prove `atom` is never a valid first arg
- **Does not**: enforce at runtime, generate runtime guards, narrow types inside the function body
- **Does**: serve as documentation, help Dialyzer when cross-module analysis is limited, catch spec/implementation mismatches

**`-type` and `-opaque`:**
```erlang
-type coord() :: {float(), float()}.
-opaque handle() :: {pid(), reference()}.
```
- `-type` is a type alias — transparent everywhere, fully expanded by Dialyzer
- `-opaque` creates an **abstract type**: only the defining module can see the internal structure. From outside, `handle()` is opaque — Dialyzer will warn if external code pattern-matches on it
- Opaque types are enforced **only by Dialyzer**, not by the runtime

**Union types in Dialyzer:**
```erlang
-type result() :: {ok, Value :: term()} | {error, Reason :: term()}.
```
Dialyzer tracks union types as sets of type constraints. It can:
- Narrow after pattern match branches (within a single function, limited inter-procedurally)
- Track which constructor was used through guards and pattern matches
- Warn on unreachable clauses

Limitations on union narrowing:
- Inter-procedural narrowing is limited — once a union crosses a function boundary, the receiving function sees the full union
- No exhaustiveness checking on unions (unlike Haskell or Gleam)

**Gradual typing:** Dialyzer is not gradual in the academic sense (no `?` types, no consistency relation). It's more accurately *optional static analysis with sound inference*. `term()` acts as the top type (like `any`), and functions accepting `term()` are never warned about.

**The Set-Theoretic / New Erlang Type System (OTP Research):**

This is active research at Ericsson/OTP team, collaborating with the Elixir team (José Valim, Giuseppe Castagna's set-theoretic type theory):

Core ideas:
- **Set-theoretic types**: every type is a set of values. Union is `∪`, intersection is `∩`, negation is `¬`
- `integer() ∩ ¬0` is "non-zero integers"
- Function types become **arrow types with intersection**: `(integer() -> integer()) ∩ (atom() -> atom())` means the function handles both
- **Gradual typing**: introduces `?` (dynamic type) with a consistency relation rather than equality
- Goal: replace Dialyzer's success typing with a proper bidirectional type system that still doesn't require full annotation

Papers driving this: Giuseppe Castagna's work on semantic subtyping and set-theoretic types. The Elixir type system is essentially this system implemented first for Elixir, with the intent to backport concepts to Erlang.

Timeline: Elixir is ahead. Erlang OTP proper is still in research phase.

**Limits of Dialyzer (what it cannot catch):**
- Runtime errors from `throw`/`exit`/`error` not reflected in specs
- Message passing: no typing of what messages a `receive` block expects
- Process state: no typing of `gen_server` state across callbacks
- Dynamic dispatch via `apply/3` — loses all type information
- ETS table contents — untyped
- Exhaustiveness: won't warn that a case/receive is non-exhaustive
- Spec violations that are "consistent" with success types won't warn even if semantically wrong
- Anything going through `term()` loses precision
- No effect typing (no tracking of side effects)

## 2. Elixir

### Current State: Typespecs

```elixir
@type result(a) :: {:ok, a} | {:error, String.t()}
@spec fetch(String.t()) :: result(User.t())
def fetch(id), do: ...
```

- `@type` — type alias, transparent
- `@opaque` — opaque type, same as Erlang's `-opaque`
- `@spec` — spec annotation fed to Dialyzer (Elixir compiles to Erlang and Dialyzer runs on BEAM bytecode)
- `@typep` — module-private type

Currently: all runtime-erased, Dialyzer-consumed only, same limitations as Erlang.

### The New Type System (Elixir 1.17+/1.18+)

**This is the significant development.** José Valim announced and has been shipping this incrementally.

Theoretical foundation: **set-theoretic types** (Castagna et al.), same foundation as the OTP research.

Key properties:

**1. Gradual typing with dynamic():**
```elixir
# dynamic() is the gradual unknown, not term()
# term() = all Elixir terms (top type)
# dynamic() = "I don't know yet, check at runtime"
```
The distinction matters: `term()` means "could be anything, that's fine". `dynamic()` means "this is untyped code, propagate uncertainty".

**2. Pattern matching is first-class in the type system:**
```elixir
def process({:ok, value}), do: value
def process({:error, reason}), do: raise reason
```
The type system understands that after matching `{:ok, value}`, `value` has whatever type the second element of that tuple is. Pattern match branches **narrow the type**.

**3. Intersection types for function overloads:**
```elixir
# A function that handles multiple patterns has an intersection type
# process :: ({:ok, a} -> a) ∩ ({:error, String.t()} -> no_return())
```

**4. Exhaustiveness checking:**
- With set-theoretic types, the compiler can determine if a `case`/function clause is exhaustive over a union type
- This is a *new capability* — current Dialyzer cannot do this

**5. Incremental rollout strategy:**
- **Phase 1** (1.17): type inference for expressions, warnings for obvious type errors, no annotations required
- **Phase 2**: typed function signatures begin to participate
- **Phase 3**: full gradual system with `dynamic()` propagation

**How it handles PIDs and message passing:**

Honest answer: **this is the unsolved hard problem**. The new type system does not (yet) type message passing. PIDs are `pid()` — an opaque runtime value. The type system has no way to statically know what messages a given PID's process will accept.

The reason: in OTP systems, message routing is dynamic. `GenServer.call(pid, msg)` — `pid` is looked up at runtime, the message type depends on which process that PID refers to.

Potential future approaches being considered:
- Session types (linear/behavioral types) — theoretically sound but enormous complexity
- Effect typing on receive blocks
- Typed process registries (a `Registry` that knows the message type of registered names)

**None of these are in the shipped type system.** Typed message passing on BEAM remains an open research problem.

**Pattern matching and types:**

This is where the set-theoretic approach shines:
```elixir
def f(x :: integer() | atom()) do
  case x do
    n when is_integer(n) ->
      # type of n here: integer()
      n + 1
    a ->
      # type of a here: atom()
      to_string(a)
  end
end
```

Guards narrow types. The type of `x` after `is_integer(n)` is `integer() ∩ (integer() | atom()) = integer()`. This is set-theoretic intersection in action.

The type system models guards as **type refinement functions** — `is_integer/1` has type `(term() -> boolean())` but also carries the refinement `(x -> x :: integer())` for the truthy branch.

## 3. Gleam

### Full Static Type System on BEAM

Gleam is **fully statically typed, no escape hatches in pure Gleam code**. No `dynamic()`, no `term()`, no gradual typing. This is the fundamental design choice that distinguishes it from Elixir/Erlang.

Type system: **Hindley-Milner with let-polymorphism**, similar to OCaml/Haskell/Elm.

```gleam
fn add(x: Int, y: Int) -> Int {
  x + y
}

// Type inference — no annotations needed
fn double(x) {
  x * 2  // inferred: fn(Int) -> Int
}
```

**Algebraic Data Types:**
```gleam
pub type Result(value, error) {
  Ok(value)
  Error(error)
}

pub type Shape {
  Circle(radius: Float)
  Rectangle(width: Float, height: Float)
}
```

- Sum types (tagged unions) with constructor functions
- Pattern matching is exhaustive — compiler errors if not all cases handled
- No null, no nil (use `Option(a)` which is `Some(a) | None`)

**Type Inference (Hindley-Milner):**
- Full inference, annotations optional but recommended for public APIs
- Unification-based: type variables resolved through constraint propagation
- Rank-1 polymorphism (no higher-rank types, intentional simplicity choice)
- No type classes (uses module-level functions and explicit passing instead)

### Erlang Interop: The `external` Type Approach

This is where Gleam necessarily punts on static guarantees:

```gleam
// Declaring an external function from Erlang
@external(erlang, "erlang", "now")
pub fn now() -> #(Int, Int, Int)

// External types — opaque wrappers around Erlang values
pub type Pid

@external(erlang, "erlang", "self")
pub fn self() -> Pid

@external(erlang, "erlang", "send")
pub fn send(to: Pid, message: anything) -> anything
```

Key points:
- `external` types have **no constructors in Gleam** — you can hold them but not construct or destructure them in Gleam code
- Return types of external functions are **trusted, not verified** — it's a lie the programmer tells the compiler
- `anything` (the type variable used above) is a genuine type variable, not a top type — but in practice, `send` takes `anything` meaning it's polymorphic and unchecked

The stdlib wraps Erlang/OTP with typed interfaces. `gleam/erlang/process` wraps PIDs with typed subjects.

### Message Passing: Typed Subjects (Not Raw PIDs)

This is Gleam's key innovation for typing concurrent code:

```gleam
import gleam/erlang/process.{type Subject}

// Subject(msg) is a typed channel — a PID that only accepts msg
pub type Subject(message)

// Sending is typed
pub fn send(to: Subject(message), msg: message) -> Nil

// Receiving is typed  
pub fn receive(from: Subject(message), within timeout: Int) -> Result(message, Nil)

// Selecting from multiple subjects
pub fn new_selector() -> Selector(message)
pub fn add_message_handler(
  selector: Selector(combined),
  subject: Subject(msg),
  transform: fn(msg) -> combined,
) -> Selector(combined)
```

**How this works:**
- `Subject(MyMessage)` is an opaque wrapper around a PID + a reference
- The type parameter `MyMessage` is *phantom* — erased at runtime, exists only for type checking
- `send(subject, msg)` — compiler verifies `msg :: MyMessage`
- This gives you typed channels at the cost of: you cannot send arbitrary Erlang messages to a Gleam process, you cannot use raw PIDs from Erlang ecosystem directly

**The fundamental limitation:** This works within Gleam code. When interfacing with OTP (GenServer, Supervisor, etc.), you fall off the typed cliff. Gleam has its own actor library (`gleam_otp`) that reimplements OTP patterns with typed subjects, but it's not full OTP.

### Tradeoffs Gleam Made

**No processes in the core type system:**
- Processes exist via `gleam/erlang/process` stdlib module
- The language spec has no process primitive — it's a library concern
- This means: no built-in `spawn`, no built-in `receive` syntax, no process dictionary

**No OTP in the type system:**
- Gleam's `gleam_otp` provides typed actors, supervisors — but it's a library
- GenServer's callback protocol (init/handle_call/handle_cast/handle_info) is untyped in Erlang; Gleam rewrote this with typed subjects
- The cost: Gleam processes cannot be supervised by raw Erlang supervisors without wrapping

**No type classes / traits:**
- Deliberately chosen for simplicity
- Consequence: no `Eq`, no `Ord`, no `Show` typeclasses — functions for these are explicit
- No operator overloading

**No higher-kinded types:**
- Cannot abstract over `List`, `Option`, `Result` generically (no `Functor`, `Monad`)
- Consequence: `map` on List and `map` on Option are different functions, no unification

**What Gleam gains from these tradeoffs:**
- Simple, predictable type inference (HM terminates, is decidable, no annotation burden)
- Fast compilation
- Easy to read error messages
- Accessible to programmers without type theory background

## 4. TypeScript

### Structural Typing vs Nominal Typing

TypeScript is **structurally typed** (duck typing at the type level):

```typescript
interface Point { x: number; y: number }
interface Named { x: number; y: number; name: string }

function plot(p: Point): void { ... }

const n: Named = { x: 1, y: 2, name: "origin" }
plot(n)  // OK — Named is structurally a subtype of Point (has all required fields)
```

Structural subtyping rules:
- Object types: `A <: B` if A has all fields of B (with compatible types)
- Function types: **contravariant** in parameters, **covariant** in return type
- `(Animal -> void) <: (Dog -> void)` — a function accepting Animal can be used where Dog-accepting is expected

**Why this matters:** No explicit `implements` required. Consequences:
- Accidental structural compatibility (two unrelated types happen to have same shape)
- Can't distinguish `UserId: string` from `ProductId: string` without workarounds

**Simulating nominal typing:**
```typescript
// Brand pattern
type UserId = string & { readonly __brand: 'UserId' }
type ProductId = string & { readonly __brand: 'ProductId' }

function makeUserId(s: string): UserId { return s as UserId }
// Now UserId and ProductId are incompatible even though both are string
```
This is a hack — the `__brand` field doesn't exist at runtime.

### Type Erasure at Runtime

TypeScript types are **completely erased** at compilation. The emitted JavaScript has zero type information.

Consequences:
- No `instanceof` checks on interface types (interfaces don't exist at runtime)
- `typeof x === 'string'` works (JS runtime check)
- `x instanceof MyClass` works (classes exist at runtime as constructor functions)
- No runtime reflection of type parameters — `Array<string>` and `Array<number>` are identical at runtime

```typescript
function process<T>(items: T[]): void {
  // Cannot do: items[0] instanceof T  — T is erased
  // Cannot do: typeof T              — T is erased
}
```

**Implications for type safety:** Any runtime value coming in from external sources (`JSON.parse`, network, `any`) is unchecked. You can lie to the compiler with `as`:
```typescript
const x = JSON.parse(data) as UserRecord  // no runtime check, just assertion
```

### Gradual Typing: `unknown` vs `any`

**`any`:** Opt-out of type checking entirely. Assignable to anything, accepts anything. Infectious — operations on `any` produce `any`.

```typescript
const x: any = "hello"
x.nonExistent.deeply.nested  // no error — compiler trusts you
x * 2                         // no error
```

**`unknown`:** The type-safe top type. Assignable from anything, but you must narrow before use.

```typescript
const x: unknown = getValue()
x.toUpperCase()    // ERROR — must narrow first

if (typeof x === 'string') {
  x.toUpperCase()  // OK — narrowed to string
}
```

**`never`:** Bottom type — no value has this type. Useful for exhaustiveness:
```typescript
function assertNever(x: never): never {
  throw new Error(`Unhandled case: ${x}`)
}
```

**Gradual typing mechanics:**
- TypeScript is not formally gradual (no consistency relation in the academic sense)
- `any` is the escape hatch — it's unsound (can cause runtime errors that the type checker doesn't catch)
- `unknown` is the sound version — forces you to prove type before use
- `strictNullChecks: true` turns on null/undefined tracking (opt-in, not default in older configs)

### Union Types and Discriminated Unions

**Union types:**
```typescript
type StringOrNumber = string | number

function format(x: string | number): string {
  if (typeof x === 'string') return x.toUpperCase()  // narrowed to string
  return x.toFixed(2)                                  // narrowed to number
}
```

**Discriminated unions (tagged unions):**
```typescript
type Shape =
  | { kind: 'circle'; radius: number }
  | { kind: 'rectangle'; width: number; height: number }
  | { kind: 'triangle'; base: number; height: number }

function area(shape: Shape): number {
  switch (shape.kind) {
    case 'circle':     return Math.PI * shape.radius ** 2
    case 'rectangle':  return shape.width * shape.height
    case 'triangle':   return 0.5 * shape.base * shape.height
    // If you add a new variant and miss a case, TypeScript warns (with noImplicitReturns)
  }
}
```

The discriminant (`kind`) must be a **literal type** (string literal, number literal, boolean). TypeScript narrows the union based on the discriminant check.

**Narrowing mechanics:**
- `typeof x === 'string'` — narrows to `string`
- `x instanceof Foo` — narrows to `Foo`
- `'kind' in x` — narrows to types containing `kind`
- Truthiness narrowing — `if (x)` removes `null | undefined | false | 0 | ''`
- Assignment narrowing — after `x = "hello"`, `x` is narrowed to `string`
- Custom type guards:

```typescript
function isUser(x: unknown): x is User {
  return typeof x === 'object' && x !== null && 'id' in x
}
// After isUser(x) is true, x is narrowed to User in that branch
```

**Control flow analysis:** TypeScript tracks types through branches, loops, assignments. The narrowed type at any point is the *intersection* of possible types given the control flow path.

## 5. Kotlin

### Null Safety

Kotlin's type system has a **nullable/non-nullable distinction** baked in at the language level:

```kotlin
val name: String = "Alice"    // non-nullable — can never be null
val name: String? = null      // nullable — may be null

name.length      // OK — compiler knows non-null
name?.length     // Safe call — returns Int? (null if name is null)
name!!.length    // Non-null assertion — throws NPE if null at runtime
name ?: "default" // Elvis operator — provide default if null
```

**How this works in the type system:**
- `String` and `String?` are distinct types
- `String <: String?` (non-null is subtype of nullable)
- `null` has type `Nothing?` (bottom of the nullable hierarchy)
- Platform types from Java are `String!` — "I don't know, trust me" (gradual escape hatch for Java interop)

**Java interop and platform types:**
```kotlin
// Java: String getName() — could return null, no annotation
val name = javaObject.name  // type is String! — platform type
// Compiler does not warn, but NPE possible at runtime
// With @NotNull/@Nullable annotations on Java side, Kotlin respects them
```

### Smart Casts

Kotlin's control flow analysis narrows types automatically:

```kotlin
fun process(x: Any) {
  if (x is String) {
    x.uppercase()  // smart cast: x is String here, no explicit cast needed
  }
  
  // After null check:
  val name: String? = getName()
  if (name != null) {
    name.length  // smart cast: name is String here
  }
  
  // With when:
  when (x) {
    is String  -> x.length     // String
    is Int     -> x * 2        // Int
    is List<*> -> x.size       // List<*>
  }
}
```

**Smart cast conditions (when smart cast is NOT applied):**
- `var` that could be modified by another thread
- Properties with custom getters
- `open` or `abstract` properties (could be overridden)
- Delegated properties

For these cases, you must use explicit `as` casts or local `val` copies.

### Reified Generics

Normal JVM generics are **erased** at runtime — `List<String>` and `List<Int>` are identical at runtime. Kotlin adds `reified` for inline functions:

```kotlin
inline fun <reified T> isInstance(value: Any): Boolean {
  return value is T  // OK only because T is reified
}

inline fun <reified T> Gson.fromJson(json: String): T {
  return this.fromJson(json, T::class.java)  // T::class.java available!
}

// Usage:
val user: User = gson.fromJson(jsonString)  // T inferred as User
```

**How it works:** `inline` functions are **inlined at call sites**. At the call site, the actual type is known, so `T` is substituted with the real type before bytecode generation. The `is T` check becomes `is User` at the call site.

**Limitations:**
- Only works in `inline` functions
- Cannot return `reified T` from a non-inline function and have the type available
- Cannot use reified T in class-level generic parameters

### Sealed Classes for Exhaustive `when`

```kotlin
sealed class Result<out T> {
  data class Success<T>(val value: T) : Result<T>()
  data class Failure(val exception: Exception) : Result<Nothing>()
  object Loading : Result<Nothing>()
}

fun handle(result: Result<User>): String = when (result) {
  is Result.Success  -> "Got: ${result.value}"
  is Result.Failure  -> "Error: ${result.exception.message}"
  is Result.Loading  -> "Loading..."
  // Exhaustive — no else needed. Adding a new subclass is a compile error here.
}
```

**Sealed class rules:**
- All direct subclasses must be in the **same package and module** (Kotlin 1.5+: same package, previously same file)
- `when` on a sealed class is exhaustive — the compiler knows all subclasses
- `sealed interface` also works (Kotlin 1.5+)

Kotlin 1.7+ adds **sealed + data class** (data classes can now extend sealed classes directly).

### Variance: `in` / `out`

Kotlin uses **declaration-site variance** (unlike Java's use-site wildcards):

```kotlin
// out (covariant) — T only appears in output position
interface Producer<out T> {
  fun produce(): T  // OK — T is returned
  // fun consume(t: T) — ERROR: T in input position
}

// in (contravariant) — T only appears in input position  
interface Consumer<in T> {
  fun consume(t: T)  // OK — T is consumed
  // fun produce(): T — ERROR: T in output position
}

// Variance in action:
val stringProducer: Producer<String> = ...
val anyProducer: Producer<Any> = stringProducer  // OK! Producer<String> <: Producer<Any> (covariant)

val anyConsumer: Consumer<Any> = ...
val stringConsumer: Consumer<String> = anyConsumer  // OK! Consumer<Any> <: Consumer<String> (contravariant)
```

**Use-site variance** also available:
```kotlin
fun copy(from: Array<out T>, to: Array<in T>) { ... }
// out/in here are use-site variance annotations (like Java wildcards)
```

**Star projection:** `List<*>` — "I don't know the type parameter". Read-only, reads as `Any?`.

### Extension Functions and Types

```kotlin
fun String.isPalindrome(): Boolean = this == this.reversed()

"racecar".isPalindrome()  // true
```

**Type system view:**
- Extension functions are **statically resolved** — dispatch based on the declared type at compile time, not runtime type
- They are **not** methods in the class — compiled to static functions with the receiver as first parameter
- This means: no polymorphic dispatch, no overriding

```kotlin
open class Base
class Derived : Base()

fun Base.hello() = "Base"
fun Derived.hello() = "Derived"

val x: Base = Derived()
x.hello()  // "Base" — static dispatch on declared type Base
```

Extension functions can be defined on **nullable receivers**:
```kotlin
fun String?.orEmpty(): String = this ?: ""
null.orEmpty()  // "String" — no NPE
```

Extension functions on generic types with constraints:
```kotlin
fun <T : Comparable<T>> List<T>.max(): T? = ...
```

**Scope functions** (`let`, `run`, `with`, `apply`, `also`) are library functions using extension functions + lambdas with receivers — not special syntax.

## 6. Scala

### Path-Dependent Types

Scala has **dependent types** at the path level — a type can depend on a *value* (an object instance):

```scala
trait Container {
  type Item  // abstract type member
  def get(): Item
}

val c1: Container { type Item = Int } = new Container { type Item = Int; def get() = 42 }
val c2: Container { type Item = String } = new Container { type Item = String; def get() = "hi" }

// c1.Item and c2.Item are DIFFERENT types even though both are Container
def process(c: Container)(item: c.Item): Unit = ...  // item's type depends on which c
```

**Why this is powerful (and dangerous):**
- `c.Item` is a path-dependent type — it refers to the `Item` type *of the specific object `c`*
- `c1.Item =:= Int` but `c2.Item =:= String`
- This enables type-safe heterogeneous containers, type-safe state machines, etc.

The classic use: type-safe builder patterns where the type tracks what has been configured.

### Akka Typed: `Behavior[T]` and `ActorRef[T]`

Akka Typed (Akka 2.6+, Akka 2.7+ as default) adds type parameters to actors:

```scala
import akka.actor.typed._
import akka.actor.typed.scaladsl._

// Define message protocol
sealed trait Command
case class Greet(whom: String, replyTo: ActorRef[Greeted]) extends Command
case class Greeted(whom: String, from: ActorRef[Command]) extends Command

// Behavior[Command] — this actor only accepts Command messages
val greeter: Behavior[Command] = Behaviors.receive { (context, message) =>
  message match {
    case Greet(whom, replyTo) =>
      replyTo ! Greeted(whom, context.self)  // replyTo :: ActorRef[Greeted], can only send Greeted
      Behaviors.same
  }
}

// ActorRef[Command] — you can only send Command to this ref
val actorRef: ActorRef[Command] = system.systemActorOf(greeter, "greeter")
actorRef ! Greet("World", ...)  // OK
actorRef ! Greeted(...)         // COMPILE ERROR — Greeted is not Command
```

**How the types work:**
- `ActorRef[T]` has only `def !(msg: T): Unit` — the send operator is typed
- `Behavior[T]` describes an actor that processes `T` messages
- `context.self` returns `ActorRef[T]` — typed to the current actor's protocol
- `context.spawn(behavior, name)` returns `ActorRef[U]` for `behavior: Behavior[U]`

**Receptionist for service discovery (typed):**
```scala
val ServiceKey = ServiceKey[Command]("greeter")
// Registry maps ServiceKey[T] -> Set[ActorRef[T]] — type-safe lookup
```

### Untyped-to-Typed Migration

The hard problem: classic Akka was `ActorRef` (no type param). Migration strategies:

**`ActorRef.toTyped[T]`:** Unsafe cast — you claim the untyped actor accepts `T`.
```scala
val untyped: akka.actor.ActorRef = ...
val typed: ActorRef[Command] = untyped.toTyped[Command]  // runtime lie
```

**`Behaviors.receive` wrapping:** Typed actor that spawns classic child actors internally.

**Classic adapter:**
```scala
// Typed actor creates an adapter for classic messages
val adapter: ActorRef[Response] = context.messageAdapter {
  case r: Response => r  // convert classic Response to typed Response
}
classicActorRef.tell(Request(adapter), ActorRef.noSender)
```

**`ActorSystem[T]` vs `ActorSystem` (classic):**
- New typed system uses `ActorSystem[T]` where T is the guardian's message type
- Classic system uses `ActorSystem` — incompatible, migration requires wrapper layer

The migration is genuinely difficult when classic and typed actors need to communicate. Akka provides `akka.actor.typed.scaladsl.adapter._` import for interop helpers.

### Union Types in Scala 3

```scala
// A | B is a true union type (not a wrapper)
def describe(x: Int | String): String = x match
  case n: Int    => s"integer: $n"
  case s: String => s"string: $s"

// Union with pattern matching and exhaustiveness
type Id = Int | String | UUID

// Union in function signatures
def process(value: Int | Double | Float): Double = value match
  case i: Int    => i.toDouble
  case d: Double => d
  case f: Float  => f.toDouble
```

**Key differences from TypeScript unions:**
- Scala 3 unions are **commutative and associative**: `A | B =:= B | A`
- No discriminant required — type tests (pattern matching with `: TypeName`) do the narrowing
- Unions are **transparent** — `Int | Int =:= Int`
- The type checker uses **union elimination**: when you match all cases of `A | B`, the result type is the union of the branch result types

**Intersection types** (`A & B`):
```scala
trait Flyable { def fly(): Unit }
trait Swimmable { def swim(): Unit }

def traverse(creature: Flyable & Swimmable): Unit = {
  creature.fly()
  creature.swim()
}
```

### Opaque Types in Scala 3

```scala
opaque type UserId = Long
opaque type ProductId = Long

object UserId {
  def apply(n: Long): UserId = n  // constructor accessible here
  extension (id: UserId) def value: Long = id  // accessor
}

val id: UserId = UserId(42L)
val n: Long = id           // COMPILE ERROR — outside the companion, Long ≠ UserId
val n: Long = id.value     // OK via extension
val id2: ProductId = id    // COMPILE ERROR — UserId ≠ ProductId (even though both are Long)
```

**How opaque types work:**
- Inside the defining scope (companion object/enclosing object), the underlying type is visible
- Outside, the alias is hidden — `UserId` is a distinct type from `Long`
- Zero runtime overhead — `UserId` is literally `Long` at runtime, no boxing
- Unlike Haskell `newtype`, Scala opaque types are module-scoped (defined in an object/package object)

**Opaque types vs type aliases:**
```scala
type UserId = Long   // transparent alias — UserId =:= Long everywhere
opaque type UserId = Long  // opaque — UserId is distinct outside defining scope
```

## 7. Swift

### Protocol-Oriented Programming

Swift's primary abstraction mechanism is **protocols** (equivalent to Haskell typeclasses, Rust traits, but with some key differences):

```swift
protocol Drawable {
  func draw() -> String
  var area: Double { get }
}

struct Circle: Drawable {
  let radius: Double
  func draw() -> String { "Circle(r:\(radius))" }
  var area: Double { .pi * radius * radius }
}
```

**Protocol composition:**
```swift
typealias DrawableAndComparable = Drawable & Comparable
// or inline:
func process(_ x: Drawable & Hashable) { ... }
```

**Default implementations via protocol extensions:**
```swift
extension Drawable {
  func describe() -> String { "A shape with area \(area)" }
  // All Drawable conformers get this for free
}
```

**Retroactive conformance:**
```swift
extension Int: Drawable {  // Add Drawable to Int after the fact
  func draw() -> String { "Int(\(self))" }
  var area: Double { Double(self) }
}
```

**Where protocols differ from interfaces:**
- Protocols can have **associated types** (see below)
- Protocols can require **initializers**
- Protocols can have **default implementations** (unlike Java/C# interfaces historically, though those now support default methods too)
- Protocol conformances can be retroactive

### Associated Types

Associated types make protocols **type-constructor-like** (higher-kinded in practice, though not technically HKT):

```swift
protocol Container {
  associatedtype Item
  mutating func append(_ item: Item)
  var count: Int { get }
  subscript(i: Int) -> Item { get }
}

struct Stack<Element>: Container {
  typealias Item = Element  // fulfill associated type
  var items: [Element] = []
  mutating func append(_ item: Element) { items.append(item) }
  var count: Int { items.count }
  subscript(i: Int) -> Element { items[i] }
}
```

**Type constraints on associated types:**
```swift
protocol SortedContainer: Container where Item: Comparable {
  // Item must be Comparable
}

// Protocol with multiple associated types:
protocol Transformation {
  associatedtype Input
  associatedtype Output
  func transform(_ input: Input) -> Output
}
```

**The associated type problem (existentials):**

Before Swift 5.7, you could NOT use a protocol with associated types as a type directly:
```swift
// ERROR (pre-5.7): Protocol 'Container' can only be used as a generic constraint
func process(_ c: Container) { ... }

// You had to use generics:
func process<C: Container>(_ c: C) { ... }
```

Swift 5.7 introduced `any Protocol` (existentials) and `some Protocol` (opaque types) to resolve this.

### Opaque Types: `some Protocol`

```swift
// Concrete return type hidden — caller knows it's Drawable but not which concrete type
func makeShape() -> some Drawable {
  return Circle(radius: 5.0)
}

// Vs generic:
func makeShape<T: Drawable>() -> T { ... }  // caller chooses T
// With some: implementation chooses T, caller gets abstract type
```

**Rules for `some`:**
- The function must always return the **same concrete type** (even if the type is computed)
- The concrete type is fixed at compile time — not an existential (no vtable dispatch)
- Performance: no boxing, no dynamic dispatch — optimized like concrete type calls

**`any Protocol` (existentials, Swift 5.7+):**
```swift
func process(_ shapes: [any Drawable]) {  // heterogeneous array
  for shape in shapes {
    print(shape.draw())  // dynamic dispatch
  }
}
```

- `any Drawable` is an **existential** — boxes the value, dynamic dispatch, runtime cost
- `some Drawable` is an **opaque type** — no boxing, static dispatch, no runtime cost
- The `any` keyword was made explicit in 5.7 to make the cost visible

**`some` in protocol requirements (Swift 5.7+):**
```swift
protocol View {
  associatedtype Body: View
  var body: Body { get }
}

// SwiftUI uses this — each View's body is some View (opaque, chosen by implementation)
struct ContentView: View {
  var body: some View {  // opaque type
    Text("Hello")
  }
}
```

### Enums with Associated Values

Swift enums with associated values are **algebraic sum types** — the direct equivalent of Erlang atoms/tuples, Gleam custom types, Haskell data constructors:

```swift
enum Result<Value, Error: Swift.Error> {
  case success(Value)
  case failure(Error)
}

enum NetworkError: Error {
  case notFound
  case unauthorized
  case serverError(code: Int, message: String)
  case timeout(after: TimeInterval)
}

// Pattern matching — exhaustive
func handle(_ error: NetworkError) -> String {
  switch error {
  case .notFound:
    return "404"
  case .unauthorized:
    return "401"
  case .serverError(let code, let message):
    return "Server error \(code): \(message)"
  case .timeout(let duration):
    return "Timed out after \(duration)s"
  // Exhaustive — compiler errors if a case is missing
  }
}
```

**Enums as state machines:**
```swift
enum ConnectionState {
  case disconnected
  case connecting(attempt: Int)
  case connected(socket: Socket, since: Date)
  case failed(error: Error, attempts: Int)
}
```

**Recursive enums (indirect):**
```swift
indirect enum Tree<T> {
  case leaf
  case node(value: T, left: Tree<T>, right: Tree<T>)
}
// `indirect` needed to break the value-type recursion (enums are value types)
```

**Enum methods and computed properties:**
```swift
enum Direction: CaseIterable {
  case north, south, east, west
  
  var opposite: Direction {
    switch self {
    case .north: return .south
    case .south: return .north
    case .east:  return .west
    case .west:  return .east
    }
  }
}

Direction.allCases  // [.north, .south, .east, .west] — CaseIterable protocol
```

**Comparing to Erlang atoms:** Erlang's `{ok, Value}` / `{error, Reason}` tuples are untagged at the type level — Dialyzer uses structural matching. Swift's associated value enums are **tagged** — each case is a distinct constructor, and pattern matching is exhaustive and type-safe. This is the key structural difference: Swift enums are nominally tagged, Erlang tuples are structurally typed.

## Cross-Cutting Observations for Language Design

**The central tension** you're researching: static typing wants to verify programs before they run; functional/dynamic runtime semantics (message passing, late binding, hot code reload, polymorphic dispatch) resist static characterization.

**Key observations:**

1. **Message passing is universally the unsolved problem.** No production language on BEAM fully types message passing. Gleam's Subject approach is the best engineering compromise: typed channels, but typed at the library level, not the language level.

2. **Set-theoretic types are the convergence point.** Erlang (OTP research), Elixir (1.17+), CDuce, TypeScript's union/intersection — they all converge on set-theoretic foundations because sum types, intersection types, and negation types map cleanly to runtime tag checks and pattern matching.

3. **Gradual typing is a spectrum, not binary.** TypeScript's `any` is unsound. Elixir's `dynamic()` is designed to be sound (gradual guarantee). Erlang's Dialyzer avoids the question by only flagging definite errors. The choice determines whether the type system is a soft safety net or a hard guarantee.

4. **Exhaustiveness checking requires closed worlds.** Gleam (sealed ADTs), Kotlin (sealed classes), Swift (enums) — all require that the sum type's variants are *enumerable at compile time*. Erlang/Elixir atoms are an open universe, making exhaustiveness checking hard by design.

5. **Opaque types are the abstraction boundary.** Every mature type system has them: Erlang `-opaque`, Elixir `@opaque`, Gleam external types, TypeScript brands (hacked), Kotlin (no built-in, use wrappers), Scala 3 opaque types, Swift (modules + access control). They're how you enforce invariants without exposing representation.

6. **Type erasure at runtime is the cost of JVM/BEAM/JS.** Scala on JVM, Kotlin on JVM, TypeScript on JS — all erase generics. Gleam on BEAM erases phantom types. The only way around this is either a custom runtime (Swift on its own runtime has reified types) or language tricks (Kotlin's `reified` via inlining).
