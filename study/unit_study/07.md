## 1. rebar3 — The Erlang Build Tool

### Project Structure

A standard rebar3 OTP application:

```
my_app/
  rebar.config          # build configuration
  rebar.lock            # locked dependency versions
  src/
    my_app.app.src      # OTP application resource template
    my_app.erl          # application callback module
    my_app_sup.erl      # top-level supervisor
    *.erl               # other modules
  include/
    my_app.hrl          # shared header files
  priv/
    *.so                # NIFs, static assets, anything non-BEAM
  test/
    my_app_SUITE.erl    # Common Test suites
    my_app_tests.erl    # EUnit test modules
  _build/               # all build output, never commit
    default/
      lib/
        my_app/
          ebin/         # compiled .beam files + .app file
          include/
          priv/
      rel/              # assembled releases
```

An umbrella (multi-app) project:

```
my_umbrella/
  rebar.config          # top-level config, declares all apps
  apps/
    app_a/
      rebar.config      # app-level overrides (optional)
      src/
      include/
      priv/
    app_b/
      src/
  _build/
```

rebar3 finds apps via `{project_app_dirs, ["apps/*", "lib/*", "."]}` in `rebar.config`. The default covers the patterns above.

### Dependency Resolution

rebar3 resolves deps using a SAT-style solver built around the hex.pm registry. The algorithm:

1. Reads all `{deps, [...]}` from `rebar.config` plus the `deps` of every dependency's `rebar.config` transitively.
2. Builds a constraint graph: each package/version pair has a set of version requirements it imposes on others.
3. Runs a backtracking solver (based on hex's `Hex.Resolver`) that tries to satisfy all constraints simultaneously. When it can't, it picks the highest version of the highest-priority package first, then backtracks if a conflict arises.
4. Writes the resolved set to `rebar.lock`.

On subsequent runs, if `rebar.lock` exists, rebar3 uses it exactly — no resolution runs. `rebar3 upgrade` unlocks one or all deps and re-resolves.

Dep sources in priority order:
- `_checkouts/` — local directory override, highest priority, bypasses lock
- `{path, "..."}` — local path
- `{git, ...}` — git SCM
- hex package name + version — fetched from hex.pm CDN, verified by sha256 checksum

### Compile Provider

`rebar3 compile` runs the `compile` provider which:

1. Runs `app_discovery` to find all project apps and their deps
2. Runs `install_deps` — fetches/unpacks any missing deps
3. For each app (deps first, then project apps) in topological order:
   a. Compiles `.xrl` (leex) → `.erl`
   b. Compiles `.yrl` (yecc) → `.erl`
   c. Compiles `.mib` (SNMP) → `.beam`
   d. Compiles `.erl` → `.beam` via `erlc`, respecting `erl_opts`
   e. Generates `.app` from `.app.src` by substituting `{modules, []}` with the discovered module list
4. Runs any `provider_hooks` registered for `{post, [{compile, SomeProvider}]}`

The compiler tracks file modification times and module dependency graphs (via `-include`, `-include_lib`, `-behaviour`, `-parse_transform`) to do incremental builds. A change to a parse transform triggers recompilation of all modules using it.

### Multiple Apps (Umbrella)

In an umbrella, `{project_app_dirs, ["apps/*", "lib/*"]}` causes rebar3 to discover each sub-app. Each sub-app can have its own `rebar.config` for app-level overrides. The top-level `rebar.config` governs global deps, profiles, and relx. Compilation order is determined by OTP application dependencies declared in each `.app.src`'s `{applications, [...]}` list.

### Writing a Custom Compiler Plugin

There are two interfaces.

**Interface 1: Compiler Module (rebar3 ≥ 3.7, preferred for simple cases)**

```erlang
-module(kore_compiler).
%% No explicit behaviour, but must export these callbacks:
-export([context/1, dependencies/4, needed_files/4, compile_and_track/4, clean/2]).

%% Tell rebar3 where sources are and what to produce
context(AppInfo) ->
    AppDir = rebar_app_info:dir(AppInfo),
    OutDir = rebar_app_info:out_dir(AppInfo),
    #{
        src_dirs     => [filename:join(AppDir, "src")],
        include_dirs => [filename:join(AppDir, "include")],
        src_ext      => ".kore",           % source extension for KorE
        out_mappings => [{".beam", filename:join(OutDir, "ebin")}]
    }.

%% Return list of files this source file depends on
dependencies(Source, _SourceDir, _AllSourceDirs, _State) ->
    %% parse Source for import declarations, return their resolved paths
    parse_imports(Source).

%% Decide which files need recompilation
needed_files(G, AllFiles, [{".beam", EbinDir}], AppInfo) ->
    %% Check DAG timestamps, compiler options changes, etc.
    Stale = [F || F <- AllFiles, is_stale(G, F, EbinDir)],
    {{[], []}, {Stale, []}}.  % {Priority, {Sequential, Parallel}}

%% Compile one file, report artifacts back to DAG
compile_and_track(Source, [{".beam", EbinDir}], _AppConfig, _Opts) ->
    Beam = filename:join(EbinDir, beam_name(Source)),
    case kore:compile(Source, Beam) of
        ok    -> {ok, [{Source, Beam, #{}}]};
        Error -> {error, [format_error(Error)], []}
    end.

clean(Files, AppInfo) ->
    EbinDir = filename:join(rebar_app_info:out_dir(AppInfo), "ebin"),
    [file:delete(filename:join(EbinDir, beam_name(F))) || F <- Files],
    ok.
```

Register it in the plugin init:

```erlang
-module(rebar3_kore).
-export([init/1]).

init(State) ->
    %% prepend so KorE files that generate .erl are processed before erlc
    State1 = rebar_state:prepend_compilers(State, [kore_compiler]),
    {ok, State1}.
```

**Interface 2: Compiler Plugin (pre-3.7 or complex cases)**

```erlang
-module(rebar3_kore_prv).
-behaviour(provider).
-export([init/1, do/1, format_error/1]).

-define(PROVIDER, compile).
-define(NAMESPACE, kore).
-define(DEPS, [{default, app_discovery}]).

init(State) ->
    Provider = providers:create([
        {name,       ?PROVIDER},
        {namespace,  ?NAMESPACE},
        {module,     ?MODULE},
        {bare,       true},
        {deps,       ?DEPS},
        {example,    "rebar3 kore compile"},
        {short_desc, "Compile KorE source files"},
        {desc,       "Compiles .kore files to BEAM bytecode"},
        {opts,       []}
    ]),
    {ok, rebar_state:add_provider(State, Provider)}.

do(State) ->
    Apps = case rebar_state:current_app(State) of
               undefined -> rebar_state:project_apps(State);
               App       -> [App]
           end,
    [compile_app(App) || App <- Apps],
    {ok, State}.

compile_app(AppInfo) ->
    Dir    = rebar_app_info:dir(AppInfo),
    OutDir = rebar_app_info:out_dir(AppInfo),
    Sources = filelib:wildcard(filename:join([Dir, "src", "*.kore"])),
    [kore:compile(Src, OutDir) || Src <- Sources].

format_error(Reason) ->
    io_lib:format("~p", [Reason]).
```

Hook it to `compile`:

```erlang
%% in project rebar.config:
{provider_hooks, [{pre, [{compile, {kore, compile}}]}]}.
```

### The relx Release System

A **release** is a self-contained Erlang system described by a `.rel` file, which specifies every OTP application and its version. From the `.rel`, `systools` generates a `.boot` (binary) and `.script` (text) file that the ERTS loader uses to start the node — analogous to an OS boot sequence.

`rebar3 release` invokes relx which:
1. Reads `{relx, [...]}` from `rebar.config`
2. Resolves the closure of all OTP applications listed in the release spec
3. Copies (or symlinks in dev mode) each app's `ebin/` and `priv/` into `_build/<profile>/rel/<name>/lib/<app>-<vsn>/`
4. If `include_erts: true`, copies the ERTS runtime into `erts-X.Y.Z/`
5. Generates `releases/<vsn>/start.boot` and `start.script`
6. Copies/renders `sys.config` and `vm.args` (or `.src` variants)
7. Writes the `bin/<release_name>` start script (extended start script)

Release directory structure:

```
_build/prod/rel/my_app/
  bin/
    my_app              # start script
  erts-14.2.3/          # embedded ERTS (if include_erts: true)
    bin/
      erl, erlc, ...
  lib/
    my_app-0.1.0/
      ebin/
        my_app.app
        *.beam
      priv/
    cowboy-2.10.0/
      ebin/
      priv/
    kernel-9.2/
      ebin/
    stdlib-5.2/
    ...
  releases/
    0.1.0/
      my_app.rel
      start.boot
      start.script
      start_clean.boot
      sys.config          # or sys.config.src rendered at runtime
      vm.args             # or vm.args.src rendered at runtime
      env.sh
    COOKIE
    start_erl.data        # "ERTS_VSN REL_VSN" for start script
```

`sys.config` format (Erlang terms):

```erlang
%% config/sys.config.src — env vars substituted at runtime
[
  {my_app, [
    {port,      ${PORT:-8080}},
    {db_host,   "${DB_HOST:-localhost}"},
    {log_level, ${LOG_LEVEL:-info}}
  ]},
  {kernel, [
    {logger_level, info}
  ]}
].
```

`vm.args.src`:

```
## Node name
-name ${NODE_NAME:-my_app@127.0.0.1}

## Distribution cookie
-setcookie ${RELEASE_COOKIE:-secret}

## Increase process limit
+P 1048576

## SMP schedulers
+S 4:4

## Enable JIT
+JMsingle true
```

### rebar3 escriptize

`rebar3 escriptize` packages the project and all deps into a single self-executing zip file. The BEAM runtime must already be installed on the target (unlike a release). Configure in `rebar.config`:

```erlang
{escript_main_app, my_cli}.
{escript_name, "my_tool"}.
{escript_shebang, "#!/usr/bin/env escript\n"}.
{escript_comment, "%%\n"}.
{escript_emu_args, "%%! -escript main my_cli_main\n"}.
{escript_incl_apps, [jsx, getopt]}.  % extra apps beyond the main app's deps
```

The main module must export `main/1`:

```erlang
-module(my_cli_main).
-export([main/1]).

main(Args) ->
    %% Args is a list of strings
    ok.
```

### Dependency Resolution

Mix uses hex.pm's solver. The algorithm is a backtracking SAT solver (the same one used by rebar3, since it's a shared Hex library). Key behaviors:

- Deps without SCM (`:git`, `:path`) go to hex.pm
- `mix.lock` pins exact package versions including SHA-256 checksum of the tarball
- `mix deps.get` respects `mix.lock` exactly; upgrades require `mix deps.update`
- `:only` restricts a dep to specific environments — those deps are never fetched when the parent package is a dep of something else

### Mix Compiler Pipeline

`mix compile` runs the compiler pipeline in order:
1. `Mix.Tasks.Compile.Erlang` — compiles `.erl` files in `src/`
2. `Mix.Tasks.Compile.Leex` — `.xrl` files
3. `Mix.Tasks.Compile.Yecc` — `.yrl` files
4. `Mix.Tasks.Compile.Elixir` — invokes the Elixir compiler on `lib/**/*.ex`
5. `Mix.Tasks.Compile.App` — generates the `.app` file from `mix.exs`'s `application/0`
6. Protocol consolidation — merges all protocol implementations into optimal dispatch modules (in `_build/ENV/consolidated/`)

Custom compilers are added to the `:compilers` list:

```elixir
def project do
  [
    compilers: [:kore_compiler] ++ Mix.compilers(),
    ...
  ]
end
```

A custom compiler implements `Mix.Task.Compiler` behaviour:

```elixir
defmodule Mix.Tasks.Compile.Kore do
  use Mix.Task.Compiler

  @impl Mix.Task.Compiler
  def run(args) do
    # Find all .kore files in src/
    sources = Path.wildcard("src/**/*.kore")
    # Compile each to _build/ENV/lib/APP/ebin/
    Enum.each(sources, &compile_file/1)
    {:ok, []}
  end

  @impl Mix.Task.Compiler
  def clean do
    # Remove compiled artifacts
    :ok
  end

  @impl Mix.Task.Compiler
  def manifests do
    # Return paths to manifest files for incremental build tracking
    [manifest_path()]
  end
end
```

### Mix Releases

`mix release` (introduced in Elixir 1.9) produces an OTP release equivalent to what relx produces. The key differences from rebar3/relx:

| Feature | mix release | rebar3/relx |
|---|---|---|
| Config language | Elixir (`runtime.exs`) | Erlang (`sys.config.src`) |
| ERTS included | Yes (default) | Yes (with `include_erts: true`) |
| Hot upgrades | Not supported out of box | Supported via appup/relup |
| Config providers | Pluggable (`Config.Provider`) | Limited |
| Env vars at runtime | `config/runtime.exs` (Elixir) | `sys.config.src` with `${VAR}` |

Release directory structure (same OTP structure as relx):

```
_build/prod/rel/my_app/
  bin/
    my_app              # start script
    my_app.bat
  erts-14.2.3/
  lib/
    my_app-0.1.0/
      ebin/
      priv/
    elixir-1.16.0/
    logger-1.16.0/
    ...
  releases/
    0.1.0/
      consolidated/
      elixir, iex       # Elixir-specific start helpers
      start.boot
      start.script
      start_clean.boot
      sys.config        # compiled from runtime.exs output
      vm.args
      runtime.exs       # copied here, evaluated at boot
      env.sh
    COOKIE
    start_erl.data
  tmp/
```

### Config Layers

```
config/config.exs       — always loaded at compile time
  └─ import_config "#{config_env()}.exs"
       config/dev.exs   — when MIX_ENV=dev
       config/test.exs  — when MIX_ENV=test
       config/prod.exs  — when MIX_ENV=prod

config/runtime.exs      — loaded at runtime (both `mix run` and in releases)
                          MUST use `import Config`, not `use Mix.Config`
                          MUST NOT call Mix.*
                          MUST NOT import_config other files
```

`config/runtime.exs` example:

```elixir
import Config

config :my_app, MyApp.Repo,
  url: System.fetch_env!("DATABASE_URL")

config :my_app, MyApp.Endpoint,
  secret_key_base: System.fetch_env!("SECRET_KEY_BASE"),
  http: [port: String.to_integer(System.get_env("PORT", "4000"))]

if config_env() == :prod do
  config :my_app, :feature_flags,
    new_ui: System.get_env("ENABLE_NEW_UI") == "true"
end
```

### Application Callback

Every OTP application started by a release needs an Application callback module:

```elixir

  @impl Application
  def start(_type, _args) do
    children = [
      MyApp.Repo,
      {Phoenix.PubSub, name: MyApp.PubSub},

  @impl Application
  def stop(_state), do: :ok

def application do

    ]
  end

  defp deps do

    []
  end

  defp releases do
    [
      full_system: [
        applications: [
          app_a: :permanent,
          app_b: :permanent
        ]
      ]
    ]
  end
end
```

Child `apps/app_a/mix.exs`:

## 3. hex.pm — The BEAM Package Registry

### Package Format

A hex package is a `.tar` archive with this structure:

```
my_package-1.0.0.tar
  metadata.config       # Erlang terms: name, version, description, licenses,
                        # requirements, build_tools, files, app, elixir, etc.
  contents.tar.gz       # the actual source/beam files
  CHECKSUM              # SHA-256 of contents.tar.gz
```

`metadata.config` example:

```erlang
{<<"name">>,        <<"my_package">>}.
{<<"version">>,     <<"1.0.0">>}.
{<<"description">>, <<"A BEAM package">>}.
{<<"licenses">>,    [<<"Apache-2.0">>]}.
{<<"build_tools">>, [<<"mix">>]}.           % or <<"rebar3">> or <<"gleam">>
{<<"requirements">>, [
  #{<<"app">>         => <<"jason">>,
    <<"optional">>    => false,
    <<"requirement">> => <<"~> 1.4">>}
]}.
{<<"files">>, [<<"lib/my_package.ex">>, <<"mix.exs">>, ...]}.
{<<"elixir">>,      <<"~> 1.14">>}.
```

`contents.tar.gz` contains whatever files are listed in `:files` — typically `lib/`, `src/`, `mix.exs` or `rebar.config`, `README.md`, `LICENSE`. It does **not** need to contain pre-compiled `.beam` files; compilation happens on the consumer's machine during `deps.get`/`deps.compile`.

### Lockfiles

**mix.lock:**

```elixir
%{
  "cowboy": {:hex, :cowboy, "2.10.0",
    "ff9465a75b5ff589a9b6a72a29d96571e93bb7cb24e6c26f8e45c8db60e5cf7b",
    [:make, :rebar3], [:cowlib, :ranch], "hexpm", "a95..."},
  "cowlib": {:hex, :cowlib, "2.12.1",
    "a602d9c2831f8f3fd3a53e4c43ea8ad1e0d8a59a21a29fb4da49e4f8162c5381",
    [:make, :rebar3], [], "hexpm", "1b4..."},
  "jason": {:hex, :jason, "1.4.1",
    "fbb01ecdca458b4a9e59f8f3a4a4e6e8c10fb23b82de02ef3be4f6b11e5e0a16",
    [:mix], [:decimal], "hexpm", "bc3..."},
}
```

Each entry: `{:hex, pkg_atom, version, outer_checksum, build_tools, deps, repo, inner_checksum}`.

**rebar.lock:**

```erlang
{"1.2.0",
[{<<"cowboy">>, {pkg, <<"cowboy">>, <<"2.10.0">>,
    <<"ff9465a75b5ff589a9b6a72a29d96571e93bb7cb24e6c26f8e45c8db60e5cf7b">>,
    <<"a95...">>}, 0},
 {<<"cowlib">>, {pkg, <<"cowlib">>, <<"2.12.1">>,
    <<"a602d9c2831f8f3fd3a53e4c43ea8ad1e0d8a59a21a29fb4da49e4f8162c5381">>,
    <<"1b4...">>}, 1}
]}.
[{pkg_hash_ext, [
  {<<"cowboy">>, <<"a95...">>},
  {<<"cowlib">>, <<"1b4...">>}
]}].
```

Both lockfiles record the outer checksum (of the `.tar`) and inner checksum (of `contents.tar.gz`) for supply-chain integrity.

### Multi-Language Packages on hex.pm

hex.pm is language-agnostic. The `build_tools` field in metadata tells the consumer which tool to use. Mix detects `rebar.config` → uses rebar3; detects `mix.exs` → uses mix; detects `gleam.toml` → uses gleam. You can override with `manager: :rebar3` in a mix dep tuple.

An Erlang package on hex.pm works as a dep in:
- Erlang project: native rebar3
- Elixir project: mix calls `mix rebar3 compile` on it transparently
- Gleam project: gleam resolves it as a hex dep and compiles it via rebar3 or mix

### Version Requirement Syntax

The hex.pm version requirement format (used by Mix, Gleam, and partially rebar3):

| Operator | Meaning |
|---|---|
| `~> 1.0` | `>= 1.0.0 and < 2.0.0` |
| `~> 1.0.3` | `>= 1.0.3 and < 1.1.0` |
| `~> 1.0.0-rc.1` | `>= 1.0.0-rc.1 and < 1.1.0` |
| `>= 1.0.0` | any version ≥ 1.0.0 |
| `== 1.0.0` | exact version |
| `>= 1.0.0 and < 2.0.0` | explicit range (Gleam style) |
| `!= 1.0.5` | excludes specific version |

rebar3 uses a similar but slightly different syntax from `semver.erl`. In `rebar.config`, you can use `"~> 1.0"` (hex compatible) or `">= 1.0.0, < 2.0.0"` (comma-separated constraints).

### Private Hex Repositories

Self-hosted hex.pm (via `hexpm` OSS or commercial):

```erlang
%% rebar.config
{hex, [{repos, [
  #{name => <<"my_company">>,
    api_url  => <<"https://hex.mycompany.com/api">>,
    repo_url => <<"https://hex.mycompany.com/repo">>,
    repo_public_key => <<"-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----">>}
]}]}.

%% Dep references private repo:
{deps, [{my_private_pkg, {pkg, <<"my_private_pkg">>, "1.0.0", #{repo => <<"my_company">>}}}]}.
```

```elixir
# mix.exs — private org on hex.pm SaaS
{:my_private_pkg, "~> 1.0", repo: "my_company"}
```

## 5. OTP Releases

### What a Release Is

An OTP release is the fundamental unit of deployment for BEAM systems. It is defined by:

- **`.rel` file** — declares the release name, version, ERTS version, and the complete list of OTP applications with their versions
- **`.script` file** — generated from `.rel` by `systools:make_script/2`, contains ordered boot instructions
- **`.boot` file** — binary form of `.script`, what ERTS actually reads at startup
- **`sys.config`** — application environment configuration loaded at startup
- **`vm.args`** — flags passed to `erl`

`.rel` file format:

```erlang
{release,
  {"my_app", "0.1.0"},    % release name + version
  {erts, "14.2.3"},        % ERTS version to use
  [
    {kernel,  "9.2"},
    {stdlib,  "5.2"},
    {sasl,    "4.2.1"},    % SASL for release logging
    {my_dep,  "1.0.0"},
    {my_app,  "0.1.0"}
  ]
}.
```

### Boot Sequence

When `bin/my_app start` runs:
1. The shell script locates ERTS, sets up paths, reads `vm.args`
2. `erl` is invoked with `-boot releases/VSN/start` and `-config releases/VSN/sys`
3. ERTS loads `start.boot`, which contains instructions to:
   - Start the `init` process
   - Load code paths (`lib/app-vsn/ebin/` for every app)
   - Start each application in dependency order via `application:start/2`
4. `sys.config` is applied to the application environment
5. Each OTP app's `application:start` callback is called
6. The system is running

### Release Directory Structure (annotated)

```
my_release/
  bin/
    my_release          # POSIX start script (extended start script)
    my_release.bat      # Windows start script
  erts-14.2.3/          # Embedded ERTS
    bin/
      erl               # the Erlang runtime
      erlc
      run_erl           # for daemon mode
      to_erl            # attach to daemon
    lib/                # ERTS internal libraries
  lib/
    kernel-9.2/
      ebin/
        kernel.app
        *.beam
    stdlib-5.2/
    sasl-4.2.1/
    my_dep-1.0.0/
      ebin/
      priv/
    my_app-0.1.0/
      ebin/
        my_app.app      # final .app file
        *.beam
      priv/
  releases/
    0.1.0/
      my_release.rel    # release descriptor
      start.boot        # binary boot script
      start.script      # text boot script (readable)
      start_clean.boot  # boot without user apps (for eval/rpc)
      sys.config        # application configuration
      vm.args           # VM flags
    COOKIE              # distribution cookie
    start_erl.data      # "ERTS_VSN REL_VSN"
```

### Hot Code Upgrades (relup)

Hot code upgrades allow upgrading a running system without stopping it. The mechanism:

1. **`.appup` file** — per-application instructions for upgrading from version A to B and downgrading from B to A. Located at `ebin/my_app.appup` in the new release.

```erlang
{"0.2.0",                       % this version
  [{"0.1.0",                    % upgrading from
    [{update, my_server,         % update this gen_server
       {advanced, []},           % call code_change/3
       brutal_purge,             % purge old code brutally
       soft_purge,               % soft purge new code loading
       []                        % dependent modules
     }
    ]}],
  [{"0.1.0",                    % downgrading to
    [{update, my_server, {advanced, []}, brutal_purge, soft_purge, []}]
   }]
}.
```

2. **`.relup` file** — generated by `systools:make_relup/4` from the `.rel` and `.appup` files of both releases. Contains the complete upgrade/downgrade instruction sequence.

3. **Deployment**: package the new release as a tarball, place it in `releases/0.2.0/`, then:
```
bin/my_release install 0.2.0
bin/my_release upgrade 0.2.0
```

This calls `release_handler` which runs the relup instructions: suspends processes, loads new code, calls `code_change/3` on gen_servers, resumes processes.

**Practical note**: hot upgrades require careful process state management. They're rarely used in modern deployments; blue/green or rolling restarts are preferred. Neither `mix release` nor standard Gleam supports generating `.appup` files.

### Runtime vs Compile-time Config

| | Erlang (`sys.config.src`) | Elixir (`config/runtime.exs`) |
|---|---|---|
| When evaluated | At release boot | At release boot |
| Language | Erlang terms | Elixir code |
| Env vars | `${VAR:-default}` substitution | `System.get_env/2` |
| Logic | None (static terms only) | Full Elixir (if/case/etc.) |
| Config providers | N/A | Pluggable `Config.Provider` |

## 6. Project Structure Best Practices

### OTP App Structure

Every deployable unit is an OTP application. The canonical structure:

```
my_app/
  src/
    my_app.app.src      # application resource file template
    my_app_app.erl      # Application behaviour callback (optional for libraries)
    my_app_sup.erl      # top-level supervisor
    my_app.erl          # main API module
    my_app_worker.erl   # worker gen_server
  include/
    my_app.hrl          # public types, macros, records
  priv/
    schemas/            # JSON schemas, SQL migrations
    native/             # compiled NIFs (.so files)
    templates/          # any non-BEAM runtime assets
  test/
    my_app_SUITE.erl    # Common Test
    my_app_tests.erl    # EUnit
```

### .app.src File

The `.app.src` is processed by the build tool to produce the final `.app` file. The `modules` field is filled in automatically.

```erlang
{application, my_app, [
  {description,  "My OTP application"},
  {vsn,          "0.1.0"},
  {modules,      []},          % FILLED IN by rebar3/mix from discovered .beam files
  {registered,   [my_app_sup]},
  {applications, [
    kernel,
    stdlib,
    sasl,              % include if you want SASL logs
    crypto,            % external OTP apps you use
    my_dep             % hex dependencies
  ]},
  {mod,          {my_app_app, []}},   % Application callback; omit for library apps
  {env,          [               % default application environment
    {port, 8080},
    {log_level, info}
  ]},
  {maxT,         infinity}       % max time for app to run
]}.
```

### priv/ Directory

`priv/` is the designated place for any file that needs to be present at runtime but isn't Erlang source. The ERTS function `code:priv_dir(AppName)` returns its path, which is stable whether you're in a source tree, a release, or an escript.

Contents by convention:
- `priv/native/` — NIF shared libraries (`.so`, `.dll`)
- `priv/ssl/` — certificates
- `priv/static/` — web static assets
- `priv/templates/` — template files
- `priv/migrations/` — database migrations
- `priv/schemas/` — schemas, .proto files, .graphql

### include/ Directory

`include/` holds `.hrl` header files shared across modules within or between apps. Headers are accessed with:

```erlang
-include("my_record.hrl").              % from own include/
-include_lib("other_app/include/rec.hrl").  % from a dependency
```

In rebar3 you can add custom include paths via `{erl_opts, [{i, "include"}]}`. Mix automatically adds `include/` for Erlang files in `src/`.

### Test Conventions

**EUnit** — unit tests, typically in `test/` or inline in modules:

```erlang
%% test/my_module_tests.erl
-module(my_module_tests).
-include_lib("eunit/include/eunit.hrl").

my_function_test() ->
    ?assertEqual(expected, my_module:function(input)).

my_function_test_() ->
    [?_assertEqual(1, my_module:add(0, 1)),
     ?_assertEqual(2, my_module:add(1, 1))].
```

Run: `rebar3 eunit` or `rebar3 as test eunit --module my_module_tests`

**Common Test** — integration/system tests:

```erlang
%% test/my_app_SUITE.erl
-module(my_app_SUITE).
-include_lib("common_test/include/ct.hrl").
-export([all/0, init_per_suite/1, end_per_suite/1, my_test/1]).

all() -> [my_test].

init_per_suite(Config) ->
    application:ensure_all_started(my_app),
    Config.

end_per_suite(_Config) ->
    application:stop(my_app).

my_test(_Config) ->
    Result = my_app:some_function(),
    ?assertEqual(expected, Result).
```

Run: `rebar3 ct`

**ExUnit** (Elixir):

```elixir
# test/my_module_test.exs
defmodule MyModuleTest do
  use ExUnit.Case, async: true

  test "adds numbers" do
    assert MyModule.add(1, 2) == 3
  end

  describe "edge cases" do
    test "handles zero" do
      assert MyModule.add(0, 0) == 0
    end
  end
end
```

Run: `mix test` or `mix test test/my_module_test.exs:10`

## 7. Dependency Management Patterns

### Semantic Versioning on hex.pm

All hex packages must follow semver. The practical rules:
- Pre-1.0: breaking changes allowed in minor (0.x.0)
- Post-1.0: major version bumps for breaking changes
- `~> 1.2` is the idiomatic constraint — allows patch and minor upgrades but not major

### Mixed Language Dependency Graph

When a project mixes Erlang/Elixir/Gleam deps, compilation proceeds like this:

```
Resolution phase (all languages use same hex solver):
  gleam.toml / mix.exs / rebar.config
      → unified package set in lockfile

Compilation phase (each package uses its own build tool):
  rebar3 packages  → rebar3 compile (called by Mix/Gleam as subprocess)
  mix packages     → mix compile
  gleam packages   → gleam build
```

Mix's interop with Erlang rebar3 packages: Mix calls `mix rebar3 compile` (using a bundled rebar3) when it encounters a dep with `rebar.config`. The compiled `.beam` files end up in `_build/ENV/lib/dep_name/ebin/` alongside Elixir packages.

Gleam's interop: When Gleam encounters a rebar3 dep, it invokes rebar3 in the dep's directory. When it encounters a mix dep, it invokes mix. The `.beam` files from all three tools end up in `build/ENV/erlang/app_name/ebin/`.

### Dependency Conflict Resolution

The hex solver uses a **backtracking CDCL** (Conflict-Driven Clause Learning) algorithm:

1. Start with the top-level requirements
2. For each requirement, add the newest compatible version to the candidate set
3. Recursively add that version's requirements
4. If a conflict is detected (two requirements on the same package that can't be satisfied simultaneously), backtrack and try an older version
5. If no solution exists, report the conflict with an explanation of which packages created the conflicting requirements

The solver never downgrades a package below what was already selected unless forced by a conflict. This means `mix deps.get` is deterministic given a lockfile, and re-running without a lockfile may produce different results as new versions are published.

### Lockfile as Reproducibility Guarantee

The lockfile records:
- Exact version (e.g. `1.4.1`)
- SHA-256 checksum of both the outer tarball and inner contents
- Repo the package was fetched from

This means:
- Two developers with the same lockfile get bit-for-bit identical dep tarballs
- A tampered or replaced package on hex.pm will fail checksum verification
- Always commit the lockfile to version control

### Vendoring

rebar3: `_checkouts/` directory — place any dep source there and it takes priority over hex/git:

```
_checkouts/
  my_dep/
    rebar.config
    src/
```

Mix: `{:my_dep, path: "vendor/my_dep"}` in deps. No official vendoring mechanism but path deps serve the purpose.

Gleam: `my_dep = { path = "../my_dep" }` in `[dependencies]`.

## 8. Cross-Language Compilation in Mixed Projects

### How an Elixir Project Depends on an Erlang Package

No configuration needed. Declare in `mix.exs`:

```elixir
defp deps do
  [{:cowboy, "~> 2.10"}]  # cowboy is an Erlang rebar3 package
end
```

Mix detects `rebar.config` in the dep and invokes the bundled rebar3 (`~/.mix/rebar3`) to compile it. The resulting `.beam` files are placed in `_build/ENV/lib/cowboy/ebin/` and are on the code path like any Elixir dep.

Calling the Erlang module from Elixir is transparent — it's all BEAM:

```elixir
:cowboy.start_clear(:http, [{:port, 8080}], %{})
```

### How a Gleam Project Depends on an Elixir Package

Declare in `gleam.toml`:

```toml
[dependencies]
phoenix_html = ">= 4.0.0 and < 5.0.0"
```

Gleam will detect `mix.exs` in the dep, invoke Mix to compile it, and place the `.beam` files in the build directory. Call it from Gleam via FFI:

```gleam
// Elixir modules are prefixed with Elixir.
@external(erlang, "Elixir.PhoenixHTML", "safe_to_string")
pub fn safe_to_string(html: a) -> String
```

### Compilation Order in Mixed Projects

Build tools determine compilation order by reading OTP application dependency graphs from each app's `.app.src` / `mix.exs` `application/0` / `gleam.toml`. The rule is: an app must be compiled before any app that lists it in `{applications, [...]}`.

For a mixed project in Mix:
1. All Erlang deps (rebar3) compiled first, in dep-graph order
2. Then Elixir deps (mix)
3. Then Gleam deps (gleam)
4. Then the project's own code

Gleam handles this similarly: rebar3 deps → mix deps → gleam deps → project source.

### What KorE Packages Should Look Like

For KorE to be consumable from Erlang, Elixir, and Gleam, a KorE package needs to produce a standard OTP application. The key invariants:

**1. Must produce standard `.beam` files and a valid `.app` file**

Everything in the BEAM ecosystem consumes `.beam` files. The KorE compiler must emit BEAM bytecode that passes `beam_lib:chunks/2` validation. The `.app` file must list all modules.

**2. Must be consumable as a hex.pm package**

KorE packages on hex.pm should include:
- `gleam.toml` or `rebar.config` or `mix.exs` as the build tool indicator
- Pre-compiled `.beam` files in `ebin/` (optional but useful for cross-tool consumption)
- Or source files + a build tool config that the consuming ecosystem's tool can invoke

The cleanest approach for maximum compatibility: ship **pre-compiled `.beam` files** in the hex tarball alongside the KorE source. Set `build_tools = ["kore"]` in hex metadata, but also include a `rebar.config` that treats the pre-compiled beams as-is (no recompilation needed), so rebar3/mix can use it without having KorE installed.

**3. The `.app.src` / OTP app spec must be correct**

```erlang
%% src/my_kore_lib.app.src
{application, my_kore_lib, [
  {description,  "A KorE library"},
  {vsn,          "0.1.0"},
  {modules,      []},   % filled by KorE build tool
  {registered,   []},
  {applications, [kernel, stdlib]},  % accurate dep list
  {env,          []}
]}.
```

**4. Use standard module naming**

KorE modules must compile to Erlang module names that don't collide with Erlang (`snake_case`), Elixir (`Elixir.PascalCase`), or Gleam (`package@module`) conventions. A reasonable convention: `kore_package_name@module_name` or just `package_module` in snake_case (matching Erlang/Gleam style).

**5. Interop-friendly exported types**

Functions that need to be called from Erlang, Elixir, or Gleam should export standard BEAM types: atoms, binaries, lists, maps, tuples. Avoid opaque types in the public API if cross-language consumption is expected.

## Key Insights for KorE Build System Design

Synthesizing all of the above:

**The `_build/` convention.** All three tools use a separate build output directory (`_build/` for rebar3/mix, `build/` for Gleam). KorE should follow this pattern. Never mix build artifacts with source.

**The `.app` file is the lingua franca.** Every BEAM tool speaks OTP application format. KorE's build tool must generate a valid `.app` file or the ecosystem won't be able to use KorE packages.

**Profile/environment separation.** rebar3 uses profiles, Mix uses `MIX_ENV`, Gleam is simpler. KorE should have at minimum `dev` and `prod` build modes.

**The lockfile is non-negotiable.** Any package manager integration must generate and respect a lockfile. Commit it.

**`priv/` + `code:priv_dir/1` is the portable runtime asset pattern.** KorE packages that ship non-BEAM files should use `priv/`.

**Pre-compiled beams in the hex tarball** is the pragmatic choice for cross-tool consumption. It lets rebar3/mix/gleam use KorE packages without needing the KorE compiler installed. The source is still included for reference and for the KorE toolchain.

**Custom compiler module interface** (rebar3 ≥ 3.7) is the right integration point for KorE into rebar3. Implement `context/1`, `dependencies/4`, `needed_files/4`, `compile_and_track/4`, `clean/2`. Register via `rebar_state:prepend_compilers/2` in the plugin's `init/1`.

**Mix compiler task** (`Mix.Task.Compiler` behaviour) is the integration point for Mix. Add `:kore` to the `:compilers` list in `mix.exs`.

**Gleam FFI** is the integration point for Gleam consuming KorE — Gleam doesn't have a plugin system for custom compilers, so KorE packages need to ship pre-compiled `.beam` files when targeting Gleam consumers, or the KorE compiler needs to produce `.gleam`-compatible interop stubs.
