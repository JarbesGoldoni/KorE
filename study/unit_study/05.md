# BEAM Interoperability: Exhaustive Technical Reference for KorE Language Design

## 1. How Elixir Calls Erlang

### 1.1 Exact Call Syntax

Erlang modules are atoms. In Elixir you prefix the module name with `:` to force atom interpretation:

```elixir
# Erlang: lists:sort([3,2,1])
:lists.sort([3, 2, 1])

# Erlang: string:to_upper("hello")
:string.to_upper("hello")

# Erlang: crypto:hash(sha256, <<"data">>)
:crypto.hash(:sha256, "data")

# All BIFs live in :erlang
:erlang.make_ref()
:erlang.system_time(:millisecond)
:erlang.term_to_binary({:ok, 42})

# tuple access (Erlang is 1-indexed, Elixir elem/2 is 0-indexed wrapper)
:erlang.element(1, {:a, :b, :c})   # => :a  (raw BIF)
elem({:a, :b, :c}, 0)               # => :a  (Elixir wrapper, 0-indexed)
```

### 1.2 Atoms Across the Boundary

Both Erlang and Elixir atoms are the same BEAM atom table entries. The syntactic difference is cosmetic:

```elixir
# Elixir atom syntax          Erlang atom syntax
:ok                    ==      ok
:error                 ==      error
:undefined             ==      undefined
:"hello world"         ==      'hello world'

# Elixir module aliases expand to atoms with "Elixir." prefix
MyModule               ==      'Elixir.MyModule'
String                 ==      'Elixir.String'

# You can verify:
is_atom(String)        # => true
String == :'Elixir.String'  # => true
```

When Erlang code calls back into an Elixir module, it must use the mangled atom:

```erlang
% Erlang calling Elixir's String.upcase/1
'Elixir.String':upcase(<<"hello">>).
```

### 1.3 How Elixir Structs Cross the Boundary

Elixir structs are **maps with a `__struct__` key** whose value is the module atom:

```elixir
defmodule Point do
  defstruct x: 0, y: 0
end

p = %Point{x: 1, y: 2}
# At the BEAM level this is literally:
# %{__struct__: Point, x: 1, y: 2}
# which Erlang sees as:
# #{__struct__ => 'Elixir.Point', x => 1, y => 2}
```

From Erlang you can read struct fields using map syntax, but you lose struct semantics:

```erlang
% Erlang side - accessing an Elixir struct
P = elixir_module:get_point(),  % returns an Elixir struct
X = maps:get(x, P),             % works fine - just a map access
Struct = maps:get('__struct__', P),  % 'Elixir.Point'
```

KorE implication: KorE data classes / value types that need to be readable from Elixir must either (a) emit maps with `__struct__` or (b) accept that Elixir callers see plain maps.

### 1.4 Elixir Macros and Protocols at the Boundary

Macros are **compile-time only**. They expand to AST before the `.beam` file is written. Erlang callers never see macros — only their expanded output.

```elixir
# This macro:
defmacro unless(condition, do: body) do
  quote do: if(!unquote(condition), do: unquote(body))
end

# Is invisible to Erlang. Erlang only sees whatever functions
# the macro expansion eventually produced.
```

Protocols compile to a dispatcher module + per-type implementations:

```elixir
defprotocol Greet do
  def hello(thing)
end

defimpl Greet, for: BitString do
  def hello(s), do: "Hello, #{s}"
end
```

This produces BEAM modules: `Elixir.Greet` (the protocol module) and `Elixir.Greet.BitString` (the impl). Erlang can call `'Elixir.Greet':hello(<<"world">>)` and dispatch works correctly, since protocol dispatch is a normal function call to the consolidated dispatcher.

### 1.5 Calling Erlang BIFs from Elixir

BIFs are in the `:erlang` module. Many are auto-imported by Elixir's `Kernel`:

```elixir
# Auto-imported BIFs (available without module prefix in Elixir):
is_atom(:foo)           # erlang:is_atom/1
is_binary("hello")      # erlang:is_binary/1
is_integer(42)          # erlang:is_integer/1
length([1,2,3])         # erlang:length/1
hd([1,2,3])             # erlang:hd/1
tl([1,2,3])             # erlang:tl/1
node()                  # erlang:node/0
self()                  # erlang:self/0
send(pid, msg)          # erlang:send/2 (Elixir uses Kernel.send)

# BIFs NOT auto-imported, require :erlang prefix:
:erlang.make_ref()
:erlang.unique_integer([:positive, :monotonic])
:erlang.process_info(self(), :message_queue_len)
:erlang.system_info(:atom_count)
:erlang.term_to_binary(term)
:erlang.binary_to_term(bin)
:erlang.phash2(term)
:erlang.garbage_collect()
```

### 1.6 Using OTP Behaviours from Elixir

Elixir wraps OTP behaviours with `use` macros that inject `@behaviour` annotations and default implementations. At the BEAM level it is identical to Erlang's `:gen_server`:

```elixir
defmodule MyServer do
  use GenServer   # injects @behaviour :gen_server, defines child_spec/1

  def start_link(init_arg) do
    GenServer.start_link(__MODULE__, init_arg, name: __MODULE__)
  end

  # Callbacks that map 1:1 to gen_server callbacks:
  @impl true
  def init(args), do: {:ok, %{count: 0}}

  @impl true
  def handle_call(:get, _from, state), do: {:reply, state.count, state}

  @impl true
  def handle_cast(:inc, state), do: {:noreply, %{state | count: state.count + 1}}

  @impl true
  def handle_info(:tick, state) do
    Process.send_after(self(), :tick, 1000)
    {:noreply, state}
  end

  @impl true
  def terminate(reason, state), do: :ok

  @impl true
  def code_change(_old_vsn, state, _extra), do: {:ok, state}
end
```

At the wire level `GenServer.start_link/3` calls `:gen_server.start_link/3`. Erlang can call this GenServer directly:

```erlang
% Erlang calling an Elixir GenServer
:gen_server.call('Elixir.MyServer', get).
gen_server:call('Elixir.MyServer', get).
```

The `Supervisor` behaviour similarly:

```elixir
defmodule MySup do
  use Supervisor

  def init(_) do
    children = [
      {MyServer, []},
      {Task.Supervisor, name: MyTaskSup}
    ]
    Supervisor.init(children, strategy: :one_for_one)
  end
end
```

### 1.7 How Elixir Compiles to .beam

Elixir compiles to **Erlang Abstract Format (EAF)** first, then to BEAM bytecode. The result is indistinguishable from compiled Erlang at the file level. Each Elixir module produces exactly one `.beam` file.

What Erlang sees when it loads `'Elixir.MyModule'`:
- Exported functions are plain BEAM exports
- Module attributes (like `@vsn`, `@behaviour`) become Erlang module attributes
- Elixir-specific metadata (`__info__/1`) is an extra exported function

```elixir
# Elixir module:
defmodule Foo do
  def bar(x), do: x * 2
end

# Produces BEAM module named 'Elixir.Foo' with exports:
#   bar/1
#   __info__/1       <- Elixir metadata function
#   module_info/0    <- standard Erlang module_info
#   module_info/1
```

### 1.8 Module Naming: Elixir → Erlang

The rule is absolute: every Elixir module `Foo.Bar.Baz` becomes the atom `'Elixir.Foo.Bar.Baz'`.

```erlang
% Erlang calling Elixir:
'Elixir.String':downcase(<<"HELLO">>).
'Elixir.Enum':map([1,2,3], fun(X) -> X * 2 end).
'Elixir.MyApp.Router':dispatch(Request).

% Erlang module (bstring.erl) wrapping Elixir for ergonomics:
-module(bstring).
-export([downcase/1]).

downcase(Bin) ->
    'Elixir.String':downcase(Bin).
```

There is no reverse mangling for Elixir module names that don't start with uppercase — lowercase Elixir atom modules (e.g., `:my_module`) map to `my_module` with no prefix. This is used for Erlang-style interop modules.

## 2. How Gleam Calls Erlang

### 2.1 The @external Attribute

`@external` replaces the function body with a reference to an Erlang (or JS) function:

```gleam
// Syntax: @external(erlang, "erlang_module_name", "function_name")
@external(erlang, "erlang", "system_time")
pub fn system_time(unit: Atom) -> Int

@external(erlang, "lists", "reverse")
pub fn reverse(list: List(a)) -> List(a)

@external(erlang, "crypto", "hash")
pub fn crypto_hash(algorithm: Atom, data: BitArray) -> BitArray

// You can provide a Gleam fallback for the JS target while using Erlang impl:
@external(erlang, "erlang", "phash2")
pub fn hash(term: a) -> Int {
  // This body is used on JS target; ignored on Erlang target
  todo
}
```

The compiler **trusts the type annotation completely**. It does zero runtime type checking. If the Erlang function returns something that doesn't match the declared Gleam type, you get a runtime crash with no helpful error message.

### 2.2 Atoms at the Gleam/Erlang Boundary

Atoms are **not a first-class type in Gleam**. The `gleam_erlang` stdlib provides an opaque `Atom` type:

```gleam
import gleam/erlang/atom

// Safe lookup: only succeeds if atom already exists in table
pub fn get_ok() -> Result(Atom, Nil) {
  atom.get("ok")
}

// Unsafe creation: inserts into atom table (may crash VM if overused)
pub fn create_atom(name: String) -> Atom {
  atom.create(name)
}

// Convert back to string
pub fn atom_name(a: Atom) -> String {
  atom.to_string(a)
}

// Using atoms at Erlang boundary - pattern: use known atoms as opaque handles
@external(erlang, "gen_server", "call")
fn raw_call(server: Pid, request: a) -> b

// The gleam_erlang process module wraps atoms internally:
// process.Normal, process.Killed, process.Abnormal(reason) map to
// Erlang atoms normal, kill, {reason}
```

The critical design constraint: **never convert user-controlled strings to atoms**. The `atom.get/1` function uses `erlang:existing_atom` under the hood and returns `Error(Nil)` rather than creating a new atom.

### 2.3 Erlang Records at the Gleam Boundary

Erlang records are **compile-time tuples** — there is no record type at runtime, only `{tag, field1, field2, ...}` tuples. Gleam has no record syntax, so you work with the raw tuple representation:

```gleam
// An Erlang record defined as:
//   -record(person, {name, age}).
// Is at runtime: {person, Name, Age}
// Access at index:
//   #person.name == 2  (1-indexed, +1 for tag)
//   #person.age  == 3

// In Gleam, you must work with Dynamic and decode:
import gleam/dynamic
import gleam/dynamic/decode

type Person {
  Person(name: String, age: Int)
}

fn decode_person(d: dynamic.Dynamic) -> Result(Person, dynamic.DecodeError) {
  // Record is a tuple: {person, Name, Age}
  let decoder = decode.tuple3(
    decode.atom,     // tag: person atom
    decode.string,   // name
    decode.int,      // age
  )
  use #(_, name, age) <- decode.then(decoder(d))
  Ok(Person(name, age))
}
```

The `process.select_record/4` function in `gleam_erlang` is the intended mechanism for receiving raw Erlang-style tuple messages:

```gleam
// Select for {mytag, field1} messages from non-Gleam processes:
let selector =
  process.new_selector()
  |> process.select_record(
       tag: atom.create("mytag"),
       fields: 1,
       mapping: fn(dyn) {
         // decode the Dynamic here
         todo
       }
     )
```

### 2.4 PIDs and Processes at the Boundary

`gleam/erlang/process.Pid` is an opaque type wrapping the Erlang PID. You can send to it and spawn from it, but you cannot pattern-match on it in Gleam.

```gleam
import gleam/erlang/process

// Self PID
let me: Pid = process.self()

// Spawn a linked process
let child: Pid = process.spawn(fn() {
  io.println("running in child")
})

// Typed Subject - the idiomatic Gleam IPC pattern
// Subject wraps a PID + a unique reference tag
let subject: Subject(String) = process.new_subject()
process.send(subject, "hello")
let msg = process.receive(subject, within: 1000)

// Sending to a raw Erlang PID from outside Subject system:
// You must use Erlang FFI - there's no direct Gleam API for raw pid send
@external(erlang, "erlang", "send")
fn raw_send(pid: Pid, message: a) -> a
```

### 2.5 Gleam Module Name Mangling

Gleam uses `@` as separator. Module `my_app/router` compiles to the Erlang module atom `my_app@router`. This matters for:

```erlang
% Erlang calling Gleam:
my_app@router:handle(Request).

% The @ is a valid atom character but unusual — Erlang code needs quoting:
'my_app@router':handle(Request).
```

Nested modules: `my_app/http/router` → `my_app@http@router`.

From Erlang calling a Gleam module directly:
```erlang
% Calling gleam's stdlib list module:
gleam@list:map(List, Fun).
gleam@int:to_string(42).
```

### 2.6 How Gleam Publishes for Erlang Callers

Gleam exports all `pub fn` functions. The types visible to Erlang callers are the underlying BEAM terms — Gleam's type system is erased at compile time exactly like Erlang's.

Gleam custom types compile to tagged tuples:
```gleam
pub type Shape {
  Circle(radius: Float)
  Rectangle(width: Float, height: Float)
}
```

At BEAM level:
```erlang
{circle, 1.0}            % Circle(radius: 1.0)
{rectangle, 2.0, 3.0}   % Rectangle(width: 2.0, height: 3.0)
```

Erlang code can construct and pattern-match these directly, but has no compile-time safety.

### 2.7 The gleam_erlang Stdlib Wrapper

`gleam_erlang` is a thin typed wrapper over BEAM primitives. It provides:

| Gleam Module | Wraps |
|---|---|
| `gleam/erlang/atom` | atom table operations |
| `gleam/erlang/process` | processes, PIDs, Subjects, Selectors |
| `gleam/erlang/charlist` | `List(Int)` ↔ Erlang charlists |
| `gleam/erlang/node` | distributed Erlang nodes |
| `gleam/erlang/port` | Erlang ports |
| `gleam/erlang/reference` | `make_ref()` |
| `gleam/erlang/application` | OTP application API |

The `Subject(msg)` / `Selector(msg)` design is particularly important — it is the typed IPC layer that Gleam overlays on raw Erlang mailboxes. A Subject is internally `{reference(), pid()}` — a unique reference plus the owner PID. Sending to a Subject wraps the message: `{ref, actual_message}`. This means Gleam-to-Gleam communication uses a message format Erlang processes won't accidentally receive.

### 2.8 Gleam Interop Limitations

- **No OTP behaviour macros**: Gleam has no `use GenServer`. You must FFI into `:gen_server` directly or use community libraries like `gleam_otp`.
- **No Erlang record syntax**: Always tuple decomposition via `Dynamic`.
- **No atom literals**: Cannot write `:ok` — must use `atom.create("ok")` or define constants.
- **No process dictionary**: Gleam has no access to the Erlang process dictionary.
- **No receive clause pattern matching on arbitrary shapes**: Must use `Selector` with pre-registered handlers.
- **No `catch` / `try..catch` on arbitrary Erlang exception classes**: `gleam_erlang` exposes `ExitReason` but catching raw Erlang errors requires FFI.

## 3. LFE (Lisp Flavoured Erlang) Interop

LFE is the minimal-friction reference case: it is essentially Erlang with a Lisp syntax. The interop story is near-zero friction because LFE compiles to the same Erlang Abstract Format that Erlang itself uses.

### 3.1 Calling Erlang from LFE

```lisp
;; LFE syntax — module:function(args) becomes (module:function args)
(lists:sort '(3 2 1))
;; => (1 2 3)

(io:format "Hello ~s~n" '("world"))

(:erlang.make_ref)

;; Guards work identically to Erlang
(defun safe-head
  ([(h . _)] (when (is_list h)) h)
  ([_] undefined))
```

### 3.2 Module Naming

LFE module names are unmangled atoms — `(defmodule my-module ...)` produces `my-module.beam`. Erlang calls it as `my-module:function()`. Hyphens in module names are valid Erlang atoms.

```lisp
;; LFE module:
(defmodule my-lfe-lib
  (export (greet 1)))

(defun greet (name)
  (lists:concat '("Hello, " name)))
```

```erlang
% Erlang calling LFE:
my-lfe-lib:greet("Alice").
% This requires quoting in Erlang if the atom contains hyphens:
'my-lfe-lib':greet("Alice").
```

### 3.3 LFE Records

LFE has Erlang-compatible record syntax as macros:

```lisp
;; Define a record (same as Erlang's -record)
(defrecord person
  name
  (age 0))

;; Create
(let ((p (make-person name "Alice" age 30)))
  (person-name p))    ;; => "Alice"

;; At BEAM level: {person, "Alice", 30}
;; Identical to Erlang's #person{name="Alice", age=30}
```

This is the key advantage of LFE: **record syntax that round-trips perfectly with Erlang records**. The record is just syntactic sugar over tuples, and LFE's macros expand identically to Erlang's preprocessor.

### 3.4 OTP Behaviours in LFE

```lisp
(defmodule my-server
  (behaviour gen_server)
  (export (start_link 0)
          (init 1)
          (handle_call 3)
          (handle_cast 2)
          (handle_info 2)
          (terminate 2)
          (code_change 3)))

(defun start_link ()
  (gen_server:start_link `#(local ,(MODULE)) (MODULE) '() '()))

(defun init (args)
  `#(ok 0))

(defun handle_call (request from state)
  (case request
    ('get `#(reply ,state ,state))
    (_ `#(reply unknown ,state))))
```

The `behaviour` declaration is the same Erlang attribute, and the callback module `(MODULE)` resolves to the current module atom. Erlang supervisors supervise LFE gen_servers transparently.

## 4. Hamler (Haskell on BEAM)

Hamler is less mature and less documented than the others. The key design decisions and impedance mismatches:

### 4.1 Type System Mismatch

Haskell's type system (type classes, higher-kinded types, lazy evaluation by default) maps poorly to BEAM's strict-evaluation, dynamic-dispatch runtime:

- **Type classes** compile to dictionary-passing — Hamler passes implicit dictionaries as extra arguments, invisible from Erlang callers
- **Algebraic data types** compile to tagged tuples, same as Gleam
- **Lazy evaluation**: Hamler uses **strict evaluation** (unlike GHC Haskell) because BEAM's scheduler doesn't support thunks natively
- **Monads**: `IO` monad compiles to direct BEAM side-effect calls — the monad wrapper is erased at codegen

### 4.2 Hamler Module Naming

Hamler uses `.` separator, similar to Erlang modules with dots. `Data.List` maps to `Data.List` atom. This is a valid Erlang atom that requires quoting: `'Data.List':sort(L)`.

### 4.3 Interop Approach

Hamler uses a foreign import mechanism similar to GHC's FFI:

```haskell
-- Hamler FFI syntax (from Hamler docs/source)
foreign import erlang_module_function :: Type -> Type
```

Type mappings:
- `Integer` → Erlang integer
- `Float` → Erlang float
- `Atom` → Erlang atom (special type, not first-class)
- `Binary` → Erlang binary
- `[a]` → Erlang list (proper)
- `Tuple` types → Erlang tuples
- `Pid` → Erlang pid
- `Fun` → Erlang fun

The Haskell `String` = `[Char]` impedance mismatch is the primary problem: Hamler must either use `Binary` (Erlang binaries) or `[Char]` (charlists) for string interop, mirroring the exact same problem Elixir has.

## 5. BEAM External Term Format (ETF)

### 5.1 Wire Format Overview

Every ETF message starts with byte `131` (0x83) as version magic, followed by tag+data:

```
131 | Tag | Data
```

For distributed messages with a distribution header, the `131` byte is omitted from each term (implied by the header).

### 5.2 Atom Encoding (Critical for KorE)

Since OTP 20, atoms are always UTF-8 in distribution:

| Tag | Byte | Format |
|---|---|---|
| `ATOM_UTF8_EXT` | 118 | 2-byte length + UTF-8 bytes (max 255 chars) |
| `SMALL_ATOM_UTF8_EXT` | 119 | 1-byte length + UTF-8 bytes |
| `ATOM_CACHE_REF` | 82 | 1-byte index into atom cache |
| `ATOM_EXT` (deprecated) | 100 | Latin-1, still decoded |
| `SMALL_ATOM_EXT` (deprecated) | 115 | Latin-1, still decoded |

The **atom cache** is crucial for performance: the distribution header maintains a cache of 2048 atoms (8 segments × 256). Atoms seen before are sent as 1-byte cache references rather than re-encoding the string. KorE should be aware that:

1. Frequently-sent atom values get cached automatically
2. The cache is per-connection, not global
3. New connections reset the cache

### 5.3 Key Term Encodings

```
Integer (small, 0-255):   97 | value
Integer (signed 32-bit):  98 | big-endian-4-bytes
Float (IEEE 754):         70 | 8-byte big-endian
Nil (empty list []):      106
Binary:                   109 | 4-byte-length | bytes
Small tuple (≤255 elems): 104 | arity-1-byte | elements
Large tuple:              105 | arity-4-bytes | elements
Map:                      116 | arity-4-bytes | key1 val1 key2 val2 ...
List:                     108 | length-4-bytes | elements | tail
String (list of bytes):   107 | length-2-bytes | bytes  (optimization for byte lists)
Pid:                      88  | node-atom | id-4-bytes | serial-4-bytes | creation-4-bytes
Reference:                90  | len-2-bytes | node-atom | creation-4-bytes | id-words
Fun:                      112 | size | arity | uniq-16-bytes | index | numfree | ...
Bignum (small):           110 | n-1-byte | sign | digits
Bignum (large):           111 | n-4-bytes | sign | digits
```

### 5.4 How This Affects KorE Cross-Language Data Passing

When a KorE process sends a message to an Erlang process via distributed Erlang:

1. KorE terms are serialized to ETF on the KorE node
2. Transmitted over the distribution channel
3. Deserialized on the receiving node

The receiving node doesn't know or care what language produced the ETF. All BEAM languages are equal at this level.

**Critical constraint**: KorE must produce valid ETF. The atom size limit (255 **characters**, not bytes — in UTF-8 that can be up to 1020 bytes on wire) applies to every atom KorE creates. Kotlin identifiers that become BEAM module names or atoms must be truncated or hashed if they exceed 255 characters.

### 5.5 RECORD_EXT (OTP 29, new)

OTP 29 introduced `RECORD_EXT` (tag 67) — a native record encoding that carries field names. This is opt-in and not yet widely used. KorE should be aware it exists but should not rely on it for OTP compatibility.

## 6. Critical Boundary Problems

### 6.1 Atom Table Limits and GC

**Historical limit**: 1,048,576 atoms (1M). Since OTP 26, the table is dynamically sized — but growth has limits and the VM will crash with `atom table overflow` if too many unique atoms are created.

**Atoms are never garbage collected.** Once created, an atom lives until the VM shuts down. This is the single most dangerous property for a language like KorE that might auto-generate atoms from Kotlin identifiers.

Concrete danger scenarios for KorE:
```kotlin
// BAD: if KorE converts arbitrary strings to atoms for map keys
fun toErlangMap(m: Map<String, Any>): ErlangMap {
    return m.mapKeys { atom(it.key) }  // Each unique key = one atom forever
}

// BAD: process registry with user-supplied names
fun register(name: String, pid: Pid) {
    erlang.register(atom(name), pid)  // User input → atoms = VM bomb
}

// GOOD: use binaries as map keys when keys are dynamic
// GOOD: use atom.get(name) which fails if atom doesn't exist
// GOOD: intern atoms at compile time only
```

Check atom count:
```erlang
erlang:system_info(atom_count).    % current count
erlang:system_info(atom_limit).    % max (default 1M, configurable with +t)
```

KorE design recommendation: KorE should have **two atom tiers**:
1. **Compile-time atoms**: KorE identifiers that become atoms, safe because fixed at compile time
2. **Dynamic strings**: Map to Erlang binaries, not atoms

### 6.2 String/Binary/Charlist Representation War

This is the biggest day-to-day interop pain point in the BEAM ecosystem:

| Language | "String" type | BEAM representation |
|---|---|---|
| Erlang | "hello" | `[104,101,108,108,111]` — charlist (list of integers) |
| Erlang | `<<"hello">>` | binary |
| Elixir | `"hello"` | UTF-8 binary (`<<104,101,108,108,111>>`) |
| Elixir | `'hello'` | charlist (deprecated as string, valid as atom syntax) |
| Gleam | `"hello"` | UTF-8 binary |
| LFE | `"hello"` | charlist (Erlang-compatible) |

When Elixir calls Erlang's `:string` module (which expects charlists), it must convert:

```elixir
# Erlang's string module expects charlists:
:string.to_upper('hello')           # => 'HELLO' (charlist in, charlist out)
:string.to_upper("hello")           # => ERROR: "hello" is binary, not charlist

# Must convert:
"hello"
|> String.to_charlist()             # => [104, 101, 108, 108, 111]
|> :string.to_upper()               # => [72, 69, 76, 76, 79]
|> List.to_string()                 # => "HELLO"

# Elixir's own String module uses binaries throughout, which is better
String.upcase("hello")              # => "HELLO"
```

For KorE, the design decision: **Kotlin `String` should map to Erlang binary, not charlist.** Charlists are a historical artifact. Any Erlang function that requires charlists should be wrapped to do the conversion at the boundary. Functions returning charlists should be wrapped to convert to binary before returning to KorE code.

### 6.3 Record Access from Outside the Defining Module

Erlang records are **macros expanded at compile time**. The field positions are baked into the calling module's bytecode at compile time. There is no runtime record descriptor (until OTP 29's `RECORD_EXT`, which is optional).

```erlang
% Module a.erl defines:
-record(point, {x, y}).

% Module b.erl CANNOT do:
b_function(P) ->
    P#point.x.   % COMPILE ERROR: record 'point' not defined in b.erl
```

The standard solution is to put the record in a `.hrl` header file:

```erlang
% point.hrl
-record(point, {x, y}).

% a.erl
-include("point.hrl").
% b.erl  
-include("point.hrl").
```

This means: **if an Erlang library uses records internally and doesn't expose accessor functions, you cannot safely access those fields from another language without knowing the field layout at compile time.**

For KorE interop, the correct approach is:
1. Use the library's accessor functions if provided
2. Write a thin Erlang shim that includes the `.hrl` and exposes the fields as functions
3. Access by raw tuple index (fragile, breaks on record changes)
4. Use OTP 29's `erlang:record_info/2` if available and the record is exported

Example shim:
```erlang
% kore_inet_shim.erl
-include_lib("kernel/include/inet.hrl").
-export([get_inet_address/1, get_inet_port/1]).

get_inet_address(#hostent{h_addr_list = Addrs}) -> Addrs.
get_inet_port(#hostent{h_name = Name}) -> Name.
```

### 6.4 Exception Class Mapping

Erlang has three exception classes, each with completely different semantics:

```erlang
% Three distinct exception classes:
throw(some_value)       % non-local return; always caught by caller's catch
error(badarg)           % programming error; generates stack trace
exit(normal)            % process exit signal; used for OTP lifecycle
```

Caught differently:
```erlang
try Expr of
  Value -> ok
catch
  throw:Reason -> handle_throw(Reason);
  error:Reason -> handle_error(Reason);
  exit:Reason  -> handle_exit(Reason)
end.
```

Elixir maps these as follows:
```elixir
# Erlang throw:X  → Elixir catch :throw, value  (via try/catch)
# Erlang error:X  → Elixir raise RuntimeError (wraps as ErlangError)
# Erlang exit:X   → Elixir catch :exit, reason

try do
  :erlang.error(:badarg)
rescue
  e in ErlangError -> e.original  # => :badarg
end

try do
  :erlang.throw(:my_value)
catch
  :throw, value -> value           # => :my_value
end

try do
  :erlang.exit(:normal)
catch
  :exit, reason -> reason          # => :normal
end
```

Gleam's `ExitReason` type:
```gleam
pub type ExitReason {
  Normal
  Killed
  Abnormal(reason: dynamic.Dynamic)  // covers both error and throw classes
}
```

**KorE design implication**: KorE must decide how to map these three classes to Kotlin exceptions. Recommendation:
- `throw` → checked exception or `Result` type (it's a flow-control mechanism)
- `error` → unchecked exception (programming error)
- `exit` → process lifecycle signal, handled at process/actor level, not as exceptions

When KorE code raises a Kotlin exception that propagates out of a BEAM callback (e.g., GenServer `handle_call`), it will become an `error` class exception with the Kotlin exception as the reason term. OTP supervisors will see it as a crash and may restart the process. This is correct behavior.

### 6.5 Module Naming Conventions and Conflicts

Current landscape of module name namespacing by language:

| Language | Example | Erlang atom |
|---|---|---|
| Erlang | `lists` | `lists` |
| Elixir | `MyApp.Router` | `'Elixir.MyApp.Router'` |
| Gleam | `my_app/router` | `'my_app@router'` |
| LFE | `my-module` | `'my-module'` |
| Hamler | `Data.List` | `'Data.List'` |

For KorE, the recommendation based on prior art:
- Use a language-specific prefix: `KorE.` or `kore@`
- Kotlin packages `com.example.MyClass` → `'kore@com.example.MyClass'` (using `@` as separator)
- Or: `'KorE.com.example.MyClass'` (using `Elixir.`-style prefix)

The `@` approach (Gleam-style) avoids conflicts with Elixir's `'Elixir.'` namespace. The `.` approach (Hamler/Elixir-style) is more readable but risks collision with Elixir if someone names a Kotlin module `Elixir.Something`.

**Recommendation for KorE**: Use `'KorE.'` prefix. This is unambiguous, readable, and mirrors the established Elixir convention. `com.example.MyClass` → `'KorE.com.example.MyClass'`.

### 6.6 Hot Code Reload Across Language Boundaries

BEAM hot code reload is:
1. Load new `.beam` file: `code:load_file(Module)`
2. Old module version runs until all processes exit its current call frame
3. Two versions co-exist briefly (`current` and `old`)
4. Third load purges the `old` version; processes still running old code get killed

The `code_change/3` callback in `gen_server` handles state migration:

```elixir
@impl true
def code_change(old_vsn, state, extra) do
  # Transform state from old format to new format
  new_state = migrate_state(old_vsn, state)
  {:ok, new_state}
end
```

**Cross-language boundary problems with hot reload**:

1. **Record layout changes**: If an Erlang module changes a record definition and hot-reloads, all other modules that include that `.hrl` file and have the old tuple layout baked in will silently misread fields. This is dangerous even in pure Erlang. For KorE, if you've inlined tuple offsets from an Erlang record, hot reload of that Erlang module silently breaks KorE code.

2. **Elixir struct changes**: If `%MyStruct{}` adds a field, existing struct instances in process state won't have the field. Hot reload of the struct module doesn't migrate existing instances. The `code_change` callback must handle this.

3. **KorE class changes**: If a KorE class is the state of a GenServer and the class layout changes (new field), `code_change/3` must transform the old BEAM term representation to the new one. KorE should generate serializable state representations and provide migration hooks.

4. **Distributed hot reload**: Hot reload is per-node. In a multi-node cluster with KorE and Erlang nodes, you can have different versions running on different nodes. Message passing between nodes with mismatched schemas is undefined behavior.

### 6.7 Distribution: Sending KorE Terms to Erlang Nodes

When a KorE process sends a message to an Erlang process on another node, the message goes through:

```
KorE term → ETF serialization → TCP/TLS distribution channel → ETF deserialization → Erlang term
```

The Erlang node receives whatever BEAM terms ETF decoded to. It doesn't know the message came from KorE. This is the beauty of BEAM distribution — **language-transparent at the message level**.

However:

**Atoms**: KorE-generated atom names (from Kotlin identifiers, with `KorE.` prefix) that Erlang has never seen before will be created in the Erlang node's atom table on first receipt. This is by design but contributes to atom table growth on Erlang nodes receiving lots of diverse KorE messages.

**Funs/Closures**: Erlang funs embedded in messages encode their originating module. If you send a fun from a KorE module and an Erlang node tries to call it, it will call back into the KorE module's BEAM code — which works, but requires the KorE `.beam` files to be accessible on the Erlang node (or via remote code loading).

**PIDs**: PIDs encode the originating node. Sending a PID from KorE to Erlang is safe; Erlang can `send/2` to it and the message routes back to the KorE node via distribution.

**References**: Same as PIDs — node-scoped, route correctly across distribution.

## 7. How Kotlin/JVM Handles Native Interop (Reference for KorE)

### 7.1 @JvmStatic, @JvmName, @JvmOverloads

```kotlin
class Config {
    companion object {
        @JvmStatic
        fun load(path: String): Config = TODO()
        // Java: Config.load("path")  (static call)
        // Without @JvmStatic: Config.Companion.load("path")

        @JvmField
        val DEFAULT_TIMEOUT: Int = 5000
        // Java: Config.DEFAULT_TIMEOUT  (direct field)
    }
}

// @JvmName renames the generated JVM method
@JvmName("filterValidStrings")
fun List<String>.filterValid(): List<String> = filter { it.isNotBlank() }
// Without annotation: filterValid(List<String>) — same erasure as List<Int>

// @JvmOverloads generates n overloads for n default parameters
@JvmOverloads
fun connect(host: String, port: Int = 5432, timeout: Int = 5000) {}
// Java sees: connect(String), connect(String,int), connect(String,int,int)

// @Throws declares checked exceptions for Java
@Throws(IOException::class)
fun readFile(path: String): String = File(path).readText()
// Java callers must catch IOException
```

### 7.2 How Kotlin Compiles to JVM Bytecode

```kotlin
// Kotlin top-level functions in file Foo.kt → Java class FooKt
// package org.example, file foo.kt → org.example.FooKt

// @file:JvmName("Foo") renames to org.example.Foo
@file:JvmName("Foo")
package org.example

fun bar() {}  // Java: org.example.Foo.bar()

// Kotlin data class:
data class Point(val x: Int, val y: Int)
// Java sees: constructor, getX(), getY(), component1(), component2(),
//            copy(), equals(), hashCode(), toString()

// Kotlin internal visibility → public in JVM bytecode but name-mangled:
internal fun doInternal() {}
// JVM: doInternal$module_name()  (mangled to deter Java callers)

// Kotlin inline value classes → unboxed at JVM level
@JvmInline
value class Meters(val value: Double)
fun distance(): Meters = Meters(5.0)
// JVM bytecode: distance() returns Double, not Meters
// @JvmExposeBoxed generates a boxed variant for Java callers
```

### 7.3 Impedance Mismatches Kotlin Solved (KorE Lessons)

| Problem | Kotlin's JVM Solution | KorE's BEAM Solution |
|---|---|---|
| Null safety | `@Nullable`/`@NotNull` annotations; runtime NPE checks on boundaries | Return `{ok, Value}` or `{error, Reason}` tuples; use `Result` type |
| No static methods | `@JvmStatic` in companion objects | N/A — BEAM modules are collections of functions |
| Name mangling of module-level funs | `@file:JvmName` | `@BEAMName` annotation to control Erlang module name |
| Default parameter overloads | `@JvmOverloads` | Emit separate arities (Erlang/BEAM pattern) |
| Checked exceptions mismatch | `@Throws` annotation | Map to Erlang error/throw/exit classes explicitly |
| Kotlin-specific type erasure | `@JvmName` to disambiguate | Kotlin generics erase to `Dynamic`/`any()` at BEAM level |
| Generics variance | `@JvmWildcard`, `@JvmSuppressWildcards` | Not applicable — BEAM has no generics at runtime |
| Companion object visibility | `@JvmField`, `@JvmStatic` | Module functions are always plain exported functions |
| Internal visibility | name mangling (`$module`) | Unexported BEAM functions |

**The critical lesson from Kotlin/JVM for KorE**:

Kotlin took the JVM's constraints seriously and provided escape hatches via annotations. Each annotation is an acknowledgement that "the host platform's calling convention differs from Kotlin's model here." KorE should do the same:

- `@ErlangName("module", "function")` — specifies the Erlang module/function name for `@external`-style FFI
- `@BEAMModule("my_module")` — overrides the generated Erlang module atom
- `@ErlangExport` — marks a function as exported to Erlang callers (with appropriate name)
- `@ThrowsErlang(class = :error)` — declares what Erlang exception class this function may raise
- `@NativeAtom("ok")` — declares a compile-time atom literal

## Summary: Key Design Decisions for KorE

1. **Module naming**: `'KorE.com.example.MyClass'` — prefixed, unambiguous, no collision with Elixir or Gleam
2. **String type**: Kotlin `String` = Erlang binary (UTF-8). Never charlist. Wrap Erlang functions that return charlists.
3. **Atom strategy**: Two tiers. Compile-time Kotlin identifiers → atoms. Dynamic strings → binaries. No user-input-to-atom conversion.
4. **Struct/data class interop**: KorE data classes exposed to Elixir should optionally emit `__struct__` maps. Default is tagged tuples (Gleam-style).
5. **Exception mapping**: Three Kotlin exception types mapping to Erlang's three classes. OTP lifecycle (exit) handled at actor level, not as Kotlin exceptions.
6. **Records**: Never inline Erlang record tuple offsets. Always use accessor shims.
7. **Hot reload**: KorE `code_change/3` hooks with explicit state migration. State types should serialize deterministically.
8. **Annotation approach**: Follow Kotlin/JVM's annotation model for platform-specific overrides rather than trying to hide the impedance mismatch.
