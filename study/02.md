#### `lists` — Singly-Linked List Processing

The most-used module in Erlang. All functions are pure. Lists are singly-linked, so prepend is O(1) and append is O(N).

```erlang
lists:map(fun(X) -> X * 2 end, [1,2,3]).               % [2,4,6]
lists:filter(fun(X) -> X rem 2 =:= 0 end, [1..5]).     % [2,4]
lists:foldl(fun(X, Acc) -> X + Acc end, 0, [1,2,3]).   % 6
lists:partition(fun(X) -> X > 3 end, [1,2,3,4,5]).     % {[4,5],[1,2,3]}
lists:zip([1,2,3], [a,b,c]).                            % [{1,a},{2,b},{3,c}]
lists:enumerate([a,b,c]).                               % [{1,a},{2,b},{3,c}]
lists:uniq([1,2,1,3,2]).                                % [1,2,3]
lists:keysort(2, [{a,3},{b,1},{c,2}]).                  % [{b,1},{c,2},{a,3}]
lists:seq(1, 10, 2).                                    % [1,3,5,7,9]
lists:flatmap(fun(X) -> [X, X*2] end, [1,2,3]).        % [1,2,2,4,3,6]
lists:mapfoldl(fun(X, Acc) -> {X*2, Acc+X} end, 0, [1,2,3]).
% {[2,4,6], 6}
```

Full function inventory (grouped):

| Category | Functions |
|---|---|
| Transform | `map/2`, `filtermap/2`, `flatmap/2`, `mapfoldl/3`, `mapfoldr/3` |
| Filter | `filter/2`, `partition/2`, `takewhile/2`, `dropwhile/2` |
| Fold | `foldl/3`, `foldr/3` |
| Search | `member/2`, `search/2`, `any/2`, `all/2`, `keyfind/3`, `keymember/3`, `keysearch/3` |
| Sort | `sort/1,2`, `usort/1,2`, `keysort/2`, `ukeysort/2`, `merge/1,2,3`, `keymerge/3` |
| Slice | `nth/2`, `nthtail/2`, `sublist/2,3`, `split/2`, `splitwith/2`, `droplast/1` |
| Build | `seq/2,3`, `duplicate/2`, `zip/2,3`, `zipwith/3`, `enumerate/1,2,3`, `join/2`, `append/1,2` |
| Unpack | `unzip/1`, `unzip3/1`, `flatten/1,2`, `last/1`, `reverse/1,2` |
| Aggregate | `sum/1`, `max/1`, `min/1`, `foldl/3` |
| Key-tuple ops | `keydelete/3`, `keyreplace/4`, `keystore/4`, `keytake/3`, `keymap/3` |
| Dedup | `uniq/1,2`, `usort/1,2`, `ukeysort/2`, `umerge/1,2,3` |
| Set-like | `subtract/2`, `prefix/2`, `suffix/2` |
| Side effects | `foreach/2` |

#### `maps` — Hash Map (Primary Key-Value Store)

Implemented as HAMT. O(1) average. Keys compared with `=:=` (strict). Default since OTP 17; prefer over `dict`.

```erlang
M = #{name => alice, age => 30},
maps:get(name, M),                                    % alice
maps:get(missing, M, default),                        % default
maps:find(name, M),                                   % {ok, alice}
maps:put(email, "alice@example.com", M),
maps:update_with(age, fun(V) -> V + 1 end, M),
maps:remove(age, M),
maps:filter(fun(_K, V) -> is_integer(V) end, M),
maps:map(fun(_K, V) -> V end, M),
maps:fold(fun(K, V, Acc) -> [{K,V}|Acc] end, [], M),
maps:merge(M, #{city => london}),
maps:with([name], M),                                 % #{name => alice}
maps:without([age], M),
maps:to_list(M),
maps:from_list([{a,1},{b,2}]),
maps:groups_from_list(fun(X) -> X rem 2 end, [1,2,3,4,5]).
% #{0 => [2,4], 1 => [1,3,5]}
```

| Category | Functions |
|---|---|
| Read | `get/2,3`, `find/2`, `is_key/2`, `keys/1`, `values/1`, `size/1` |
| Write | `put/3`, `update/3`, `update_with/3,4`, `remove/2`, `take/2` |
| Bulk | `merge/2`, `merge_with/3`, `intersect/2`, `intersect_with/3`, `with/2`, `without/2` |
| Transform | `map/2`, `filter/2`, `filtermap/2`, `fold/3`, `foreach/2` |
| Convert | `to_list/1`, `from_list/1`, `from_keys/2`, `groups_from_list/2,3` |
| Iterate | `iterator/1,2`, `next/1` |

#### `sets` / `ordsets` / `gb_sets` — Set Types

Three implementations with the same logical interface but different performance characteristics.

| Module | Backing | Key comparison | Ordered? | Lookup |
|---|---|---|---|---|
| `sets` | HAMT (v2) | `=:=` | No | O(1) avg |
| `ordsets` | Sorted list | `==` | Yes | O(N) |
| `gb_sets` | AVL tree | `==` | Yes | O(log N) |

```erlang
%% sets — fast, unordered
S = sets:from_list([3,1,4,1,5]),
sets:to_list(sets:union(S, sets:from_list([6,7]))),

%% ordsets — sorted list, numeric coercion in equality
ordsets:to_list(ordsets:from_list([3,1,4,1,5])), % [1,3,4,5]

%% gb_sets — ordered, range queries
G = gb_sets:from_list([5,3,8,1,9]),
gb_sets:smallest(G),    % 1
gb_sets:largest(G),     % 9
I = gb_sets:iterator_from(4, G),
gb_sets:next(I).        % {5, ...}
```

Common interface: `new/0`, `add_element/2`, `del_element/2`, `is_element/2`, `is_empty/1`, `size/1`, `union/1,2`, `intersection/1,2`, `subtract/2`, `is_subset/2`, `is_disjoint/2`, `from_list/1`, `to_list/1`, `filter/2`, `map/2`, `fold/3`

#### `gb_trees` — Ordered Key-Value Store

AVL tree map. O(log N) all ops. Keys compared by term order (`<`). Best when you need sorted keys or range iteration.

```erlang
T = gb_trees:from_orddict([{a,1},{b,2},{c,3}]),
gb_trees:get(b, T),        % 2
gb_trees:to_list(T),       % [{a,1},{b,2},{c,3}]
gb_trees:smallest(T),      % {a,1}
gb_trees:largest(T),       % {c,3}
```

---

#### `queue` — Double-Ended FIFO Queue

Amortized O(1) enqueue and dequeue from both ends.

```erlang
Q = queue:from_list([1,2,3,4,5]),
{{value, 1}, Q2} = queue:out(Q),
{{value, 5}, Q3} = queue:out_r(Q),
queue:in(6, Q),
queue:peek(Q).  % {value, 1}
```

---

#### `array` — Sparse Functional Array

O(log N) access. Supports sparse indices with a default value.

```erlang

A2 = array:set(1000, value, A),
array:sparse_to_orddict(A2).  % [{1000, value}]
```

#### `proplists` — Property/Option Lists

### Group 2: String and Binary

---

#### `string` — Unicode String Processing

Handles both string/0 (codepoint list) and binary/0. Grapheme-cluster aware.

```erlang
string:length("héllo"),              % 5 (grapheme clusters)
string:to_upper("héllo"),            % "HÉLLO"
string:split("a,b,,c", ",", all),   % ["a","b","","c"]
string:trim("  hello  "),            % "hello"
string:find("hello world", "world"), % "world"
string:pad("hi", 10),               % "hi        "
string:jaro_similarity("kitten", "sitting"). % ~0.746
```

---

#### `binary` — Binary Data

Low-level, efficient due to binary sharing.

```erlang
binary:split(<<"hello world">>, <<" ">>),       % [<<"hello">>,<<"world">>]
binary:match(<<"hello world">>, <<"world">>),   % {6,5}
binary:part(<<"hello world">>, 6, 5),           % <<"world">>
binary:replace(<<"hello">>, <<"hello">>, <<"bye">>),
binary:encode_unsigned(1024),                   % <<4,0>>
```

---

#### `unicode` — Encoding Conversion

```erlang
unicode:characters_to_binary("héllo"),          % <<"héllo"/utf8>>

```

### Group 6: ETS / Storage

---

#### `ets` — In-Memory Term Storage

Shared across processes on the same node. O(1) average for `set`/`bag`.

Table types: `set`, `ordered_set`, `bag`, `duplicate_bag`

```erlang
T = ets:new(cache, [set, public, named_table]),
ets:insert(T, {alice, 30}),
ets:lookup(T, alice),               % [{alice,30}]
ets:lookup_element(T, alice, 2),    % 30
ets:update_counter(T, counter, 1),  % atomic increment
ets:first(T), ets:next(T, alice),
ets:tab2list(T),
ets:select(T, MatchSpec),
ets:info(T).
```

Creation options: `named_table`, `public`/`protected`/`private`, `{keypos, N}`, `{heir, Pid, Data}`, `compressed`, `{read_concurrency, true}`, `{write_concurrency, true}`

---

#### `dets` — Disk-Based Term Storage

ETS-compatible API but persistent. Max 2GB per file.

```erlang
{ok, Ref} = dets:open_file(store, [{file,"/tmp/data.dets"},{type,set}]),
dets:insert(Ref, {user, alice, 30}),
dets:sync(Ref),
dets:close(Ref).
```

---

#### `mnesia` — Distributed Database

Transactions, replication, in-memory/disk tables.

```erlang
mnesia:create_schema([node()]),
mnesia:start(),
mnesia:create_table(person, [{attributes, record_info(fields, person)},
                              {disc_copies, [node()]}]),
mnesia:transaction(fun() ->
  mnesia:write(#person{name=alice, age=30}),
  mnesia:read(person, alice)
end).
```

#### `persistent_term` — Global Read-Optimized Terms

```erlang

```

### Group 1: Collections

---

#### `kotlin.collections` — Core Collection Types

Kotlin has immutable read-only interfaces and mutable counterparts.

| Type | Read-only | Mutable |
|---|---|---|
| Ordered | `List<T>` | `MutableList<T>` |
| Unordered | `Set<T>` | `MutableSet<T>` |
| Key-Value | `Map<K,V>` | `MutableMap<K,V>` |

```kotlin
// Creation
val list = listOf(1, 2, 3)
val mList = mutableListOf(1, 2, 3)
val map = mapOf("a" to 1, "b" to 2)
val mMap = mutableMapOf("a" to 1)
val set = setOf(1, 2, 3)
val array = arrayOf(1, 2, 3)

// Concrete implementations
val linked = LinkedHashMap<String, Int>()    // insertion-ordered
val sorted = TreeMap<String, Int>()          // sorted
val hash = HashMap<String, Int>()            // hash, no order
```

**Transform extensions:**

```kotlin
listOf(1,2,3).map { it * 2 }               // [2,4,6]
listOf(1,2,3).flatMap { listOf(it, it*2) } // [1,2,2,4,3,6]
listOf(1,2,3,4).filter { it % 2 == 0 }    // [2,4]
listOf(1,2,3).mapNotNull { if(it>1) it else null } // [2,3]
listOf(listOf(1,2), listOf(3,4)).flatten() // [1,2,3,4]
```

**Fold/Reduce:**

```kotlin
listOf(1,2,3,4,5).fold(0) { acc, x -> acc + x }    // 15
listOf(1,2,3).reduce { acc, x -> acc + x }           // 6
listOf(1,2,3).runningFold(0) { acc, x -> acc + x }  // [0,1,3,6]
listOf(1,2,3).scan(0) { acc, x -> acc + x }         // [0,1,3,6]
```

**Grouping and partitioning:**

```kotlin
listOf(1,2,3,4,5).groupBy { it % 2 }        // {1:[1,3,5], 0:[2,4]}
listOf(1,2,3,4,5).partition { it > 3 }      // ([4,5], [1,2,3])
listOf(1,2,3,4,5).chunked(2)                // [[1,2],[3,4],[5]]
listOf(1,2,3,4,5).windowed(3)               // [[1,2,3],[2,3,4],[3,4,5]]
listOf(1,2,3,4,5).windowed(3, step=2)       // [[1,2,3],[3,4,5]]
listOf(1,2,3).associate { it to it*it }     // {1:1, 2:4, 3:9}
listOf("a","ab","b").groupingBy { it[0] }.eachCount() // {a:2, b:1}
```

**Search:**

```kotlin
listOf(1,2,3).any { it > 2 }               // true
listOf(1,2,3).all { it > 0 }               // true
listOf(1,2,3).none { it > 5 }              // true
listOf(1,2,3).count { it > 1 }             // 2
listOf(1,2,3).find { it > 1 }              // 2
listOf(1,2,3).findLast { it > 1 }          // 3

listOf(1,2,3).firstOrNull { it > 5 }       // null
listOf(1,2,3).indexOf(2)                   // 1
listOf(1,2,3).contains(2)                  // true (also: 2 in list)
```

**Aggregation:**


**Sorting:**

**Slice/Take/Drop:**


### Group 2: Scope Functions

These are one of Kotlin's most important DX features. They change the context (`this`/`it`) of a lambda.

| Function | Receiver | Returns | Purpose |
|---|---|---|---|
| `let` | `it` (arg) | lambda result | Transform or null-check |
| `run` | `this` | lambda result | Object config + result |
| `with` | `this` (not extension) | lambda result | Multiple ops on object |
| `apply` | `this` | receiver | Object construction/config |
| `also` | `it` (arg) | receiver | Side effects (logging, debug) |

## Part 3: Mapping Strategies — Stdlib Design for KorE

---

### 3.1 The Collections API

**The problem:** Erlang's collections are module-prefixed (`lists:map`, `maps:get`). Kotlin's are method-chained extensions (`list.map { }`). These are fundamentally different invocation styles.

**Option A — Pure Kotlin Method Chain (Recommended)**

Expose all collections as KorE types with chainable extension functions. The BEAM native types (list, map, binary) are wrapped at the language boundary.

```kore
// All operations are extensions on the collection type
val evens = listOf(1, 2, 3, 4, 5)
    .filter { it % 2 == 0 }
    .map { it * it }
    .sorted()

val grouped = users
    .groupBy { it.role }
    .mapValues { it.sortedBy { u -> u.name } }
```

This compiles down to `lists:filter`, `lists:map`, `lists:sort` etc. The developer never sees the Erlang module names. This is exactly what Elixir does with the `Enum` module — a single namespace for all collection operations.

Pros: Familiar to Kotlin/Java devs. Clean business logic. IDE-friendly.
Cons: Wrapper overhead (minimal on BEAM due to binary sharing). Hides BEAM idioms from new learners.

---

**Option B — Dual API (Functional + Chained)**

Expose both styles. Module-style for performance-critical/low-level code, chain-style for business logic.

```kore
// Chain style (default)
users.filter { it.active }.map { it.name }

// Module style (explicit, for when you need it)
Lists.filter(users) { it.active }
Maps.merge(m1, m2)
```

This is how Elixir works — `Enum.map` is the explicit style; pipe operator `|>` provides chaining. Gleam does the same.

Pros: Gives power users access to raw module semantics.
Cons: Two ways to do the same thing can split codebases.

---

**Option C — Pipe Operator as Primary Chaining Mechanism**

Instead of Kotlin's dot-chain, use a `|>` pipe operator as the canonical way to chain. Feels more BEAM-native.

```kore
users
    |> filter { it.active }
    |> map { it.name }
    |> sortedBy { it }
```

This is Elixir and Gleam's approach. It maps directly to Erlang function call chaining.

Pros: BEAM-native feel. No wrapping needed — it's just `lists:filter(lists:map(...))` rewritten left-to-right.
Cons: Less familiar to Kotlin developers. Requires the developer to know which module each function lives in.

---

**My recommendation: Option A as default, Option C as optional syntax sugar.**

Use Kotlin's extension function chain as the primary DX. Implement `|>` as an optional operator (Scala 3 has it, Kotlin doesn't natively). Kotlin developers feel at home; Erlang/Elixir developers get their pipe operator too.

---

### 3.2 Scope Functions — Let, Apply, Also, Run, With

**The problem:** Kotlin's scope functions (`let`, `apply`, `also`, `run`, `with`) are idioms for transforming values, building objects, and adding side effects inline. Erlang has no equivalent — you just bind variables.

**Option A — Keep Kotlin Scope Functions As-Is (Recommended)**

Since KorE has a Kotlin-flavored syntax, `let`, `apply`, `also`, `run`, `with` are first-class. They compile down to immediate function application.

```kore
val connection = DbConnection()
    .apply {
        host = "localhost"
        port = 5432
        timeout = 5000
    }

val result = payload
    .also { logger.debug("Processing: $it") }
    .let { transform(it) }
    .takeIf { it.isValid() }
    ?: throw ValidationError("invalid payload")
```

This is pure syntax — zero BEAM overhead. A `.apply { }` block is just a function that takes a receiver and returns it. `let` is `fun <T, R>(T, (T) -> R): R`. Both compile to trivial BEAM function calls.

---

**Option B — Pipe Operator Instead of Let**

Instead of `.let { }`, use `|>` for transformation and drop the other scope functions.

```kore
payload
    |> tap { logger.debug("Processing: $it") }    // = also
    |> transform(_)
    |> validate(_)
```

The `tap` function (from Ruby/Elixir) does what `also` does: side effect, return original. This is cleaner in a pipe-heavy style.

Pros: Consistent with pipe-first philosophy.
Cons: Loses the distinction between `apply` (builder pattern) and `let` (transform). Enterprise Kotlin devs will miss `apply`.

---

**Option C — Elixir-style with/2 for Error Pipelines**

For error-handling pipelines, Elixir's `with` macro chains operations that return `{:ok, val} | {:error, reason}`. This is different from Kotlin's `with` but extremely powerful for BEAM.

```kore
// KorE with-pipeline (inspired by Elixir's with)
val result = with {
    val user  <- findUser(userId)        // unwraps Result<User>
    val order <- createOrder(user)       // unwraps Result<Order>
    val _     <- sendConfirmation(order) // unwraps Result<Unit>
    order
} catch {
    UserNotFound -> handleMissing()
    OrderFailed  -> handleOrderError()
}
```

This is the most powerful option for business logic that involves multiple steps that can each fail.

Pros: Natural error handling for BEAM-style code. Eliminates nested `if/else` or `try/catch` chains.
Cons: Introduces new semantics that Kotlin developers don't know. Requires a new mental model.

---

**My recommendation: Keep all five Kotlin scope functions (Option A). Additionally provide `with`-pipeline (Option C) as a separate, named construct (perhaps `pipeline { }` to avoid name conflict with Kotlin's `with`). Do not replace scope functions with pipes — both can coexist.**

---

### 3.3 Functional Chaining — Map, Filter, Fold

**The problem:** Erlang uses `lists:map(Fun, List)`. Kotlin uses `list.map { }`. KorE must pick a canonical style.

**Option A — Extension Functions on BEAM Types**

`list.map`, `map.filter`, `binary.split` as first-class extension functions on native BEAM types. This is the Elixir approach with more Kotlin syntax.

```kore
val doubled = [1, 2, 3].map { it * 2 }   // compiles to lists:map
val filtered = myMap.filter { _, v -> v > 0 }  // compiles to maps:filter
```

Pros: Simplest for the developer. One way to do things.
Cons: Type-inference heavy. Need to decide: does `[1,2,3]` return a KorE `List` type or an Erlang list?

---

**Option B — Separate KorE Collection Types**

KorE has its own `List<T>`, `Map<K,V>`, `Set<T>` types that wrap BEAM structures and provide the extension API. Interop with raw Erlang is explicit.

```kore
val koreList: List<Int> = listOf(1, 2, 3)  // KorE type
val erlList: ErlList    = erlang.list([1,2,3])  // raw BEAM

koreList.map { it * 2 }         // KorE API
erlList.toList().map { it * 2 } // convert first
```

Pros: Clean type system. No ambiguity.
Cons: Interop with Erlang libraries requires explicit conversion — friction when calling OTP APIs.

---

**Option C — Transparent Unification**

KorE's collection types compile to BEAM native types. `List<T>` IS an Erlang list at runtime. No wrapper. Extension functions are compile-time sugar that emit `lists:*` calls directly.

```kore
val xs: List<Int> = [1, 2, 3]   // this IS an Erlang list
xs.map { it * 2 }               // compiles to: lists:map(fun(X) -> X*2 end, xs)
```

This is the Gleam approach. Zero overhead. Full Erlang interop.

Pros: Zero overhead. Erlang libraries work directly.
Cons: Type system is constrained by what BEAM can represent. Harder to provide Kotlin-specific features like lazy evaluation.

---

**My recommendation: Option C for core collection types (List, Map, Set, Binary), Option A's API surface. Lazy sequences (Kotlin's `Sequence`) map to Erlang generators/comprehensions or a custom lazy list structure. This gives zero-overhead interop with full Kotlin-style API.**

---

### 3.4 Sequences and Lazy Evaluation

**The problem:** Kotlin's `Sequence<T>` is lazy. Erlang has lazy evaluation via generators and list comprehensions, but no standard lazy sequence type.

**Option A — Map Sequence to Erlang Generators**

```kore
// KorE
val fib = generateSequence(Pair(0, 1)) { (a, b) -> Pair(b, a + b) }
    .map { it.first }
    .take(10)
    .toList()
```

Compiles to a recursive function that generates elements on demand. Not a persistent data structure — evaluated once.

---

**Option B — Use Erlang's List Comprehensions**

Expose list comprehensions as a KorE `sequence { }` builder.

```kore
val evens = sequence {
    for (x in 1..100) {
        if (x % 2 == 0) yield(x)
    }
}
// compiles to: [X || X <- lists:seq(1,100), X rem 2 =:= 0]
```

Pros: Direct mapping to native BEAM construct. No overhead.
Cons: Not truly lazy — list comprehensions evaluate eagerly.

---

**Option C — Lazy List as a KorE Primitive**

Implement a proper lazy list type using BEAM processes or closures.

```kore
// Each element is a closure returning {head, tail}
val naturals: LazyList<Int> = lazyList { n -> n } // generates 1,2,3,...
```

Pros: Truly lazy. Can model infinite streams.
Cons: Closure overhead. Not idiomatic BEAM.

---

**My recommendation: Option A for `generateSequence` and finite lazy pipelines (maps to tail-recursive functions). Option B for comprehension-style builders. Don't implement Option C — BEAM already has processes for true streams; use them instead (this bridges to Session 4's Flow/GenStage discussion).**

---

### 3.5 Error Handling — Result vs Exceptions vs Tagged Tuples

**The problem:** Erlang uses `{ok, Value} | {error, Reason}` tagged tuples everywhere. Kotlin uses exceptions and `Result<T>`. These are very different mental models.

**Option A — Kotlin Result<T> as the Surface API**

KorE functions return `Result<T>`. Under the hood, `{ok, V}` becomes `Result.success(V)` and `{error, R}` becomes `Result.failure(reason)`. Erlang OTP functions are automatically wrapped.

```kore
fun readFile(path: String): Result<String> =
    runCatching { File.readFile(path) }  // wraps {ok,_} | {error,_}

readFile("/etc/hostname")
    .map { it.trim() }
    .onSuccess { println("Host: $it") }
    .onFailure { println("Error: $it") }
```

Pros: Familiar to Kotlin developers. Composable with `map`, `flatMap`.
Cons: Hides BEAM's supervisory error philosophy. "Let it crash" becomes unnatural.

---

**Option B — Keep Tagged Tuples, Add Pattern Matching Syntax**

KorE uses BEAM's `{ok, v} | {error, reason}` natively. Pattern matching handles both cases cleanly.

```kore
when (val r = readFile("/etc/hostname")) {
    is Ok  -> println("Host: ${r.value}")
    is Err -> println("Error: ${r.reason}")
}
```

Where `Ok` and `Err` are KorE-defined sealed classes that pattern-match against `{ok, _}` and `{error, _}` tuples transparently.

Pros: Stays true to BEAM. No wrapping overhead. OTP interop is natural.
Cons: Less ergonomic for Kotlin developers who expect `Result`.

---

**Option C — Dual Mode**

Both `Result<T>` and `{ok, _} | {error, _}` are valid. Provide conversion functions.

```kore
val result: Result<String> = readFile(path)  // KorE style
val tagged: OkErr<String>  = readFile(path).toOkErr()  // BEAM style

// Tagged tuple functions work with when:
when (tagged) {
    is Ok  -> tagged.value
    is Err -> tagged.reason
}
```

---

**Option D — Railway-Oriented Programming (Gleam-style)**

Gleam's approach: all functions return `Result(Ok(a), Err(e))`. Pipe operator chains results automatically unwrapping successes and short-circuiting on errors.

```kore
// The |> operator unwraps Ok and short-circuits on Err
val result = validateInput(input)
    |> processPayment(_)
    |> sendConfirmation(_)
    |> logTransaction(_)
```

If any step returns `Err`, the entire chain returns that `Err`. This is `Result.flatMap` chaining with pipe syntax.

Pros: Extremely clean business logic. Explicit about errors. No exceptions.
Cons: New model for both Kotlin and Erlang developers.

---

**My recommendation: Option B as the primary model (`Ok`/`Err` sealed classes over tagged tuples) + Option D's pipeline syntax for chains. This is the most BEAM-aligned choice. Option A's `Result<T>` can be provided as a compatibility adapter for Kotlin library interop. The key insight is: KorE should NOT hide `{ok,_}|{error,_}` — it should embrace it with better syntax.**

---

### 3.6 String and Binary Handling

**The problem:** Erlang has two string representations (char lists and binaries) plus `iolist`. Kotlin has a single `String` type.

**Option A — KorE String = UTF-8 Binary**

`String` in KorE compiles to Erlang `binary()` with UTF-8 encoding. String interpolation compiles to binary construction.

```kore
val name = "Alice"             // <<"Alice">>
val msg = "Hello, $name!"     // <<"Hello, ", Name/binary, "!">>

// Binary operations available on String
name.length                    // string:length(Name)
name.toUpperCase()             // string:to_upper(Name)
name.split(",")               // binary:split(Name, <<",">>)
```

Pros: Single string type. No `iolist` confusion. Efficient.
Cons: Char lists (used by some OTP APIs) require explicit conversion.

---

**Option B — KorE String = Iolist Under the Hood**

`String` is an iolist. Concatenation is O(1) (just wrapping in a list). When an API needs a binary, auto-convert.

```kore
val parts = ["Hello", ", ", "World"]
val msg = parts.joinToString("")   // iolist, not yet a binary
send(msg)                          // auto-converts to binary when needed
```

Pros: Zero-copy string building (huge performance win for large strings).
Cons: Surprise type behavior. Debugging shows iolists, not strings.

---

**Option C — Explicit String vs Binary Types**

```kore
val str: String = "hello"           // char list internally
val bin: Binary = b"hello"          // binary literal
val raw: Iolist = [str, bin, "\n"]  // iolist
```

Pros: Full type precision. No surprises.
Cons: More verbose. Requires developers to think about encoding.

---

**My recommendation: Option A. UTF-8 binary as the universal `String` type. Iolist is available as `Iolist` type for performance-critical string building but not the default. Char lists from legacy OTP APIs are auto-converted at the KorE boundary. This is what Elixir does, and it works well.**

### 3.7 The Concurrency Stdlib — Processes, Tasks, Channels

**The problem:** Kotlin's concurrency is coroutines (cooperative, on JVM threads). Erlang's concurrency is lightweight processes with message passing. They are fundamentally different. KorE should expose BEAM's model, not fake coroutines.

**Option A — Expose BEAM Processes Directly**

KorE's `spawn`, `send`, `receive` are thin wrappers over Erlang BIFs with Kotlin-friendly syntax.

```kore
val pid = spawn {
    receive { msg ->
        when (msg) {
            is Stop  -> return@spawn
            is Greet -> println("Hello, ${msg.name}")
        }
    }
}

pid.send(Greet("Alice"))
pid.send(Stop)
```

Pros: Zero abstraction. Full BEAM power. Teaches the BEAM model directly.
Cons: Unfamiliar for Kotlin/JVM developers.

---

**Option B — Coroutine-Like Syntax Mapping to Processes**

Use `async { }` and `await` as syntax sugar over `spawn_monitor` + `receive`.

```kore
val deferred = async {
    computeExpensiveThing()
}
val result = deferred.await()  // compiles to spawn_monitor + receive
```

Pros: Familiar syntax for Kotlin developers.
Cons: Misleading — BEAM async is not cooperative like coroutines. `await` implies thread blocking but on BEAM it's a `receive` that suspends the process, not the thread. Could cause confusion about scheduling.

---

**Option C — Task Abstraction (Elixir-style)**

```kore
val task = Task.async { computeExpensiveThing() }
val result = Task.await(task, timeout = 5.seconds)

// Parallel map
val results = Task.awaitAll(
    Task.async { fetchA() },
    Task.async { fetchB() },
    Task.async { fetchC() }
)
```

This maps directly to Elixir's `Task` module, which wraps `spawn_monitor` + `receive`. Clean, familiar to Elixir users, approachable for Kotlin users.

Pros: Simple abstraction. Direct BEAM mapping. Used in production at scale.
Cons: Still requires understanding message-passing for advanced use.

---

**My recommendation: Option C as the high-level API (`Task.async`/`Task.await`). Option A's raw `spawn`/`send`/`receive` are always available for power users. Option B is explicitly NOT provided — fake coroutine syntax on BEAM is a footgun. Session 4 covers GenServer, which is the real actor abstraction.**

### 3.8 Logging

**Option A — Map to Erlang's `logger`**

```kore
Logger.info("Server started on port $port")
Logger.error("Connection failed", mapOf("reason" to reason))
Logger.debug { "Expensive: ${computeDebugInfo()}" }  // lazy
```

Compiles to `logger:info`, `logger:error`. The lambda form for debug compiles to a guard-checked call (no evaluation if level is above debug).

---

**Option B — Structured Logging First**

```kore
log {
    level = Level.INFO
    message = "User authenticated"
    fields {
        userId = user.id
        method = "oauth2"
        duration = elapsed
    }
}
```

Compiles to `logger:info(#{level => info, msg => ..., meta => #{...}})`. Structured logging natively on BEAM's `logger` metadata system.

---

**My recommendation: Option B with Option A as shorthand. Structured logging is the right default for production systems. Short `Logger.info(...)` is acceptable for simple cases but structured maps should be the canonical form.**

### Summary Table — Stdlib Mapping Decisions

| Area | Recommended Approach | Key Decision |
|---|---|---|
| Collection API | Kotlin-style extension functions, transparent BEAM types | `list.map { }` → `lists:map` |
| Chaining | Extension chain + optional `\|>` | Both styles valid |
| Scope functions | Keep all 5 Kotlin scope functions | `apply`, `let`, `also`, `run`, `with` |
| Error handling | `Ok`/`Err` sealed classes over tagged tuples | No hiding of BEAM error model |
| Error pipelines | Railway `\|>` short-circuit on `Err` | Explicit `pipeline { }` construct |
| Strings | UTF-8 binary as `String` | Single type, auto-convert from charlists |
| Lazy evaluation | `generateSequence` → tail recursion, `sequence { }` → comprehensions | No fake lazy lists |
| Concurrency | `Task.async`/`Task.await` over BEAM processes | No fake coroutines |
| Logging | Structured `log { }` builder, `Logger.level()` shorthand | BEAM `logger` underneath |
| Math | `kotlin.math` naming, same functions | Direct mapping |
| Time | `kotlin.time.Duration` API, compiles to `erlang:monotonic_time` | No JVM time classes |
| Collections mutability | Read-only by default | Mutable variants are explicit |

---

**Key decisions to make before Session 3:**

1. Do you want `|>` as a first-class operator or just `.let { }`? This affects the entire stdlib design philosophy.
2. `Ok`/`Err` vs `Result<T>` — which should be the canonical error type? My recommendation is `Ok`/`Err`, but this is a values question about how close to BEAM you want to stay.
3. Should `Task.async` timeout be mandatory (Elixir forces it) or optional (Kotlin's `Deferred.await` has no default timeout)? Erlang's "let it crash" philosophy says mandatory — orphaned processes are a bug.
