# Session 9: Error Messages and Developer Feedback

## 9.0 Why This Session Matters

Error messages are not a polish concern. They are a language design concern. The quality of error messages determines whether a developer trusts the compiler, whether they can make progress alone, and whether the learning curve feels approachable or punishing. Rust's reputation was built in large part on error quality. Elm's error messages are regularly cited as best-in-class despite the language having limited adoption. TypeScript's errors are notoriously bad despite massive adoption — and that reputation has a real cost in productivity.

KorE has a specific challenge: it sits on top of two compilation stages (KorE frontend → Erlang Abstract Format → BEAM), meaning errors can originate at multiple levels and point to generated code rather than KorE source. Getting this right requires deliberate architectural decisions, not afterthought formatting.

---

## 9.1 The Error Origin Problem

KorE has four distinct layers where errors can originate:

```
Layer 1: KorE source (parse errors, type errors, name resolution)
Layer 2: Erlang compiler backend (EAF validation, lint errors)
Layer 3: BEAM runtime (crash reports, exit signals, timeouts)
Layer 4: OTP framework (gen_server crashes, supervisor reports)
```

The critical rule: **every error the developer sees must point to KorE source, not to generated Erlang or BEAM bytecode**. A stack trace that says `my_module.erl line 47` when the developer only wrote `.kore` files is a failure of the toolchain.

### The source map problem

KorE must thread source locations through every compilation stage:

```
KorE source position {file, line, column}
    → erl_anno:new({Line, Column}) in EAF nodes
    → cerl:set_ann(Node, [{file, "foo.kore"}, {location, {L, C}}]) in Core Erlang
    → line/1 BEAM instruction in .beam bytecode
    → debug_info chunk (maps BEAM instruction offsets back to source)
    → stack trace display
```

At runtime, BEAM stack traces show `{module, function, arity, [{file, F}, {line, L}]}`. The `file` and `line` come from the `line` instructions in the bytecode, which come from the EAF `Anno` values, which come from KorE source positions. If this chain is maintained, BEAM crash reports automatically show KorE source locations.

**The generated Erlang file name problem**: KorE should use the KorE source file name in all `Anno` values, not a generated `.erl` file name. When `erl_anno:new({Line, Column})` carries the KorE filename, the BEAM debugger and crash reports will reference the KorE file. This is what Elixir does — Elixir source locations appear in crash reports, not generated Erlang.

## 9.2 The Error Message Standard

Every KorE error message must answer four questions:

1. **What went wrong** — precise description, not a code or a raw type
2. **Where it went wrong** — file, line, column with source snippet
3. **Why it went wrong** — the semantic reason, not just the syntactic observation
4. **How to fix it** — at minimum a hint, ideally an example

This is the Rust standard. Before Rust, compilers answered question 1 and 2 only. Elm and Rust proved that 3 and 4 are feasible and worth the implementation cost.

---

## 9.3 Error Message Design: Reference Languages

### Rust

Rust's error messages are the current gold standard. Key properties:

```
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
  --> src/main.rs:6:5
   |
5  |     let r1 = &s;
   |              -- immutable borrow occurs here
6  |     s.push_str(", world");
   |     ^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
7  |     println!("{}", r1);
   |                    -- immutable borrow later used here
   |
   = help: consider using a `let` binding to separate the borrows
```

Design principles:
- **Error codes** (`E0502`) are searchable in documentation
- **Carets and labels** point to multiple relevant source locations simultaneously
- **The narrative is causal**: "because it is also borrowed" explains the chain
- **`help:` and `note:`** are separate from the error itself — the error describes the problem, help describes the solution
- Colors: red for errors, yellow for warnings, blue for notes

### Elm

Elm's errors are famous for never using jargon and always speaking to the developer's intent:

```
-- TYPE MISMATCH ------------------------------------ src/Main.elm

The 1st argument to `div` is not what I expect:

17|         div model.count 2
                ^^^^^^^^^^^
This `count` value is a:

    String

But `div` needs the 1st argument to be:

    Int

Hint: Use String.toInt to convert it to an integer. Check out the docs for more
info: https://package.elm-lang.org/packages/elm/core/latest/String#toInt
```

Design principles:
- **No error codes** — the message is the identifier
- **"I expect" / "I need"** — anthropomorphizes the compiler, makes it feel like a conversation
- **Shows the type it found and the type it needed** side by side
- **Docs links** — directs to documentation, not just fixes
- **Horizontal rule with filename** — visually separates error contexts

### TypeScript (what not to do)

```
Type '{ name: string; }[]' is not assignable to type 'User[]'.
  Type '{ name: string; }' is not assignable to type 'User'.
    Object literal may only specify known properties, and 'name' does not exist in type 'User'.
```

Problems:
- The full structural type is printed, which is unreadable for complex types
- The error is phrased in terms of structural subtyping rules, not developer intent
- No source snippet shown (in raw tsc output)
- No hint about what to do
- Nested indentation makes it hard to parse the most important line

TypeScript IDEs (VS Code) compensate with inline squiggles that make this more bearable, but the raw error output is poor.

### GHC / Haskell

```
Main.hs:5:10: error:
    • Couldn't match expected type 'Int' with actual type '[Char]'
    • In the expression: "hello"
      In an equation for 'foo': foo = "hello"
  |
5 | foo = "hello"
  |       ^^^^^^^
```

Reasonable but the `•` bullets and `[Char]` instead of `String` (which is what the developer wrote) create unnecessary friction.

### Gleam

Gleam has excellent error messages that feel lightweight and precise:

```
error: Type mismatch
  ┌─ /src/my_module.gleam:12:5
  │
12│   add("hello", 1)
  │       ^^^^^^^

Expected type:
  Int

Found type:
  String
```

Clean, minimal, no unnecessary ceremony. The box-drawing characters make the source snippet visually distinct.

## 9.4 KorE Error Message Format Design

### Options

**Option A: Rust-style** — Full color terminal output with caret spans, multiple labeled locations, error codes, help sections.

```
error[KE0014]: type mismatch
  --> src/counter.kore:15:12
   |
14 |     fun add(a: Int, b: Int): Int {
   |                                - expected Int because of return type here
15 |         return "hello"
   |                ^^^^^^^ found String
   |
   = help: remove the quotes to make this an integer literal: 42
```

Pros: industry standard, IDE-friendly (error codes), very precise.
Cons: requires significant implementation investment.

**Option B: Gleam-style** — Minimal box-drawing, single location focus, no error codes.

```
error: Type mismatch
  ┌─ src/counter.kore:15:12
  │
15│     return "hello"
  │            ^^^^^^^

Expected type:
  Int

Found type:
  String
```

Pros: clean, fast to implement, pleasant to read.
Cons: no error codes, single location limits expressiveness for multi-site errors.

**Option C: Elm-style** — Prose-heavy, anthropomorphized, single location.

```
-- TYPE MISMATCH ----------------------------------- src/counter.kore

The return value of `add` is not what I expect:

15|     return "hello"
               ^^^^^^^

This is a:
    String

But `add` is declared to return:
    Int

Hint: Did you mean to return a number? Try: return 42
```

Pros: very approachable for newcomers, explicitly enterprise-developer-friendly.
Cons: verbose, can feel patronizing to experienced developers.

**Option D: Two-tier** — short form by default, verbose form with `--explain`.

Short (default):
```
error[KE0014]: type mismatch in return at src/counter.kore:15:12
  expected: Int, found: String
```

Verbose (`kore build --explain` or `kore explain KE0014`):
```
error[KE0014]: type mismatch
  --> src/counter.kore:15:12
   |
14 |     fun add(a: Int, b: Int): Int {
   |                                - expected Int (declared here)
15 |         return "hello"
   |                ^^^^^^^ found String
   |
  = The function `add` declares a return type of `Int` but the expression
    being returned is of type `String`. These types are not compatible.
  
  = help: to return a string, change the return type declaration:
      fun add(a: Int, b: Int): String {
    
    or to fix the return value, use an integer:
      return 42
```

**My recommendation: Option D**.

The short form is essential for CI/CD pipelines and terminal workflows where you're scanning through many errors. The verbose form with `--explain` follows `rustc --explain E0502` which is a proven pattern. The verbose form can be as rich as you want without making the default output noisy. Error codes (`KE0014`) make every error searchable and documentable.

## 9.5 Error Code Taxonomy

A structured taxonomy of KorE error codes. Format: `KE` prefix + 4-digit code.

```
KE0001–KE0099: Syntax / Parse errors
  KE0001: unexpected token
  KE0002: unterminated string literal
  KE0003: invalid escape sequence
  KE0004: unexpected end of file
  KE0005: mismatched brackets/parens/braces
  KE0010: invalid numeric literal
  KE0020: invalid atom syntax

KE0100–KE0199: Name resolution errors
  KE0100: undefined variable
  KE0101: undefined function
  KE0102: undefined module
  KE0103: undefined type
  KE0104: ambiguous name (multiple modules export this name)
  KE0110: variable already bound in this scope
  KE0111: unused variable (warning)
  KE0112: unused import (warning)
  KE0120: circular module dependency

KE0200–KE0299: Type errors
  KE0200: type mismatch
  KE0201: cannot unify types
  KE0202: missing type annotation (where required)
  KE0210: wrong number of arguments
  KE0211: wrong number of type arguments
  KE0220: cannot call non-function type
  KE0230: null safety violation (non-nullable assigned null)
  KE0231: unchecked nullable dereference
  KE0240: exhaustiveness failure (when missing case)
  KE0241: redundant pattern (can never match)
  KE0250: opaque type violation (accessing internal representation)
  KE0260: variance violation (covariant/contravariant)

KE0300–KE0399: OTP / Concurrency errors
  KE0300: GenServer callback return type mismatch
  KE0301: missing required GenServer callback
  KE0302: handle_call message type not covered (exhaustiveness)
  KE0310: send to untyped Pid without explicit Dynamic marker
  KE0320: supervisor child spec invalid

KE0400–KE0499: Interop errors
  KE0400: @External function not found in Erlang module
  KE0401: @External type annotation required
  KE0410: atom table overflow risk (too many dynamic atoms)
  KE0420: Erlang record field access without shim

KE0500–KE0599: Build / Module errors
  KE0500: module not found in project or deps
  KE0501: duplicate module name
  KE0502: circular dependency in module graph
  KE0510: incompatible dep version

KE9000–KE9999: Internal compiler errors (should never reach user)
  KE9000: internal: unexpected AST node
  KE9001: internal: Core Erlang lint failure
```

## 9.6 Multi-Site Errors

Some errors require pointing to two or more source locations simultaneously. These are the hardest to display well and the most informative when done right.

### Type inference conflict

When a type variable is constrained in two incompatible ways:

```
error[KE0201]: conflicting type constraints
  --> src/map_ops.kore:22:18
   |
18 |     fun process(items: List<Int>): List<String> {
   |                                        ------  return type declared here
   ...
22 |         return items.map { it * 2 }
   |                  ^^^^^^^^^^^^^^^^^^
   |                  this maps Int → Int, but return type requires List<String>
   |
   = note: the type variable T was first inferred as Int at line 22
     and as String from the declared return type at line 18
```

### Pattern exhaustiveness

```
error[KE0240]: non-exhaustive pattern match
  --> src/handler.kore:30:5
   |
25 |     sealed class Response {
   |         class Ok(val body: String) : Response()
   |         class NotFound : Response()
   |         class ServerError(val code: Int) : Response()  ← this case is missing
   |
...
30 |     when (response) {
   |     ^^^^^^^^^^^^^^^^ all cases of Response must be handled
31 |         is Response.Ok -> send(it.body)
32 |         is Response.NotFound -> send404()
   |     }  ← Response.ServerError not handled
   |
   = help: add a case for ServerError:
       is Response.ServerError -> send500(it.code)
     or add a catch-all:
       else -> sendError()
```

### Double-binding (val already bound)

```
error[KE0110]: variable `x` already bound in this scope
  --> src/calc.kore:8:9
   |
5  |     val x = computeA()
   |         - first binding here
...
8  |     val x = computeB()
   |         ^ second binding — use a different name
   |
   = note: in KorE, `val` creates a new binding. If you intended to shadow,
     this is allowed in nested scopes but not at the same level.
   = help: rename the second binding:
       val x2 = computeB()
```

## 9.7 Runtime Error Translation

### The BEAM crash report problem

When a KorE process crashes, the BEAM generates a crash report. Without intervention it looks like:

```
=ERROR REPORT==== 5-Jun-2026::10:30:00 ===
Error in process <0.234.0> with exit value:
{badmatch,{error,not_found},[
  {'KorE.com.example.UserService',lookup,1,[{file,"user_service.erl"},{line,47}]},
  {'KorE.com.example.UserController',handle_call,3,[{file,"user_controller.erl"},{line,23}]},
  {gen_server,try_handle_call,4,[{file,"gen_server.erl"},{line,1113}]},
  ...
]}
```

With proper source location threading, the same crash looks like:

```
=ERROR REPORT==== 5-Jun-2026::10:30:00 ===
Error in process <0.234.0> with exit value:
{badmatch,{error,not_found},[
  {'KorE.com.example.UserService',lookup,1,[{file,"src/user_service.kore"},{line,47}]},
  {'KorE.com.example.UserController',handle_call,3,[{file,"src/user_controller.kore"},{line,23}]},
  {gen_server,try_handle_call,4,[{file,"gen_server.erl"},{line,1113}]},
  ...
]}
```

The KorE frames show `.kore` source files. The OTP frames still show `.erl`. This is the correct behavior — it mirrors how Elixir frames appear in Elixir stack traces while OTP frames appear as Erlang.

### KorE crash reporter

KorE should ship a custom logger handler (using Erlang's `logger` module) that:

1. Intercepts crash reports
2. Translates `{file, "...kore"}` frames into clickable source links (for terminals that support it)
3. Filters/simplifies OTP internal frames (the 4–6 `gen_server` frames that appear in every crash)
4. Formats the exception reason ergonomically

```
KorE crash report ─── process <0.234.0> ─── 2026-06-05 10:30:00
  reason: badmatch — pattern match failed
  value:  {error, not_found}

  stack trace:
    UserService.lookup/1        src/user_service.kore:47
    UserController.handleCall/3 src/user_controller.kore:23
    [gen_server internal frames hidden — use --verbose-crash to show]

  process info:
    registered name: none
    message queue:   0 messages
    last message:    {call, {get_user, "alice"}, <0.100.0>, #Reference<0.1.2.3>}
```

**Options for the crash reporter:**

**Option A: Custom logger handler (recommended)** — implement `logger_handler` behaviour, intercept crash events, format them with KorE-aware logic. Ships as part of the KorE standard library. Activated by default when a KorE application starts.

**Option B: System flag** — use `process_flag(error_handler, kore_error_handler)` at process level to intercept undef errors. Limited to one type of error.

**Option C: Observer integration** — ship a custom Observer plugin that provides a GUI crash browser. Useful for development but not production.

**My recommendation: Option A** as default, Option C as a dev tool.

## 9.8 REPL / Interactive Shell

KorE needs an interactive shell equivalent to Elixir's `iex` or Erlang's `erl` shell.

### Reference: iex

`iex` provides:
- Expression evaluation with full Elixir syntax
- Autocomplete (Tab) based on loaded modules
- `h Module` and `h Module.function` for inline documentation
- `i value` for runtime value inspection
- `v(n)` to reference the nth result
- `r Module` to recompile and reload a module
- `c "file.ex"` to compile a file
- Pry-based debugging (`require IEx; IEx.pry()`)
- `IEx.configure(inspect: [limit: 20])` to control output formatting

### Reference: Erlang shell

The Erlang shell:
- Each expression is a top-level clause — bindings reset per line unless `f()` is called
- `b()` shows current bindings
- `f(X)` forgets binding X
- `h(Module, Function, Arity)` shows documentation (EEP-48)
- `c(Module)` compiles and loads
- `l(Module)` loads a pre-compiled module
- `q()` to quit (sends init:stop())
- Process dictionary and shell job control (`^G`)
- `observer:start()` launches the Observer GUI

### KorE REPL design options

**Option A: Wrap the Erlang shell** — patch the Erlang shell to accept KorE syntax. Feasible but fragile — the Erlang shell is deeply tied to Erlang syntax.

**Option B: Wrap iex** — since KorE produces BEAM files that Elixir can load, use iex as the host REPL with KorE modules loaded. Developers would write Elixir expressions to call KorE functions, which is awkward.

**Option C: KorE-native REPL** — build a dedicated REPL that:
- Accepts KorE expressions
- Compiles each expression to a temporary function and calls it
- Maintains a binding environment across expressions
- Provides KorE-aware autocomplete
- Loads the current project's modules

**Option D: REPL via compile-to-script** — each REPL line is compiled to a KorE "script" expression, executed in a subprocess, result printed. Simpler implementation but slower (subprocess overhead per expression).

**My recommendation: Option C**, implemented incrementally. Start with Option D for MVP (fast to ship), upgrade to Option C for the 1.0 release. The REPL is a significant implementation investment but is essential for the enterprise developer experience KorE is targeting.

### KorE REPL features (design specification)

```
kore> val x = 42
x: Int = 42

kore> val y = x * 2
y: Int = 84

kore> fun double(n: Int) = n * 2
defined: double(Int): Int

kore> listOf(1, 2, 3).map { double(it) }
res0: List<Int> = [2, 4, 6]

kore> import com.example.UserService
imported: UserService

kore> UserService.findById(1)
res1: Result<User> = Ok(User(id=1, name="Alice"))

kore> :h UserService.findById
UserService.findById(id: Int): Result<User>
  Looks up a user by their integer ID.
  Returns Ok(User) if found, Err(.not_found) if not.

kore> :reload UserService
recompiled: UserService (0.23s)

kore> :type listOf(1, 2, 3)
List<Int>

kore> :info 42
value: 42
type:  Int
beam:  integer (4 bytes in process heap)
```

Special REPL commands prefixed with `:`:
- `:h Module.function` — inline docs
- `:type expr` — show inferred type without evaluating
- `:reload Module` — recompile and hot-reload
- `:load "path"` — compile and load a file
- `:modules` — list loaded KorE modules
- `:info value` — runtime type info and memory size
- `:processes` — list running BEAM processes
- `:reset` — clear all bindings
- `:quit` or `:q` — exit

## 9.9 Warning System

Warnings are separate from errors — the build succeeds but the developer is informed of potential issues.

### Warning categories

```
KW0001: unused variable (prefix with _ to suppress)
KW0002: unused import
KW0003: unused function (private functions never called)
KW0004: unused value (expression result discarded without side effect intent)
KW0010: pattern always matches (redundant guard or type test)
KW0011: pattern never matches (dead code)
KW0020: deprecated function usage
KW0021: deprecated module usage
KW0030: implicit Dynamic conversion (crossing typed/untyped boundary)
KW0031: unsafe atom creation at runtime
KW0040: large number of atoms declared (atom table growth warning)
KW0050: potential message queue buildup (receive without timeout in loop)
KW0051: unbounded recursion without tailrec annotation
```

### Warning suppression

```kotlin
// Suppress a specific warning at the declaration site:
@Suppress("KW0003")
private fun debugHelper() { ... }

// Suppress at file level:
@file:Suppress("KW0001", "KW0002")

// Or with underscore convention for unused vars (no annotation needed):
val _ = sideEffectingFunction()
fun handler(_unusedParam: String) { ... }
```

### Warning escalation

```
// In kore.toml:
[compiler]
warnings_as_errors = true           // all warnings become errors
warnings_as_errors = ["KW0031"]     // specific warnings become errors
suppress_warnings  = ["KW0001"]     // suppress globally
```

## 9.10 IDE Integration

KorE's error messages need to work in two contexts: the terminal (CI, raw build) and IDEs (VS Code, IntelliJ). These have different requirements.

### Language Server Protocol (LSP)

KorE must ship a Language Server (`kore-language-server`) that implements LSP. This is the foundation for IDE support across all editors.

LSP capabilities KorE must implement from day one:
- `textDocument/publishDiagnostics` — errors and warnings inline in the editor
- `textDocument/completion` — autocomplete
- `textDocument/hover` — type on hover
- `textDocument/definition` — go to definition
- `textDocument/references` — find all references
- `textDocument/rename` — refactoring rename
- `textDocument/formatting` — code formatting

LSP capabilities for later:
- `textDocument/inlayHints` — inline type annotations
- `textDocument/codeLens` — run/debug lens over functions
- `workspace/executeCommand` — custom commands (run, test, reload)

### Diagnostic severity levels

```json
{
  "uri": "file:///src/counter.kore",
  "diagnostics": [
    {
      "range": {
        "start": {"line": 14, "character": 8},
        "end":   {"line": 14, "character": 15}
      },
      "severity": 1,
      "code": "KE0200",
      "source": "kore",
      "message": "Type mismatch: expected Int, found String",
      "relatedInformation": [
        {
          "location": {
            "uri": "file:///src/counter.kore",
            "range": {"start": {"line": 8, "character": 24}, "end": {"line": 8, "character": 27}}
          },
          "message": "return type Int declared here"
        }
      ]
    }
  ]
}
```

The `relatedInformation` array is how multi-site errors work in LSP — the primary error has a location, and related locations (where the conflicting constraint comes from) appear as secondary underlines in the editor.

### Code actions

Code actions are quick-fix suggestions that appear as lightbulb actions in IDEs:

- `KE0240` (non-exhaustive when): offer to add missing cases
- `KW0002` (unused import): offer to remove it
- `KE0230` (null safety): offer to add `?` null check or `!!` assertion
- `KW0001` (unused variable): offer to prefix with `_`
- `KE0100` (undefined variable): offer to add import if a matching module is found
- `KE0302` (missing handle_call case): offer to add the missing message handler

## 9.11 Documentation System

### EEP-48 (Erlang documentation standard)

EEP-48 defines a standard documentation chunk in `.beam` files (`Docs` chunk). It was adopted in OTP 23 and is supported by `iex`, the Erlang shell, and ExDoc. KorE must emit EEP-48 documentation so that KorE functions show up in `iex` help and Erlang `h/3`.

The `Docs` chunk structure:

```erlang
#docs_v1{
  format      = <<"text/markdown">>,       % documentation format
  anno        = Anno,
  beam_language = kore,                    % custom language identifier
  metadata    = #{},
  module_doc  = #{<<"en">> => <<"Module documentation in markdown">>},
  docs        = [
    {
      {function, lookup, 1},               % MFA
      Anno,
      [<<"id :: Int">>],                   % signature list
      #{<<"en">> => <<"Looks up a user by ID.\n\nReturns Ok(User) or Err(.not_found).\n">>},
      #{}                                  % metadata (deprecated, since, etc.)
    }
  ]
}.
```

### KorE doc comment syntax

```kotlin
/**
 * Looks up a user by their integer ID.
 *
 * Returns `Ok(User)` if found, `Err(.not_found)` if not.
 *
 * ## Example
 * ```kore
 * val user = UserService.findById(1)
 * when (user) {
 *     is Ok -> println(it.name)
 *     is Err -> println("not found")
 * }
 * ```
*
* @param id The user's integer identifier
* @return Result<User, .not_found>
* @since 0.1.0
  */
  fun findById(id: Int): Result<User> = ...
```

### Doc generation

`kore docs` generates HTML documentation from EEP-48 chunks. This should integrate with ExDoc (the Elixir documentation generator) since it already reads EEP-48 and produces excellent output. KorE packages can be documented alongside Elixir and Erlang packages on hexdocs.pm.

## 9.12 Formatting

A canonical code formatter (`kore fmt`) eliminates style debates and ensures consistent codebases.

### Reference formatters

- **`rustfmt`** — opinionated, nearly no configuration, respects `//fmt:skip` directives
- **`mix format`** — opinionated, minimal config, integrates with CI via `--check-formatted`
- **`gleam format`** — no configuration at all, absolute
- **`prettier`** (JS/TS) — configurable but defaults are good

**My recommendation**: follow Gleam's approach — zero configuration. One canonical style. This is the right call for a new language where community style conventions haven't calcified yet. Any configuration option creates two camps.

### Formatter integration

```
kore fmt                    # format all .kore files in the project
kore fmt src/counter.kore   # format specific file
kore fmt --check            # check formatting, exit 1 if any file needs changes
kore fmt --diff             # show diff without modifying files
```

Git pre-commit hook:
```sh
#!/bin/sh
kore fmt --check
```

CI check:
```yaml
- name: Check formatting
  run: kore fmt --check
```

## 9.13 Debugging

### Options for KorE debugging

**Option A: BEAM Observer** — the built-in Observer GUI provides process lists, message queues, memory usage, supervisor trees. Available in any BEAM node. Access via `observer:start()` from the KorE shell. No KorE-specific work needed; just ensure it's included in dev dependencies.

**Option B: Erlang debugger** — the `:debugger` OTP application provides step-through debugging of BEAM code. Works with any module compiled with `debug_info`. KorE modules compiled with debug info can be stepped through — but the debugger shows generated Erlang, not KorE source.

For this to show KorE source, KorE would need a custom debugger frontend that uses the source map (EEP-48 / debug info chunk) to translate BEAM execution positions back to KorE line numbers.

**Option C: Print-based debugging with structured output** — Erlang's `dbg` module and `recon` library provide trace-based debugging without breakpoints. This is the idiomatic BEAM debugging approach for production systems.

`recon_trace` from the `recon` library:
```erlang
recon_trace:calls({my_module, my_function, '_'}, 10).
% traces up to 10 calls to my_module:my_function with any args
```

KorE equivalent:
```kotlin
// KorE standard library debug utilities:
Debug.trace(UserService::findById, maxCalls = 10)
Debug.traceAll(UserService, maxCalls = 50)
Debug.processInfo(pid)
Debug.messageQueue(pid)
```

**Option D: DAP (Debug Adapter Protocol)** — the LSP-equivalent for debugging. Implementing DAP would allow VS Code's debugger UI to work with KorE: breakpoints, step-through, variable inspection. This requires the most implementation work but provides the best IDE experience.

**My recommendation**: Option A for day 1 (zero work, immediate value), Option C as KorE stdlib utilities, Option D as a stretch goal for the IDE experience.

## 9.14 Test Output

KorE's test framework output should follow the same error quality standard as the compiler.

### Reference: ExUnit output

```
  1) test UserService finds user by id (UserServiceTest)
     test/user_service_test.exs:10
     Assertion with == failed
     code:  assert UserService.find(1) == {:ok, %User{name: "Alice"}}
     left:  {:ok, %User{name: "Alice", id: 1}}
     right: {:ok, %User{name: "Alice"}}
     stacktrace:
       test/user_service_test.exs:11: (test)
```

Key properties: shows the code that failed, the left and right values, the file and line.

### KorE test output design

```
FAIL  UserServiceTest.findById finds user by id
      src/test/user_service_test.kore:10

      assertion failed: assertEqual

      expected:
        Ok(User(id=1, name="Alice"))

      received:
        Ok(User(id=1, name="Alice", email=null))

      difference:
        User(id=1, name="Alice")
               ─── missing field: email=null ───
               add email to the expected User, or use a partial matcher

      call stack:
        UserServiceTest.findById    src/test/user_service_test.kore:11
```

Diff-based failure display: rather than showing left/right, show what is different. This is what Rust's `pretty_assertions` crate does and what makes failures faster to read.

## 9.15 Summary: Error Quality Checklist

For every error KorE emits, validate against this checklist:

- [ ] Points to KorE source, not generated Erlang or BEAM bytecode
- [ ] Shows a source snippet with carets at the relevant position
- [ ] States what went wrong in plain language (no raw type expressions)
- [ ] States why (the semantic cause, not just the syntactic observation)
- [ ] Has a `help:` or `hint:` suggesting a fix
- [ ] Has an error code (`KE####`) that is searchable
- [ ] For multi-site errors: shows all relevant locations simultaneously
- [ ] For runtime errors: shows KorE source frames, hides/collapses OTP internals
- [ ] Warning messages are distinct from error messages (different color / prefix)
- [ ] Can be suppressed at declaration, file, or project level
- [ ] Works in both color terminal and plain text (CI) modes
