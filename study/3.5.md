# Session 3.5 — Pre-OTP Foundation Decisions

These three decisions are load-bearing. Everything in Session 4 sits on top of them. The goal here is not to list options endlessly — it's to reason through each one completely and land on a direction.

---

## Decision 1: `loop`/`recur` vs `tailrec` — What is the Primary Process Loop Idiom?

### The Core Tension

Erlang/BEAM process loops are structurally this:

```erlang
loop(State) ->
    receive
        {call, From, Msg} ->
            NewState = handle(Msg, State),
            From ! {reply, result},
            loop(NewState);   %% <-- tail call, never returns
        stop ->
            ok
    end.
```

This is an infinite tail-recursive function. The BEAM guarantees it never stack-overflows because the last call in every branch is the recursive call. This is not just an optimization — it is the execution model. The process *is* the loop.

A Kotlin developer sees that and thinks: "that's a while loop with state." They're right. The question is which surface you expose.

---

### Option A: `tailrec` Only (Pure BEAM Style)

Expose the raw BEAM model directly, with Kotlin's `tailrec` modifier guaranteeing the tail-call is valid at compile time.

```kotlin
tailrec fun loop(state: State): Nothing {
    val msg = receive()
    val newState = when (msg) {
        is Msg.Increment -> state.copy(count = state.count + 1)
        is Msg.Stop      -> return  // exits process
    }
    loop(newState)
}
```

**Cross-reference:**
- Elixir does exactly this — recursive functions with no `loop` abstraction
- Gleam does the same — recursive functions are idiomatic, no special construct
- Scala/Akka hides the loop inside the `receive` block — developers never write it

**Pros:**
- Zero abstraction — what you write is what runs on BEAM
- `tailrec` gives compile-time guarantee the tail-call is valid
- Idiomatic for developers who understand the BEAM model
- No magic — debuggable, transparent

**Cons:**
- Unfamiliar to most Kotlin/JVM developers
- Recursive `loop` function with `Nothing` return type is conceptually jarring for enterprise devs
- Pattern is easy to break (accidentally not tail-calling) despite `tailrec` guard

---

### Option B: `loop`/`recur` as Primary (Clojure-Inspired)

A `loop` block that establishes rebinding points; `recur` jumps back with new values. No explicit recursive call.

```kotlin
loop(state = initialState) {
    val msg = receive()
    when (msg) {
        is Msg.Increment -> recur(state.copy(count = state.count + 1))
        is Msg.Stop      -> done()
    }
}
```

**Cross-reference:**
- Clojure: `(loop [state init] ... (recur new-state))` — exactly this model
- Clojure's `recur` only compiles if it is in tail position — same guarantee as `tailrec`
- Swift: no equivalent, uses `while` + mutation
- Scala: `@tailrec` annotation on recursive functions — closer to Option A

**Pros:**
- Familiar to Kotlin devs who think in loops
- `recur` makes the "jump back" intent explicit
- `done()` or `exit()` for termination reads naturally
- Compiler can statically verify `recur` is in tail position

**Cons:**
- Introduces a new construct that doesn't exist in Kotlin
- The binding semantics of `loop { }` are non-obvious (are these `val`s? `var`s?)
- Hides the fact that you're writing a BEAM process loop
- Clojure's `loop`/`recur` is limited to single functions — process loops span `receive` blocks which adds complexity

---

### Option C: `while (true)` Desugaring to Tail Recursion (Transparent Illusion)

A `while (true)` construct that *looks* like a JVM loop but compiles to a tail-recursive BEAM function. State mutation becomes explicit variable rebinding (the `var` = Elixir-style pointer rebinding from Session 1).

```kotlin
var state = initialState
while (true) {
    val msg = receive()
    state = when (msg) {
        is Msg.Increment -> state.copy(count = state.count + 1)
        is Msg.Stop      -> break
    }
}
```

**Cross-reference:**
- Elixir allows `var` rebinding as syntactic sugar over pattern matching reassignment
- Swift uses `while true` + `break` extensively for event loops — familiar and readable
- This is what Elixir does internally in `GenServer` — the loop is hidden in the OTP behaviour

**Pros:**
- Maximally familiar to any developer from any language
- `break` exits naturally
- State mutation via `var` is exactly the "pointer rebinding" model from Session 1 — consistent

**Cons:**
- Hiding tail recursion behind `while` is a lie — the mental model breaks down when you need to reason about BEAM behaviour (e.g. garbage collection per-iteration, process hibernation)
- `break` with a value is awkward in Kotlin semantics
- The illusion fails at the edges: you cannot `break` from inside a nested `when` and return a value cleanly

---

### Option D: Graduated — `tailrec` Primary, `loop`/`recur` as Syntactic Sugar

`tailrec` is the canonical BEAM-native form. `loop`/`recur` is offered as a convenience that desugars to `tailrec`. Both are first-class. Developers choose their comfort level.

```kotlin
// BEAM-native form — what KorE compiles to
tailrec fun loop(state: CounterState): Nothing {
    val newState = when (val msg = receive<CounterMsg>()) {
        is CounterMsg.Increment -> state.copy(count = state.count + 1)
        is CounterMsg.Stop      -> return
    }
    loop(newState)
}

// Convenience form — desugars to the above
loop(state = initialState) {
    when (val msg = receive<CounterMsg>()) {
        is CounterMsg.Increment -> recur(state.copy(count = state.count + 1))
        is CounterMsg.Stop      -> done()
    }
}
```

Both are valid KorE. The compiler emits identical BEAM bytecode. Documentation teaches `tailrec` first to build the right mental model, then introduces `loop`/`recur` as sugar.

**Cross-reference:**
- Elixir: only recursive form, no sugar — but Elixir devs are already functional thinkers
- Gleam: only recursive form — same philosophy
- Scala/Akka: the loop is hidden entirely inside `AbstractBehavior.onMessage` — furthest from the metal
- KorE's audience includes JVM developers, so the graduated path is justified where Elixir/Gleam's audience does not need it

---

### My Recommendation: Option D

**`tailrec` is primary. `loop`/`recur` is sugar.**

Here is why:

The BEAM process loop *is* the language's concurrency model. Hiding it behind `while (true)` (Option C) breeds misunderstanding the moment developers need to reason about memory, hibernation, or code_change in hot upgrades. They need the mental model to be correct.

But forcing `tailrec fun loop` on every Kotlin developer on day one creates unnecessary friction. The graduated approach (Option D) is honest: teach the real model, offer the ergonomic shortcut. The key is that `loop`/`recur` is never *hiding* anything — it is shorthand for something the developer already understands.

Critically, for GenServer in Session 4: **the process loop is mostly hidden inside the OTP behaviour anyway.** GenServer callbacks do not write `loop()` themselves — the framework provides it. So this decision mainly affects raw actor code and lower-level process design, not the day-to-day Spring-like experience.

## Decision 2: Atom Syntax — Committing to a Form

### What Atoms Need to Do in OTP

Before picking syntax, catalogue every place atoms appear in OTP:

```
// Return values from GenServer callbacks
{:ok, state}
{:noreply, state}
{:reply, value, state}
{:stop, reason, state}
{:error, reason}

// Process lifecycle
{:ok, pid}
{:error, :already_started}
{:EXIT, pid, reason}
{:DOWN, ref, :process, pid, reason}

// Pattern matching tags
{:call, from, msg}
{:cast, msg}
{:info, msg}

// ETS / Mnesia / application returns
{:atomic, result}
{:aborted, reason}
:undefined
:ok
:error
:normal
:infinity
```

The syntax must:
1. Be lightweight — atoms appear in every return value, every pattern match
2. Be distinguishable from identifiers at a glance
3. Compose naturally inside tuples and data structures
4. Feel native in `when` patterns

---

### Option A: Elixir-Style Colon Prefix — `:atom`

```kotlin
val result: Pair<Atom, State> = Pair(:ok, state)

when (msg) {
    Pair(:call, payload) -> handleCall(payload)
    Pair(:cast, payload) -> handleCast(payload)
    :stop               -> exit()
}
```

**Cross-reference:**
- Elixir: `:ok`, `:error`, `:noreply` — universally known in BEAM ecosystem
- Gleam: uses `Ok`, `Error` as types, not atoms — no colon prefix
- Ruby: `:symbol` — identical syntax, widely known in scripting world
- Swift: no atoms — uses enums

**Pros:**
- Any Elixir developer reads KorE immediately
- Visually distinct from identifiers, types, and strings
- Works in any position: tuple element, `when` branch, standalone expression
- No ceremony — `:ok` is two characters

**Cons:**
- Kotlin already uses `:` heavily — type annotations (`val x: Int`), lambda result types, class inheritance (`class Foo : Bar`)
- `:ok` in a type annotation context (`val result: ok`) would require careful parser disambiguation
- Feels like Elixir, not Kotlin — might undermine the "Kotlin-flavored" identity
- Uppercase convention clash: Kotlin types are `PascalCase`, atoms in Elixir are `:snake_case`

---

### Option B: `#atom` Hash Prefix

```kotlin
val result = Pair(#ok, state)

when (msg) {
    Pair(#call, payload) -> handleCall(payload)
    Pair(#cast, payload) -> handleCast(payload)
    #stop               -> exit()
}
```

**Cross-reference:**
- No major language uses `#` for atoms — novel
- C# uses `#` for preprocessor directives — potential confusion
- Swift uses `#` for special expressions (`#available`, `#selector`) — similar "meta" feeling
- Erlang uses `?` for macros — adjacent idea

**Pros:**
- Completely unambiguous — `#ok` cannot be confused with anything in Kotlin grammar
- Visually distinct
- Novel enough to signal "this is a KorE concept"

**Cons:**
- No prior art in the developer population KorE targets
- `#` for atoms is arbitrary — no mnemonic reason
- Swift developers might expect `#ok` to be a compiler directive
- Harder to type on some keyboard layouts

---

### Option C: `@atom` At-Prefix (Annotation-Like)

```kotlin
val result = Pair(@ok, state)

when (msg) {
    Pair(@call, payload) -> handleCall(payload)
    @stop               -> exit()
}
```

**Cross-reference:**
- Kotlin uses `@` for annotations — could create confusion (`@Override` vs `@ok`)
- Elixir uses `@` for module attributes — also a naming conflict
- No language uses `@` for atoms

**Pros:**
- Very visually distinct
- Short

**Cons:**
- Directly conflicts with Kotlin's annotation syntax — `@ok` looks like an annotation
- Confusing to both Kotlin and Elixir developers
- Eliminated.

---

### Option D: Companion Object / Enum-Backed (No Prefix, Uppercase)

Atoms are Kotlin objects in a sealed hierarchy. No prefix.

```kotlin
object Atoms {
    object Ok : Atom("ok")
    object Error : Atom("error")
    object Noreply : Atom("noreply")
    object Reply : Atom("reply")
    object Stop : Atom("stop")
}

// Usage
val result = Pair(Atoms.Ok, state)
// or with import
import Atoms.*
val result = Pair(Ok, state)
```

**Cross-reference:**
- Scala: `case object Ok extends Atom` — exactly this pattern
- Gleam: `Ok`, `Error` as type constructors — closest to this model
- Swift: `enum Result { case ok, error }` — similar feel

**Pros:**
- Pure Kotlin — no new syntax
- IDE autocompletion works perfectly
- Type-safe: `Ok` is a known type, not an arbitrary string
- Interops with Kotlin's sealed class pattern matching

**Cons:**
- Verbose — `Atoms.Ok` or requiring `import Atoms.*` is noise
- Loses the lightweight feel — `:ok` in a return value is ergonomic; `Ok` requires the namespace
- Doesn't scale to user-defined atoms gracefully (every new atom needs a declaration)
- The BEAM atom table is dynamic — user code creates atoms freely; forcing declarations contradicts the runtime model

---

### Option E: Two-Tier — `.atom` Dotted for OTP Atoms, `atom {}` Block for User Atoms

From Session 3's recommendation: built-in OTP atoms use dotted lowercase (`.ok`, `.noreply`, `.error`). User-defined atoms use an `atoms {}` declaration block. The dot is read as "atom namespace access."

```kotlin
// Built-in OTP atoms — always available
fun init(args: Args): Pair<Atom, State> = Pair(.ok, CounterState(0))

// User-defined atoms — declared in atoms block
atoms {
    pending
    running
    complete
    failed
}

fun status(): Atom = .pending   // from atoms block

// Pattern matching
when (response) {
    Pair(.ok, data)      -> process(data)
    Pair(.error, reason) -> log(reason)
    .undefined           -> skip()
}
```

**Cross-reference:**
- Swift: `.north`, `.south` for enum cases — exactly this `.member` syntax on enums
- Swift's dot syntax only works when the type is known/inferred — KorE can use the same inference rule
- Elixir: `:atom` — same concept, different sigil
- Gleam: `Ok`, `Error` — typed, but KorE's `.ok` is more lightweight

**Pros:**
- `.ok` is visually lighter than `:ok` and avoids Kotlin's `:` collision
- Swift developers immediately recognize `.ok` as a member shorthand
- Aligns with how Kotlin handles enum members in some contexts — `.VALUE`
- Two-tier approach addresses dynamic vs static atom creation
- `.noreply`, `.reply`, `.stop` read naturally as return instructions

**Cons:**
- `.ok` can look like a method call with no receiver (`something.ok`)
- Parser must distinguish `.ok` (atom literal) from `.ok` (property access on implicit receiver)
- The `atoms {}` block for user-defined atoms adds a new construct

---

### Disambiguation: `.atom` vs Property Access

This is the critical parser concern for Option E. Consider:

```kotlin
val x = foo.ok      // property access on foo — standard Kotlin
val x = .ok         // atom literal — starts with dot, no receiver
```

The rule is simple: **a dot at the start of an expression with no left-hand side is an atom literal.** This is exactly Swift's rule. Inside a `when` branch or a return expression where the expected type is `Atom`, the inference narrows it further. This is unambiguous to parse.

```kotlin
// Ambiguous? No.
foo.ok          // foo is an identifier — property access
.ok             // no identifier before dot — atom literal
return .ok      // clearly atom
Pair(.ok, x)   // clearly atom (inside tuple constructor)
```

---

### My Recommendation: Option E (`.atom` with `atoms {}`)

**Commit to `.atom` syntax.** Here is the complete rationale:

1. Swift developers already read `.north` / `.south` / `.ok` as lightweight member references — it has prior art in a mainstream language
2. The parser rule (dot with no left-hand side = atom literal) is clean, unambiguous, and teachable in one sentence
3. `.ok`, `.error`, `.noreply`, `.reply`, `.stop` read as natural return keywords in OTP callbacks — almost imperative in feel
4. It avoids every collision that plagues `:atom` (Kotlin type annotations) and `@atom` (annotations)
5. The two-tier design (`atoms {}` for user-defined) keeps the atom table discipline that serious BEAM code requires

This locks in the atom syntax for Session 4. Every OTP return value will use `.ok`, `.noreply`, `.reply`, `.stop`, `.error`, `.normal`.

## Decision 3: Sealed Class vs Tagged Tuples for OTP Returns

### The Problem in Full

GenServer callbacks in Erlang return tagged tuples:

```erlang
%% From handle_call
{reply, Result, NewState}
{noreply, NewState}
{stop, Reason, Reply, NewState}

%% From handle_cast / handle_info
{noreply, NewState}
{noreply, NewState, {continue, Msg}}
{noreply, NewState, hibernate}
{noreply, NewState, Timeout}
{stop, Reason, NewState}

%% From init
{ok, State}
{ok, State, {continue, Msg}}
{ok, State, hibernate}
{ok, State, Timeout}
{stop, Reason}
ignore
```

KorE must represent all of these. The question is what data structure represents them in KorE source.

---

### Option A: Raw Tagged Tuples (Pure BEAM Feel)

Using Decision 2's atom syntax, return tuples directly using Kotlin's `Triple` / `Pair` or a lightweight tuple type:

```kotlin
fun handleCall(msg: CounterMsg, from: From, state: CounterState): Triple<Atom, Any, CounterState> {
    return when (msg) {
        is CounterMsg.Get       -> Triple(.reply, state.count, state)
        is CounterMsg.Increment -> Triple(.noreply, Unit, state.copy(count = state.count + 1))
        is CounterMsg.Stop      -> Triple(.stop, .normal, state)
    }
}
```

**Cross-reference:**
- Elixir: `{:reply, result, new_state}` — exactly this, with pattern-matched atoms
- Pure Erlang: same
- Gleam: uses typed return values — not tagged tuples

**Pros:**
- Closest to the wire — what you write maps 1:1 to BEAM tuple representation
- No translation layer — zero overhead
- Familiar to any Elixir developer

**Cons:**
- `Triple<Atom, Any, CounterState>` is not type-safe — the second element type depends on the first atom
- IDE cannot help you: `Triple(.reply, result, state)` — what type should `result` be?
- Typos in atoms (`Triple(.relpy, ...)`) are not caught at compile time unless specifically checked
- No exhaustiveness checking — the compiler cannot verify you handled all return forms

---

### Option B: Full Sealed Class Hierarchy (Maximum Type Safety)

A sealed class hierarchy for every callback's return type. The compiler enforces exhaustiveness and type safety.

```kotlin
sealed class CallResult<out S, out R> {
    data class Reply<S, R>(val reply: R, val state: S) : CallResult<S, R>()
    data class NoReply<S>(val state: S) : CallResult<S, Nothing>()
    data class Continue<S, R>(val state: S, val continue: Any) : CallResult<S, R>()
    data class Stop<S, R>(val reason: Any, val reply: R, val state: S) : CallResult<S, R>()
    data class StopNoReply<S>(val reason: Any, val state: S) : CallResult<S, Nothing>()
    data class Hibernate<S>(val state: S) : CallResult<S, Nothing>()
    data class Timeout<S>(val state: S, val timeout: Long) : CallResult<S, Nothing>()
}

sealed class CastResult<out S> {
    data class NoReply<S>(val state: S) : CastResult<S>()
    data class Stop<S>(val reason: Any, val state: S) : CastResult<S>()
    data class Hibernate<S>(val state: S) : CastResult<S>()
    data class Timeout<S>(val state: S, val timeout: Long) : CastResult<S>()
    data class Continue<S>(val state: S, val continue: Any) : CastResult<S>()
}

// Usage
fun handleCall(msg: CounterMsg, from: From, state: CounterState): CallResult<CounterState, Int> {
    return when (msg) {
        is CounterMsg.Get       -> CallResult.Reply(state.count, state)
        is CounterMsg.Increment -> CallResult.NoReply(state.copy(count = state.count + 1))
        is CounterMsg.Stop      -> CallResult.Stop(.normal, Unit, state)
    }
}
```

**Cross-reference:**
- Gleam: uses Result types and custom return types — closest to this approach
- Scala/Akka: `Behaviors.same`, `Behaviors.stop`, `Behaviors.withStash` — sealed behavior returns
- Scala Akka Typed is the clearest reference: `Effect.reply(result).thenNoOp()` — fluent typed API
- Rust: exhaustive enums for all returns — the same philosophy

**Pros:**
- Full compile-time type safety — `Reply` carries both the reply value type and state type
- IDE autocompletes all valid return forms
- Exhaustiveness checking in `when`
- No invalid states representable

**Cons:**
- Verbose — `CallResult.NoReply(newState)` vs `{:noreply, newState}`
- Two separate sealed hierarchies (`CallResult`, `CastResult`, `InitResult`) is a lot of type surface
- Harder to extend — adding a new return form requires changing the sealed hierarchy
- The type parameter proliferation (`CallResult<S, R>`) makes signatures complex

---

### Option C: Builder/Fluent DSL (Akka-Typed Inspired)

Return values are constructed via a builder object, using method chaining. No tuples, no sealed classes — just a fluent API.

```kotlin
fun handleCall(msg: CounterMsg, from: From, state: CounterState) =
    when (msg) {
        is CounterMsg.Get       -> reply(state.count, state)
        is CounterMsg.Increment -> noReply(state.copy(count = state.count + 1))
        is CounterMsg.Stop      -> stop(.normal, state)
    }

fun handleCast(msg: CounterMsg, state: CounterState) =
    when (msg) {
        is CounterMsg.Increment -> noReply(state.copy(count = state.count + 1))
        is CounterMsg.Reset     -> noReply(state.copy(count = 0))
    }
```

The functions `reply`, `noReply`, `stop`, `hibernate`, `continueWith` are provided by the `GenServer` base class or a context receiver. They return opaque `CallDirective` / `CastDirective` types.

**Cross-reference:**
- Akka Typed: `Effect.reply(replyTo, response)`, `Effect.noReply`, `Effect.stop` — exactly this pattern
- Akka's `Effect` / `ReplyEffect` is the closest real-world reference to this approach
- Spring WebFlux: `ServerResponse.ok().bodyValue(data)` — same fluent style
- This is the "Spring-like enterprise feel" KorE aims for

**Pros:**
- Cleanest call site — `reply(value, state)`, `noReply(state)`, `stop(reason, state)` read like instructions
- No types to import — the functions are inherited from the base class
- Familiar to enterprise Kotlin developers (Spring-like method calls)
- Easy to add new directives (just add a method) without changing a sealed hierarchy
- `reply` and `noReply` are self-documenting

**Cons:**
- Opaque — `CallDirective` returned from `reply()` hides what's happening
- Testing is harder — you can't pattern match on the return value directly, you get an opaque object
- The base class / context receiver approach creates an implicit dependency — anti-explicit
- Akka Typed's `Effect` API is notoriously confusing at the edges (reply vs noReply effects)

---

### Option D: Hybrid — DSL Functions that Return Transparent Sealed Types

The call site looks like the builder DSL (Option C) but the return type is a transparent sealed class (Option B). The functions `reply()`, `noReply()`, `stop()` are convenience constructors for the sealed classes, not opaque builders.

```kotlin
// Framework provides these as top-level functions or extensions
fun <S, R> reply(value: R, state: S): CallResult<S, R>    = CallResult.Reply(value, state)
fun <S>    noReply(state: S): CallResult<S, Nothing>       = CallResult.NoReply(state)
fun <S>    hibernate(state: S): CallResult<S, Nothing>     = CallResult.Hibernate(state)
fun <S, R> stop(reason: Any, reply: R, state: S): CallResult<S, R> = CallResult.Stop(reason, reply, state)
fun <S>    stop(reason: Any, state: S): CastResult<S>      = CastResult.Stop(reason, state)

// Usage — reads like DSL
fun handleCall(msg: CounterMsg, from: From, state: CounterState): CallResult<CounterState, Int> =
    when (msg) {
        is CounterMsg.Get       -> reply(state.count, state)
        is CounterMsg.Increment -> noReply(state.copy(count = state.count + 1))
        is CounterMsg.Stop      -> stop(.normal, Unit, state)
    }

// Testable — return type is transparent
val result = myServer.handleCall(CounterMsg.Get, from, CounterState(42))
result is CallResult.Reply<*, *>  // true
(result as CallResult.Reply<*, *>).reply == 42  // true
```

**Cross-reference:**
- Gleam: typed return values with named constructors — closest to this
- Rust: `Ok(value)` / `Err(reason)` as named constructors on transparent enums — same philosophy
- Elixir: none — Elixir doesn't have types
- Akka Typed: `Effect.reply(...)` returns `ReplyEffect` — opaque; this option makes it transparent

**Pros:**
- Best of both worlds: clean call site (`reply(v, s)`) + transparent type (`CallResult.Reply`)
- Fully testable — you can inspect the return value directly
- IDE autocompletes `reply(`, `noReply(`, `stop(` because they're regular functions
- Exhaustiveness checking still works because the underlying type is sealed
- No magic — `reply(v, s)` is just a function, its body is visible

**Cons:**
- Still requires type parameter discipline at the function signature level
- Two sealed hierarchies (`CallResult`, `CastResult`) still exist, just less visible at call sites
- Devs unfamiliar with the pattern may be confused when they see `CallResult.Reply` in stack traces vs `reply()` in source

---

### Option E: Atom-Tuple (Decision 2 Integration)

Now that we have committed to `.atom` syntax, revisit tagged tuples using proper KorE tuple types with atom tags. This is Option A but with the atom syntax decision applied.

```kotlin
// KorE tuple syntax with atom tags
fun handleCall(msg: CounterMsg, from: From, state: CounterState) =
    when (msg) {
        is CounterMsg.Get       -> (.reply, state.count, state)
        is CounterMsg.Increment -> (.noreply, state)
        is CounterMsg.Stop      -> (.stop, .normal, Unit, state)
    }

// Pattern matching on returns
when (val result = server.handleCall(msg, from, state)) {
    (.reply, value, newState)   -> sendReply(from, value); loop(newState)
    (.noreply, newState)        -> loop(newState)
    (.stop, reason, _, newState) -> terminate(reason, newState)
}
```

This requires KorE to have first-class tuple literals with structural pattern matching — which Erlang has natively but Kotlin does not.

**Cross-reference:**
- Erlang/Elixir: exactly this model
- Gleam: tuple pattern matching is first-class
- Swift: tuple pattern matching in `switch` is first-class — `.ok` in a tuple pattern is natural

**Pros:**
- Closest to the BEAM model — zero translation overhead
- Atom-tuple returns are what Erlang emits and expects — perfect BEAM interop
- Pattern matching on returns is the most expressive form
- Consistent with the whole language — one pattern everywhere

**Cons:**
- Requires first-class tuple types in KorE (not in Kotlin today — `Pair`/`Triple` are limited)
- No type safety on the second element — the type of `.reply`'s value depends on context
- No compiler exhaustiveness checking for tuple patterns
- Interop with Kotlin libraries that return typed results breaks the pattern

---

### The Underlying Tradeoff Table

| | Type Safety | Ergonomics | BEAM Proximity | Testability | Extensibility |
|---|---|---|---|---|---|
| A: Raw tuples | Low | Medium | Highest | Low | High |
| B: Sealed classes | Highest | Low | Low | Highest | Low |
| C: Builder DSL | Medium | Highest | Low | Low | Highest |
| D: DSL + transparent sealed | High | High | Medium | High | Medium |
| E: Atom-tuples | Low | High | Highest | Low | High |

---

### My Recommendation: Option D for GenServer API, Option E for Raw Process Code

**Two-tier depending on abstraction level:**

**At the GenServer/OTP level (high-level API):** use Option D — DSL functions returning transparent sealed classes. This is where enterprise Kotlin developers spend most of their time. `reply(value, state)` reads like a Spring controller returning a response. The sealed class is transparent for testing. The type system catches errors.

**At the raw process level (bare `receive` loops):** use Option E — atom-tuple returns. When a developer drops below the GenServer abstraction and writes a raw BEAM process loop with `tailrec` or `loop`/`recur`, atom-tuples are the right model. They interop perfectly with Erlang/Elixir code, they're lightweight, and the developer at that level is expected to understand the BEAM.

In practice this looks like:

```kotlin
// GenServer level — DSL + sealed (Option D)
actor class Counter : GenServer<CounterState, CounterMsg>() {

    override fun init(args: Args) = ok(CounterState(0))

    override fun handleCall(msg: CounterMsg, from: From, state: CounterState) =
        when (msg) {
            is CounterMsg.Get       -> reply(state.count, state)
            is CounterMsg.Increment -> noReply(state.copy(count = state.count + 1))
        }
}

// Raw process level — atom-tuples (Option E)
tailrec fun pingLoop(partner: Pid, count: Int): Nothing {
    val msg = receive<PingMsg>()
    partner ! (.ping, self(), count)
    val reply = receive<PongMsg>()
    pingLoop(partner, count + 1)
}
```

The two layers are explicit and the developer always knows which level they're at. The line is: if you're using `GenServer`, `Supervisor`, or any OTP behaviour — Option D. If you're writing a raw process — Option E.

## Summary: The Three Decisions

| Decision | Chosen Direction |
|---|---|
| Loop idiom | `tailrec` primary, `loop`/`recur` as desugar. GenServer hides the loop entirely. |
| Atom syntax | `.atom` (dot prefix, no left receiver). `atoms {}` block for user-defined atoms. |
| OTP returns | Option D at GenServer level (`reply()`, `noReply()` → transparent sealed). Option E at raw process level (atom-tuples). |

These three decisions are now locked in for Session 4. The GenServer API will use `reply()`, `noReply()`, `ok()`, `stop()` as DSL functions. The atom syntax will be `.ok`, `.noreply`, `.reply`, `.stop`, `.error`. Raw process code will use atom-tuples. The loop in a GenServer is invisible to the user — the framework provides it.

Session 3.5 is done. Three decisions locked in:

1. **Loop idiom** — `tailrec` is primary (BEAM-native, correct mental model), `loop`/`recur` is syntactic sugar that desugars to it. GenServer hides the loop entirely — most developers never write it.

2. **Atom syntax** — `.atom` dot-prefix with no left receiver. Parser rule: dot at start of expression = atom literal, same as Swift enum members. OTP atoms are `.ok`, `.noreply`, `.reply`, `.stop`, `.error`, `.normal`. User atoms declared in `atoms {}` blocks.

3. **OTP returns** — Two-tier: at GenServer level, `reply(value, state)` / `noReply(state)` / `stop(reason, state)` are DSL functions returning transparent sealed classes (testable, type-safe, Spring-like). At raw process level, atom-tuples are idiomatic. Developers always know which level they're at.
