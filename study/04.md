# Session 4: GenServers and OTP

## Foundations Before Starting

The decisions from Session 3.5 that shape everything here:

- **Atoms:** `.ok`, `.noreply`, `.reply`, `.stop`, `.error`, `.normal` — dot-prefix, no receiver
- **OTP DSL returns:** `reply(value, state)`, `noReply(state)`, `stop(reason, state)` — DSL functions producing sealed classes
- **Loop idiom:** `tailrec` is primary, `loop`/`recur` is sugar; GenServer hides the loop entirely
- **Data:** `data class` over Maps; Records as opt-in performance annotation

## 4.1 The BEAM Process Model — Concepts You Must Understand First

Before mapping OTP to KorE syntax, the underlying model must be clear. Every design decision below follows from it.

### What a BEAM Process Is

A BEAM process is:
- A unit of **isolated memory** — no shared heap between processes
- A unit of **concurrency** — scheduled by the BEAM scheduler, not the OS
- A unit of **failure** — it can crash without affecting any other process
- A unit of **communication** — all interaction is via message passing (mailbox)

This is categorically different from a JVM thread. A JVM thread shares memory with other threads. A BEAM process does not. This is why BEAM can run millions of processes: each is small (~300 words initial heap), independent, and GC'd individually.

```
JVM mental model:          BEAM mental model:
Thread 1 ─┐               Process 1 [mailbox] [heap]
Thread 2 ─┼─ shared heap  Process 2 [mailbox] [heap]
Thread 3 ─┘               Process 3 [mailbox] [heap]
           ↓                         ↓
     race conditions           no sharing = no races
```

### The Mailbox

Every process has a mailbox — a FIFO queue of messages. `receive` selects the first message matching a pattern, leaving non-matching messages in the mailbox. This selective receive is what makes protocols clean.

```erlang
receive
    {reply, Value} -> handle(Value);  % matches first
    timeout        -> give_up()       % matches second if no reply
after 5000 ->
    timed_out()
end
```

### Links and Monitors

**Link:** bidirectional — if either side crashes, the other receives an exit signal. Default behavior: propagate the crash. With `trap_exit: true`: convert to a `{'EXIT', pid, reason}` message instead.

**Monitor:** unidirectional — the monitoring process receives `{'DOWN', ref, :process, pid, reason}` if the monitored process dies. The monitored process is unaffected.

```
Links:    A ←——→ B    (bidirectional crash propagation)
Monitors: A ——→  B    (A watches B; B doesn't know)
```

This asymmetry is the foundation of supervision trees.

### The Supervision Tree

Erlang's "let it crash" philosophy works because crashes are contained and recovery is automatic. The supervision tree is the mechanism:

```
Application
└── TopSupervisor  (strategy: one_for_one)
    ├── WebSupervisor (strategy: one_for_all)
    │   ├── HttpServer (worker)
    │   └── Router (worker)
    └── ServiceSupervisor (strategy: rest_for_one)
        ├── DatabaseWorker (worker)
        ├── CacheWorker (worker)
        └── BusinessLogicWorker (worker)
```

If `CacheWorker` crashes: `rest_for_one` restarts it and all workers started after it (`BusinessLogicWorker`), leaving `DatabaseWorker` running.

## 4.2 `gen_server` — The Core Abstraction

### What It Is

`gen_server` is an OTP behaviour — a contract. You implement callbacks, OTP provides the loop, message dispatch, error handling, hot code upgrade hooks, sys introspection, and crash reporting.

The loop it hides looks like this in raw Erlang:

```erlang
loop(State) ->
    receive
        {'$gen_call', {Pid, Ref}, Request} ->
            {reply, Reply, NewState} = handle_call(Request, {Pid, Ref}, State),
            Pid ! {Ref, Reply},
            loop(NewState);
        {'$gen_cast', Msg} ->
            {noreply, NewState} = handle_cast(Msg, State),
            loop(NewState);
        Msg ->
            {noreply, NewState} = handle_info(Msg, State),
            loop(NewState)
    end.
```

You never write this. `gen_server` writes it for you.

### The Callback Contract

| Callback | Triggered by | Must return |
|---|---|---|
| `init(args)` | `start_link` | `{ok, state}` \| `{ok, state, timeout/hibernate}` \| `{stop, reason}` \| `ignore` |
| `handle_call(req, from, state)` | `gen_server:call/2,3` (sync) | `{reply, reply, state}` \| `{noreply, state}` \| `{stop, reason, reply, state}` |
| `handle_cast(msg, state)` | `gen_server:cast/2` (async) | `{noreply, state}` \| `{stop, reason, state}` |
| `handle_info(msg, state)` | Raw messages (`!`) | `{noreply, state}` \| `{stop, reason, state}` |
| `terminate(reason, state)` | Shutdown/crash | `any` (return value ignored) |
| `code_change(vsn, state, extra)` | Hot upgrade | `{ok, newstate}` \| `{error, reason}` |

### Full Erlang Example — Counter Server

```erlang
-module(counter).
-behaviour(gen_server).

%% API
-export([start_link/0, increment/0, increment/1, reset/0, get/0]).
%% Callbacks
-export([init/1, handle_call/3, handle_cast/2, handle_info/2,
         terminate/2, code_change/3]).

-define(SERVER, ?MODULE).

%% -- API --
start_link() ->
    gen_server:start_link({local, ?SERVER}, ?MODULE, 0, []).

increment()  -> gen_server:cast(?SERVER, increment).
increment(N) -> gen_server:cast(?SERVER, {increment, N}).
reset()      -> gen_server:cast(?SERVER, reset).
get()        -> gen_server:call(?SERVER, get).

%% -- Callbacks --
init(InitialValue) ->
    {ok, InitialValue}.

handle_call(get, _From, State) ->
    {reply, State, State};
handle_call(_Unknown, _From, State) ->
    {reply, {error, unknown_request}, State}.

handle_cast(increment, State) ->
    {noreply, State + 1};
handle_cast({increment, N}, State) ->
    {noreply, State + N};
handle_cast(reset, _State) ->
    {noreply, 0};
handle_cast(_Unknown, State) ->
    {noreply, State}.

handle_info(_Msg, State) ->
    {noreply, State}.

terminate(_Reason, _State) ->
    ok.

code_change(_OldVsn, State, _Extra) ->
    {ok, State}.
```

## 4.3 KorE GenServer — Design Options

Now the core question: how do you surface `gen_server` in KorE syntax?

### Option A — Annotation-Driven (Spring-like)

The closest to Spring Boot. Annotations drive wiring; no explicit behaviour declaration.

```kotlin
@GenServer(name = "counter")
class CounterServer(initialValue: Int = 0) {

    private var state = initialValue

    @Call
    fun get(): Int = state

    @Cast
    fun increment() {
        state += 1
    }

    @Cast
    fun increment(n: Int) {
        state += n
    }

    @Cast
    fun reset() {
        state = 0
    }
}

// Usage
val counter = CounterServer.startLink()
counter.increment(5)
val value = counter.get()   // synchronous call
```

**Pros:** Minimal boilerplate, familiar to Spring devs, zero OTP vocabulary required.
**Cons:** The boundary between `call` (sync) and `cast` (async) is hidden in annotations — a critical semantic distinction becomes invisible. Also hides supervision, which is where things get complicated.
**Cross-reference:** Similar to Akka Typed's `@ActorRef` patterns, but those had to be abandoned because hiding actor semantics behind annotations caused bugs. Spring does it but JVM threads are forgiving; BEAM isn't.

**My verdict:** Tempting but dangerous. The `call`/`cast` distinction is load-bearing; obscuring it costs you correctness.

---

### Option B — Interface/Abstract Class (Kotlin-native)

Map gen_server callbacks to abstract functions. Familiar to Kotlin developers who know abstract classes.

```kotlin
abstract class GenServer<S>(initialState: S) {
    protected var state: S = initialState

    abstract fun handleCall(request: Any, from: From): CallResult<S>
    abstract fun handleCast(message: Any): CastResult<S>
    open fun handleInfo(message: Any): CastResult<S> = noReply(state)
    open fun onTerminate(reason: Any) {}
    open fun onCodeChange(oldVsn: Any): S = state
}

// Implementation
class CounterServer(initial: Int = 0) : GenServer<Int>(initial) {

    override fun handleCall(request: Any, from: From) = when (request) {
        is Get -> reply(state, state)
        else   -> reply(Err("unknown"), state)
    }

    override fun handleCast(message: Any) = when (message) {
        is Increment    -> noReply(state + 1)
        is IncrementBy  -> noReply(state + message.n)
        is Reset        -> noReply(0)
        else            -> noReply(state)
    }

    companion object {
        fun startLink(initial: Int = 0) =
            GenServer.startLink(CounterServer(initial), name = .counter)
    }
}

// Usage
val pid = CounterServer.startLink()
pid.cast(Increment)
val value = pid.call<Int>(Get)
```

**Pros:** Clear callback contract, type-safe state, Kotlin idioms, `when` pattern matching is natural.
**Cons:** `handleCall`/`handleCast` still take `Any` — you lose type safety on the request unless you add a sealed class per server (which is verbose). The `companion object` for `startLink` is boilerplate that every server repeats.
**Cross-reference:** This is essentially Akka Classic's Actor model. Akka Typed moved away from it precisely because `Any` message types cause bugs at scale.

**My verdict:** A solid middle ground. Gets the semantics right. Can be improved by adding typed message sealed classes.

---

### Option C — Typed Protocol DSL (Akka Typed-inspired)

Explicitly type the message protocol as a sealed class. The GenServer is parameterized on the message type.

```kotlin
// Define the protocol explicitly
sealed class CounterMsg {
    object Increment : CounterMsg()
    data class IncrementBy(val n: Int) : CounterMsg()
    object Reset : CounterMsg()
    data class Get(val replyTo: ReplyChannel<Int>) : CounterMsg()
}

// Server is typed on its message protocol
class CounterServer : GenServer<CounterMsg, Int>(initialState = 0) {

    override fun receive(msg: CounterMsg, state: Int) = when (msg) {
        is CounterMsg.Increment    -> noReply(state + 1)
        is CounterMsg.IncrementBy  -> noReply(state + msg.n)
        is CounterMsg.Reset        -> noReply(0)
        is CounterMsg.Get          -> reply(msg.replyTo, state, state)
    }

    companion object {
        fun startLink() = GenServer.startLink<CounterMsg, Int>(
            ::CounterServer,
            name = .counterServer
        )
    }
}

// Usage — typed, no casting
val ref: ServerRef<CounterMsg> = CounterServer.startLink()
ref.cast(CounterMsg.Increment)
ref.cast(CounterMsg.IncrementBy(5))
val n: Int = ref.ask(CounterMsg.Get)  // ask = call with built-in replyTo
```

**Pros:** Fully type-safe. The message protocol is a first-class citizen. `when` exhaustiveness check covers all messages. No `Any` anywhere.
**Cons:** More ceremony — every server needs a sealed class. For simple servers this is verbose. `call`/`cast` distinction moves to message design (messages that carry a `replyTo` are calls; others are casts) — elegant but different from raw OTP.
**Cross-reference:** This is exactly Akka Typed's `Behavior<T>`. It's also very close to Gleam's approach where every actor is typed. Gleam calls the `replyTo` pattern a "subject".

**My verdict:** The best long-term design for serious applications. The verbosity cost is paid back in correctness and toolability. The `ask` pattern for typed calls is elegant.

---

### Option D — Two-Tier: DSL Surface + Protocol Depth (Recommended)

Simple servers get the annotation/abstract path. Complex servers with rich protocols get typed messages. Both compile to the same underlying gen_server.

**Tier 1 — Simple server (annotation-driven, for simple stateful components):**

```kotlin
@GenServer
class CounterServer {
    var state: Int = 0

    @Call fun get(): Int = state

    @Cast fun increment()      { state += 1 }
    @Cast fun increment(n: Int){ state += n }
    @Cast fun reset()          { state = 0  }
}
```

**Tier 2 — Protocol server (typed, for complex message flows):**

```kotlin
// Explicit protocol definition
protocol CounterProtocol {
    cast Increment
    cast IncrementBy(n: Int)
    cast Reset
    call Get -> Int
}

@GenServer(protocol = CounterProtocol::class)
class CounterServer : ProtocolServer<CounterProtocol, Int>(state = 0) {

    override fun CounterProtocol.Increment.handle(state: Int) =
        noReply(state + 1)

    override fun CounterProtocol.IncrementBy.handle(state: Int) =
        noReply(state + n)

    override fun CounterProtocol.Reset.handle(state: Int) =
        noReply(0)

    override fun CounterProtocol.Get.handle(state: Int) =
        reply(state, state)
}
```

**Cross-reference:** This tiered approach mirrors how Elixir projects naturally evolve — simple `GenServer` for basic stateful services, typed protocols for public-facing ones. Spring Boot does this too: `@Service` for simple cases, explicit contract interfaces for complex ones.

**My verdict:** This is what I recommend for KorE. It respects the skill gradient of enterprise developers — easy entry via annotations, full power accessible without switching languages.

---

### The `startLink` Problem — Registration

In Erlang, a server can be registered under a local atom name, a global name, or left anonymous (PID only). In KorE:

```kotlin
// Option A: implicit name from class name
CounterServer.startLink()
// → registered as .counterServer (camelCase of class name)

// Option B: explicit name
CounterServer.startLink(name = .myCounter)

// Option C: anonymous (PID ref only)
val pid: ServerRef<CounterMsg> = CounterServer.startLink(anonymous = true)

// Option D: global registration
CounterServer.startLink(scope = Registry.global)
```

**My recommendation:** Option A as default (convention over configuration — Spring-like), Options B/C/D as explicit overrides.

## 4.4 Supervisors

### The Erlang Supervisor Contract

```erlang
init([]) ->
    SupFlags = #{
        strategy  => one_for_one,   % restart strategy
        intensity => 5,             % max restarts in...
        period    => 10             % ...this many seconds
    },
    ChildSpecs = [
        #{
            id       => worker_a,
            start    => {worker_a, start_link, []},
            restart  => permanent,   % always restart
            shutdown => 5000,        % ms to wait before kill
            type     => worker,
            modules  => [worker_a]
        }
    ],
    {ok, {SupFlags, ChildSpecs}}.
```

**Restart strategies:**
- `one_for_one` — only the crashed child restarts
- `one_for_all` — all children restart when one crashes (used when children are interdependent)
- `rest_for_one` — crashed child + all children started after it restart (used for ordered dependencies)
- `simple_one_for_one` — dynamic pool of identical workers (deprecated; use `supervisor` + `dynamic_supervisor`)

**Restart values:**
- `permanent` — always restarted
- `temporary` — never restarted (runs once)
- `transient` — only restarted on abnormal exit (not `.normal`)

### KorE Supervisor Options

**Option A — Builder DSL:**

```kotlin
@Supervisor(strategy = .oneForOne, maxRestarts = 5, within = 10.seconds)
class AppSupervisor : Supervisor() {

    override fun children() = supervise {
        worker(::CounterServer) {
            restart = .permanent
            shutdown = 5.seconds
        }
        worker(::DatabaseWorker) {
            restart = .permanent
            shutdown = 10.seconds
        }
        supervisor(::WebSupervisor) {
            restart = .permanent
        }
    }
}
```

**Option B — Declarative annotation (full annotation-driven):**

```kotlin
@Supervisor(
    strategy = Strategy.ONE_FOR_ONE,
    maxRestarts = 5,
    period = 10
)
@Child(type = CounterServer::class, restart = Restart.PERMANENT)
@Child(type = DatabaseWorker::class, restart = Restart.PERMANENT, shutdown = 10000)
@Child(type = WebSupervisor::class, type = ChildType.SUPERVISOR)
class AppSupervisor
```

**Option C — Functional style (no class):**

```kotlin
val appSupervisor = supervisor(.oneForOne) {
    maxRestarts(5) within 10.seconds
    
    worker(CounterServer::startLink) {
        restart(.permanent)
        shutdown(5.seconds)
    }
    worker(DatabaseWorker::startLink) {
        restart(.permanent)
        shutdown(10.seconds)
    }
    childSupervisor(WebSupervisor::startLink)
}
```

**Cross-reference:**
- **Elixir:** Uses `use Supervisor` + `def children` returning a list of child specs — very close to Option A
- **Scala/Akka:** `Behaviors.supervise(childBehavior).onFailure(SupervisorStrategy.restart)` — per-child strategy, not tree-level
- **Spring:** `@Component` + `@Autowired` — supervisor tree is implicit, not explicit

**My verdict:** Option A (builder DSL inside a class) is best for KorE. It mirrors Elixir's approach, gives you a named class you can test and introspect, and the DSL is readable without being magic. Option C is good for dynamic/programmatic trees.

### Dynamic Supervisor

For creating processes on demand (like spawning a process per user connection):

```kotlin
@DynamicSupervisor(strategy = .oneForOne)
class SessionSupervisor : DynamicSupervisor() {

    fun startSession(userId: String): ServerRef<SessionMsg> {
        return startChild(SessionWorker::startLink, userId)
    }

    fun stopSession(ref: ServerRef<SessionMsg>) {
        terminateChild(ref)
    }
}

// Usage
val sup = SessionSupervisor.startLink()
val session = sup.startSession("user-123")
session.cast(SessionMsg.Send("hello"))
sup.stopSession(session)
```

**Erlang equivalent:**

```erlang
supervisor:start_child(SessionSupervisor, [UserId]).
supervisor:terminate_child(SessionSupervisor, ChildPid).
```

## 4.5 `gen_statem` — Finite State Machines

### The Erlang Model

`gen_statem` replaced `gen_fsm` in OTP 19. It supports two callback modes:
- `state_functions` — one function per state, events dispatched by name
- `handle_event_function` — single function, all states and events

```erlang
%% Callback mode declaration
callback_mode() -> state_functions.

%% State function: locked/3
locked(cast, {push, Button}, Data = #{code := Code, acc := Acc}) ->
    NewAcc = Acc ++ [Button],
    case check_code(Code, NewAcc) of
        true  -> {next_state, open, Data#{acc := []}};
        false -> {keep_state, Data#{acc := NewAcc}}
    end;
locked(EventType, EventContent, Data) ->
    handle_common(EventType, EventContent, locked, Data).

%% State function: open/3
open({state_timeout, lock, Data}) ->
    {next_state, locked, Data};
open(cast, {push, _}, Data) ->
    {keep_state, Data}.
```

### KorE `gen_statem` Options

**Option A — Enum-based states with `when`:**

```kotlin
@StateMachine
class DoorLock(private val code: List<Int>) : StateMachine<DoorState, DoorEvent, DoorData>() {

    override fun initial() = transition(DoorState.Locked, DoorData(acc = emptyList()))

    override fun DoorState.Locked.on(event: DoorEvent, data: DoorData) = when (event) {
        is DoorEvent.Push -> {
            val newAcc = data.acc + event.button
            if (checkCode(code, newAcc))
                transitionTo(DoorState.Open, data.copy(acc = emptyList()))
                    .timeout(10.seconds, DoorEvent.LockTimeout)
            else
                stay(data.copy(acc = newAcc))
        }
        else -> stay(data)
    }

    override fun DoorState.Open.on(event: DoorEvent, data: DoorData) = when (event) {
        is DoorEvent.LockTimeout -> transitionTo(DoorState.Locked, data)
        is DoorEvent.Push        -> stay(data)
        else                     -> stay(data)
    }
}

sealed class DoorState { object Locked : DoorState(); object Open : DoorState() }
sealed class DoorEvent {
    data class Push(val button: Int) : DoorEvent()
    object LockTimeout : DoorEvent()
}
data class DoorData(val acc: List<Int>)
```

**Option B — DSL with `state { on<Event> { } }` blocks:**

```kotlin
@StateMachine
class DoorLock(code: List<Int>) {
    val machine = stateMachine<DoorData>(initial = DoorData(emptyList())) {

        state(.locked) {
            on<Push> { event, data ->
                val newAcc = data.acc + event.button
                if (checkCode(code, newAcc))
                    transitionTo(.open, data.copy(acc = emptyList()))
                        .after(10.seconds, fire(LockTimeout))
                else
                    stay(data.copy(acc = newAcc))
            }
        }

        state(.open) {
            on<LockTimeout> { _, data -> transitionTo(.locked, data) }
            on<Push>        { _, data -> stay(data) }
        }
    }
}
```

**My verdict:** Option A is cleaner for type safety and IDE support — each state is a class that can implement an interface, so the compiler enforces exhaustive event handling per state. Option B is more readable for simple machines. I'd offer both, using the class/sealed approach as the primary.

### State Machine Return Actions

KorE should expose all of `gen_statem`'s actions cleanly:

```kotlin
// State transition
transitionTo(NewState, newData)
transitionTo(NewState, newData).timeout(5.seconds, TimeoutEvent)
transitionTo(NewState, newData).stateTimeout(5.seconds, TimeoutEvent)

// Stay in current state
stay(newData)
stay(newData).timeout(5.seconds, TimeoutEvent)

// Stop
stop(.normal)
stop(.shutdown)
stop(CustomReason)

// Postpone current event (re-queue it)
postpone()

// Generate internal event
internalEvent(MyEvent)

// Reply (for call events)
replyTo(from, value).andStay(newData)
replyTo(from, value).andTransition(NewState, newData)
```

## 4.6 `gen_event` — Event Managers

### Concept

An event manager is a process that holds a set of event handler modules. When an event is sent to the manager, it's dispatched to all handlers. Handlers are dynamic — they can be added and removed at runtime.

Primary use case: logging, metrics, audit trails — where multiple independent consumers process the same events without coordination.

```erlang
%% Manager: start and add handlers
{ok, Mgr} = gen_event:start_link({local, event_bus}),
gen_event:add_handler(Mgr, audit_handler, []),
gen_event:add_handler(Mgr, metrics_handler, []),

%% Emit events
gen_event:notify(Mgr, {user_login, UserId, Timestamp}),
gen_event:sync_notify(Mgr, {order_placed, OrderId}).   % synchronous

%% Handler module
-module(audit_handler).
-behaviour(gen_event).

init([])                    -> {ok, []}.
handle_event({user_login, UserId, _T}, State) ->
    log_login(UserId),
    {ok, State};
handle_event(_, State)      -> {ok, State}.
handle_call(_, State)       -> {ok, ok, State}.
handle_info(_, State)       -> {ok, State}.
terminate(_, _)             -> ok.
code_change(_, State, _)    -> {ok, State}.
```

### KorE `gen_event` Options

**Option A — Interface-based handlers with a typed bus:**

```kotlin
// Define the event type for this bus
sealed class AppEvent {
    data class UserLogin(val userId: String, val at: Instant) : AppEvent()
    data class OrderPlaced(val orderId: String) : AppEvent()
    data class SystemAlert(val msg: String, val level: Level) : AppEvent()
}

// Event bus (the manager)
@EventManager
class AppEventBus : EventBus<AppEvent>()

// Handler
class AuditHandler : EventHandler<AppEvent> {
    override fun on(event: AppEvent) = when (event) {
        is AppEvent.UserLogin  -> auditLog("login: ${event.userId}")
        is AppEvent.OrderPlaced -> auditLog("order: ${event.orderId}")
        else -> Unit
    }
}

// Usage
val bus = AppEventBus.startLink()
bus.addHandler(AuditHandler())
bus.addHandler(MetricsHandler())
bus.notify(AppEvent.UserLogin("alice", Instant.now()))
```

**Option B — Lambda-based (reactive/flow-like feel):**

```kotlin
val bus = eventBus<AppEvent>()

bus.on<AppEvent.UserLogin> { event ->
    auditLog("login: ${event.userId}")
}
bus.on<AppEvent.OrderPlaced> { event ->
    metrics.increment("orders.placed")
}

bus.emit(AppEvent.UserLogin("alice", Instant.now()))
```

**My verdict:** Option A for production handlers (testable, named, restartable). Option B as a convenience API for quick handler registration. Option A maps to the actual `gen_event` handler lifecycle; Option B is sugar that registers anonymous handlers under auto-generated IDs.

## 4.7 `Registry` — Named Process Registry

### Erlang Primitives

Erlang has three registration mechanisms:

| Mechanism | Scope | Keys | Notes |
|---|---|---|---|
| `erlang:register/2` | Local node | Atoms only | Global table, no lookup by value |
| `global:register_name/2` | All nodes | Any term | Distributed, uses locks |
| `Registry` (Elixir) | Local node | Any term | Per-key, process-linked |
| `pg` | Cluster-wide | Group name | Multiple PIDs per group |
| `gproc` (lib) | Local/global | Any term | Most powerful, external dep |

KorE should provide a unified `Registry` abstraction:

```kotlin
// Define a registry with a typed key
@Registry
object UserSessions : Registry<String, SessionMsg>()

// Register
UserSessions.register("user-alice", sessionPid)

// Lookup
val session: ServerRef<SessionMsg>? = UserSessions.find("user-alice")

// Unregister
UserSessions.unregister("user-alice")

// Lookup or start
val session = UserSessions.getOrStart("user-alice") {
    SessionWorker.startLink("user-alice")
}
```

**Internal mapping:**

```kotlin
// Simple keys → erlang:register/2 with mangled atom names
// Complex keys → ETS table as lookup, PID monitoring for cleanup
// Cluster-wide → global or pg underneath
```

## 4.8 Process Lifecycle Management

### Spawn and Link Primitives

KorE must expose raw spawn for cases where `gen_server` is overkill:

```kotlin
// Spawn anonymous process
val pid: Pid = spawn {
    receive {
        is MyMessage -> handle(it)
    }
}

// Spawn linked (crashes propagate)
val pid: Pid = spawnLink {
    // ...
}

// Spawn with monitor
val (pid, ref) = spawnMonitor {
    // ...
}

// Receive with timeout
receive(timeout = 5.seconds) {
    is Reply      -> handle(it)
    is Timeout    -> giveUp()   // generated by runtime on timeout
}

// Receive forever
receive {
    is Command -> process(it)
}
```

**Erlang underneath:**

```erlang
% spawn { ... }   → erlang:spawn(fun() -> ... end)
% spawnLink { } → erlang:spawn_link(fun() -> ... end)
% spawnMonitor{} → erlang:spawn_monitor(fun() -> ... end)
```

### Process Flags

```kotlin
// Trap exit signals (convert to messages)
Process.trapExits(true)

// Set priority
Process.priority(.high)  // .normal | .high | .max | .low

// Set scheduler affinity
Process.scheduler(1)
```

### Message Send

From Session 3.5: `!` is the primary send operator. For the enterprise DX layer:

```kotlin
pid ! MyMessage                // raw send
pid.send(MyMessage)            // method syntax
pid.sendAfter(5.seconds, Timeout)  // timer-based send
pid.cast(MyMessage)            // if pid is a ServerRef
val result = pid.call(Request) // synchronous call
val result = pid.ask(Request, timeout = 5.seconds)  // with explicit timeout
```

This is the payoff — a full KorE OTP application showing how everything connects.

### Erlang Reference (what we're mapping from)

```erlang

```

### KorE Equivalent

```kotlin
// Application entry point
@Application(name = "shop")
class ShopApp : KoreApplication() {
    override fun start() = ShopSupervisor.startLink()
}

// Top supervisor
@Supervisor(strategy = .oneForOne, maxRestarts = 5, within = 10.seconds)
class ShopSupervisor : Supervisor() {
    override fun children() = supervise {
        worker(CatalogServer::startLink) {
            restart = .permanent
            shutdown = 5.seconds
        }
        worker(OrdersServer::startLink) {
            restart = .permanent
            shutdown = 5.seconds
        }
        supervisor(SessionSupervisor::startLink) {
            restart = .permanent
        }
    }
}

// Dynamic supervisor for sessions
@DynamicSupervisor(strategy = .oneForOne, maxRestarts = 10, within = 10.seconds)
class SessionSupervisor : DynamicSupervisor() {

    fun startSession(userId: String): ServerRef<SessionMsg> =
        startChild(SessionServer::startLink, userId) {
            restart = .temporary
            shutdown = 2.seconds
        }

    fun stopSession(ref: ServerRef<SessionMsg>) = terminateChild(ref)
}

// A worker in the tree
@GenServer
class CatalogServer : GenServer<CatalogState>(CatalogState()) {

    @Cast
    fun addProduct(product: Product) {
        state = state.copy(products = state.products + (product.id to product))
    }

    @Cast
    fun removeProduct(id: String) {
        state = state.copy(products = state.products - id)
    }
}

data class CatalogState(
    val products: Map<String, Product> = emptyMap()

data class Product(val id: String, val name: String, val price: Double)
```

## 4.10 `Process.flag(:trap_exit)` and Error Handling Patterns

### The "Let It Crash" Pattern

In Erlang/OTP the primary pattern is: don't defend against errors, let the process crash, let the supervisor restart it clean.

```kotlin
// Wrong (defensive — hides real errors):
@GenServer
class BadWorker : GenServer<State>(State()) {
    @Cast
    fun process(data: Data) {
        try {
            doWork(data)
        } catch (e: Exception) {
            logger.error("failed: $e")  // swallows the crash
        }
    }
}

// Right (let it crash):
@GenServer
class GoodWorker : GenServer<State>(State()) {
    @Cast
    fun process(data: Data) {
        doWork(data)  // if this throws, process crashes, supervisor restarts it
    }
}
```

### Trapping Exits for Cleanup

When a worker needs to clean up resources on shutdown, it traps exits:

```kotlin
@GenServer
class DatabaseWorker : GenServer<DbState>(DbState()) {

    override fun onInit() {
        Process.trapExits(true)         // convert exit signals to messages
        state = state.copy(conn = DB.connect())
    }

    // handle_info receives exit signals as messages when trap_exit is true
    override fun onMessage(msg: Any) = when (msg) {
        is ExitSignal -> {
            state.conn.close()          // clean shutdown
            stop(.normal)
        }
        else -> noReply(state)
    }

    override fun onTerminate(reason: Any) {
        state.conn.close()              // also called on normal gen_server stop
    }
}
```

### Linking for Dependency Chains

```kotlin
// If ServiceA must die when ServiceB dies
@GenServer
class ServiceA : GenServer<StateA>(StateA()) {

    private lateinit var serviceBRef: ServerRef<ServiceBMsg>

    override fun onInit() {
        serviceBRef = ServiceBRegistry.find(.serviceB)!!
        Process.link(serviceBRef.pid)   // if B dies, A receives exit signal
    }
}
```

## 4.11 Hot Code Upgrade

### The Erlang Mechanism

BEAM supports loading new module versions while the system is running. gen_server participates via `code_change/3`:

```erlang
%% Old version state: {state, Count}
%% New version state: #{count => Count, started_at => Now}
code_change("1.0", {state, Count}, _Extra) ->
    NewState = #{count => Count, started_at => erlang:system_time()},
    {ok, NewState};
code_change(_OldVsn, State, _Extra) ->
    {ok, State}.
```

### KorE `code_change` Options

**Option A — Typed migration function:**

```kotlin
@GenServer
class CounterServer : GenServer<CounterState>(CounterState()) {

    @CodeChange(from = "1.0")
    fun migrateFrom1(old: OldCounterState): CounterState =
        CounterState(
            count = old.count,
            startedAt = Instant.now()
        )
}

// Old state shape (from version 1.0)
data class OldCounterState(val count: Int)

// New state shape
data class CounterState(val count: Int, val startedAt: Instant)
```

**Option B — Version-keyed migration map:**

```kotlin
@GenServer
class CounterServer : GenServer<CounterState>(CounterState()) {

    override val migrations = migrations<CounterState> {
        from("1.0") { old: OldCounterState ->
            CounterState(old.count, Instant.now())
        }
        from("1.1") { old: CounterState11 ->
            CounterState(old.count, old.startTime)
        }
    }
}
```

**My verdict:** Option A — annotated migration function per version. It's explicit, testable (you can call the function directly in unit tests), and the type system enforces that old and new state types are declared. This is a significant DX improvement over raw Erlang.

## 4.13 Telemetry and Observability

### `:telemetry` (Erlang/Elixir standard)

Telemetry is a lightweight event system for metrics, tracing, and logging. It's a de facto standard in the BEAM ecosystem.

```erlang
%% Emit a telemetry event
telemetry:execute(
    [myapp, request, stop],       % event name (list of atoms)
    #{duration => Duration},      % measurements
    #{route => Route}             % metadata
).

%% Attach a handler
telemetry:attach(
    my_handler,                   % handler id
    [myapp, request, stop],       % event to handle
    fun handle_event/4,
    []
).
```

### KorE Telemetry

```kotlin
// Emit telemetry
Telemetry.emit(
    event  = listOf(.shop, .order, .placed),
    measurements = mapOf(.duration to duration.inMs),
    metadata = mapOf(.orderId to order.id, .userId to userId)
)

// Attach handler (declarative)
@TelemetryHandler
class OrderMetrics {
    @On([.shop, .order, .placed])
    fun onOrderPlaced(measurements: Map<Atom, Any>, metadata: Map<Atom, Any>) {
        metrics.increment("orders.placed")
        metrics.histogram("orders.placement_duration", measurements[.duration] as Long)
    }
}

// Convenience: automatic span instrumentation
@GenServer
class OrdersServer : GenServer<OrdersState>(OrdersState()) {

    @Call
    @Telemetry(event = [.shop, .orders, .get])  // auto-emits start/stop events
    fun getOrder(id: String): Order? = state.orders[id]
}
```

## 4.15 Summary: The Four Design Decisions for OTP in KorE

These are the foundational calls that will shape the entire OTP DX:

**Decision 1 — GenServer surface API**
Recommendation: **Two-tier** — `@GenServer` annotations for simple servers, typed `protocol` blocks with `ProtocolServer<P, S>` for complex ones. Simple servers appeal to Spring developers. Protocol servers appeal to Akka developers and anyone building distributed systems.

**Decision 2 — Supervisor tree definition**
Recommendation: **Builder DSL inside a class** — `@Supervisor class MySup : Supervisor() { override fun children() = supervise { ... } }`. Gives you a named, testable, introspectable supervisor. Avoids the annotation soup of Option B. Avoids the namelessness of Option C.

**Decision 3 — Process spawn syntax**
Recommendation: **`spawn { }` / `spawnLink { }` / `spawnMonitor { }`** as primary, with `receive { }` as the mailbox DSL inside. Keep `!` as the send operator. Add `.cast()` / `.call()` / `.ask()` as typed aliases on `ServerRef<M>`.

**Decision 4 — Configuration**
Recommendation: **Typed `@AppConfig` data class** read from a `config/config.kore` file with environment variable interpolation. Generates the `application:get_env` calls underneath. Elixir's `config.exs` proven this model works well for BEAM applications.
