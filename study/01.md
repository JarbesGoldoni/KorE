# Part 1 — Erlang Keywords

## 1.1 Control Flow

### `if` / `end`
Evaluates guard sequences top to bottom; executes the first branch whose guard is `true`. Every branch is a guard — no arbitrary expressions allowed. If no branch matches, a runtime error is thrown. This is unlike most languages: Erlang's `if` has no concept of a boolean expression, only guard tests.

```erlang
classify(X) ->
    if
        X > 0  -> positive;
        X < 0  -> negative;
        true   -> zero      %% 'true' is the catch-all guard
    end.
```

### `case` / `of` / `end`
Full pattern matching with optional guard clauses. More powerful than `if` because patterns destructure data. The `of` keyword separates the subject expression from the clause list.

```erlang
describe(Shape) ->
    case Shape of
        {circle, R} when R > 0 -> {area, math:pi() * R * R};
        {rect, W, H}           -> {area, W * H};
        _                      -> unknown
    end.
```

### `when`
Introduces a guard expression after a pattern in function heads, `case`, `receive`, and `try`. Guards are restricted to a safe whitelist of expressions (no side effects, no arbitrary function calls).

```erlang
%% In function head
abs(X) when X < 0 -> -X;
abs(X)            -> X.

%% Comma = AND, semicolon = OR within guards
in_range(X) when X >= 0, X =< 100 -> true;
in_range(_)                         -> false.
```

### `begin` / `end`
Groups a sequence of expressions into a single expression block. The block evaluates to its last expression. Used when a single expression is syntactically required but you need multiple steps.

```erlang
Result = begin
    A = fetch_user(),
    B = fetch_orders(A),
    {A, B}
end.
```

### `cond`
Reserved word — not implemented in standard Erlang. Proposed as a more readable alternative to nested `if`. Knowing it's reserved is important: you cannot use it as an atom without quoting.

### `let`
Reserved word — not used in current Erlang. Legacy reservation from early Prolog heritage.

## 1.2 Pattern Matching & Receive

### `receive` / `after` / `end`
Suspends the current process and scans the mailbox for the first message matching any clause. Clauses are tried in order against each message. Non-matching messages stay in the mailbox. `after N` provides a timeout in milliseconds; `after 0` is a non-blocking poll.

```erlang
%% Blocking receive with timeout
wait_for_reply(Ref) ->
    receive
        {reply, Ref, Value} -> {ok, Value};
        {error, Ref, Reason} -> {error, Reason}
    after 5000 ->
        {error, timeout}
    end.

%% Non-blocking poll
flush_one() ->
    receive
        Msg -> {got, Msg}
    after 0 ->
        empty
    end.
```

### `fun`
Creates an anonymous function (lambda) or captures a named function reference. Closures over variables in scope at definition time. Arity must be fixed.

```erlang
Double = fun(X) -> X * 2 end.
Ref    = fun lists:reverse/1.
LocalRef = fun my_func/2.

%% Multi-clause fun
Classify = fun
    (X) when X > 0 -> positive;
    (X) when X < 0 -> negative;
    (_)             -> zero
end.
```

## 1.3 Exception Handling

### `try` / `catch` / `after` / `of` / `end`
Full structured exception handling. The `of` clause pattern-matches the success value (making it behave like `case`). `catch` clauses match on exception class and value. `after` always runs (finalizer).

```erlang
safe_divide(A, B) ->
    try A / B of
        Result -> {ok, Result}
    catch
        error:badarith          -> {error, division_by_zero};
        error:Reason:Stacktrace -> {error, {Reason, Stacktrace}};
        exit:Reason             -> {exit, Reason};
        throw:Value             -> {thrown, Value}
    after
        log_attempt()
    end.
```

**Exception classes:**
- `error` — runtime VM errors (`badmatch`, `badarith`, `badarg`) or `erlang:error/1`
- `exit` — process exit signals via `erlang:exit/1`
- `throw` — controlled non-local jumps via `erlang:throw/1`

### `catch` (standalone expression)
Prefix operator that wraps any expression and returns `{'EXIT', Reason}` on error or the value itself on success. Cruder than `try`; cannot distinguish exception classes.

```erlang
Result = catch risky_operation().
%% Returns value or {'EXIT', Reason}
```

## 1.4 Boolean & Logical Operators

| Keyword | Short-circuit | Notes |
|---|---|---|
| `and` | No | Both sides always evaluated |
| `or` | No | Both sides always evaluated |
| `not` | — | Unary |
| `xor` | — | Exclusive OR |
| `andalso` | Yes | Right side skipped if left is `false` |
| `orelse` | Yes | Right side skipped if left is `true` |

```erlang
%% Use andalso/orelse in guards and conditions
is_valid(X) when is_integer(X) andalso X > 0 -> true;
is_valid(_) -> false.

%% and/or are safe in guards (both evaluated, but no side effects there)
check(X) when X > 0 and X < 100 -> in_range.
```

**Key distinction:** `andalso`/`orelse` are short-circuit and can be used with expressions that may fail. `and`/`or` evaluate both sides.

## 1.5 Arithmetic Operators (Keyword-form)

### `div` / `rem`
Integer division and remainder. Both are keyword-form infix operators, not functions.

```erlang
Q = 17 div 5.    %% 3
R = 17 rem 5.    %% 2
N = -17 rem 5.   %% -2  (sign follows dividend)
```

## 1.6 Bitwise Operators

All are keyword-form infix (or prefix for `bnot`):

| Keyword | Operation |
|---|---|
| `band` | Bitwise AND |
| `bor` | Bitwise OR |
| `bxor` | Bitwise XOR |
| `bnot` | Bitwise NOT (ones' complement) |
| `bsl` | Bit shift left |
| `bsr` | Bit shift right |

```erlang
Flags = 2#1010 band 2#1100.  %% 2#1000
Mask  = 1 bsl 4.             %% 16
Neg   = bnot 0.              %% -1
```

## 1.7 Module System Directives

### `-module(Name)`
Declares module identity. Must match the `.erl` filename. The atom `Name` becomes the namespace for all exported functions.

```erlang
-module(user_service).
```

### `-export([F/A, ...])`
Makes functions publicly callable. The `F/A` notation (name/arity) is fundamental to Erlang's function identity model — functions are identified by both name and arity.

```erlang
-export([create/1, find_by_id/1, update/2]).
```

### `-import(Mod, [F/A, ...])`
Allows calling `Mod`'s functions without the `Mod:` prefix. Rarely used in practice — considered harmful to readability. Explicit `Mod:func()` calls are idiomatic.

### `-define(Name, Value)` / `-define(Name(Args), Body)`
Compile-time macros. Referenced as `?Name`. No hygiene guarantees (unlike Elixir macros). Primarily used for constants and debug helpers.

```erlang
-define(TIMEOUT, 5000).
-define(LOG(X), io:format("~p~n", [X])).

connect() -> connect(?TIMEOUT).
```

### `-record(Name, {Fields})`
Defines a named tuple with field names. Records are compile-time syntactic sugar — they compile to plain tuples. The record name becomes the first element (the tag). Field access requires the record name at every access site.

```erlang
-record(user, {id, name, email, role = guest}).

create(Name, Email) ->
    #user{id = make_ref(), name = Name, email = Email}.

greet(#user{name = N}) ->
    io:format("Hello, ~s~n", [N]).

promote(User = #user{}) ->
    User#user{role = admin}.    %% record update syntax
```

### `-type` / `-opaque` / `-spec` / `-callback`
The type annotation system, used by Dialyzer for static analysis. Not enforced at runtime.

```erlang
-type user_id() :: pos_integer().
-opaque session_token() :: binary().   %% internal structure hidden

-spec find_user(user_id()) -> {ok, #user{}} | {error, not_found}.
find_user(Id) -> ...
```

### `-behaviour(Name)`
Declares that this module implements a behaviour contract. The compiler checks that all `-callback` functions are implemented.

```erlang
-behaviour(gen_server).
```

### Conditional Compilation: `-ifdef` / `-ifndef` / `-else` / `-endif`
C-preprocessor-style conditional compilation based on macro definitions.

```erlang
-ifdef(TEST).
-include_lib("eunit/include/eunit.hrl").
-endif.
```

## 1.8 Bit Syntax

Erlang's binary pattern matching is unique and extraordinarily powerful for network protocol and binary format work.

```
<<Segment, ...>>
Segment = Value | Value:Size | Value/TypeSpec | Value:Size/TypeSpec
```

**Type specifiers:** `integer`, `float`, `binary`, `bitstring`, `utf8`, `utf16`, `utf32`
**Endianness:** `big` (default), `little`, `native`
**Signedness:** `unsigned` (default), `signed`
**Unit:** `unit:N`

```erlang
%% Parse IPv4 header
parse_ip(<<Version:4, IHL:4, _DSCP:8, Length:16,
           _Id:16, _Flags:3, _Offset:13,
           TTL:8, Protocol:8, _Checksum:16,
           SrcIP:32, DstIP:32, _Rest/binary>>) ->
    {Version, IHL, Length, TTL, Protocol, SrcIP, DstIP}.

%% Build a frame
frame(Type, Data) ->
    Len = byte_size(Data),
    <<Type:8, Len:16/big, Data/binary>>.

%% UTF-8 string building
Greeting = <<"Hello"/utf8, " world"/utf8>>.
```

## 1.9 Comprehensions

### List comprehension: `[Expr || Qualifiers]`
### Binary comprehension: `<< Expr || Qualifiers >>`
### Map comprehension (OTP 26+): `#{K => V || Qualifiers}`

Generators use `<-` (list), `<=` (binary), or `:=` (map). Non-matching patterns in generators are silently skipped — this is a filter mechanism.

```erlang
%% Extract only successful results
Values = [V || {ok, V} <- Results].

%% Double all bytes in a binary
Doubled = <<(X*2):8 || <<X:8>> <= Binary>>.

%% Invert a map
Inverted = #{V => K || K := V <- Map}.

%% Nested generators (cartesian product)
Combos = [{X, Y} || X <- [1,2,3], Y <- [a,b], X rem 2 =:= 1].
```

## 1.10 Special Syntax Forms

| Form | Role |
|---|---|
| `_` | Wildcard pattern — matches anything, binds nothing |
| `_Name` | Named wildcard — documents intent, not bound |
| `=` | Match operator (pattern unification + first-bind assignment) |
| `!` | Message send: `Pid ! Message` |
| `#{K => V}` | Map construction (any key) |
| `#{K := V}` | Map update/match (key must exist) |
| `#rec{f = V}` | Record construction/match |
| `Rec#rec{f = V}` | Record update (creates new record) |
| `?MODULE` | Macro: current module atom |
| `?LINE` | Macro: current line number |
| `?FUNCTION_NAME` | Macro: current function name atom |

## 1.11 Process & Concurrency Primitives

These are BIFs (built-in functions), not keywords, but they are the linguistic primitives of Erlang's concurrency model and belong in any design reference.

| BIF | Role |
|---|---|
| `spawn(Fun)` | Create a new process; returns PID |
| `spawn_link(Fun)` | Spawn + bidirectional failure link |
| `spawn_monitor(Fun)` | Spawn + returns `{Pid, MonitorRef}` |
| `self()` | Current process PID |
| `exit(Reason)` | Terminate self |
| `exit(Pid, Reason)` | Send exit signal to another process |
| `link(Pid)` / `unlink(Pid)` | Create/remove bidirectional link |
| `monitor(process, Pid)` | One-way monitor; delivers `'DOWN'` message |
| `process_flag(trap_exit, true)` | Convert exit signals to messages |
| `register(Name, Pid)` | Name a process globally |
| `whereis(Name)` | Look up a named process |
| `send(Pid, Msg)` | Equivalent to `Pid ! Msg` |

# Part 2 — Kotlin Keywords

## 2.1 Variable Declaration

### `val`
Declares a read-only local variable or property. The reference is fixed after assignment; the referenced object may be mutable. This is not deep immutability.

```kotlin
val pi = 3.14159
val user = User("Alice")  // user cannot be reassigned, but user.name might be mutable
```

### `var`
Declares a mutable variable or property. The reference can be reassigned.

```kotlin
var count = 0
count += 1
```

---

## 2.2 Functions

### `fun`
Declares a function. Can be a top-level function, member function, local function, or extension function. Can be a single-expression function with `=`.

```kotlin
fun add(a: Int, b: Int): Int = a + b

fun greet(name: String) {
    println("Hello, $name")
}

// Extension function
fun String.shout(): String = this.uppercase() + "!"
```

---

## 2.3 Control Flow

### `if` / `else`
Both a statement and an expression. When used as an expression, both branches must return a value. Replaces the ternary operator.

```kotlin
val label = if (score > 90) "A" else if (score > 80) "B" else "C"
```

### `when`
Multi-branch expression/statement. Can match on value, type, range, guard condition, or arbitrary expression. When used as an expression, must be exhaustive (or have `else`).

```kotlin
when (result) {
    is Success -> result.value
    is Failure -> throw result.error
    else -> null
}

when {
    x > 100 -> "big"
    x > 0   -> "small"
    else    -> "non-positive"
}
```

### `for`
Iterates over anything implementing `Iterable` or providing `iterator()`. Uses `in`.

```kotlin
for (item in collection) { ... }
for (i in 1..10 step 2) { ... }
for ((key, value) in map) { ... }
```

### `while` / `do`
Standard loop constructs. `while` checks pre-condition; `do...while` checks post-condition.

```kotlin
while (condition) { ... }
do { ... } while (condition)
```

### `break` / `continue`
Exit or skip in loops. Can be labeled to target an outer loop.

```kotlin
outer@ for (i in 1..5) {
    for (j in 1..5) {
        if (j == 3) continue@outer
        if (i == 4) break@outer
    }
}
```

### `return`
Returns from a function. In lambdas, `return` returns from the enclosing named function unless labeled. Local returns require a label.

```kotlin
fun findFirst(list: List<Int>): Int? {
    list.forEach {
        if (it > 10) return it   // returns from findFirst
    }
    return null
}
```

### `throw`
Throws an exception. Is an expression of type `Nothing`, so it can appear on the right side of `=`.

```kotlin
val name = input ?: throw IllegalArgumentException("name required")
```

### `try` / `catch` / `finally`
Exception handling block. Also an expression — the last expression in `try` or `catch` is the value.

```kotlin
val result = try {
    parseJson(input)
} catch (e: JsonParseException) {
    null
} finally {
    closeStream()
}
```

## 2.4 Type System

### `class`
Declares a class. Classes are `final` by default (must be marked `open` to subclass). Constructor parameters can be auto-promoted to properties with `val`/`var`.

```kotlin
class User(val id: Long, var name: String)
```

### `interface`
Declares an interface. Can have default method implementations and abstract properties.

```kotlin
interface Repository<T> {
    fun findById(id: Long): T?
    fun save(entity: T): T
    fun count(): Int = 0  // default impl
}
```

### `object`
Three distinct uses: singleton declaration, companion object, anonymous object.

```kotlin
object Config { val timeout = 5000 }                    // singleton
class Foo { companion object { fun create() = Foo() } } // companion
val handler = object : ClickListener { override fun onClick() {} } // anonymous
```

### `enum class`
Enumeration with a fixed set of instances. Each instance can have properties and methods.

```kotlin
enum class Status(val code: Int) {
    ACTIVE(1), INACTIVE(0), DELETED(-1);
    fun isVisible() = this != DELETED
}
```

### `sealed class` / `sealed interface`
Restricts the type hierarchy to a known set of subtypes within the same module. Enables exhaustive `when` without `else`.

```kotlin
sealed class Result<out T> {
    data class Success<T>(val value: T) : Result<T>()
    data class Failure(val error: Throwable) : Result<Nothing>()
}
```

### `data class`
Automatically generates `equals`, `hashCode`, `toString`, `copy`, and `componentN` functions. Primary use: value objects.

```kotlin
data class Point(val x: Double, val y: Double)
val p1 = Point(1.0, 2.0)
val p2 = p1.copy(y = 5.0)
```

### `abstract`
Declares a class or member without implementation. Abstract classes cannot be instantiated.

```kotlin
abstract class Shape {
    abstract fun area(): Double
    fun describe() = "Area: ${area()}"
}
```

### `open`
Allows a class to be subclassed or a member to be overridden. All Kotlin classes are `final` by default.

```kotlin
open class Animal(val name: String) {
    open fun sound(): String = "..."
}
```

### `override`
Overrides a member from a supertype. Required explicitly — accidental overrides are a compile error.

```kotlin
class Dog : Animal("Dog") {
    override fun sound() = "Woof"
}
```

### `final`
Prevents further overriding. Applied to a member in an `open` class to stop the override chain.

```kotlin
open class Base {
    open fun foo() {}
}
class Middle : Base() {
    final override fun foo() {}  // no further override allowed
}
```

### `typealias`
Creates a name alias for an existing type. No new type is created; purely a readability tool.

```kotlin
typealias UserId = Long
typealias Handler = (Request) -> Response
```

### `is` / `!is`
Type check with automatic smart cast. After `is X` in a branch, the compiler knows the type and casts automatically.

```kotlin
when (val shape = getShape()) {
    is Circle  -> shape.radius   // smart cast to Circle
    is Rectangle -> shape.width * shape.height
    else -> 0.0
}
```

### `as` / `as?`
Unsafe cast (`as`) throws `ClassCastException` on failure. Safe cast (`as?`) returns `null`.

```kotlin
val s: String = x as String       // throws if x is not String
val s: String? = x as? String     // null if x is not String
```

### `in` / `!in`
Membership test in ranges and collections.

```kotlin
if (age in 18..65) println("working age")
if (name !in blacklist) proceed()
```

### `null`
The null reference. All types in Kotlin are non-nullable by default; `null` can only be assigned to nullable types (`T?`).

```kotlin
val x: String? = null
val len = x?.length ?: 0
```

### `true` / `false`
Boolean literals.

## 2.6 Class Modifiers

### `data`
See 2.4.

### `inner`
Allows a nested class to access the outer class instance. Without `inner`, nested classes are static.

```kotlin
class Outer(val x: Int) {
    inner class Inner {
        fun get() = x   // accesses Outer.x
    }
}
```

### `companion`
Declares a singleton object scoped to the class. The closest Kotlin equivalent to Java's static members.

```kotlin
class User private constructor(val id: Long) {
    companion object {
        fun create(): User = User(nextId())
    }
}
```

### `annotation`
Declares an annotation class. Used for metadata that can be processed at compile-time or runtime.

```kotlin
@Target(AnnotationTarget.FUNCTION)
annotation class Transactional(val timeout: Int = 30)
```

### `value`
Declares an inline value class — a wrapper around a single property that is unboxed at runtime where possible. Used for type-safe wrappers with zero runtime overhead.

```kotlin
@JvmInline
value class UserId(val raw: Long)
value class Email(val address: String)
```

## 2.7 Function Modifiers

### `suspend`
Marks a coroutine function. Can be paused and resumed without blocking a thread. The cornerstone of Kotlin's structured concurrency.

```kotlin
suspend fun fetchUser(id: Long): User {
    return withContext(Dispatchers.IO) { db.find(id) }
}
```

### `tailrec`
Asks the compiler to verify a function is tail-recursive and optimize it into a loop. Compile error if the function is not actually tail-recursive.

```kotlin
tailrec fun factorial(n: Long, acc: Long = 1L): Long =
    if (n <= 1) acc else factorial(n - 1, acc * n)
```

### `inline`
Inlines the function body at every call site. Primarily used to avoid the overhead of lambda allocation. Enables `reified` type parameters.

```kotlin
inline fun <reified T> instanceOf(value: Any): Boolean = value is T
```

### `infix`
Allows a function to be called without the dot and parentheses.

```kotlin
infix fun Int.to(other: Int) = Pair(this, other)
val pair = 1 to 2
```

### `operator`
Marks a function as an operator overload, enabling the use of standard operator symbols.

```kotlin
operator fun Point.plus(other: Point) = Point(x + other.x, y + other.y)
val p = Point(1, 2) + Point(3, 4)
```

### `vararg`
Allows a parameter to accept a variable number of arguments, accessible as an array.

```kotlin
fun log(level: String, vararg messages: String) {
    messages.forEach { println("[$level] $it") }
}
```

### `noinline` / `crossinline` / `reified`
Fine-grained modifiers for inline functions. `reified` exposes the type parameter at runtime — unique to Kotlin.

```kotlin
inline fun <reified T> deserialize(json: String): T = gson.fromJson(json, T::class.java)
```

## 2.8 Property Modifiers

### `const`
Compile-time constant. Value must be a primitive or String, known at compile time. Only top-level or in `companion object`.

```kotlin
const val VERSION = "1.0.0"
const val MAX_RETRIES = 3
```

### `lateinit`
Defers initialization of a non-null `var` property. Used for dependency injection patterns. Accessing before initialization throws `UninitializedPropertyAccessException`.

```kotlin
@Inject
lateinit var userService: UserService
```

### `by`
Delegation for properties or class interfaces.

```kotlin
val cached: String by lazy { expensiveComputation() }
val map = mutableMapOf<String, Any>()
var name: String by map   // stored in map
```

## 2.9 Generics

### `out` (covariance)
The type parameter can only appear in output positions (return types). Enables `List<Cat>` to be used where `List<Animal>` is expected.

```kotlin
class Box<out T>(val value: T)
```

### `in` (contravariance)
The type parameter can only appear in input positions (parameter types). Enables `Comparator<Animal>` to be used where `Comparator<Cat>` is expected.

```kotlin
class Sorter<in T> { fun sort(items: List<T>) { ... } }
```

### `where`
Specifies multiple upper bounds for a type parameter.

```kotlin
fun <T> process(item: T) where T : Serializable, T : Comparable<T> { ... }
```

### `package`
Declares the package namespace for the file.

```kotlin
package com.example.kore.runtime
```

### `import`
Brings a declaration into scope. Can alias with `as`.

```kotlin
import com.example.User
```

## 2.11 Multiplatform

### `expect` / `actual`
Used in Kotlin Multiplatform. `expect` declares the API in common code; `actual` provides the platform-specific implementation. Relevant to KorE: `expect` declarations in common KorE code could have `actual` implementations that delegate to BEAM primitives.

```kotlin
// common
expect fun currentTimeMillis(): Long

// beam target
actual fun currentTimeMillis(): Long = :erlang.system_time(:millisecond)
```

### `external`
Marks a declaration as implemented outside Kotlin (JNI or JS). For KorE's BEAM target, this is the mechanism for declaring Erlang BIF/NIF bindings.

```kotlin
external fun erlangSelf(): Pid
```

# Part 3 — Syntax Matching & Mapping Strategies

This is the core design space of KorE. For each major concept, I present multiple options, cross-language references, and a recommendation.

---

## 3.1 Immutability: `val` / `var` → Erlang

### The Problem
Erlang variables are single-assignment. Once `X = 1` is written, `X` cannot be rebound — it can only be matched against. This forces `X1`, `X2`, `X3` patterns in long function bodies and makes iterative code painful to write.

Elixir solved this by allowing rebinding (the variable is rebound, the underlying value is always immutable). The BEAM does not care — it generates SSA-form code internally either way.

### Options

**Option A — Direct Elixir model (Recommended)**
`val` compiles to a single-assignment Erlang binding. `var` allows rebinding exactly as Elixir does: each assignment generates a new SSA variable in the compiled BEAM bytecode, but the developer writes natural rebinding syntax.

```kotlin
// KorE
val name = "Alice"       // single-assignment, compiler error if reassigned
var count = 0
count = count + 1        // valid — compiles to count_1 = count_0 + 1 in BEAM

// Attempting to rebind a val
val x = 10
x = 20  // COMPILE ERROR: Val cannot be reassigned
```

This is the exact model Elixir uses. It is proven, idiomatic, and removes the `X1, X2` noise without sacrificing immutability of values.

**Option B — `val` only, no `var`**
Force pure Erlang semantics. Only `val` exists. All mutation is expressed through recursion and process state. This is the Gleam approach.

```kotlin
// KorE (Option B)
val x = 10
// x = 20 is a SYNTAX ERROR — no var keyword
```

*Opinion:* Too hostile for Kotlin developers. Gleam targets functional programmers; KorE targets enterprise Kotlin/Java developers. This creates unnecessary friction.

**Option C — `val` / `var` + `mut` annotation (Rust-influenced)**
`var` is syntactic sugar for a mutable cell. The developer sees an explicit `mut` qualifier on function parameters that can change.

```kotlin
fun increment(mut counter: Int): Int {
    counter = counter + 1
    return counter
}
```

*Opinion:* Adds noise without benefit on the BEAM. Rust needs `mut` because it has ownership and borrow checking. BEAM has neither. This is complexity for complexity's sake.

**Recommendation: Option A.** It matches what Elixir already proved works, Kotlin developers understand `val`/`var` immediately, and the `var`-rebinding model compiles cleanly to BEAM bytecode. The mental model is: "values are always immutable, `var` just lets you point at a new one."

## 3.2 Data Structures: `data class` → Records / Maps

### The Problem
Kotlin's `data class` is a named, typed, structured value object. Erlang has two candidates:
- **Records:** Named tuples, compile-time field resolution, fast access, but defined globally in header files and verbose at access sites
- **Maps:** Runtime key-value store, flexible, but no schema enforcement and slower field access

### Options

**Option A — `data class` compiles to Erlang Maps (Recommended for primary use)**
Maps are the modern Erlang way. They allow runtime introspection, partial updates, and pattern matching without requiring compile-time knowledge of the full schema. The `data class` header becomes the schema documentation and generates constructor/accessor functions.

```kotlin
// KorE
data class User(val id: Long, val name: String, val email: String, val role: Role = Role.GUEST)

// Usage
val user = User(id = 1L, name = "Alice", email = "alice@example.com")
val admin = user.copy(role = Role.ADMIN)

// Pattern matching on data class
when (event) {
    is UserCreated -> handleCreation(event.user)
    is UserUpdated(id, _, email, _) -> sendConfirmation(id, email)
}
```

Compiles to something equivalent to:
```erlang
%% Generated constructor
create_user(Id, Name, Email) ->
    #{id => Id, name => Name, email => Email, role => guest}.

%% Generated copy
copy_user(User, Overrides) ->
    maps:merge(User, Overrides).
```

**Option B — `data class` compiles to Erlang Records**
Records are faster for known-schema access and pattern match better in classic Erlang code. But they require the record definition to be available at compile time everywhere they are used (via `.hrl` headers).

```kotlin
// KorE data class → generates -record definition
data class User(val id: Long, val name: String, val email: String)

// Compiles to:
// -record(user, {id, name, email}).
```

*Opinion:* Records are a legacy mechanism. They cannot be passed across module boundaries cleanly, and their global-header requirement creates coupling that the module system of KorE would need to work around. Maps are the right target for modern Erlang code.

**Option C — Three-tier system (complex but expressive)**
Expose three options with distinct semantics:

1. `data class` → Maps (full-featured, runtime-flexible, default)
2. `record class` → Erlang Records (performance-critical paths, fixed schema)
3. `struct` → Simple tuples with positional access (raw performance)

```kotlin
data class User(val id: Long, val name: String)      // → Map
record class Header(val type: Int, val len: Int)     // → Record (fast)
struct RawFrame(val type: Int, val payload: Binary)  // → Tuple
```

*Opinion:* This is the right long-term design but adds cognitive load early. Consider shipping Option A first with `record class` as a later performance annotation. This matches Elixir's evolution: Elixir started with maps and added structs (which are maps with a `__struct__` key).

**Elixir reference:** Elixir's `defstruct` compiles to a Map with a `__struct__` key. This gives schema documentation + pattern matching + runtime flexibility. KorE's `data class` should do the same, using a `__type__` key or similar tag.

**Gleam reference:** Gleam uses records that compile to Erlang tuples with the record name as the first element. Clean, but the lack of named field access in pattern matching is a DX regression.

**Recommendation: Option A as the default, with Option C's `record class` as an opt-in performance primitive.** The `data class` → Map mapping is the cleanest path and the one that will feel most natural to Kotlin developers. Document the `record class` escape hatch for when you need raw performance.

## 3.3 Pattern Matching: `when` → Erlang's `case` / function heads

### The Problem
This is the most important design decision in KorE. Erlang's pattern matching is structural and deep — it matches inside tuples, lists, maps, binaries, and binds variables in one step. Kotlin's `when` is multi-branch but primarily works on types and equality. The two are not equivalent.

### Options

**Option A — Extend `when` to full structural pattern matching (Recommended)**
Keep `when` as the KorE pattern matching keyword but extend it to support all Erlang-style structural patterns. This means `when` becomes significantly more powerful than Kotlin's `when`.

```kotlin
// KorE extended when
when (message) {
    {ok, value}              -> process(value)
    {error, :not_found}      -> handleNotFound()
    {error, reason}          -> handleError(reason)
    [head, ..tail]           -> processListHead(head, tail)
    User(id, name, _)        -> greet(name)
    x if x > 100             -> handleLarge(x)
    _                        -> ignore()
}
```

This is the Elixir `case` equivalent written in Kotlin syntax. The `{...}` tuple syntax, `[head, ..tail]` list destructuring, and atom literals (`:not_found`) all become part of `when`'s pattern grammar.

*Opinion:* This is the right choice. `when` is already Kotlin's multi-branch expression, Kotlin developers will pick up the extended syntax naturally, and it maps 1:1 to Erlang's `case ... of`.

**Option B — `match` keyword (Swift/Scala-influenced)**
Introduce a `match` expression distinct from `when`. `when` retains Kotlin semantics; `match` is full structural pattern matching.

```kotlin
// Standard Kotlin-like when
when (status) {
    Status.OK   -> ok()
    Status.FAIL -> fail()
}

// BEAM structural match
match (response) {
    {ok, body}    -> render(body)
    {error, code} -> error(code)
}
```

Swift uses `switch` with associated value patterns; Scala uses `match`. This is a clean separation but adds a keyword.

*Opinion:* The dual-keyword approach creates cognitive burden. When do you use `when` vs `match`? The line is fuzzy. Unifying them under `when` is cleaner.

**Option C — Function head pattern matching (Elixir/Gleam style)**
The primary pattern matching idiom is multi-clause functions, not a `when`/`match` expression.

```kotlin
fun process({ok, value}: Tuple) = handle(value)
fun process({error, reason}: Tuple) = handleError(reason)
fun process(_) = ignore()
```

*Opinion:* This is elegant and maps perfectly to Erlang, but it requires a radical departure from Kotlin's single-signature function model. It's worth supporting alongside `when`, not instead of it. Multi-clause functions are a powerful tool in KorE, but `when` expressions should also work.

**Option D — Combined: multi-clause functions + extended `when`**
Both patterns coexist. Multi-clause functions for structural dispatch at module boundaries, `when` for inline decision-making within a function body.

```kotlin
// Multi-clause function (outer dispatch)
fun handle(Success(value): Result) = process(value)
fun handle(Failure(error): Result) = logError(error)

// Extended when (inline decision)
fun route(msg: Message) = when (msg) {
    is Ping         -> pong()
    is Data(bytes)  -> process(bytes)
    is Stop         -> shutdown()
}
```

**My recommendation: Option D.** Multi-clause functions with pattern matching in the function signature, plus a fully-extended `when` expression for inline matching. This gives KorE two idioms that cover different scales of problem, matching how experienced Erlang/Elixir developers actually write code. The Kotlin developer gets `when` as their entry point; they discover multi-clause functions as they get more comfortable with the BEAM model.

## 3.4 Guard Clauses

### The Problem
Erlang's `when` guards are restricted to a whitelist of side-effect-free expressions. This restriction is fundamental to BEAM's ability to use guards in pattern matching without causing side effects or errors during the matching process itself.

KorE needs to preserve this restriction while providing a familiar syntax.

### Options

**Option A — `if` guards on `when` branches (Swift-influenced)**

```kotlin
when (x) {
    n if n > 100 -> "big"
    n if n > 0   -> "small"
    _            -> "non-positive"
}
```

Swift uses `where` in `switch` cases; this uses `if` which is more familiar to Kotlin/Java developers.

**Option B — `where` guards (Kotlin generics / Swift-influenced)**

```kotlin
when (x) {
    n where n > 100 -> "big"
    n where n > 0   -> "small"
}
```

Follows Swift's `switch` pattern exactly. Clean but `where` already has meaning in Kotlin's generic system.

**Option C — Inline condition in pattern (Gleam-influenced)**
Gleam embeds conditions directly into function clause guards using `if` after `->`. Not recommended — it reverses the natural reading order.

**Recommendation: Option A (`if` guards).** `if n > 100` reads naturally in English and is unambiguous. It avoids overloading `where`. Multi-clause functions use the same `if` guard syntax on the function signature.

```kotlin
fun classify(n: Int) if n > 100 = :big
fun classify(n: Int) if n > 0   = :small
fun classify(_)                  = :zero
```

## 3.5 Module System: `-module` / `-export` → Kotlin packages

### The Problem
Erlang's module system is explicit: every function is tagged with its module, exports are opt-in, and the module is a compilation unit. Kotlin's package system is a namespace only — visibility is controlled by modifiers.

### Options

**Option A — File = Module, `internal` = private, `public` = exported (Recommended)**
Each `.kore` file is one module. The module name is derived from the filename (matching Erlang's convention). Public functions are exported automatically; `internal` and `private` are not.

```kotlin
// user_service.kore → module :user_service
package com.example.app

fun create(name: String): User = ...           // exported
fun validate(user: User): Boolean = ...        // exported
internal fun hashPassword(pwd: String) = ...  // NOT exported (internal to file)
```

**Option B — Explicit `@Export` annotation**
Kotlin functions are private by default; mark specific functions for export.

```kotlin
@Export
fun create(name: String): User = ...

fun validate(user: User): Boolean = ...  // module-private
```

*Opinion:* This mirrors Erlang's `-export` exactly but feels verbose for KorE's "business logic first" philosophy.

**Option C — Erlang-style explicit export block**
A top-of-file export declaration.

```kotlin
module UserService {
    export [create/1, findById/1, update/2]
    
    fun create(name: String) = ...
}
```

*Opinion:* The `module` block is the Elixir/Gleam approach. It provides clear visibility at a glance of the module's public API but is verbose.

**Recommendation: Option A.** Kotlin developers understand visibility modifiers. Using `public`/`internal`/`private` to control BEAM exports is consistent with the language's existing model and requires no new concepts. The file-as-module convention follows Erlang's requirement without ceremony.

## 3.6 Anonymous Functions

### The Problem
Erlang's `fun` and Kotlin's `{ }` lambda syntax need to be unified. The BEAM `fun` is also used for function reference capture (`fun module:name/arity`).

### Options

**Option A — Kotlin lambdas + `::` function references (Recommended)**

```kotlin
val double = { x: Int -> x * 2 }
val ref = ::myFunction
val moduleRef = UserService::create
```

For multi-clause lambdas (a uniquely Erlang feature), use an extended block form:

```kotlin
val classify = fun {
    n: Int if n > 0  -> :positive
    n: Int if n < 0  -> :negative
    _                -> :zero
}
```

**Option B — Elixir's `fn ... end` syntax**

```kotlin
val double = fn(x: Int) -> x * 2 end
```

*Opinion:* This conflicts with `fun` which KorE uses for named functions. Confusing.

**Option C — Explicit `lambda` keyword**

```kotlin
val double = lambda { x: Int -> x * 2 }
```

*Opinion:* Unnecessary verbosity.

**Recommendation: Option A.** Kotlin lambda syntax `{ }` is familiar to KorE's target audience, `::` for function references is idiomatic Kotlin, and the multi-clause `fun { }` form handles Erlang's more advanced lambda patterns.

## 3.7 Exception Handling: Erlang's three-class system → KorE

### The Problem
Erlang has three exception classes: `error`, `exit`, `throw`. Kotlin has checked/unchecked exceptions (well, only unchecked on JVM). The BEAM distinction between these three classes is semantically important — `exit` signals process lifecycle events, `throw` is for non-local flow control, `error` is for bugs/runtime faults.

### Options

**Option A — Map to Kotlin's `catch` with typed exception classes**

```kotlin
try {
    riskyOperation()
} catch (e: BeamError) {    // Erlang error class
    handleError(e.reason)
} catch (e: BeamExit) {     // Erlang exit class
    handleExit(e.reason)
} catch (e: BeamThrow) {    // Erlang throw class
    handleThrow(e.value)
} finally {
    cleanup()
}
```

*Opinion:* Clean mapping but requires Kotlin developers to learn three new exception types.

**Option B — Collapse to Kotlin-style `try/catch` with `Result` type for `throw`**
Use standard `try/catch` for `error` and `exit`, and expose `throw` as a `Result<T>` monad return.

```kotlin
val result: Result<Value> = runCatching { fetchData() }
result.onSuccess { ... }.onFailure { ... }
```

*Opinion:* This hides the three-class distinction which is important in OTP for supervision trees. `exit` signals should propagate; catching them naively is wrong. Hiding this is dangerous.

**Option C — Explicit three-class `catch` with smart defaults (Recommended)**
`catch` handles `error` class by default (most common case). `exit` and `throw` require explicit handling and are called out specifically.

```kotlin
try {
    operation()
} catch (e: Exception) {         // catches Erlang error class only
    recover(e)
} catchExit (reason) {           // explicitly catch exit signals
    handleShutdown(reason)
} catchThrow (value) {           // explicitly catch throw values
    handleJump(value)
} finally {
    cleanup()
}
```

**Recommendation: Option C.** The distinction between `error`, `exit`, and `throw` is not an implementation detail — it is fundamental to how supervision trees and OTP work correctly. KorE must surface it. The `catch` / `catchExit` / `catchThrow` naming is clear and teaches the model to Kotlin developers without requiring them to know Erlang first. The `finally` keyword is preserved from Kotlin and maps to Erlang's `after`.

## 3.8 Concurrency Primitives: `spawn` / `receive` / `!` → KorE

This deserves its own session (Session 4 covers OTP in depth), but the keyword-level decisions belong here.

### `spawn`

**Option A — Top-level function**
```kotlin
val pid: Pid = spawn { receiveLoop() }
val pid: Pid = spawn(::receiveLoop)
```

**Option B — `process { }` block (Elixir `spawn` with cleaner syntax)**
```kotlin
val pid: Pid = process {
    receiveLoop()
}
```

**Recommendation: Option B.** `process { }` makes the concurrency intent explicit and reads well. It also opens a natural path to `supervisedProcess { }` and `linkedProcess { }` variants.

### `receive`

**Option A — `receive` block with `when`-style pattern matching**
```kotlin
receive {
    {reply, ref, value} -> process(value)
    {error, ref, reason} -> handleError(reason)
    after(5000) -> timeout()
}
```

This is an obvious and clean mapping. `receive` is kept as a keyword, its body uses `when`-style patterns, and `after` handles timeouts.

### Message Send: `!` operator

**Option A — `!` operator preserved**
```kotlin
pid ! Message(payload)
```

**Option B — `.send()` extension**
```kotlin
pid.send(Message(payload))
```

**Recommendation: Keep `!` as a KorE operator.** It is instantly recognizable to any Erlang/Elixir developer, and having two syntaxes (`!` and `.send()`) for the same operation is noise. Kotlin developers will learn it in one day. If the KorE style guide wants to be conservative, `.send()` can be offered as an alias.

## 3.9 The `null` Problem

### The Problem
Erlang has no `null`. It uses atoms (`:ok`, `:error`, `:none`, `:undefined`) and tagged tuples (`{ok, Value}`, `{error, Reason}`, `:none`) for optional and error values. Kotlin has null-safety built into the type system with `T?` and `?.` / `?:`.

### Options

**Option A — Preserve Kotlin null-safety as a compile-time abstraction (Recommended)**
KorE allows `T?` in type annotations and `?.` / `?:` operators. The compiler translates nulls to `:undefined` atoms on the BEAM. Pattern matching on `null` compiles to a pattern match on `:undefined`.

```kotlin
// KorE
fun findUser(id: Long): User? = ...

val user: User? = findUser(42L)
val name = user?.name ?: "unknown"
```

Compiles to:
```erlang
find_user(Id) -> ... % returns undefined | #{}

Name = case find_user(42) of
    undefined -> <<"unknown">>;
    User      -> maps:get(name, User)
end.
```

*Opinion:* This is the right call. Kotlin developers depend on null-safety ergonomics. Stripping it out creates bugs. Mapping to `:undefined` is exactly what Elixir's `nil` does.

**Option B — No null, force `Result<T>` and `Option<T>` types**
Remove `null` entirely; everything is `Result<T, E>` or `Option<T>`.

```kotlin
fun findUser(id: Long): Option<User> = ...
val name = findUser(42L).map { it.name }.getOrElse { "unknown" }
```

*Opinion:* Cleaner semantically and more aligned with the functional BEAM world, but abandons a significant ergonomic advantage of Kotlin. Do not force this. Offer it as a style option via an `Option<T>` type in the stdlib.

**Recommendation: Option A, with `Option<T>` in the stdlib for developers who prefer it.** Kotlin null-safety is a feature worth preserving. Map `null` to `:undefined` on the BEAM. Document the convention clearly.

## 3.10 Type System: Generics → Erlang's Dynamic Types

### The Problem
Erlang has no generics. It has a dynamic type system with optional Dialyzer type annotations. Kotlin's generics are compile-time only on JVM (type erasure). On the BEAM, generics would also be compile-time only — they add safety during KorE compilation but disappear in BEAM bytecode.

### Strategy
Generics in KorE are purely a compile-time type-checking feature. They do not exist at runtime on the BEAM. This is acceptable and even analogous to how Java/Kotlin generics work on the JVM. The KorE compiler uses them to generate Dialyzer `-spec` annotations, giving you static analysis tooling.

```kotlin
// KorE
fun <T> wrap(value: T): Result<T, Nothing> = Success(value)

// Generated Dialyzer spec
// -spec wrap(T) -> {ok, T}.
```

## 3.11 Summary: KorE Keyword Design Decisions

| Concept | KorE Keyword | Maps To | Rationale |
|---|---|---|---|
| Immutable binding | `val` | Erlang single-assignment | Direct, familiar |
| Rebound binding | `var` | Elixir rebinding (SSA under hood) | Avoids X1/X2 noise |
| Function declaration | `fun` | Erlang function | Same keyword, cleaner |
| Multi-clause dispatch | `fun` with multiple signatures | Erlang function heads | Native BEAM idiom |
| Pattern matching | `when` (extended) | Erlang `case ... of` | Familiar entry point |
| Guard clauses | `if` on branch | Erlang `when` guard | Avoids `when` overload |
| Process spawn | `process { }` | Erlang `spawn` | Intent-revealing |
| Message receive | `receive { }` | Erlang `receive` | Direct mapping |
| Message send | `!` operator | Erlang `!` | Idiomatic BEAM |
| Data class | `data class` → Map | Erlang Map | Modern, flexible |
| High-perf struct | `record class` | Erlang Record | Opt-in performance |
| Optional values | `T?` → `:undefined` | Elixir `nil` | Kotlin ergonomics |
| Exception (runtime error) | `catch (e: Exception)` | Erlang `error` class | Familiar |
| Exception (exit signal) | `catchExit (reason)` | Erlang `exit` class | Explicit OTP intent |
| Exception (throw/jump) | `catchThrow (value)` | Erlang `throw` class | Explicit non-local flow |
| Module visibility | `public`/`internal`/`private` | Erlang `-export` | Kotlin-native model |
| Compile-time constant | `const val` | Erlang `-define` macro | Familiar |
| Type annotation | `-spec` generated from signatures | Erlang `-spec` | Dialyzer integration |
| Behaviours | `interface` + `@Behaviour` | Erlang `-behaviour` | OTP bridge |
