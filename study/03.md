## 3.1 The Atom Strategy

Atoms are one of the most important primitives in Erlang. They are interned, constant, globally unique values used for everything: status codes, message tags, module names, boolean-like flags, and the foundation of pattern matching logic. Any language targeting the BEAM must have a clean, ergonomic answer for atoms.

### What atoms are in Erlang

```erlang
ok                        % status atom
{error, not_found}        % atom as tag in tagged tuple
gen_server:call(Pid, get) % atom as message
is_atom(hello)            % true
```

Atoms are not strings. They are interned symbols. The VM has a global atom table limited to ~1M atoms by default. You cannot create atoms dynamically at scale (e.g. from user input) without risking atom table exhaustion and a VM crash.

---

### How reference languages handle atoms

**Elixir** — keeps atoms as `:name` syntax. Lowercase-start atoms are `:ok`, `:error`, `:not_found`. Capitalized atoms (like module names) are written as `MyModule` but are actually atoms internally. String-to-atom conversion is guarded: `String.to_existing_atom/1` is preferred over `String.to_atom/1`.

```elixir
:ok
:error
{:error, :not_found}
MyModule          # atom alias
:my_atom |> to_string()  # "my_atom"
```

**Gleam** — has no atoms. Uses custom types (enums) for everything atoms do in Erlang. Interoperates with Erlang atoms via `atom.create_from_string` in a controlled way. This is the strictest approach: fully typed, zero dynamic atom creation.

```gleam
type Status { Ok  Error(String) }
```

**Swift** — uses `enum` cases for atom-like constants. They are typed and exhaustive. Swift also uses `String`-backed raw enums when interoperating with string-like identifiers.

```swift
enum Status { case ok, error, notFound }
enum HttpMethod: String { case get = "GET", post = "POST" }
```

**Scala/Akka** — uses `case object` for singleton value types, and `Symbol` (deprecated in Scala 3) was the closest thing to Erlang atoms. Modern Scala uses `enum` (Scala 3) or `sealed trait` + `case object`.

```scala
// Scala 3
enum Status { case Ok, Error, NotFound }
case object Ping
case object Pong
```

---

### Options for KorE

---

#### Option A: Prefix syntax (Elixir-style)

Use a sigil prefix like `:` or `#` to denote atom literals inline.

```kore
val status: Atom = :ok
val result = Pair(:error, :not_found)

when (msg) {
    :ping -> :pong
    :stop -> shutdown()
}
```

Pros:
- Instantly readable as "this is an atom, not a string"
- Familiar to anyone coming from Elixir
- Compact in pattern matching
- No namespace pollution — `:ok` and `ok` (variable) are distinct

Cons:
- Feels un-Kotlin; Kotlin developers won't recognise the sigil immediately
- `:` conflicts with Kotlin's type annotation syntax — would need the parser to disambiguate
- Creates a new primitive type not present in Kotlin at all

---

#### Option B: `atom` companion object (Kotlin-style declaration)

Define atoms via a companion object or top-level singleton. No special syntax — atoms are just typed constants.

```kore
object Atom {
    val ok       = atom("ok")
    val error    = atom("error")
    val notFound = atom("not_found")
}

// usage
val result = Atom.ok
when (result) {
    Atom.ok    -> handleOk()
    Atom.error -> handleError()
}
```

Pros:
- Pure Kotlin syntax — no new sigil to learn
- IDE autocomplete works naturally
- Type-safe; cannot confuse atoms with strings

Cons:
- Verbose to declare; `object Atom { val ok = atom("ok") }` is a lot for something Erlang writes as `ok`
- Loses the ad-hoc, lightweight feel of atoms — Erlang's power is using atoms anywhere without declaring them
- Makes interop with Erlang libraries awkward (every Erlang atom must be pre-declared)

---

#### Option C: `enum`-backed atoms (Gleam/Swift-style)

Map atoms to `enum` or `sealed class` entries. Atoms only exist as enum members.

```kore
enum Status { ok, error, notFound }
enum ServerMsg { ping, pong, stop, get, set }

fun handle(msg: ServerMsg) = when (msg) {
    ServerMsg.ping -> ServerMsg.pong
    ServerMsg.stop -> shutdown()
    else           -> unhandled()
}
```

Pros:
- Fully type-safe — exhaustive pattern matching via `when`
- Familiar to Kotlin/Swift/Scala developers
- No atom table explosion risk — enum values are fixed at compile time

Cons:
- Loses Erlang's ad-hoc atom power entirely
- Erlang libraries use open-ended atoms; mapping them requires wrapping every external API
- OTP conventions (`:ok`, `:error`, `{:error, reason}`) become cumbersome enum-wrapped types
- `{ok, Value}` tagged tuples become harder to express cleanly

---

#### Option D: Two-tier system — keyword atoms + open atoms (Recommended)

This is the design I recommend. It acknowledges that atoms serve two distinct purposes in Erlang code:

1. **Well-known status/protocol atoms** — `:ok`, `:error`, `:normal`, `:stop` — used as literal values in pattern matching. These should have keyword-level support.
2. **Structural/dynamic atoms** — module names, custom message tags, library-specific atoms — these need a safe creation path.

```kore
// Tier 1: built-in well-known atoms as keyword-like constants
// These compile directly to BEAM atoms
val result: Atom = .ok       // Swift-style dot syntax for known atoms
val code   = .notFound
val flag   = .true           // distinct from Boolean true if needed

// Pattern matching reads cleanly
when (response) {
    .ok          -> process(value)
    .error       -> recover()
    .timeout     -> retry()
}

// Tier 2: declared atom namespaces for custom atoms
atoms HttpStatus {
    ok, created, badRequest, notFound, internalError
}

atoms ServerProtocol {
    ping, pong, stop, getState, setState
}

// Usage is dot-qualified
send(pid, HttpStatus.ok)
send(pid, ServerProtocol.ping)

// Tier 3: unsafe escape hatch for Erlang interop
val erlangAtom = Atom.unsafe("some_erlang_atom")  // explicit, visible, discouraged
```

Why this works:

- The `.ok` shorthand gives you Elixir-like brevity for the most common atoms without the `:` conflict
- `atoms` block (inspired by Swift enums and Gleam custom types) gives you typed namespaces for protocol atoms in your own code
- `Atom.unsafe` makes dynamic atom creation visible and discouraged — the name signals the risk
- Pattern matching stays clean with `.ok`, `.error` etc. — the most common cases look terse
- KorE can pre-register the most common OTP atoms (`.ok`, `.error`, `.normal`, `.stop`, `.noreply`, `.reply`, `.timeout`) as global unqualified atoms

**Cross-reference:** Swift's implicit member expression (`.someCase` when the type is known) is the closest analogue and is well-loved by Swift developers for exactly this reason — it reads like an English sentence: `status == .ok`.

---

### Summary decision table for atoms

| Concern | Option A (`:atom`) | Option B (`Atom.ok`) | Option C (`enum`) | Option D (`.ok` + `atoms`) |
|---|---|---|---|---|
| Brevity | High | Low | Medium | High |
| Type safety | Low | High | High | Medium-High |
| Erlang interop | High | Medium | Low | High |
| Kotlin familiarity | Low | High | High | Medium |
| Dynamic atom safety | None | Enforced | Complete | Enforced via escape hatch |
| OTP protocol atoms | Natural | Verbose | Awkward | Natural |

**My recommendation: Option D.** The two-tier approach is the only one that handles both BEAM idioms and Kotlin developer comfort without compromise. `.ok` costs nothing to learn and reads well. The `atoms` block gives structure where structure is needed.

## 3.2 The Loop-to-Recursion Framework

This is one of the most fundamental translation problems for KorE. Erlang and the BEAM have no mutable loop variables — all iteration is recursion. JVM Kotlin developers write `for`, `while`, and `do-while` naturally. KorE must bridge this without forcing every developer to think in recursion while still generating correct tail-recursive BEAM bytecode.

### The core problem

In Erlang, this:

```erlang
loop(State) ->
    receive
        {increment, N} -> loop(State + N);
        {get, From}    -> From ! State, loop(State);
        stop           -> ok
    end.
```

...is not just style. It is the only mechanism. The BEAM's process model has no stack-based loop construct. Every "loop" is a tail call. The Erlang compiler optimises tail calls into jumps. If you do not write tail calls, you get stack overflows.

A Kotlin developer writes this naturally:

```kotlin
var state = 0
while (true) {
    when (receive()) {
        is Increment -> state += it.n
        is Get       -> it.from.send(state)
        is Stop      -> break
    }
}
```

KorE's job is to accept something close to the Kotlin form and emit correct tail-recursive BEAM code.

---

### How reference languages handle this

**Elixir** — no loop constructs. Uses recursion, `Enum`/`Stream` for collections, and `for` comprehensions. Developers write recursive functions. The `with` macro is used for sequential happy-path operations. It works, but requires a mental shift from imperative backgrounds.

```elixir
defp loop(state) do
  receive do
    {:increment, n} -> loop(state + n)
    {:get, from}    -> send(from, state); loop(state)
    :stop           -> :ok
  end
end
```

**Gleam** — no loop constructs either. Pure recursion. Gleam's `use` sugar helps flatten callback chains but does not address iteration directly. Gleam leans into the functional style without apology.

```gleam
fn loop(state: Int) -> Nil {
  case process.receive(subject, 5000) {
    Increment(n) -> loop(state + n)
    Get(from)    -> process.send(from, state); loop(state)
    Stop         -> Nil
  }
}
```

**Scala/Akka** — Akka actors use `context.become` for state transitions, which is a functional approach to stateful loops. Scala also has `@tailrec` annotation for compile-time verification of tail recursion, which is a useful safety net.

```scala
@tailrec
def loop(state: Int): Unit = {
  val msg = mailbox.receive()
  msg match {
    case Increment(n) => loop(state + n)
    case Get(from)    => from ! state; loop(state)
    case Stop         => ()
  }
}
```

**Kotlin** — `tailrec` modifier exists and enforces tail-call optimisation on the JVM where possible. The constraint is that JVM TCO is limited (no mutual recursion, no indirect calls). BEAM TCO is unconditional.

```kotlin
tailrec fun loop(state: Int): Unit {
    val msg = receive()
    return when (msg) {
        is Increment -> loop(state + msg.n)
        is Get       -> { msg.from.send(state); loop(state) }
        is Stop      -> Unit
    }
}
```

---

### Options for KorE

---

#### Option A: `tailrec` annotation only (Kotlin-native)

Keep Kotlin's `tailrec` modifier and require developers to write recursive functions explicitly. KorE validates tail position and emits correct BEAM bytecode.

```kore
tailrec fun loop(state: Int): Unit {
    val msg = receive()
    return when (msg) {
        is Increment -> loop(state + msg.n)
        is Get       -> { msg.from.send(state); loop(state) }
        is Stop      -> Unit
    }
}
```

Pros:
- No new concepts — Kotlin developers know `tailrec`
- Compiler validates at call site — if `loop(...)` is not in tail position, it is a compile error
- Transparent: what you write is what runs on the BEAM
- Works for process loops, collection folds, tree traversal — general purpose

Cons:
- Still forces developers to think recursively for state loops
- Less approachable for developers coming from pure imperative backgrounds
- `tailrec` does not compose well with `try`/`catch` (Erlang has the same constraint)

---

#### Option B: `loop` / `recur` construct (Clojure-style)

Introduce a `loop`/`recur` construct where `loop` establishes binding sites and `recur` jumps back with new values.

```kore
// loop declares mutable-looking bindings
// recur jumps back to loop with new values
// compiles to a tail-recursive function on the BEAM

fun processMessages(): Unit = loop(state = 0) {
    val msg = receive()
    when (msg) {
        is Increment -> recur(state = state + msg.n)
        is Get       -> { msg.from.send(state); recur(state = state) }
        is Stop      -> Unit   // exit loop by not recurring
    }
}
```

Pros:
- Hides recursion completely — developers think in terms of "loop state variables"
- `recur` makes it explicit that you are jumping back, not calling a new function
- Reads naturally: "loop with state=0, update state on each iteration"
- Inspired by Clojure's proven `loop`/`recur` — battle-tested in a BEAM-adjacent (JVM) language

Cons:
- New construct that is not in Kotlin — adds learning surface
- `recur` must be syntactically restricted to tail position (compile error otherwise)
- Slightly awkward for multiple state variables: `recur(count = count + 1, acc = [head | acc])`

---

#### Option C: `while` / `for` desugaring

Allow `while` and `for` as syntactic sugar that the KorE compiler rewrites into tail-recursive functions automatically.

```kore
// This KorE while loop...
fun sum(list: List<Int>): Int {
    var acc = 0
    var rest = list
    while (rest.isNotEmpty()) {
        acc += rest.first()
        rest = rest.drop(1)
    }
    return acc
}

// ...compiles to this BEAM equivalent:
// _loop([], Acc) -> Acc;
// _loop([H|T], Acc) -> _loop(T, Acc + H).
```

```kore
// for loop over collections
fun printAll(items: List<String>) {
    for (item in items) {
        println(item)
    }
}
// compiles to: lists:foreach(fun(Item) -> io:format(...) end, Items)
```

Pros:
- Maximum developer comfort — they write exactly what they know
- No new constructs to learn at all
- Works for the 80% case: iteration over collections and simple accumulators

Cons:
- `while (true)` with mutable state is the hardest case — the compiler must detect that `acc` and `rest` are the "loop state" and generate a correct recursive function
- Complex mutations inside a while body (nested ifs, early returns) are genuinely hard to compile to correct tail recursion
- Hides the BEAM model entirely — developers will be confused when they encounter recursion in error messages, stack traces, or documentation
- `break` semantics in tail-recursive context are non-trivial (must be modelled as a "done" base case)

---

#### Option D: Graduated approach — three levels (Recommended)

Offer all three in a hierarchy of abstraction. Developers choose their level based on the task.

**Level 1 — Collection operations (stdlib, no loops needed)**

```kore
// Most iteration should not be loops at all
val total = list.fold(0) { acc, x -> acc + x }
val evens = list.filter { it % 2 == 0 }
val names = users.map { it.name }
```

**Level 2 — `loop`/`recur` for stateful iteration (new construct)**

```kore
// For process message loops and stateful traversals
fun serverLoop(): Unit = loop(state = initialState()) {
    when (val msg = receive()) {
        is Get       -> { reply(msg.from, state); recur(state) }
        is Set       -> recur(state = state.update(msg.key, msg.value))
        is Stop      -> Unit
    }
}
```

**Level 3 — `tailrec` for explicit, transparent recursion**

```kore
// For developers who want to write and understand the BEAM model directly
tailrec fun countdown(n: Int): Unit {
    if (n == 0) return
    println(n)
    countdown(n - 1)
}
```

**`for` and `while` are allowed but strictly constrained:**

```kore
// for is allowed over Iterable — compiles to forEach/map/fold on BEAM
for (item in items) { println(item) }

// while is ONLY allowed as a compile-time desugaring hint
// the compiler will reject while bodies that cannot be proven tail-recursive
// and guide the developer to loop/recur instead
while (condition()) {
    doWork()
}
// ERROR if while body mutates variables that are not trivially loop-expressible
// HINT: consider loop { ... recur(...) }
```

Pros:
- Collection operations cover 70% of iteration needs with no loops at all
- `loop`/`recur` handles process loops and complex stateful iteration naturally
- `tailrec` gives access to the raw BEAM model for power users
- `for`/`while` work for simple cases and give useful errors for complex cases — no silent performance issues

Cons:
- Three paradigms to document
- Developers must understand which level to use — but this is guided by the compiler

**My recommendation: Option D.** This is the approach that respects both audiences. Kotlin enterprise developers will reach for `for` first; the compiler guides them toward `loop/recur` when needed. BEAM-native developers can write `tailrec` directly. Neither audience is forced into an uncomfortable model.

---

### The `loop`/`recur` formal specification

```kore
loop(<bindings>) { <body> }

// <bindings> is a comma-separated list of: name = initialValue
// <body> is a block returning either:
//   - recur(<new-bindings>)  — continue loop with updated state
//   - any other value        — exit loop, return that value

// Constraints:
// 1. recur() must be in tail position (enforced by compiler)
// 2. Bindings declared in loop are val inside the body (immutable per iteration)
// 3. New values in recur() are evaluated before any state is updated (like Erlang)
```

```kore
// Multiple state variables
fun parseTokens(input: String): List<Token> = loop(
    pos = 0,
    tokens = emptyList<Token>()
) {
    if (pos >= input.length) tokens  // exit: return accumulated tokens
    else {
        val (token, nextPos) = scanToken(input, pos)
        recur(pos = nextPos, tokens = tokens + token)
    }
}
```

---

### The `tailrec` guarantee on BEAM vs JVM

This is worth calling out explicitly because it is a language design selling point.

On the JVM, `tailrec` only works for direct self-calls. Mutual recursion (function A calls B, B calls A) cannot be optimised — you get a `StackOverflowError`. This is a fundamental JVM limitation.

On the BEAM, **all** tail calls are optimised, including mutual recursion. KorE should expose this:

```kore
// This works on BEAM, would stack overflow on JVM
tailrec fun isEven(n: Int): Boolean = if (n == 0) true else isOdd(n - 1)
tailrec fun isOdd(n: Int): Boolean  = if (n == 0) false else isEven(n - 1)

// KorE compiler emits:
// is_even(0) -> true;
// is_even(N) -> is_odd(N - 1).
// is_odd(0) -> false;
// is_odd(N) -> is_even(N - 1).
```

KorE can advertise this as a first-class feature: `tailrec` in KorE is unconditional, including mutual recursion. This is not possible in Kotlin/JVM.

## 3.3 Developer Experience (DX) and DSL Design

KorE's stated goal is to keep business logic visible and clean. This section covers the tools that enable developers to build expressive, readable domain-specific languages on top of KorE primitives.

### Foundation: Kotlin's DSL building blocks

Kotlin's DSL support rests on three pillars:

1. **Extension functions** — add behaviour to any type without modifying it
2. **Trailing lambda syntax** — `foo(x) { ... }` reads like a keyword + block
3. **`@DslMarker`** — prevents unintended scope leakage in nested DSLs

These all map cleanly to KorE because they are syntax and semantics — not JVM-specific.

---

### Extension Functions on Erlang Modules

The goal is to let developers write `myBinary.split(",")` instead of `binary:split(MyBinary, ",")`.

```kore
// KorE extension function declaration
fun Binary.split(separator: Binary): List<Binary> =
    binary.split(this, separator)

fun Binary.replace(pattern: Binary, replacement: Binary): Binary =
    binary.replace(this, pattern, replacement)

fun String.toAtom(): Atom = Atom.unsafe(this)  // marked unsafe intentionally

// Usage
val parts = <<"hello,world,foo">>.split(<<",">>)
val cleaned = <<"  hello  ">>.trim()
```

**How it compiles:** Extension functions in KorE are syntactic sugar. `binary.split` becomes `binary:split(Binary, Sep)` in BEAM bytecode. There is no runtime overhead — the extension call is a direct module function call at the BEAM level.

**Cross-reference with Scala:** Scala's implicit classes and extension methods work the same way — they are erased at compile time and become regular static/module calls. Kotlin made this cleaner by building it in as a first-class feature.

---

### Option A: Extensions only (no monkey-patching)

Extension functions can only be defined; they cannot override existing module behaviour. This is Kotlin's model.

```kore
// Define extensions in your own namespace
fun List<Int>.sum(): Int = lists.foldl({ acc, x -> acc + x }, 0, this)
fun Map<K,V>.getOrDefault(key: K, default: V): V = maps.get(key, this, default)
```

Pros:
- Safe, predictable — no modification of Erlang module behaviour
- IDE support trivial — function resolution is static
- KorE standard library can provide a set of extensions over all Erlang stdlib modules

Cons:
- Cannot replace `lists:map` with `list.map` in terms of dispatch — both coexist
- Developers coming from Elixir may expect protocol-style polymorphism

---

### Option B: Type class / protocol extensions (Elixir-style)

Allow defining a `protocol` (interface) that types implement, enabling polymorphic dispatch.

```kore
protocol Mappable<A, B> {
    fun Self.map(f: (A) -> B): Self
}

impl Mappable<A, B> for List<A> {
    fun List<A>.map(f: (A) -> B): List<B> = lists.map(f, this)
}

impl Mappable<K, V> for Map<K, V> {
    fun Map<K,V>.map(f: (V) -> V2): Map<K,V2> = maps.map({ _, v -> f(v) }, this)
}

// Now both work:
listOf(1,2,3).map { it * 2 }
mapOf("a" to 1).map { it * 10 }
```

Pros:
- Powerful polymorphism — one syntax for multiple data shapes
- Mirrors Elixir's `Protocol` exactly, which is proven
- Enables the `Enumerable` / `Collectable` pattern from Elixir

Cons:
- Significant language complexity — type classes are hard to implement correctly
- KorE's first version probably should not tackle this — it can be added later
- Requires runtime dispatch table which adds overhead for BEAM

**My view:** Worth targeting in KorE v2 but not v1. Start with extensions only.

---

### Builder DSL Pattern

This is where KorE can shine for enterprise developers. The `apply`/`with` pattern from Kotlin enables HTML-builder-style configuration DSLs.

```kore
// Route configuration DSL (Ping framework example)
val router = router {
    get("/users") { ctx ->
        ctx.json(userService.findAll())
    }
    post("/users") { ctx ->
        val user = ctx.body<CreateUserRequest>()
        ctx.status(201).json(userService.create(user))
    }
    group("/admin") {
        before { ctx -> requireAdmin(ctx) }
        get("/stats") { ctx -> ctx.json(stats()) }
    }
}
```

```kore
// Supervisor tree DSL (OTP configuration)
val appSup = supervisor {
    strategy = OneForOne
    intensity = 5
    period = 10.seconds

    worker(name = :cache,    start = { Cache.startLink(maxSize = 1000) })
    worker(name = :database, start = { DB.startLink(url = dbUrl) })
    supervisor(name = :webSup, start = { WebSupervisor.startLink() })
}
```

```kore
// Data transformation pipeline DSL
val pipeline = pipeline<RawEvent, ProcessedEvent> {
    filter { it.type != .spam }
    map    { parseEvent(it) }
    batch(size = 100, timeout = 500.milliseconds)
    sink   { events -> db.insertBatch(events) }
}
```

**How builders work in KorE:**

```kore
// A builder is a class with a @DslMarker annotation and an invoke operator
@DslMarker
annotation class RouterDsl

@RouterDsl
class RouterBuilder {
    private val routes = mutableListOf<Route>()

    fun get(path: String, handler: Handler) {
        routes.add(Route(.get, path, handler))
    }

    fun post(path: String, handler: Handler) {
        routes.add(Route(.post, path, handler))
    }

    fun group(prefix: String, block: RouterBuilder.() -> Unit) {
        val sub = RouterBuilder().also(block)
        routes.addAll(sub.routes.map { it.withPrefix(prefix) })
    }

    fun build(): Router = Router(routes)
}

fun router(block: RouterBuilder.() -> Unit): Router =
    RouterBuilder().also(block).build()
```

---

### The `|>` Pipe Operator

This is a core DX decision. Erlang has no pipe operator. Elixir made it central to the language. Kotlin has `.let { }` as a functional equivalent.

**Option A: No pipe, use `.let { }`**

```kore
val result = rawInput
    .let { validate(it) }
    .let { transform(it) }
    .let { persist(it) }
```

Kotlin developers know this. It is already idiomatic.

**Option B: Add `|>` as first-class operator**

```kore
val result = rawInput
    |> validate(_)
    |> transform(_)
    |> persist(_)
```

Inspired by Elixir and F#. `_` is the placeholder for the piped value when the function is not unary.

**Option C: Both — `|>` for function pipelines, `.` for method chains**

```kore
// Method chain (Kotlin-style): subject.verb
val sorted = list.filter { it > 0 }.sortedBy { it }

// Pipe (Erlang-style): data flows through functions
val result = rawData |> parseJson |> validateSchema |> indexById
```

**My view:** Option C. The distinction is meaningful:

- Use `.method()` chains when you are calling methods on an object (OOP style)
- Use `|>` when you are passing data through a sequence of standalone functions (FP style)

This mirrors how Elixir developers think: `|>` is for data transformation pipelines, not for method dispatch. KorE serving both audiences means offering both tools.

---

### Explicit over Implicit: The Business Logic Principle

One of KorE's stated design goals is keeping business rules visible. This has concrete implications:

**Avoid magic injection**

```kore
// BAD — Spring-style magic (what is injected here?)
class OrderService {
    @Inject lateinit var repo: OrderRepository
    @Inject lateinit var events: EventBus
}

// GOOD — explicit construction
class OrderService(
    val repo: OrderRepository,
    val events: EventBus
)
```

KorE should not build an annotation-processing DI framework. Constructor injection (explicit) is the default. A lightweight service locator for OTP processes (which are already registered by name) is sufficient.

**Prefer named arguments over positional mystery**

```kore
// BAD
startWorker(5, 1000, true, false)

// GOOD
startWorker(
    count      = 5,
    timeoutMs  = 1000,
    restartable = true,
    monitored   = false
)
```

Kotlin's named arguments are already part of the language. KorE should enforce them in public APIs via a linting rule for functions with more than 2 parameters of the same type.

**Prefer `sealed class` / `when` over `if`/`else` chains**

```kore
// BAD — open-ended, non-exhaustive
fun handleStatus(code: Int): String {
    if (code == 200) return "ok"
    else if (code == 404) return "not found"
    else return "unknown"
}

// GOOD — exhaustive, compiler-enforced
sealed class HttpStatus {
    object Ok        : HttpStatus()
    object NotFound  : HttpStatus()
    data class Error(val code: Int) : HttpStatus()
}

fun handle(status: HttpStatus): String = when (status) {
    is HttpStatus.Ok       -> "ok"
    is HttpStatus.NotFound -> "not found"
    is HttpStatus.Error    -> "error ${status.code}"
    // compiler ensures all cases are handled
}
```

### Metaprogramming and Macros

Erlang has parse transforms (compile-time AST manipulation). Elixir has hygienic macros. Kotlin has compiler plugins and symbol processors (KSP).

For KorE, the question is: how much metaprogramming do you expose?

**Option A: No macros — generate code via builder DSLs**

The KorE compiler has a fixed set of code generation features (GenServer scaffolding, supervisor tree generation, etc.) controlled by annotations. No user-defined macros.

```kore
@GenServer
class Counter(initialState: Int) {
    // compiler generates: init, handle_call, handle_cast, handle_info, etc.
}
```

Pros: Simple, predictable, no macro hygiene problems.
Cons: Cannot extend the compiler for domain-specific needs.

**Option B: Limited compile-time functions (Rust-style proc macros)**

KorE allows `@annotation`-based code generation via a plugin API. Plugins run at compile time and transform the AST.

```kore
@Route(method = .get, path = "/users")
fun getUsers(ctx: Context): Response { ... }
// annotation processor generates router registration
```

**Option C: Full macro system (Elixir-style)**

Hygienic macros that operate on the KorE AST. Powerful but complex.

**My recommendation:** Start with Option A for v1. The builder DSL pattern covers 90% of what macros are used for in practice (configuration, code generation, routing). Add an annotation processor API in v2 if the community needs it.

### Error Handling DSL

One concrete DX win KorE can provide is an ergonomic error handling syntax that maps to Erlang's `{ok, Value} | {error, Reason}` pattern.

```kore
// The KorE Result type maps to Erlang tagged tuples
sealed class Result<out T> {
    data class Ok<T>(val value: T)    : Result<T>()
    data class Err<E>(val error: E)   : Result<Nothing>()
}

// Smart constructor functions (companion object sugar)
fun <T> ok(value: T): Result<T>  = Result.Ok(value)
fun <E> err(error: E): Result<Nothing> = Result.Err(error)

// At the BEAM level these are literally {ok, Value} and {error, Reason}
```

The key DX feature is the `?` operator (inspired by Rust) or `bind`/`do` notation for early-exit on error:

```kore
// Option A: ? operator (Rust-inspired)
fun processUser(id: UserId): Result<UserDto> {
    val user    = findUser(id)?          // returns Err early if Err
    val profile = fetchProfile(user.id)? // same
    val avatar  = loadAvatar(profile.avatarUrl)?
    return ok(UserDto(user, profile, avatar))
}

// Option B: result { } block with bind
fun processUser(id: UserId): Result<UserDto> = result {
    val user    = bind { findUser(id) }
    val profile = bind { fetchProfile(user.id) }
    val avatar  = bind { loadAvatar(profile.avatarUrl) }
    UserDto(user, profile, avatar)
}

// Option C: Railway-style chaining
fun processUser(id: UserId): Result<UserDto> =
    findUser(id)
        .flatMap { user    -> fetchProfile(user.id).map { user to it } }
        .flatMap { (u, p)  -> loadAvatar(p.avatarUrl).map { Triple(u, p, it) } }
        .map     { (u, p, a) -> UserDto(u, p, a) }
```

**My view:** Offer all three but make `result { bind { } }` the idiomatic KorE style. It maps to Elixir's `with` construct (proven), is readable, and scales to complex multi-step operations. The `?` operator is a great shorthand for simple cases. Railway chaining should be available but not primary — it becomes unreadable when tuples accumulate.

### Summary of Session 3 decisions

| Topic | Recommendation | Rationale |
|---|---|---|
| Atom syntax | `.ok`, `.error` global + `atoms {}` block | Brevity for common atoms, typed namespace for protocol atoms |
| Atom interop | `Atom.unsafe()` escape hatch | Makes dynamic atom creation visible and intentional |
| Iteration default | Collection stdlib functions | Covers 70% of cases with no loop concept at all |
| Process loops | `loop { recur() }` construct | Hides recursion, generates correct tail calls, readable state |
| Explicit recursion | `tailrec` modifier | For power users; unconditional TCO on BEAM including mutual recursion |
| `for`/`while` | Allowed, compiler-guided | Simple cases compile; complex cases give error + hint |
| Extension functions | First-class, no monkey-patching | Zero-overhead, static dispatch, clean namespacing |
| Protocols/type classes | v2 feature | Too complex for v1, build on extension foundation |
| Pipe operator | `\|>` and `.` both, distinct purposes | `\|>` for data pipelines, `.` for method chains |
| Builder DSLs | `@DslMarker` + builder classes | Covers routing, OTP config, pipelines |
| Metaprogramming | Annotation-based code gen in v1 | Predictable, enough for Ping/aKt frameworks |
| Explicit DI | Constructor injection only | Business logic visibility over magic |
| Error handling | `result { bind {} }` primary, `?` shorthand | Maps to Erlang `{ok,_}/{error,_}`, reads like Elixir `with` |

Three things to think on before Session 4:

1. **`loop`/`recur` vs `tailrec`** — these are not exclusive but they serve different audiences. Decide if `loop`/`recur` is the *primary* idiom for process loops in KorE or just a convenience option. This directly shapes how GenServer callbacks are written in Session 4.

2. **`.ok` atom syntax** — Session 4 will use atoms heavily in OTP return values (`{.ok, state}`, `{.noreply, state}`, `{.reply, value, state}`). The atom design needs to feel right there before committing to it.

3. **Sealed class vs tagged tuples for OTP returns** — in Elixir you return `{:noreply, state}`. In KorE you could return a sealed class `NoReply(state)` or keep the tuple form. This is the biggest design decision in Session 4.
